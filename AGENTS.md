# Инструкция для агентов: devcontour-harness

Правила разработки этого репозитория для агентов (Claude Code, Codex и других).

## Проверки

```sh
npm run test:affected   # на каждое исправление: тесты, затронутые изменением
npm run test:fast       # весь suite без медленного яруса (> ~60 с)
npm run check           # release check: lint, typecheck, schemas:check, build, весь suite, package smoke
npm run schemas         # после изменения Zod-договоров; сгенерированные schemas/ коммитятся
node --disable-warning=ExperimentalWarning --import tsx --test tests/<file>.test.ts
```

Во время работы прогонять `npm run test:affected` (выбор и причина печатаются;
при сомнении он сам запускает весь suite); на конечном состоянии — один полный
`npm run check`. Уровни описаны в README, раздел «Разработка». Новые тесты — в `tests/*.test.ts` (их запускает `scripts/test.mjs`).
`spawn EPERM` и отказ sandbox/сети — не PASS и не доказанный дефект: повторить
штатным способом окружения или указать `blocked` с командой и сообщением.

## Порядок работы по поручению

1. Исполнитель реализует ТЗ, сам проходит матрицу приёмки целиком и передаёт
   кандидата с fingerprint (HEAD, diff, SHA-256 изменённых файлов), отчётом и
   логами проверок.
2. Приёмку проводит **агент другой модели**, чем исполнитель (например, Claude
   Code реализует — Codex принимает, и наоборот). Приёмщик не меняет
   реализацию, собирает все замечания одним списком за полный проход.
3. Исполнитель исправляет причину каждого замечания, добавляет минимальную
   регрессионную проверку и передаёт нового кандидата.
4. **Не более 8 раундов «приёмка → исправление»** на одно поручение. Если после
   восьмого раунда остаются блокеры, работа останавливается: исполнитель
   фиксирует оставшиеся замечания, спорные границы ТЗ и текущий статус каждого
   критерия и передаёт решение человеку, а не продолжает цикл.

Отчёты, постановки и материалы приёмки хранятся в `.private/` (не в git и не в
npm-пакете); публичные `docs/` не содержат постановок и локальных путей.

## Субагенты

Мы используем субагентов для независимых частей работы, которые могут идти
параллельно: отдельные группы тестов, правки в соседнем репозитории,
исследование кода по нескольким модулям, независимое ревью. Правила:

- задача субагента — узкая и самодостаточная: цель, файлы, критерии, что уже
  исключено, какие файлы он не трогает (чтобы параллельные агенты не
  пересекались);
- ядро изменения (договор данных, ключевая логика) делает один агент, чтобы
  дизайн оставался согласованным; субагентам — то, что строится поверх него;
- субагент не меняет production-код в обход договора, чтобы тест стал
  зелёным: найденный дефект он возвращает с воспроизведением;
- результат субагента проверяется основным агентом (diff, прогон тестов) до
  передачи на приёмку; его отчёт не считается доказательством сам по себе.

## Границы

Без явного поручения не публиковать пакет, не делать push, не менять номер
выпуска и зависимости, не запускать платные живые модели. Не ослаблять gates,
бюджеты попыток/повторов, правила находок и защиты worktree ради прохождения
тестов. Исторические данные прогонов не переписывать.
