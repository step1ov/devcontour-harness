# Коннектор задач: Relay v1 и Relay-2

Коннектор подключает к harness внешнее хранилище задач: читает задачу,
закрепляет её постановку, исполняет её обычным путём (ревью плана →
согласование → изолированная попытка → gates → независимое ревью → приёмка в
Git) и доставляет подтверждённый результат обратно в задачу. Это opt-in
модуль `devcontour-harness/integrations/connector`: корень пакета и
`./contracts` его не импортируют, адаптер backend загружается только для
явно выбранного provider.

Поддерживаются два независимых транспорта:

| provider        | Backend                                     | Транспорт                                                                                             |
| --------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `relay-v1-http` | Relay v1 (`/api/v1`, project-scoped routes) | HTTP, `src/integrations/relay-v1`                                                                     |
| `relay-v2-cli`  | Relay-2                                     | subprocess CLI (`--format json`, явные `--config`/`--project`/`--actor`), `src/integrations/relay-v2` |

Provider выбирается **только явно** в конфигурации — никогда по имени
бинарника `relay`. Базы v1 и v2 не взаимозаменяемы, миграции истории нет.

## Пользовательский путь

Все шаги — команды CLI; TypeScript писать не нужно.

```sh
# 1. Настроить: connector.json (см. «Конфигурация») и policy.json harness.

# 2. Проверить подключение, проект, capabilities и mapping — только чтение:
#    ни мутаций, ни записи истории, ни создания состояния.
npx harness source-check --source connector.json --policy policy.json --state ../state

# 3. Прочитать и закрепить снимок задач: graph.json, context.json, manifest.json.
npx harness source-snapshot --source connector.json --policy policy.json --state ../state --out ../snapshot

# 4. Обычное согласование (approvalMode: operator) — по файлам снимка.
npx harness review-plan --state ../state --policy policy.json --source connector.json \
  --graph ../snapshot/graph.json --context ../snapshot/context.json --author external
npx harness approve --state ../state --subject <graphId> --digest <graphDigest>
#    С --source внешние предпосылки (зависимости, выполненные через этот
#    коннектор) допускаются по решению источника (trusts) и доступности SHA в
#    target ref — те же правила, что у run; без --source доверенных receipt нет.
#    В approvalMode: agent ревью плана выполняется в шаге 5 автоматически.

# 5. Запуск: задачи перечитываются, semantic digest сверяется с закреплённым
#    снимком, eligibility проверяется — всё до любого вызова runtime.
#    Принятый результат доставляется в исходную задачу.
npx harness run --source connector.json --policy policy.json --state ../state

# 6. Локальный и внешний статус: принято / доставлено / конфликт / неизвестный
#    исход и независимое чтение получателя.
npx harness source-status --source connector.json --state ../state

# 7. Повтор или продолжение доставки — с тем же ключом операции; writer,
#    reviewer, gates и Git не вызываются.
npx harness source-deliver --source connector.json --state ../state [--work <workId>]

# 8. Разбор неизвестного исхода или конфликта (см. «Восстановление»).
npx harness source-reconcile --source connector.json --state ../state \
  --operation <key> [--decision resend|adopt:<id>|recheck]
```

`<graphId>`, `<graphDigest>`, ключи операций и ID поручений выводят
`source-snapshot` и `source-status` (JSON в stdout). Exit codes как у всего
CLI: 0 — успех, 2 — неверный вход, 3 — отказ/блокировка (в том числе
`uncertain`/`conflict` доставки и непройденная проверка), 4 — инфраструктура
(backend недоступен).

  "projectId": "AbCd1234",
  "actor": "harness-controller",
  "repository": { "id": "app" },
  "tasks": [
    {
      "ref": "PRODUCT-3",
      "role": "developer",
      "writeScope": ["apps/api/src", "packages/sdk/src"],
      "gates": ["unit"],
      "criteria": [
        { "title": "API returns displayName", "gate": "unit", "testId": "api.user.displayName" },
        { "id": "Ab3dE6gH", "gate": "typecheck", "evidence": "gate" }
      ],
      "requiredDocuments": ["Spec"]
    }
  ],
  "completion": { "mode": "complete", "historicalComment": false },
  "eligibility": { "columns": ["ready", "in-progress"] },
  "limits": {
    "documents": 20,
    "documentBytes": 262144,

| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `provider`            | `relay-v1-http` или `relay-v2-cli`; только явно                                                                                                                                                                                                                                                                 |
| `relay`               | Настройки адаптера. v1: `endpoint` (+ `timeoutMs`, `maxResponseBytes`). v2: `binary`, `config` (относительно файла конфигурации), `project?` (workspace), `env?` (например `RELAY_HOME`, на macOS `DYLD_LIBRARY_PATH`), `timeoutMs`, `maxOutputBytes`, `build?`. `projectId`/`actor` берутся из верхнего уровня |
| `projectId`           | Ожидаемая идентичность проекта backend; несовпадение блокирует чтение снимка и любые мутации                                                                                                                                                                                                                    |
| `actor`               | Автор всех записей коннектора                                                                                                                                                                                                                                                                                   |
| `stateDir`            | Каталог состояния коннектора (относительно файла); без него — `--state`                                                                                                                                                                                                                                         |
| `repository`          | ID репозитория политики (и путь для сверки)                                                                                                                                                                                                                                                                     |
| `tasks[]`             | Задачи: `ref` (постоянный ID или ключ), роль, `writeScope`, `gates`, сопоставление критериев, обязательные документы                                                                                                                                                                                            |
| `tasks[].criteria[]`  | Критерий (`id` или точный `title`) → `gate` и `testId` JUnit; `evidence: "gate"` — достаточно прошедшего gate (явный выбор)                                                                                                                                                                                     |
| `completion`          | `complete` — закрыть по правилам backend (по умолчанию в `done`); `review-only` — перевести в `review`/`column` и оставить человеку; `historicalComment` — при конфликте постановки записать явно исторический комментарий                                                                                      |
| `eligibility.columns` | Колонки, из которых задача допускается к запуску (`done`/`cancelled` — никогда)                                                                                                                                                                                                                                 |
| `limits`              | Пределы документов и постановки, число повторных чтений, срок владения доставкой                                                                                                                                                                                                                                |
| `history`             | Запись истории работы (корневая и дочерние сессии)                                                                                                                                                                                                                                                              |

### Идентичность и снимок

- Идентичность задачи — `<provider>:<projectId>:<постоянный ID>`; ID поручения
  и графа — хэш от неё. Одинаковые номера задач разных проектов/backend не
  совпадают; смена cwd на worktree идентичность не меняет.
- `SourceRef.revision` — **semantic digest** постановки: текст, определения
  критериев (без отметок выполнения), зависимости, подзадачи, значимые
  документы и digest mapping. Колонка, свой in-progress, комментарии, история
  и отметки критериев в него не входят. CAS-ревизии backend, токены
  согласованности чтения и идентичность сборки хранятся только в manifest
  снимка (никогда в поле Git SHA).
- Чтение — раундами по всем задачам; снимок принимается, когда два раунда
  подряд совпали токенами и содержимым. Изменения — не больше `rereads`
  повторов, затем явный отказ `NOT_READY`; ошибка сети/CLI — отказ, а не
  пустая доска.
- Обязательное содержимое (текст постановки, критерии, `requiredDocuments`)
  не усекается: превышение предела блокирует запуск с причиной и пределом.
  Дополнительные документы усекаются с явной отметкой в начале файла и в
  manifest (`truncated`) либо опускаются с записью в `missing` снимка.
- Eligibility проверяется отдельно от digest: `done`/`cancelled`, колонка вне
  `eligibility.columns`, незавершённая зависимость, зависимость в `done` без
  receipt этого коннектора. Колонка, в которую задачу перевела наша
  подтверждённая доставка той же постановки, повтор не блокирует.
- Статус `done` зависимости — не доказательство: предпосылка зависимой
  задачи появляется только из receipt доставки этого коннектора (издатель —
  ID коннектора, digest сверяется с его состоянием), и движок дополнительно
  проверяет доступность result SHA в target ref.

## Доставка: протокол и гарантии

Ключ операции — `sha256(provider, projectId, workId, runId, resultDigest)`.

1. **Intent до вызова.** Операция записывается в состояние коннектора до
   первого внешнего вызова. Не удалось записать — мутация не отправляется.
2. **Сверка перед мутацией.** Задача перечитывается: изменился semantic
   digest или задача отменена/закрыта другим — `conflict`; результат остаётся
   привязан к своему снимку и SHA, текущая задача не закрывается (по
   `historicalComment` — один явно исторический комментарий).
3. **Шаги**, каждый записан до и после вызова: комментарий с маркером
   `<!-- devcontour-harness:op=<key>:step=<n> -->`; отметки сопоставленных
   критериев с CAS; перемещение с CAS; закрытие истории. Критерий отмечается
   только по mapping на прошедший в integration gate/testcase принятого
   результата; ручные критерии, непрошедший testcase, незавершённые
   подзадачи и зависимости оставляют задачу незавершённой.
   Перед **каждым** неподтверждённым шагом (в том числе при продолжении
   после обрыва или перезапуска) задача перечитывается: постановка обязана
   совпасть со снимком результата, задача — не быть отменённой или закрытой
   другим, а для нового CAS-шага текущая ревизия — равняться ревизии,
   записанной после **нашего** предыдущего шага. Иначе — `conflict`, и
   изменённая задача старым результатом не закрывается.
4. **Неизвестный исход** (таймаут, обрыв ответа, падение процесса между
   вызовом и записью итога) разбирается фактами получателя: комментарий — по
   маркеру (ровно один — подтверждено); CAS-шаг — по состоянию и ревизии
   (цель достигнута, ревизия ровно на 1 больше нашей и постановка та же —
   подтверждено; цель достигнута, но ревизия или постановка ушли дальше —
   `conflict`; ревизия прежняя — не применено; ревизия
   сменилась без нашей записи — `conflict`). Ответ `conflict` получателя
   никогда не лечится повтором старой команды по новой ревизии.
5. **Подтверждённый отказ ≠ неизвестный исход.** Структурный отказ
   получателя (`refused`; `conflict` для записи без CAS — комментария;
   `unavailable` до отправки) означает, что мутации не было: шаг остаётся
   `planned`, доставка — `failed` с причиной «подтверждённый отказ
   получателя», повтор `source-deliver` безопасен (тот же маркер). Класс
   ответа задаёт адаптер: 5xx/ненулевой exit без доказательства отката для
   мутации адаптер сообщает как `uncertain`, и тогда действует п. 6.
6. **`uncertain`.** Если исход доказать нельзя (0 маркеров после возможной
   отправки, больше одного, read-back недоступен), операция получает
   `uncertain` (событие `delivery.uncertain` с ключом операции), повторная
   доставка ничего не отправляет до `source-reconcile`.
7. **Receipt.** После подтверждения всех шагов сохраняется receipt (ID
   комментария, критерии, колонка, ревизия, сессии истории); для принятого
   результата — доверенный receipt для зависимых задач.

Повторная доставка принятого результата не вызывает writer/reviewer, не
запускает gates и не меняет Git. Частично выполненная доставка продолжается
с первого неподтверждённого шага без повтора append-only записей.

### Один владелец доставки

Владение операцией — lease с токеном, сроком и fencing в SQLite состояния
коннектора (`BEGIN IMMEDIATE`). Живой владелец продлевает lease и во время
долгого вызова; второй процесс над тем же каталогом получает
`CONTROLLER_BUSY` и ничего не отправляет. Упавшего владельца можно
перехватить только после истечения срока, intent при этом не теряется;
каждая запись проверяет lease в той же транзакции, поэтому процесс,
потерявший владение, больше ничего не записывает. Срок `limits.leaseMs`
должен превышать таймаут одного вызова транспорта.

**Граница гарантии:** она действует только для процессов, разделяющих один
каталог состояния коннектора. Независимые установки с разными каталогами
состояния вне гарантии и могут доставить одну операцию дважды —
`source-check` и `source-status` показывают это в `ownership`. Distributed
lock в этой версии не реализован.

### Что гарантируется, а что нет

Доказывается тестами (`tests/connector-*.test.ts`, общий набор
`connectorSuite`):

- одна подтверждённая доставка — один комментарий с маркером, без повторных
  эффектов критериев и истории, в том числе после перезапуска процесса;
- обрыв до отправки — безопасный повтор; запись получателем без ответа —
  read-back без дубля; ответ без сохранённого receipt — без новых мутаций;
  отказ записи intent — без мутации;
- неизвестный исход не объявляется успехом и не повторяется автоматически;
- старая постановка не закрывает новую; чужое изменение между сверкой и CAS —
  конфликт без повтора;
- два процесса не отправляют одну операцию одновременно.

**Не гарантируется:** distributed exactly-once — у получателя нет
идемпотентности по `requestId` (Relay v1 явно её не обещает, у Relay-2 её
нет), а Git и Relay не образуют общей транзакции. Неоднозначные случаи
решает оператор.

### Восстановление (`source-reconcile`)

Сначала проверяются факты получателя; решение оператора нужно только там,
где факты неоднозначны.

| Ситуация                                                                            | Что видно                                   | Действие                                                                                                 |
| ----------------------------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Запись прошла, ответ потерян                                                        | маркер найден ровно один                    | `source-reconcile --operation <key>` — подтверждение по факту, доставка продолжается                     |
| Read-back был недоступен                                                            | `uncertain`, причина «read-back недоступен» | повторить `source-reconcile` после восстановления доступа                                                |
| Таймаут, маркера нет                                                                | 0 маркеров                                  | проверить получателя; если записи нет — `--decision resend` (тот же маркер)                              |
| Несколько записей с маркером                                                        | N > 1                                       | выбрать одну: `--decision adopt:<commentId>`; первая найденная не выбирается автоматически               |
| CAS-конфликт без изменения постановки (например, сдвиг ранга соседней задачей в v1) | `conflict`                                  | `--decision recheck`: постановка перечитывается, при совпадении digest шаг продолжается от новой ревизии |
| Постановка изменилась                                                               | `conflict`, `matchesSnapshot: false`        | результат остаётся историческим; новый `source-snapshot` → согласование → `run --source`                 |

## История работы

При включённой истории (`history.enabled`):

- до исполнения попытки (до вызова writer) — корневая сессия поручения с
  intent, затем fork дочерней сессии попытки, attach и её intent. Ошибка
  записи intent — отказ окружения: попытка не начинается;
- отказ попытки — отмена дочерней сессии; доставка результата — checkpoint с
  SHA и сводкой gates, завершение и приём дочерней, завершение корня (или
  отмена при непринятом результате);
- каждая запись несёт маркер; после перезапуска controller шаги разбираются
  read-back (`findSessions`, `checkpoints`, ревизия сессии) — без дублей;
  записи прерванной попытки только подтверждаются фактами и отменяются;
- ревизия сессии и run backend — fencing: если сессию перехватил другой
  владелец, устаревший run её не завершает (`conflict`);
- ID сессии/run backend, sessionId runtime и lease token попытки — разные
  значения; lease token и полный runtime log в историю не пишутся.

## В Relay уходит

Краткий итог: исход, проверяемые SHA (candidate, integration/result), target
ref, сводка gates (без журналов), таблица критериев → gate/testcase →
результат, semantic digest и CAS-ревизия снимка. Локальные пути заменяются
пометкой (они не ссылки для другого компьютера), значения секретов политики
маскируются, полный runtime log и вызовы инструментов не копируются.

## Маскирование секретов

Ошибки транспорта (тело ответа HTTP, stderr CLI) маскируются до того, как
попадут в отчёт `source-check`, `source-status`, ошибки снимка, причины
шагов и операций в состоянии коннектора, `lastError` доставки, отказ записи
истории и вывод CLI. Маскируются значения секретов политики на любом уровне
(`environment.secrets` политики, репозиториев и tool profiles — по
окружению controller; для `source-snapshot` укажите `--policy`, иначе
используется политика каталога состояния) и значения настроек provider с
именем вида `*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*KEY*`.

## Состояние коннектора

`<stateDir>/connectors/<provider>-<hash(projectId)>.sqlite` — отдельная от
`state.sqlite` база: снимки (manifest и digest), операции доставки (intent,
шаги, receipt), lease, связи с историей. Это не состояние исполнения: оно
остаётся единственным — в `state.sqlite` harness.

## Библиотека и договор адаптера

```ts
import { openConnector } from 'devcontour-harness/integrations/connector';

const connector = await openConnector('connector.json', { stateDir: '../state' });
const h = Harness.open({ stateDir: '../state', policy, baseDir, hooks: connector.hooks() });
await connector.snapshot('../snapshot');
await connector.run(h, { author: 'external' });
await connector.status(h);
```

Модуль адаптера (`src/integrations/<adapter>/index.ts`) экспортирует
`createTransport(settings, options?)` и возвращает `RelayTransport`
(`src/integrations/connector/transport.ts`). `settings` — объект `relay`
конфигурации, дополненный `projectId` и `actor` верхнего уровня; для
`relay-v2-cli` пути `binary` и `config` уже абсолютные (разрешены от каталога
файла конфигурации). Неверные настройки — `HarnessError('INVALID_INPUT')`.

### Общий набор проверки адаптера

`src/integrations/connector/testing.ts` содержит подделку backend
(`FakeRelayTransport`, fixture), обёртку точек отказа `faultyTransport` для
