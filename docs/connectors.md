# Коннектор задач: Relay v1 и Relay-2

Коннектор подключает к harness внешнее хранилище задач: читает задачу,
закрепляет её постановку, исполняет её обычным путём (ревью плана →
согласование → изолированная попытка → gates → независимое ревью → приёмка в
Git) и доставляет подтверждённый результат обратно в задачу. Это opt-in
модуль `devcontour-harness/integrations/connector`: корень пакета и
`./contracts` его не импортируют, адаптер backend загружается только для
явно выбранного provider.

Поддерживаются два независимых транспорта:

| provider        | Backend                                     | Транспорт                                                                                             |
| --------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `relay-v1-http` | Relay v1 (`/api/v1`, project-scoped routes) | HTTP, `src/integrations/relay-v1`                                                                     |
| `relay-v2-cli`  | Relay-2                                     | subprocess CLI (`--format json`, явные `--config`/`--project`/`--actor`), `src/integrations/relay-v2` |

Provider выбирается **только явно** в конфигурации — никогда по имени
бинарника `relay`. Базы v1 и v2 не взаимозаменяемы, миграции истории нет.

## Пользовательский путь

Все шаги — команды CLI; TypeScript писать не нужно.

```sh
# 1. Настроить: connector.json (см. «Конфигурация») и policy.json harness.

# 2. Проверить подключение, проект, capabilities и mapping — только чтение:
#    ни мутаций, ни записи истории, ни создания состояния.
npx harness source-check --source connector.json --policy policy.json --state ../state

# 3. Прочитать и закрепить снимок задач: graph.json, context.json, manifest.json.
npx harness source-snapshot --source connector.json --policy policy.json --state ../state --out ../snapshot

# 4. Обычное согласование (approvalMode: operator) — по файлам снимка.
npx harness review-plan --state ../state --policy policy.json --source connector.json \
  --graph ../snapshot/graph.json --context ../snapshot/context.json --author external
npx harness approve --state ../state --subject <graphId> --digest <graphDigest>
#    С --source внешние предпосылки (зависимости, выполненные через этот
#    коннектор) допускаются по решению источника (trusts) и доступности SHA в
#    target ref — те же правила, что у run; без --source доверенных receipt нет.
#    Так же допускаются зависимости из baseline (см. «Базовая линия»).
#    В approvalMode: agent ревью плана выполняется в шаге 5 автоматически.

# 5. Запуск: задачи перечитываются, semantic digest сверяется с закреплённым
#    снимком, eligibility проверяется — всё до любого вызова runtime.
#    Принятый результат доставляется в исходную задачу.
npx harness run --source connector.json --policy policy.json --state ../state

# 6. Локальный и внешний статус: принято / доставлено / конфликт / неизвестный
#    исход и независимое чтение получателя.
npx harness source-status --source connector.json --state ../state

# 7. Повтор или продолжение доставки — с тем же ключом операции; writer,
#    reviewer, gates и Git не вызываются.
npx harness source-deliver --source connector.json --state ../state [--work <workId>]

# 7a. Привязки критериев исправлены после приёмки (например, testId без
#     classname): тот же принятый результат доказывается заново, новый план
#     не нужен (см. «Повторное доказательство»).
npx harness source-deliver --source connector.json --state ../state --reprove [--work <workId>]

# 8. Разбор неизвестного исхода или конфликта (см. «Восстановление»).
npx harness source-reconcile --source connector.json --state ../state \
  --operation <key> [--decision resend|adopt:<id>|recheck]
```

`<graphId>`, `<graphDigest>`, ключи операций и ID поручений выводят
`source-snapshot` и `source-status` (JSON в stdout). Exit codes как у всего
CLI: 0 — успех, 2 — неверный вход, 3 — отказ/блокировка (в том числе
`uncertain`/`conflict` доставки и непройденная проверка), 4 — инфраструктура
(backend недоступен).

### Версия backend

`source-check`, `source-snapshot` и `run --source` сначала читают
идентичность backend и сверяют её с той, с которой проверен коннектор.
Relay v1 сообщает версию договора REST (`GET /api/v1/health` →
`contractVersion`); коннектор проверен с `contractVersion: 1`
(`RELAY_V1_CONTRACT_VERSION`). Relay-2 версию не сообщает: сверяется sha256
binary с `relay.build.sha256`, если он задан. Несовпадение в этих командах —
отказ `CONNECTOR_VERSION_MISMATCH` (exit 4) до чтения задач и любых мутаций.
`source-status`, `source-deliver` и `source-reconcile` идентичность заранее
не читают: транспорт Relay v1 сверяет версию перед первой мутацией (Relay-2 —
так же), и несовпадение там — неуспешная доставка или разбор с этой
причиной в сообщении, без отправленной мутации. Что делать: поставить пару
версий из [проверенных версий](compatibility-versions.md#транспорты) или
обновить ожидаемую сборку в конфигурации. Наблюдаемая идентичность сборки —
`identity.build` в ответе `source-check`.

## Конфигурация

```json
{
  "version": 1,
  "provider": "relay-v1-http",
  "relay": { "endpoint": "http://127.0.0.1:4700" },
  "projectId": "AbCd1234",
  "actor": "harness-controller",
  "repository": { "id": "app" },
  "tasks": [
    {
      "ref": "PRODUCT-3",
      "role": "developer",
      "writeScope": ["apps/api/src", "packages/sdk/src"],
      "gates": ["unit"],
      "criteria": [
        { "title": "API returns displayName", "gate": "unit", "testId": "api.user.displayName" },
        { "id": "Ab3dE6gH", "gate": "typecheck", "evidence": "gate" }
      ],
      "requiredDocuments": ["Spec"]
    }
  ],
  "completion": { "mode": "complete", "historicalComment": false },
  "eligibility": { "columns": ["ready", "in-progress"] },
  "limits": {
    "documents": 20,
    "documentBytes": 262144,
    "totalBytes": 4194304,
    "taskBytes": 1048576,
    "rereads": 3,
    "leaseMs": 120000
  },
  "history": { "enabled": true, "client": "devcontour-harness" }
}
```

| `relay`               | Настройки адаптера. v1: `endpoint` (+ `timeoutMs`, `maxResponseBytes`). v2: `binary`, `config` (относительно файла конфигурации), `project?` (workspace), `env?` (например `RELAY_HOME`, на macOS `DYLD_LIBRARY_PATH`), `timeoutMs`, `maxOutputBytes`, `build?`. `projectId`/`actor` берутся из верхнего уровня                 |
| `projectId`           | Ожидаемая идентичность проекта backend; несовпадение блокирует чтение снимка и любые мутации                                                                                                                                                                                                                                    |
| `actor`               | Автор всех записей коннектора                                                                                                                                                                                                                                                                                                   |
| `stateDir`            | Каталог состояния коннектора (относительно файла); без него — `--state`                                                                                                                                                                                                                                                         |
| `contextDir`          | Каталог локальных пакетов контекста `tasks[].context` (относительно файла); по умолчанию `work/context`                                                                                                                                                                                                                         |
| `repository`          | ID репозитория политики (и путь для сверки)                                                                                                                                                                                                                                                                                     |
| `tasks[]`             | Задачи: `ref` (постоянный ID или ключ), роль, `writeScope`, `gates`, сопоставление критериев, обязательные документы. Список может быть пустым: связку можно проверить до появления задач (`source-check`, `doctor`); снимок и запуск без задач — `NOT_READY`                                                                   |
| `tasks[].criteria[]`  | Критерий (`id` или точный `title`) → `gate` и `testId` JUnit — ID testcase как в отчёте, `classname.name` (node:test: `test.<имя теста>`); `evidence: "gate"` — достаточно прошедшего gate (явный выбор). Привязки — сведения доставки, не постановка: их правка не требует нового плана                                        |
| `baseline`            | Зависимости, закрытые до внедрения harness и принятые человеком: `sha`, `tasks`, `reason` (см. «Базовая линия»)                                                                                                                                                                                                                 |
| `tasks[].context`     | Локальные пакеты контекста поручения — каталоги `<contextDir>/<id>` (например, `controller-mode`); закрепляются в снимке                                                                                                                                                                                                        |
| `tasks[].labels`      | Метки поручения (0.1.0-alpha.72), как у задачи плана: `docs` — работа документации выпуска (`release.docs`), `security`, `payments`, `auth` — второй проход ревью. Backend их не хранит; правка — новое согласование, но не новая постановка (доставка не конфликтует)                                                          |
| `completion`          | `complete` — закрыть по правилам backend (по умолчанию в `done`); `review-only` — перевести в `review`/`column` и оставить человеку; `historicalComment` — при конфликте постановки записать явно исторический комментарий                                                                                                      |
| `eligibility.columns` | Колонки, из которых задача допускается к запуску (`done`/`cancelled` — никогда)                                                                                                                                                                                                                                                 |
| `limits`              | Пределы документов и постановки, число повторных чтений, срок владения доставкой                                                                                                                                                                                                                                                |
| `history`             | Запись истории работы (корневая и дочерние сессии)                                                                                                                                                                                                                                                                              |
| `taskContext`         | Контекст исполнения задачи из Relay (`relay-task-context-v1`): `mode` — `auto` (по умолчанию; читать, если Relay объявил capability) или `off`; `targetDocuments` — документы целей (по умолчанию `true`); `maxBytes` — предел одной задачи (1 МиБ); `totalBytes` — всех задач снимка (8 МиБ). См. «Контекст исполнения задачи» |
| `comments`            | `attempts`: `final` (по умолчанию) — комментарий в задаче пишет только доставка принятого результата; `all` — о каждой доставленной попытке, как до alpha.60                                                                                                                                                                    |
| `questions`           | Вопросы владельцу из Relay в представлении оператора: `enabled` (по умолчанию `true`), `limit` (20)                                                                                                                                                                                                                             |

### Локальные пакеты контекста

`tasks[].context` добавляет к поручению задачи пакеты из `<contextDir>/<id>` —
те же каталоги, что у файлового графа: файлы вкладываются в запросы writer и
reviewer, `references/` закрепляется digest без вложения. Так к задачам Relay
подключается оверлей controller-mode
(`templates/controller-mode/`): `"context": ["controller-mode"]`.

- Пакеты закрепляются в `context.json` снимка; поручение получает
  `context: [<контекст задачи>, ...пакеты]`. `source-snapshot` и manifest
  называют их в `localContext` (ID, digest, число файлов и справок, байты).
- Digest пакетов и их распределение по задачам (какие у какой, в каком
  порядке) входят в ревизию набора задач: изменённый, новый или перенесённый
  пакет — новый `source-snapshot`, ревью плана и согласование (`run --source`
  иначе отказывает `APPROVAL_STALE`). Semantic digest задачи от пакетов не
  зависит: включение поля или изменение пакета не делает доставку уже
  принятого результата конфликтом.
- Нет каталога или пакета — `NOT_READY` до чтения backend; пакет через
  symlink — `INVALID_INPUT`. `source-check` называет то и другое в `problems`.
- Пакет вне договора источника контекста (больше 30 файлов или 60 справок,
  имя файла с `*`, `?`, `:` и т. п.) — `LIMIT_EXCEEDED` в `problems` снимка и
  `source-check`: запуск отказывает до согласования, а не после него.
- Пределы контекста (файл, сумма, не больше 30 источников вместе с
  контекстами задач) проверяются при снимке: превышение — `LIMIT_EXCEEDED`, и
  задача не допускается к запуску.
- Без поля снимок, ревизия и digest задачи те же, что в прежних версиях.

### Контекст исполнения задачи

Снимок закрепляет всё, что исполнителю нужно по задаче, — для ревью плана,
согласования и приёмки. С 0.1.0-alpha.69 для этого достаточно обычной Relay
0.13 без доработок: транспорт собирает контекст сам из её маршрутов —
задача (`GET /board-tasks/{ref}`, явные цели «Реализует»), каждая цель и её
фича, сценарий и приложение (`GET /entities/get`), паспорт продукта,
неархивные документы задачи и целей (`GET /entities?kind=document&target=…&archived=false`).
Согласованность без токена сервера: после сборки ревизии задачи и всех
записей перечитываются (`GET /entities?refs=…`), расхождение — новая
сборка; снимок дополнительно сверяет два раунда чтения. Если сервер
объявляет capability `relay-task-context-v1`, тот же состав читается одним
вызовом `GET /board-tasks/{ref}/context?targetDocuments=…`. Снимок кладёт в
пакет задачи файл
`relay-context.md`: цели задачи (реализации FI/SI, фичи, сценарии) с полным
Markdown, фичи и сценарии этих целей, приложения, паспорт продукта и
документы (документы задачи — ссылкой на уже закреплённый файл
`documents/…`, документы целей — текстом). У каждой записи — ключ, ревизия и
основания включения («цель задачи (WEB-1)», «фича цели (WEB-FI-1)»).
`task.md` говорит исполнителю, что описание уже у него.

- В файл идёт только постановка: вычисляемые поля Relay (готовность,
  блокеры, время, токен согласованности) не переносятся, поэтому digest файла
  меняется только при правке записей.
- Digest файла входит в ревизию набора задач: правка FI/SI, фичи, сценария,
  паспорта или документа цели — новый `source-snapshot`, ревью плана и
  согласование (`run --source` по прежнему снимку — `APPROVAL_STALE`).
  Semantic digest задачи от контекста не зависит: доставка принятого
  результата конфликтом не становится.
- Документы задачи в контексте не делают согласование устаревшим сами по
  себе (alpha.69): в ревизию постановок контекст входит без записей,
  включённых только основанием «документ задачи». Обязательный документ
  (`requiredDocuments`) — часть постановки: его правка — новое
  согласование; необязательный (например, записанный ответ владельца) —
  `documentsDrift` в ответе `run`, исполняется закреплённый снимок, новый
  `source-snapshot` вносит документ. Документ цели (`target-document`) —
  часть постановки.
- Согласованность сборки на клиенте: после сборки перечитываются ревизии
  задачи и записей и состав прикреплённых документов (новый или
  архивированный документ — другое чтение); не согласовалось за повторы —
  раунд снимка несогласован и перечитывается, а не принимается.
- Паспорт продукта: нет записи (`ENTITY_NOT_FOUND`) — раздел пуст; нет
  маршрута или проекта — отказ чтения. Предел `taskContext.maxBytes`
  считает и краткие описания записей.
- Ревизия задачи в ответе контекста сверяется с полным чтением задачи;
  несовпадение — раунд перечитывается, граф не собирается из разных редакций.
- Пределы: `taskContext.maxBytes` на задачу (текст записей при сборке на
  клиенте; не больше 1000 записей) и `taskContext.totalBytes` на снимок;
  больше предела или `CONTEXT_TOO_LARGE` Relay — задача идёт
  без контекста (как раньше: задача, критерии, документы задачи), с отметкой
  в `missing` снимка, в manifest (`tasks[].taskContext.status: too-large`) и в
  `task.md`. Усечённого контекста нет.
- С `taskContext.mode: off` контекст не читается, и снимок, ревизия и
  digest — те же, что до alpha.60.
- Другая версия формы ответа (`contractVersion` контекста не 1) —
  `CONNECTOR_VERSION_MISMATCH` с названием версий и что обновить.

### Совместимость с Relay

Номер пакета Relay сервер по REST не сообщает, поэтому уровень
определяется по тому, что он сообщает о себе: версия договора REST
(`/api/v1/health` → `contractVersion`) и capabilities проекта. Таблица
версий — [проверенные версии](compatibility-versions.md#relay-минимальная-и-рекомендуемая-версия).

- `source-check`, `source-snapshot` и `source-status` возвращают
  `compatibility` (`level`, `taskContext`, `taskContextSource` — `client`
  (сборка harness) или `server` (маршрут Relay), `contractVersion`,
  `minimum`, `recommended`, `line`). Рекомендуемая Relay — обычная 0.13.x:
  предупреждения о версии Relay с alpha.69 нет.
- `doctor --source <connector.json>` (или `connector.json` рядом с
  `--policy`) и `init` (`--source` или `.harness/connector.json`) сверяют
  Relay так же: `RELAY_COMPATIBILITY: …` в `warnings` doctor (и поле
  `relay`), `relay-compatibility` в предупреждениях init. Недоступный Relay —
  тоже предупреждение, а не отказ команды.
- Неизвестная или слишком старая версия договора — именованный отказ
  `CONNECTOR_VERSION_MISMATCH` (exit 4) со словами, что обновить: Relay
  новее — harness, Relay старее — Relay.
- Представление оператора показывает ту же строку в `health.sources[]`
  (последнее наблюдение связки).

### Вопросы владельцу из Relay

Ведущий записывает отложенные вопросы владельцу в Relay документами по
соглашению Relay: название `Вопрос: <суть>`, тип `proposal`, состояние
`draft`, разделы `## Вопрос`, `## Варианты`, `## Рекомендация`,
`## Временный ответ`, `## Ответ`; документ прикреплён к затронутым задачам.
`source-snapshot` и `run --source` читают открытые вопросы (capability
`relay-document-library-v1`) и записывают наблюдение в состояние связки;
`source-status` показывает их живым чтением (`questions`). Чтение вопросов
ограничено 20 с и сбоем не останавливает снимок и запуск (причина — в
`questions.error`). Срез задач для `harness view` (названия и причины
неготовности) пишется в то же наблюдение при каждом чтении: колонка и
зависимости меняются без новой ревизии снимка. `harness view`
отдаёт их в `sourceQuestions[]` (вопрос, варианты, рекомендация, временный
ответ, задачи, ссылка на документ в Relay) — панель показывает их в «Нужно
от вас». harness на них не отвечает и их не меняет: ответ — в Relay (тип
`decision`, состояние `active`), после чего вопрос пропадает при следующем
наблюдении.

### Базовая линия

В существующем проекте история закрыта вручную: receipt этого коннектора у неё
нет и получить его задним числом нельзя, поэтому задача, зависящая от такой
истории, не запускается (`DEPENDENCY_UNPROVEN`). Человек принимает такие
зависимости явно:

```json
{
  "baseline": {
    "sha": "4f2c9a1e7b3d5c806e1f2a9d4b7c3e5f60a1b2c3",
    "tasks": ["PRODUCT-1", "PRODUCT-2"],
    "reason": "Closed by hand before the harness was adopted"
  }
}
```

- `sha` — полный SHA коммита (40 hex), `tasks` — точные ключи задач backend,
  `reason` — непустая причина. Шаблонов, даты отсечения и общего переключателя
  нет; лишнее поле, короткий SHA, повтор ключа или задача самой конфигурации —
  `INVALID_INPUT`.
- Завершённая зависимость вне графа без receipt и с ключом в `tasks` становится
  обычной предпосылкой: `resultSha` = `sha`, репозиторий — репозиторий
  зависимой задачи, `receipt: {kind: 'trusted', issuer, digest}`, где digest —
  запись базовой линии. Если у зависимости есть настоящий receipt, действует
  он. Незавершённая остаётся `DEPENDENCY_UNFINISHED`, не указанная —
  `DEPENDENCY_UNPROVEN`. Одна зависимость у задач разных репозиториев —
  отказ: базовая линия — один коммит.
- `trusts` принимает такую предпосылку, только если digest и SHA совпадают с
  **загруженной сейчас** конфигурацией, а backend подтверждает, что ключ — та
  самая задача (чтение задачи; ошибка backend — отказ, а не «нет записи»).
  Движок, как и для любой предпосылки, проверяет доступность SHA в target ref.
- Любая правка `baseline` меняет ревизию набора задач, даже если запись не
  использована: `run --source` по прежнему снимку отказывает `APPROVAL_STALE`,
  нужны новые `source-snapshot`, ревью плана и согласование. Возврат к прежней
  редакции (постановки или `baseline`) тоже снимается `source-snapshot`: запись
  снимка остаётся прежней (`created: false`), но снова становится последней.
  Semantic digest задачи не меняется: доставка принятого результата конфликтом
  не становится.
- Происхождение видно: `proof: 'baseline'` у зависимости и `baseline` в
  manifest, в ответах `source-snapshot`, `run --source` и `source-status`,
  строка «Зависимости без доказательства» в итоге для задачи. Предпосылка
  графа сама происхождение не несёт, поэтому `explain` его не показывает.

**Что это доказывает.** Только то, что указанный коммит есть в target ref и что
человек записал своё решение. Что работа задачи действительно входит в этот
коммит, никто не проверял: SHA общий для всех ключей, gates и ревью по нему не
запускались. Это решение оператора, а не receipt.

**Кто может её изменить.** С `baseline` файл конфигурации обязан лежать вне
репозиториев политики или внутри их `protectedPaths`: `.harness/connector.json`
при политике из `harness init` подходит (`.harness/` защищён). Иначе
`review-plan --source` и `run --source` отказывают `NOT_READY`, а `source-check`
с `--policy` называет это в `problems`. Ссылка на файл разрешается до проверки.
Runner отклоняет результат попытки, меняющий защищённый путь, а при
`isolation.mode: "os"` запись вне рабочего дерева запрещена и самому процессу.
Защита действует против писателя поручения, а не против того, кто запускает
harness: controller с доступом к файлу может его изменить, и при
`approvalMode: agent` человек такую правку не согласует. При `isolation.mode:
"none"` запрет записи вне дерева держится только на самом runtime. Конфигурация,
переданная библиотеке объектом, и прямой `Harness.run({ source })` мимо
`Connector.run` этой проверки не проходят: там за файл отвечает вызывающий код.

### Идентичность и снимок

- Идентичность задачи — `<provider>:<projectId>:<постоянный ID>`; ID поручения
  и графа — хэш от неё. Одинаковые номера задач разных проектов/backend не
  совпадают; смена cwd на worktree идентичность не меняет.
- `SourceRef.revision` — **semantic digest** постановки (v2, с alpha.66):
  текст, определения критериев (без отметок выполнения), зависимости,
  родитель, подзадачи, **обязательные** документы (`requiredDocuments`) и
  digest поручения из mapping (роль, репозиторий, `writeScope`, `gates`).
  Колонка, свой in-progress, комментарии, история, отметки критериев и
  настройки доставки (`completion`, привязки критериев) в него не входят. CAS-ревизии backend, токены согласованности
  чтения и идентичность сборки хранятся только в manifest снимка (никогда в
  поле Git SHA).
- **Привязки критериев** (`criteria[]`: gate, testId, evidence) и
  `completion` в digest не входят: в поручении их нет, они говорят доставке, чем доказать критерий.
  Исправленный testId не меняет ни ревизию набора, ни поручение: ни нового
  согласования, ни доработки принятой работы — только
  `source-deliver --reprove`.
- **Необязательные документы** — контекст: их содержимое входит в ревизию
  набора, но не в постановку задачи и не в ревизию постановок
  (`manifest.ordersRevision`, 0.1.0-alpha.68). Их правка — записанный ответ
  или решение владельца — согласования не обесценивает: `run --source`
  исполняет закреплённый снимок и называет изменённые документы
  (`documentsDrift`); в работу их вносит новый `source-snapshot`, а ревью
  неизменённого плана после одобренного раунда предел раундов не тратит.
  `APPROVAL_STALE` — только при изменённой ревизии постановок (текст,
  критерии, зависимости, обязательные документы, контекст задачи, пакеты,
  предпосылки, базовая линия), и отказ называет изменённые задачи. Снимок,
  закреплённый до alpha.68 (без `ordersRevision`), — прежнее правило. Принятый результат после правки такого документа
  (например, документа-вопроса, в который владелец записал ответ)
  доставляется без конфликта. Правка обязательного документа — изменённая
  постановка: доставка — `conflict`.
- **Обновление с версии до alpha.66.** Manifest хранит и прежние значения
  (`tasks[].legacyDigest`, `legacyRevision`): результаты и операции прежних
  версий сверяются по ним, а снимок, закреплённый прежней версией,
  остаётся закреплённым (`source-snapshot` отвечает `created: false` с его
  ревизией, `run --source` не требует нового согласования), пока постановка
  и mapping не менялись.
- Чтение — раундами по всем задачам; снимок принимается, когда два раунда
  подряд совпали токенами и содержимым. Изменения — не больше `rereads`
  повторов, затем явный отказ `NOT_READY`; ошибка сети/CLI — отказ, а не
  пустая доска.
- Обязательное содержимое (текст постановки, критерии, `requiredDocuments`)
  не усекается: превышение предела блокирует запуск с причиной и пределом.
  Дополнительные документы усекаются с явной отметкой в начале файла и в
  manifest (`truncated`) либо опускаются с записью в `missing` снимка.
- Eligibility проверяется отдельно от digest: `done`/`cancelled`, колонка вне
  `eligibility.columns`, незавершённая зависимость, зависимость в `done` без
  receipt этого коннектора и без записи в `baseline`. Колонка, в которую задачу перевела наша
  подтверждённая доставка той же постановки, повтор не блокирует.
- Статус `done` зависимости — не доказательство: предпосылка зависимой
  задачи появляется только из receipt доставки этого коннектора (издатель —
  ID коннектора, digest сверяется с его состоянием) или из явной записи
  человека в `baseline`, и движок дополнительно проверяет доступность SHA в
  target ref.

## Доставка: протокол и гарантии

Ключ операции — `sha256(provider, projectId, workId, runId, resultDigest)`.

1. **Intent до вызова.** Операция записывается в состояние коннектора до
   первого внешнего вызова. Не удалось записать — мутация не отправляется.
2. **Сверка перед мутацией.** Задача перечитывается: изменился semantic
   digest или задача отменена/закрыта другим — `conflict`; результат остаётся
   привязан к своему снимку и SHA, текущая задача не закрывается (по
   `historicalComment` — один явно исторический комментарий).
3. **Шаги**, каждый записан до и после вызова: комментарий с маркером
   `<!-- devcontour-harness:op=<key>:step=<n> -->`; отметки сопоставленных
   критериев с CAS; перемещение с CAS; закрытие истории. Критерий отмечается
   только по mapping на прошедший в integration gate/testcase принятого
   результата; ручные критерии, непрошедший testcase, незавершённые
   подзадачи и зависимости оставляют задачу незавершённой. Причина
   недоказанного критерия называет, чего нет: «testcase X отсутствует в
   evidence gate G (есть test.X: ID testcase — classname.name…)» или
   «testcase X: failed».
   Перед **каждым** неподтверждённым шагом (в том числе при продолжении
   после обрыва или перезапуска) задача перечитывается: постановка обязана
   совпасть со снимком результата, задача — не быть отменённой или закрытой
   другим, а для нового CAS-шага текущая ревизия — равняться ревизии,
   записанной после **нашего** предыдущего шага. Иначе — `conflict`, и
   изменённая задача старым результатом не закрывается.
4. **Неизвестный исход** (таймаут, обрыв ответа, падение процесса между
   вызовом и записью итога) разбирается фактами получателя: комментарий — по
   маркеру (ровно один — подтверждено); CAS-шаг — по состоянию и ревизии
   (цель достигнута, ревизия ровно на 1 больше нашей и постановка та же —
   подтверждено; цель достигнута, но ревизия или постановка ушли дальше —
   `conflict`; ревизия прежняя — не применено; ревизия
   сменилась без нашей записи — `conflict`). Ответ `conflict` получателя
   никогда не лечится повтором старой команды по новой ревизии.
5. **Подтверждённый отказ ≠ неизвестный исход.** Структурный отказ
   получателя (`refused`; `conflict` для записи без CAS — комментария;
   `unavailable` до отправки) означает, что мутации не было: шаг остаётся
   `planned`, доставка — `failed` с причиной «подтверждённый отказ
   получателя», повтор `source-deliver` безопасен (тот же маркер). Класс
   ответа задаёт адаптер: 5xx/ненулевой exit без доказательства отката для
   мутации адаптер сообщает как `uncertain`, и тогда действует п. 6.
6. **`uncertain`.** Если исход доказать нельзя (0 маркеров после возможной
   отправки, больше одного, read-back недоступен), операция получает
   `uncertain` (событие `delivery.uncertain` с ключом операции), повторная
   доставка ничего не отправляет до `source-reconcile`.
7. **Receipt.** После подтверждения всех шагов сохраняется receipt (ID
   комментария, критерии, колонка, ревизия, сессии истории); для принятого
   результата — доверенный receipt для зависимых задач.

Повторная доставка принятого результата не вызывает writer/reviewer, не
запускает gates и не меняет Git. Частично выполненная доставка продолжается
с первого неподтверждённого шага без повтора append-only записей.

### Один владелец доставки

Владение операцией — lease с токеном, сроком и fencing в SQLite состояния
коннектора (`BEGIN IMMEDIATE`). Живой владелец продлевает lease и во время
долгого вызова; второй процесс над тем же каталогом получает
`CONTROLLER_BUSY` и ничего не отправляет. Упавшего владельца можно
перехватить только после истечения срока, intent при этом не теряется;
каждая запись проверяет lease в той же транзакции, поэтому процесс,
потерявший владение, больше ничего не записывает. Срок `limits.leaseMs`
должен превышать таймаут одного вызова транспорта.

**Граница гарантии:** она действует только для процессов, разделяющих один
каталог состояния коннектора. Независимые установки с разными каталогами
состояния вне гарантии и могут доставить одну операцию дважды —
`source-check` и `source-status` показывают это в `ownership`. Distributed
lock в этой версии не реализован.

### Что гарантируется, а что нет

Доказывается тестами (`tests/connector-*.test.ts`, общий набор
`connectorSuite`):

- одна подтверждённая доставка — один комментарий с маркером, без повторных
  эффектов критериев и истории, в том числе после перезапуска процесса;
- обрыв до отправки — безопасный повтор; запись получателем без ответа —
  read-back без дубля; ответ без сохранённого receipt — без новых мутаций;
  отказ записи intent — без мутации;
- неизвестный исход не объявляется успехом и не повторяется автоматически;
- старая постановка не закрывает новую; чужое изменение между сверкой и CAS —
  конфликт без повтора;
- два процесса не отправляют одну операцию одновременно.

**Не гарантируется:** distributed exactly-once — у получателя нет
идемпотентности по `requestId` (Relay v1 явно её не обещает, у Relay-2 её
нет), а Git и Relay не образуют общей транзакции. Неоднозначные случаи
решает оператор.

### Проверка привязок до запуска

Каждый критерий связанной задачи обязан доказываться тем, что коннектор
умеет доказать: прошедшим gate (`evidence: gate`) или названным testcase
gate задачи с JUnit-отчётом. `source-check`, `doctor` (строки
`RELAY_CRITERIA_BINDING`) и `run --source` сверяют привязки с политикой и с
testcases, которые gates уже сообщали в попытках этого каталога состояния:

| Привязка                                                            | Итог                                                           |
| ------------------------------------------------------------------- | -------------------------------------------------------------- |
| gate не объявлен в политике или не входит в `gates` задачи          | ошибка: `run --source` — `NOT_READY` до попыток                |
| `evidence: test`, а у gate нет JUnit-отчёта                         | ошибка                                                         |
| testcase нет в отчётах gate, но есть `<classname>.<testId>`         | ошибка с верным ID («укажите testId «test.orders.api.access»») |
| testcase ещё не встречался, а все testcases gate с одной приставкой | предупреждение `source-check`/`doctor`                         |
| новый testcase без отчётов gate                                     | не ошибка: его напишет исполнитель                             |

Отказ называет, что исправить в `criteria[]`; правка привязок не меняет
постановку, поэтому после неё нового `source-snapshot`/плана не нужно.

### Повторное доказательство (`source-deliver --reprove`)

Подтверждённая доставка не повторяется. Если доставка принятого результата
подтверждена, но критерии остались недоказанными из-за привязок (testId не
тот), привязки исправляются в `criteria[]`, и тот же результат доказывается
заново:

```sh
npx harness source-status --source connector.json --state ../state   # tasks[].proof
npx harness source-deliver --source connector.json --state ../state --reprove [--work <workId>]
```

- Берётся результат попытки, **принявшей** поручение (не последней доработки),
  с тем же evidence. Моделей, gates, ревью и Git нет.
- Ключ операции — `sha256(..., resultDigest, 'reprove', digest привязок)`:
  те же привязки — тот же ключ, повтор ничего не отправляет; исправленные
  ещё раз — новый ключ. Прежняя доставка остаётся своей записью; в
  `harness result` у повторного доказательства ключ `<sink>:reprove-<digest>:…`.
- Шаги — как у доставки: комментарий с маркером («Повторное доказательство
  того же принятого результата…»), отметки доказанных критериев с CAS,
  перемещение по правилам `completion`. Нечего отмечать и перемещать —
  операция без записей у получателя. Второй receipt для зависимостей не
  выпускается.
- Постановка обязана быть той же, что у результата (digest v2/v1; для
  результата прежней версии с прежними привязками — по байтам закреплённого
  снимка: `task.md`, обязательные документы, зависимости, подзадачи,
  поручение; так же сверяет и обычная доставка такого результата). Иначе — `conflict` с причиной «постановка изменилась после
  снимка», задача старым результатом не закрывается.
- `source-status` показывает для принятого поручения с незакрытой задачей
  `tasks[].proof`: `reprovable` (сколько критериев докажут текущие
  привязки), `unproven` с причинами и `next` — следующий шаг.

Проблема доставки — не повод перепланировать принятую работу: новый план
открыл бы доработку (с её попытками и ревью) ради того, что код уже доказал.

### Восстановление (`source-reconcile`)

Сначала проверяются факты получателя; решение оператора нужно только там,
где факты неоднозначны.

| Ситуация                                                                            | Что видно                                   | Действие                                                                                                 |
| ----------------------------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Запись прошла, ответ потерян                                                        | маркер найден ровно один                    | `source-reconcile --operation <key>` — подтверждение по факту, доставка продолжается                     |
| Read-back был недоступен                                                            | `uncertain`, причина «read-back недоступен» | повторить `source-reconcile` после восстановления доступа                                                |
| Таймаут, маркера нет                                                                | 0 маркеров                                  | проверить получателя; если записи нет — `--decision resend` (тот же маркер)                              |
| Несколько записей с маркером                                                        | N > 1                                       | выбрать одну: `--decision adopt:<commentId>`; первая найденная не выбирается автоматически               |
| CAS-конфликт без изменения постановки (например, сдвиг ранга соседней задачей в v1) | `conflict`                                  | `--decision recheck`: постановка перечитывается, при совпадении digest шаг продолжается от новой ревизии |
| Постановка изменилась                                                               | `conflict`, `matchesSnapshot: false`        | результат остаётся историческим; новый `source-snapshot` → согласование → `run --source`                 |
| Критерии не доказаны: привязка (testId) не та                                       | `delivered`, задача не закрыта, `proof`     | исправить `criteria[]`, затем `source-deliver --reprove`; нового плана не нужно                          |

## История работы

При включённой истории (`history.enabled`):

- до исполнения попытки (до вызова writer) — корневая сессия поручения с
  intent, затем fork дочерней сессии попытки, attach и её intent. Ошибка
  записи intent — отказ окружения: попытка не начинается;
- отказ попытки — отмена дочерней сессии; доставка результата — checkpoint с
  SHA и сводкой gates, завершение и приём дочерней, завершение корня (или
  отмена при непринятом результате);
- каждая запись несёт маркер; после перезапуска controller шаги разбираются
  read-back (`findSessions`, `checkpoints`, ревизия сессии) — без дублей;
  записи прерванной попытки только подтверждаются фактами и отменяются;
- ревизия сессии и run backend — fencing: если сессию перехватил другой
  владелец, устаревший run её не завершает (`conflict`);
- ID сессии/run backend, sessionId runtime и lease token попытки — разные
  значения; lease token и полный runtime log в историю не пишутся.

## В Relay уходит

Комментарий в задаче пишет только доставка **принятого** результата
(`comments.attempts: final`, по умолчанию с alpha.60): отклонённые и
остановленные попытки видны в harness (`status`, `view`, панель), но
обсуждение задачи не засоряют. Отметки критериев, перемещение и история
работы — как прежде; `comments.attempts: all` возвращает комментарий о
каждой доставленной попытке. Работа, которая так и не принята (попытки
исчерпаны, отменена), комментария в задаче не оставляет: её итог — в harness
и в истории работы Relay.

Краткий итог: исход, проверяемые SHA (candidate, integration/result), target
ref, сводка gates (без журналов), таблица критериев → gate/testcase →
результат, semantic digest и CAS-ревизия снимка. Локальные пути заменяются
пометкой (они не ссылки для другого компьютера), значения секретов политики
маскируются, полный runtime log и вызовы инструментов не копируются.

## Маскирование секретов

Ошибки транспорта (тело ответа HTTP, stderr CLI) маскируются до того, как
попадут в отчёт `source-check`, `source-status`, ошибки снимка, причины
шагов и операций в состоянии коннектора, `lastError` доставки, отказ записи
истории и вывод CLI. Маскируются значения секретов политики на любом уровне
(`environment.secrets` политики, репозиториев и tool profiles — по
окружению controller; для `source-snapshot` укажите `--policy`, иначе
используется политика каталога состояния) и значения настроек provider с
именем вида `*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*KEY*`.

## Состояние коннектора

`<stateDir>/connectors/<provider>-<hash(projectId)>.sqlite` — отдельная от
`state.sqlite` база: снимки (manifest и digest), операции доставки (intent,
шаги, receipt), lease, связи с историей и последнее наблюдение backend
(совместимость, открытые вопросы владельцу — только для показа в `harness
view`). Это не состояние исполнения: оно
остаётся единственным — в `state.sqlite` harness.

## Библиотека и договор адаптера

```ts
import { openConnector } from 'devcontour-harness/integrations/connector';

const connector = await openConnector('connector.json', { stateDir: '../state' });
const h = Harness.open({ stateDir: '../state', policy, baseDir, hooks: connector.hooks() });
await connector.snapshot('../snapshot');
await connector.run(h, { author: 'external' });
await connector.status(h);
```

Модуль адаптера (`src/integrations/<adapter>/index.ts`) экспортирует
`createTransport(settings, options?)` и возвращает `RelayTransport`
(`src/integrations/connector/transport.ts`). `settings` — объект `relay`
конфигурации, дополненный `projectId` и `actor` верхнего уровня; для
`relay-v2-cli` пути `binary` и `config` уже абсолютные (разрешены от каталога
файла конфигурации). Неверные настройки — `HarnessError('INVALID_INPUT')`.
