# devcontour-harness 0.1.0-alpha.55 (черновик)

Выпуск собирает три изменения: оператор видит прогресс простыми словами —
почему поручение повторяется, почему не выдаётся, что проверено и как;
технические вопросы исполнителя может решать ведущий агент — только с явного
разрешения человека в политике и с записанной причиной; новая команда
`harness view` даёт панели оператора один документ только для чтения.
`stateVersion`, `policyVersion`, `handoffVersion` и `reportVersion` прежние:
изменения схем аддитивны (необязательные поля, новая команда и коды
отказов), без нового поля политики поведение alpha.54 не меняется.

Перед откатом на 0.1.0-alpha.54 прочитайте раздел «Совместимость и откат»:
записи вопросов этой версии alpha.54 не читает.

## Изменения

### Понятный прогресс

Оператор видит прогресс простыми словами, без пересказа ведущего агента.

- **Почему поручение повторяется.** Строка этапа `status`
  (`works[].stage.line`, `lineEn`) называет номер попытки из предела и
  причину остановки прошлой попытки: «попытка 3 из 6; прошлая остановлена:
  окружение — порт 3000 занят»; у ждущей и остановленной — «попыток
  использовано 3 из 6; последняя остановлена: дефект — не прошли проверки:
  unit». Сводка попыток `status` и `explain` — поле `lastFailure` (`runId`,
  корзина, класс, время, `plain`/`plainEn`). Текст строится из класса
  отказа, ID упавших gates и номера занятого порта: свободный текст ошибки
  в него не попадает.
- **Почему не выдаётся.** У каждой блокировки `status`
  (`works[].blockers[]`) — простой текст по-русски и по-английски и кто её
  снимает (`plain`, `plainEn`, `actor`): «ждёт зависимости a», «черновик —
  не утверждён», «ждёт согласования плана», «ждёт вашего ответа на вопрос
  исполнителя», «пауза очереди: бюджет». Ждущее выдачи без блокировок —
  «просто ждёт очереди — ничего не нужно». `status --human` печатает
  блокировки простым текстом, коды — в скобках. У каждого кода
  `Engine.blockers` есть текст: тест падает, если код добавлен без него.
- **Что проверено и как.** `status`, `explain`, `result`/`deliver` и отчёт
  несут `verification`: строку на gate и ревью попытки (записи текущего SHA
  фазы) — `result` (`passed`, `failed`, `reused`, `skipped`,
  `not-applicable`) и `how` (`executed-by-harness`, `reused-evidence`,
  `read-by-reviewer`, `not-run`), у ревью — runtime и вендор reviewer, что он
  запускал по записи controller и протокол ответа — и одну строку:
  «Проверено harness (запущено): lint, unit; ревью: прочитал агент openai
  (codex), только diff, ничего не запускал — одобрил; не проверялось: e2e
  (изменения его не задели)». Gate, который песочница не запустила, — «не
  запустилась — отказ среды», а не «не прошло». Только ID gates, без
  команд. Текст для человека не говорит «проверено» или "checked" без того,
  кто и как проверял. В отчёте проверки поручений держат общий предел 64 КБ.
- **Библиотека.** `plainBlocker`, `blockerCodeText`, `failurePlainOf`,
  `verificationOf`, `verificationRows`, `verificationLines`, схема
  `workVerificationSchema`.

### Технические вопросы решает ведущий

- **Влияние вопроса.** Вопрос исполнителя получил необязательное поле
  `impact`: `technical` — ни один вариант не меняет того, что видит и
  получает пользователь продукта (выбор внутри реализации), `user-visible` —
  меняет. Нет поля — `user-visible`: в сомнении вопрос идёт человеку. Каждый
  вариант получил необязательное `forUser` — одну строку простыми словами
  «что изменится для пользователя». Запрос writer объясняет, как
  классифицировать вопрос; wire-схема ответа объявляет оба поля с `null`, а
  `null` в запись не попадает. Значение `impact` вне перечня снимается
  (`normalized`), и вопрос остаётся человеку.
- **Разрешение в политике.** `inputPolicy.leadAnswers.technical: true` —
  явное согласие человека, что ведущий решает технические вопросы сам:
  `input-answer --actor lead --reason "<почему>"`. Без `--reason` —
  `INVALID_INPUT`. Вопрос с минимумом (критическая область или критический
  путь) и вопрос без `impact: technical` ведущему по этому правилу не
  доступны — `OPERATOR_ANSWER_REQUIRED`, как прежде. С `technical: true`
  вопрос для пользователя остаётся человеку при любом `maxSeverity`:
  `maxSeverity` тогда лишь ограничивает серьёзность технических вопросов.
  Без `technical` правило `maxSeverity` прежнее (оно стало необязательным;
  нужно хотя бы одно из двух). Повтор ответа с другой причиной — новая
  версия ответа.
- **Где видно.** Принятый ответ ведущего на блокирующий вопрос хранит
  правило (`basis: technical | severity`) и причину (`reason`). `status`
  (`works[].input.impact`, `answerBasis`, `leadMay`; `--human` — «решено
  ведущим (технический вопрос)»), `explain` (разрешённый технический вопрос —
  `actor: lead`, `answer-input`; ответ — с причиной), пакет передачи
  (`inputs[].impact`, `inputs[].answer.basis/reason`, Markdown) и отчёт
  (`inputs.answeredBy.leadTechnical`, строка раздела Autonomy).
- **Выбор при подготовке.** `init --lead-technical-answers` пишет правило в
  новую политику; без флага на вопросы, останавливающие работу, отвечает
  человек. `init` и `doctor --policy` показывают действующее правило простыми
  словами (поле `questions`: `leadTechnical`, `maxSeverity`, `line`,
  `lineEn`; `init --human` — строка `questions:`). Флаг при сохранённой
  политике без правила — `PATH_CONFLICT` `content-differs`: правило меняется
  правкой политики, а не молча.

#### Ведущий агент (skill `harness`)

- Перед тем как передать человеку вопрос, меняющий результат для
  пользователя, ведущий добавляет одну свою строку простыми словами: о чём
  решение и почему работа остановилась. Сам вопрос, варианты, `forUser`,
  рекомендация и серьёзность передаются дословно: ведущий их не
  переформулирует и не переупорядочивает.
- Технический вопрос при разрешённом правиле ведущий решает сам с причиной;
  если он видит, что вариант всё же меняет результат для пользователя,
  передаёт вопрос человеку.
- В начале долгого запуска ведущий запускает панель оператора через skill
  `harness-ui`, если он установлен, и даёт её URL; иначе даёт
  `harness status --human --watch`. Он говорит, что эти данные идут из
  самого harness, а не из его пересказа.

### Представление для оператора и `harness view`

- **Новая команда** `harness view --state D [--policy F] [--work ID]
[--no-titles] [--window 24h|7d] [--bucket 15m|1h] [--lang ru|en]
[--view-version 1]` — один JSON-документ только для чтения для панели
  оператора (`OperatorView`, с `--work` — `WorkDetailView`). Документ
  несёт `viewVersion: 1` и `viewRevision: 0`; схемы —
  `schemas/operator-view.schema.json` и `schemas/work-detail-view.schema.json`.
  Команда есть в `capabilities` (`readOnly: true`); операция библиотеки —
  `harnessView(options)`.
- **Чистая проекция** `operatorView(input, options)` и
  `workDetailView(input, workId, options)` в `devcontour-harness/projections`
  (без `node:*` и zod) и загрузчик `collectOperatorViewInput` для node. Числа
  — те же, что у `status` и `report`: проекция их не выводит заново.
- **Маскирование до обрезки** каждого свободного текста
  (`maskText`, `redactThenClip` теперь и в `./projections`), пределы
  списков с `truncated` и отказ `VIEW_TOO_LARGE` для документа больше
  256 КБ, токен содержимого `source.token` (SHA-256 без `generatedAt`).
- **Язык** простых строк harness — `--lang ru|en` (по умолчанию `ru`).
- **Коды ошибок.** `POLICY_REQUIRED` (exit 2): нет состояния и нет
  `--policy`. `VIEW_TOO_LARGE` (exit 4).

## Совместимость и откат

Понятный прогресс:

- Новые поля ответов необязательны: `attemptSummary.lastFailure`,
  `works[].blockers[].plain/plainEn/actor`, `works[].verification`,
  `explain.verification`, `result.verification`,
  `works.rows[].verification` отчёта. Потребитель со строгой схемой прежней
  версии должен их принять.
- Текст `status --human` и `explain --human` изменился (строка блокировок,
  строка `проверки:`, этап `queued`, раздел проверок `explain`); скрипты
  читают JSON.
- Откат этих полей на 0.1.0-alpha.54 не требует действий с данными.

Технические вопросы:

- Поля `impact`, `forUser` вопроса, `basis`, `reason` ответа, поля статуса,
  пакета передачи, отчёта, `init` и `doctor` — аддитивны.
- `implementationOutputSchema` (wire-схема ответа writer) объявляет новые
  поля обязательными с `null`. Хост, который передаёт runtime свою копию
  схемы, должен её обновить; иначе writer не вернёт `impact`, и вопрос
  останется человеку.
- `explain` на ждущий технический вопрос при разрешённом правиле называет
  `actor: lead` вместо `user`; без нового поля политики — как прежде.

Откат на 0.1.0-alpha.54:

1. Уберите `inputPolicy.leadAnswers.technical` и из `.harness/policy.json`,
   и из сохранённой копии политики в `<state>/binding.json`. `leadAnswers`
   без `maxSeverity` уберите целиком: схема alpha.54 требует `maxSeverity`.
2. Записи `input-requests` с `impact`, `forUser`, `basis` или `reason`
   alpha.54 не читает (строгая схема). Откат после вопросов исполнителя этой
   версии не поддерживается — откатывайтесь на копию состояния, снятую до
   обновления.

Подробно — [upgrade](../upgrade.md).

Представление для оператора:

- Команда, схемы и коды ошибок — аддитивны; прежние команды не меняются.
- `harness view` читает состояние неизменяемым открытием, как `report`: без
  журнала WAL в каталоге состояния не появляется ни одного файла; при идущем
  `run` SQLite может создать служебный `-shm`, как у `status`.
- Несовместимое состояние даёт `STATE_VERSION_UNSUPPORTED` (exit 4), как у
  остальных читающих команд.

- Откат: команда `view` и коды `POLICY_REQUIRED`, `VIEW_TOO_LARGE` в
  alpha.54 отсутствуют; панель или скрипт, которые их вызывают, после отката
  получают неизвестную команду. Данные состояния `view` не пишет.
