# devcontour-harness 0.1.0-alpha.54 (черновик)

## Изменения

### Обзор уже написанной ветки: `harness review-code`

- **Новая команда.** `harness review-code --state D [--policy F] --base A
--head B [--role R] [--author A] [--repository ID]` — независимый
  технический обзор кода, написанного вне harness (ведущим агентом,
  человеком, до подготовки проекта). Прежде техническое ревью принимало
  только план и контракт, а код проверялся только внутри попытки.
- **Reviewer — по правилу ревью кода роли.** Роль — `--role` (одна роль
  репозитория — по умолчанию), автор — `--author` (по умолчанию writer роли).
  Правило вендора то же, что у ревью кода попытки: reviewer другого вендора,
  того же — только при `vendor: same-vendor-allowed` (запись отмечает
  `sameVendor: true`), иначе `REVIEWER_SAME_VENDOR` до вызова модели.
- **Что видит reviewer.** Diff `merge-base(base, head)..head` (не больше
  4 МиБ) и отдельное рабочее дерево на `head` только для чтения; состояние и
  исходные checkout закрыты, дерево убирается после вызова. Пустой diff,
  ref без общего предка и неизвестный коммит — отказ до вызова.
- **Gates как приложенное наблюдение.** `harness gates` теперь пишет итог
  рядом с логами (`<state>/gates-at/<id>/result.json`). Если такой итог есть
  для `head`, `review-code` прикладывает его к запросу и к записи (`gates`);
  сама команда gates не исполняет.
- **Запись — не приёмка.** Ответ — `CodeReviewRecord`
  (`cliDataSchemas['review-code']`): `kind: code`, `acceptance: false`,
  SHA `base`, `head`, `mergeBase`, изменённые файлы, число коммитов, digest
  diff, reviewer и назначение, находки в той же форме, что у ревью плана, и
  путь артефакта. Exit 0 — одобрено, 3 — блокирующие находки. Повтор по тем
  же `--base`/`--head` — следующий раунд: reviewer называет состояние
  прежних открытых находок; одобренный `head` с тем же reviewer — тот же
  раунд без вызова. Записи хранятся в новом локальном пространстве
  `code-reviews`; поручения, попытки, target ref и счётчики отчёта не
  меняются.

### Принятая версия против текущего target ref

- **`target` у принятой работы.** `status` (`works[].target`), `result` и
  `deliver` (`target`) сверяют принятый SHA с текущим target ref:
  `acceptedSha`, `head`, `commitsSinceAccepted`, `filesSinceAccepted`,
  `diverged` (ref переписан), `unavailable` (git не ответил — не отказ
  команды) и строки `line` / `lineEn`: «принято на X; после приёмки
  2 коммита (3 файла) — не проверены» / "accepted at X; 2 commits (3 files)
  since acceptance are not verified". `status --human` печатает обе строки
  под поручением. Сверка — только чтение Git: один `rev-parse` на
  репозиторий и по три вызова git на принятый SHA.
- **Отчёт.** `harness report` с `binding.json` в каталоге состояния
  добавляет `targets` (принятые поручения, у которых ref ушёл вперёд,
  переписан или не прочитан; `checked` — сверено всего) и раздел «After
  acceptance» в Markdown и HTML. Без `binding.json` поля нет.
- **Skill.** Коммиты после приёмки ведущий называет непринятыми: им нужно
  новое поручение `run` или хотя бы `gates --sha HEAD` и `review-code`;
  одобренный `review-code` и зелёный `gates` — не приёмка.

## Совместимость

- Новые поля ответов (`works[].target`, `target`, `targets`) и команда
  `review-code` — аддитивны; прежние поля и коды не меняются.
  `stateVersion`, `policyVersion` и `reportVersion` прежние.
- Новое локальное пространство хранилища `code-reviews`
  (`codeReviewRecordSchema`). Хранилищу хоста оно нужно, только если хост
  вызывает `reviewCode`; `statusOf` поверх движка хоста `target` не
  вычисляет — это делает `Harness.status`.
- Откат на 0.1.0-alpha.53: записи `code-reviews` прежняя версия не читает;
  каталог `review-code/` и файлы `gates-at/*/result.json` можно удалить.
