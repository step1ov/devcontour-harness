# devcontour-harness 0.1.0-alpha.6

Этот выпуск добавляет:

- переносимые инструменты целевого проекта: npm, pnpm, Turborepo, Go и
  Python/uv;
- рецепт Turbo Starter;
- общий контракт внешнего источника заданий и доставки с двумя opt-in
  транспортами Relay;
- протокол истории находок ревью кода;
- нейтральную точку подключения внешней памяти.

Ядро — Engine, Runner, файловые источник и получатель, standalone CLI —
работает как раньше. Интеграции подключаются только явно, через отдельные
входы пакета. Пакет не публикуется автоматически.

## Новые входы пакета

| Вход                                        | Назначение                                                     |
| ------------------------------------------- | -------------------------------------------------------------- |
| `devcontour-harness/toolchains`             | рецепты установки, пробы версий, диагностика (`inspectPolicy`) |
| `devcontour-harness/integrations/connector` | общий контракт источника и доставки, состояние коннектора      |
| `devcontour-harness/integrations/relay-v1`  | транспорт Relay v1 (HTTP)                                      |
| `devcontour-harness/integrations/relay-v2`  | транспорт Relay-2 (subprocess CLI)                             |
| `devcontour-harness/integrations/memory`    | дополнительный `ContextSource` памяти и получатель итога       |

Корень пакета и `./contracts` эти модули не импортируют. CLI загружает
коннектор и адаптер транспорта только для явно выбранного provider.

## Изменения API и поведения

### CLI

- `source-check` — проверка подключения, проекта, capabilities и mapping;
  только чтение.
- `source-snapshot --out <dir> [--policy]` — закреплённый снимок задач:
  `graph.json`, `context.json`, `manifest.json`.
- `source-status` — локальный и внешний статус доставки.
- `source-deliver [--work]` — повтор или продолжение доставки с тем же ключом
  операции.
- `source-reconcile --operation <key> [--decision resend|adopt:<id>|recheck]` —
  явный разбор неизвестного исхода или конфликта.
- `run --source <connector.json>`: задачи перечитываются, их semantic digest
  сверяется с закреплённым снимком, eligibility проверяется. Всё это —
  до любого вызова runtime.
- `review-plan --source`: внешние предпосылки допускаются по решению
  источника (`trusts`) и доступности SHA в target ref — те же правила, что у
  `run`. Без `--source` поведение прежнее.
- `cleanup --state --run` — довести незавершённую очистку попытки.
- `run` выполняет обязательный preflight toolchain: при любой проблеме
  диагностики попытка не начинается.

Прежние команды и их коды выхода не изменились.

### Доставка

- `DeliveryOutcome` получил необязательный вариант
  `{ status: 'uncertain', operation, reason }`. Прежние получатели
  (`delivered` / `conflict`) компилируются и работают без изменений.
- `DeliveryState`: значение статуса `uncertain` и необязательное поле
  `operation`.
- Новое событие журнала `delivery.uncertain`:
  `{ sink, key, revision, attempts, operation, reason }`.
- Повтор доставки не отправляет мутацию, пока неизвестный исход не разобран
  (`source-reconcile`).
- Протокол коннектора: намерение сохраняется до внешнего вызова, затем
  read-back по маркеру, затем receipt.
  - Подтверждённый отказ получателя — безопасный повтор.
  - Неизвестный исход — `uncertain`, без автоматического повтора.
  - Перед каждым неподтверждённым шагом сверяется snapshot: старая постановка
    не закрывает новую; чужое изменение между сверкой и CAS даёт конфликт.
- Состояние коннектора — отдельный SQLite
  `<state>/connectors/<provider>-<hash>.sqlite`. Это не вторая база
  исполнения.
- Секреты маскируются в ошибках транспорта, проблемах `source-check` и
  причинах шагов.

### Протокол ревью кода

Подробно — [review-protocol](../review-protocol.md).

**История находок.**

- Находки ведутся на поручение (область = поручение + репозиторий), а не на
  попытку или SHA.
- ID находки выдаёт controller; reviewer называет состояние каждой открытой
  находки (`previous`).
- Записи ревью получили необязательные поля: `EvidenceRecord.reviewRound` и
  `findings[].id/status`. В `RunResult.evidence[]` — `findings[].id/status` и
  `review`.
- На одном SHA и фазе бывает несколько записей ревью: невалидная, затем
  валидная. Это не отказ задачи.

**Ошибка протокола.**

- Ошибка формата ответа reviewer отделена от содержательного отказа.
- Reviewer вызывается повторно ограниченное число раз, writer при этом не
  вызывается. Затем — код `REVIEW_PROTOCOL_INVALID` (класс infrastructure,
  exit 4) и вид отказа попытки `review-protocol`. Автоматического повтора
  попытки нет.
- Политика: необязательное поле `reviewProtocolRetries` (0–2, по умолчанию 1).
  Значение по умолчанию в политику не подставляется.

**Совместимость адаптеров.**

- `RuntimeCapabilities.reviewProtocol?: 1` — строгий протокол для адаптера,
  который его объявляет. `cliAdapter` (codex, claude, fixture executables) его
  объявляет.
- Адаптер хоста без этого поля получает семантику alpha.5: раунд помечается
  `legacy`, переходы не требуются. Поэтому прежние runtime-обёртки хоста
  работают без изменений.
- `RuntimeRequest.findings` — открытые и закрытые находки для адаптера с
  протоколом.

**Проверки reviewer.** `run_check` принимает `{"gate": "<id>"}`: controller
исполняет объявленный gate (его argv, cwd, окружение, путь отчёта во
временном каталоге) без записи в исходники. Другой вид — исследовательский
`{"argv": [...]}`. Подробно — [review-probes](../review-probes.md).

### Gates и отчёты

- Каждый gate `kind: test` получает `TURBO_FORCE=true` и `-count=1` в конце
  `GOFLAGS`. Дочерние процессы наследуют оба значения, поэтому они действуют
  через любую обёртку, в библиотеке и в CLI.
- Это только заставляет тесты выполниться заново и не меняет смысл
  результата. Значения записываются в заголовок журнала gate (`fresh=…`).
- Gates `kind: check` не изменились.
- JUnit: атрибуты `name`/`classname` декодируются один раз, включая двойное
  экранирование `"` репортером Node.js 24. Testcase с кавычками в имени теперь
  сопоставляется с `testId` критерия.

### Инструменты целевого проекта (toolchains)

- `repositories[].toolchain`: `tools` — проверенные версии, `packageManagers` —
  явный выбор менеджера по каталогу. Поле необязательное, аддитивное.
- Новые встроенные профили: `npm-ci`, `pnpm-frozen`, `go-gotestsum`,
  `python-uv`. Прежние профили побайтно те же, их закрепления не изменились.
- `doctor --policy` добавляет `toolchains[]`: план шагов и gates, инструменты
  и их версии, lockfiles, отчёты, неоднозначности, проблемы с кодом и полем.
- Диагностика только читает файлы и запускает ограниченные пробы версий
  (`--version`).
- Путь инструмента разрешается до канонического. Инструмент внутри
  репозитория или каталога состояния не запускается (`TOOL_IN_PROJECT`).
- Диапазон версии в `package.json` допустим, если lockfile закрепляет точную
  версию.
- Подробно — [toolchains](../toolchains.md).

### Turbo Starter

- Рецепт для Turbo Starter на закреплённом commit.
- В архиве:
  - `examples/turbo-starter/`: политика, граф, приёмочные тесты с JUnit,
    шаблоны env, подготовленные изменения;
  - lifecycle-мост `compose-bridge`: PostgreSQL на попытку и фазу, с порядком
    принятия и очистки;
  - оверлей controller mode в `templates/controller-mode/`.
- Upstream не патчится.
- Подробно — [turbo-starter](../turbo-starter.md).

### Точка подключения памяти

- Договор провайдера: `MemoryRecallProvider` и `MemoryRetainProvider`.
- `memoryContextSource` — recall как источник `ContextSnapshot`.
- `composeContext` / `mergeSnapshots` — файлы и память в одном закреплённом
  снимке.
- `memoryResultSink` — запись подтверждённого итога с собственным ключом.
- Изменений ядра нет; без памяти harness работает как прежде.
- Подробно — [hindsight](../integrations/hindsight.md).

## Совместимость

- **Прежние потребители.**
  - Реализации портов в форме alpha.5 проходят проверку типов против `.d.ts`
    архива: `WorkSource`, `ContextSource`, `ResultSink` без `uncertain`,
    `ExecutionHost` без необязательных портов, `ExecutionStore` из четырёх
    методов.
  - С ними проходит файловый сценарий через CLI, `Harness.run` и
    `Engine`/`Runner`.
  - Регистрация Relay или памяти и новый обязательный метод хоста не нужны.
- **Основания согласований.**
  - Digest политик, графов, поручений и контекста прежних примеров совпадают
    со значениями alpha.5.
  - Политика без новых полей (`toolchain`, `reviewProtocolRetries`) сохраняет
    `policyDigest`, `executionDigest` и закрепления. Политика с ними получает
    новое основание явно (новое согласование).
- **Состояние alpha.5.** alpha.6 читает его без преобразования:
  - результат, журнал и записи доставки читаются так же, строки базы не
    меняются;
  - прежние записи ревью — legacy-раунды;
  - receipts и история не переписываются.
- **Откат.**
  - Standalone-состояние с новыми полями — записи ревью с `reviewRound`,
    доставка `uncertain` — alpha.5 и alpha.4 не читают: отказ
    `STATE_VERSION_UNSUPPORTED` до любой записи.
  - Хост DevContour с адаптером alpha.4 такое состояние открывает без отказа
    и пишет в него роль controller и события. Новые поля при этом
    сохраняются, потери данных нет, но строгой гарантии нет.
  - Откат с alpha.6 в обоих случаях — только восстановлением копии состояния,
    сделанной до обновления. Матрица — [upgrade](../upgrade.md).
- **Версия движка.** Номер версии — это `engineVersion`. Правила
  alpha.2–alpha.5 действуют и между alpha.5 и alpha.6: `CONTROLLER_BUSY`, а
  `LEASE_STALE` — до истечения срока и recovery.
- **DevContour.**
  - Прежняя встройка (vendored архив, `vendor-harness.mjs`) работает с новым
    архивом без изменений DevContour: собственные runtime-обёртки DevContour
    не объявляют `reviewProtocol` и сохраняют семантику ревью alpha.5.
  - Переход DevContour на протокол ревью — отдельное изменение его адаптеров.
- Проверенные версии инструментов —
  [compatibility-versions](../compatibility-versions.md).

## Известные ограничения

- Ядро наблюдает процессы системными `ps`, `lsof` и `sysctl`. С alpha.6 они
  ищутся по штатным путям ОС (`/bin/ps`, `/usr/sbin/lsof`, `/usr/sbin/sysctl`
  и т. п.), а не через PATH: PATH из одних `node` и `git` достаточен. Только
  если ни одного штатного пути нет (нестандартная ОС), используется PATH. В
  песочнице, запрещающей запуск `ps`, containment невозможен — это отказ
  окружения.
- **Relay-2 на macOS** требует SQLite не ниже 3.44. Системная библиотека
  старше: путь к новой задаётся в `relay.env` коннектора (`DYLD_LIBRARY_PATH`).
- Доставка не обещает distributed exactly-once. У получателя нет
  идемпотентности по запросу, Git и Relay не образуют общей транзакции.
  Неоднозначные случаи решает оператор (`source-reconcile`).
- Гарантия одного владельца доставки действует только для процессов с общим
  каталогом состояния коннектора. Независимые установки с разными каталогами
  состояния вне гарантии и могут доставить одну операцию дважды; это видно в
  `ownership` у `source-check`/`source-status`.
- Готового Hindsight-адаптера нет: только договор, композиция и проверка
  поддельным провайдером.
- Встроенные профили `npm-ci`, `pnpm-frozen`, `go-gotestsum` и `python-uv`
  задают путь отчёта жёстко. В проверке reviewer `{"gate": …}` такой gate
  возвращает диагностику окружения с рецептом; gates движка работают как
  обычно.
- На macOS отмена может не найти отсоединённого не-node потомка, запущенного
  менее чем за 250 мс до отмены (опрос `ps -E`).
- **Ограничения Turbo Starter upstream.** `pnpm env:check` падает на
  Node 24.3.0. `check-types` admin-панели скачивает пакет через `npx` (нужна
  сеть). Изоляция gates в примере выключена.
