# devcontour-harness 0.1.0-alpha.23

Рабочие деревья попыток вне дерева человека. Включает всё из
[0.1.0-alpha.22](0.1.0-alpha.22.md). Формат состояния, gates, правила находок,
принятие target ref и `maxAttempts` не менялись.

## Что исправлено

- **Checkout кандидата больше не вложен в репозиторий.** При встроенном
  размещении каталог состояния лежит внутри репозитория человека
  (`<W>/.devcontour-local`), и движок создавал рабочие деревья внутри него.
  Песочница закрывает `<W>` целиком и открывает только сам checkout, поэтому
  инструменты, которые ищут конфигурацию вверх по дереву (browserslist через
  babel в jest-expo, поиск корня монорепозитория Metro/Expo, postcss,
  tsconfig, prettier), получали на `stat('<W>/package.json')` EPERM вместо
  ENOENT и падали: gate `mobile-test` не проходил при любом коде. Без
  песочницы те же инструменты прочитали бы конфигурацию рабочего дерева
  человека. Теперь рабочие деревья попыток (`…/worktrees/<runId>` и
  `…-integration`), снимки зависимостей, деревья проверок потребителей,
  проверки на SHA (`runGatesAt`), деревья слияния переноса базы (`moveBase`),
  эксперименты выполнимости, подтверждение случаев и компоненты совместной
  проверки создаются под корнем вне дерева:
  `<checkoutRoot>/<repositoryId>/<вид>/<id>`. Артефакты и логи остаются в
  каталоге состояния.
- **Выбор корня.** Хост задаёт корень явно — `checkoutRoot` у `Runner`,
  `Harness`, `JointRunner`, `runGatesAt` и `moveBase`. Без него
  `chooseCheckoutRoot` выбирает кэш пользователя, если каталог состояния (или
  каталог попыток компонента) лежит внутри репозитория политики или внутри
  закрытого песочницей пути: macOS `~/Library/Caches/devcontour-harness/<hash>`,
  Linux `$XDG_CACHE_HOME/devcontour-harness/<hash>` или
  `~/.cache/devcontour-harness/<hash>`; `<hash>` — устойчивый хэш настоящего
  пути каталога состояния. Иначе (отдельное размещение) деревья остаются на
  прежнем месте. Менеджеры пакетов (pnpm store) ставят зависимости жёсткими
  ссылками и reflink только в пределах одного тома: если кэш на другом томе,
  чем репозиторий, корень остаётся прежним, а причина видна в `note`.
  Действующий корень называют `Runner.checkoutRoot()` и `harness doctor
--state` (поле `checkouts`).
- **Проверка корня.** Корень внутри репозитория политики, закрытого пути или
  каталога состояния (например, `XDG_CACHE_HOME=<W>/.cache`) вернул бы ту же
  вложенность: выбранный по умолчанию такой корень не используется (прежнее
  место и пояснение в `note`), заданный хостом — ошибка `INVALID_INPUT`.
  Каталоги кэша (`devcontour-harness` и `<hash>`) создаются с правами 0700;
  каталог-ссылка или каталог другого пользователя — отказ с пояснением
  (заданный корень — ошибка).
- **Песочница.** Корень вне дерева закрыт целиком, как каталог состояния:
  деревья других попыток не прочитать, в том числе появившиеся после
  построения политики. Свои деревья проверки — checkout, дерево integration
  или потребителя, снимки зависимостей, scratch — открыты более конкретным
  разрешением (`checkouts` в границе проверки, `SandboxSpec` и спецификации
  probe ревьюера). Поиск конфигурации вверх по дереву от своего checkout при
  этом не ломается: в корне нет файлов конфигурации, Seatbelt на `stat`
  отсутствующего файла под запретом отвечает ENOENT, а метаданные каталогов-
  предков открыты. На Linux — та же схема, что прежде у worktree внутри закрытого каталога состояния (разрешение внутри запрета bubblewrap sandbox-runtime); под песочницей проверено на macOS, на Linux — не прогонялось.
- **Класс отказа.** Отказ чтения или `stat`, который журнал ядра (macOS)
  подтвердил для тега этой проверки, — класс `environment` с путём и
  правилом, только в форме поиска вверх по дереву: закрытый файл лежит прямо
  в строгом предке рабочего каталога проверки, и проверка упала с EPERM на
  нём (путь назван в её выводе). Чтение другого закрытого пути (`~/.ssh`,
  файл в подкаталоге репозитория) с напечатанным EPERM, отказ, который
  проверка пережила, и обычный провал тестов остаются `gate`. Отказ среды
  не тратит попытку и останавливает очередь до решения человека, поэтому
  признак узкий.
- **Git хоста.** Если файл `.git` созданного хостом рабочего дерева удалён,
  git хоста над ним не запускается: иначе он ушёл бы в репозиторий предка
  (при прежнем размещении — в checkout человека).

## Миграция и совместимость

Формат состояния и прежние поля API не меняются; новые — необязательные
(`checkoutRoot`, `checkouts` в `SandboxSpec`, границе проверки и `doctor`).
Матрица — [upgrade](../upgrade.md). Рабочие деревья, созданные прежними
версиями внутри каталога состояния, остаются там и убираются как раньше: по
пути, записанному в попытке (`finishCleanup`, `harness cleanup`), и через
`git worktree remove`/`prune` основного репозитория. Новые попытки создают
деревья под новым корнем. Если хост меняет `checkoutRoot` между падением
процесса и очисткой, окружение прерванной попытки под прежним корнем
`finishCleanup` не трогает — очистите его до смены корня.

Корни кэша не убираются, когда workspace переносят или удаляют: после
попыток в них остаются пустые каталоги видов (`worktrees`, `dependencies`…).
Каталог `~/Library/Caches/devcontour-harness/<hash>` (Linux —
`$XDG_CACHE_HOME/devcontour-harness/<hash>` или
`~/.cache/devcontour-harness/<hash>`), каталог состояния которого больше не
используется, можно удалить вручную, когда harness не запущен; действующий
корень называет `doctor`. Компоненты совместной проверки лежат в
`<root>/.joint/<id>`: имя с точки не совпадает ни с одним ID репозитория.

Хосту со встроенным размещением ничего передавать не обязательно: выбор по
умолчанию уже выносит деревья в кэш пользователя. Явный `checkoutRoot` на томе
репозиториев нужен, если кэш пользователя на другом томе или хост хочет
держать деревья в своём каталоге.

## Проверка выпуска

Тест `checkout-root`: CR01 — выбор корня на macOS и Linux (XDG, относительный
XDG игнорируется), устойчивый хэш (тот же путь через symlink — тот же корень),
отдельное размещение без изменений, заданный корень; CR02 — кэш на другом
томе — прежнее место с пояснением; CR03 — корень закрыт целиком, свои деревья
открыты; CR04 — git хоста доверяет деревьям вне дерева, подмена и удаление
`.git` дерева — отказ, дерево прежней версии в каталоге состояния убирается,
`prune` снимает удалённое мимо git; CR05 — классификация отказа чтения (форма
поиска вверх, EPERM с путём; `~/.ssh` и файл в подкаталоге — нет); CR06 под
песочницей ОС — gate, ищущий `package.json` вверх, вне дерева проходит, а
соседняя попытка закрыта; внутри закрытого репозитория — EPERM и класс
`environment` с путём; прочитанный с EPERM `~/.ssh` или файл подкаталога
репозитория и настоящий провал — `gate`; CR07 и CR08 — попытка движка при
встроенном размещении с заданным корнем и с кэшем пользователя проходит gate
обеих фаз под песочницей ОС, в дереве человека рабочих деревьев нет; CR09 —
отдельное размещение на прежнем месте; CR10 — `runGatesAt`, CR11 —
`moveBase` вне дерева; CR12 под песочницей ОС — дерево другой попытки,
созданное во время проверки, ей не прочитать; CR13 — корень внутри
репозитория, каталога состояния или закрытого пути, ссылка и чужой владелец
— отказ, каталоги кэша 0700. Мутанты обнаруживаются: без проверки
вложенности — CR01, CR02, CR08; без заданного корня — CR01, CR07, CR10,
CR11; хэш по сырому пути — CR01; без проверки тома — CR02; относительный XDG —
CR01; без класса для чтения — CR05, CR06; без требования EPERM — CR05; без
формы поиска вверх — CR05; без более конкретного открытого пути — CR05;
корень вне дерева не закрыт — CR03, CR12; удалённый `.git` дерева не отказ —
CR04; кэш или заданный корень внутри репозитория приняты, без 0700, ссылка
или чужой владелец приняты — CR13; рабочее дерево попытки на прежнем месте —
CR07 падает тем же EPERM на `package.json` репозитория, что и на пилоте.
Полный `npm run check`. Живые модели не вызывались.
