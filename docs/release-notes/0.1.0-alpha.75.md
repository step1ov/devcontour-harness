# devcontour-harness 0.1.0-alpha.75

`stateVersion`, `policyVersion`, `handoffVersion`, `reportVersion`,
`viewVersion` и `viewRevision` (`11`) прежние. Порядок обновления и отката —
`docs/upgrade.md`, раздел alpha.75.

Выпуск собран из выводов пилота 11 (тонкий режим под `harness lead drive`).

## Сдача

- **Выходы проверок исполнителя вне кандидата** (P11-5). Исполнитель гоняет
  gates в дереве работы, и их отчёты (`test-results/admin.xml`,
  `.last-run.json`, трассы Playwright) уходили в коммит сдачи — сдача
  отклонялась нарушением области. Теперь перед проверкой области harness
  убирает из индекса только новые файлы под объявленными выходами gates:
  путь JUnit-отчёта, `artifacts` gate и каталоги отчётов UI gate
  (`ui.artifacts`, у `browser` без них — `test-results/` и
  `playwright-report/`). Файлы остаются в дереве; их пути — в
  `implementation/gate-outputs.json` попытки. Изменение или удаление уже
  отслеживаемого файла под этими путями — правка исполнителя, её проверяет
  область. Во всех режимах; исполнителю сказано не коммитить выходы проверок.
- **Тесты продукта без harness** (P11-6). Исполнителю сказано: тесты продукта
  и их помощники работают и в обычном checkout — `HARNESS_ATTEMPT_ENV_FILE`
  и другие переменные harness необязательны (те же значения из обычных
  переменных окружения, либо подготовка или пропуск с понятным сообщением).
  Ревью выпуска проверяет, что документированные проверки проекта проходят в
  обычном checkout без переменных harness; тест, падающий только без них, —
  блокирующая находка.

- **Дешёвый цикл после отказа областью** (R1). Сдача, отклонённая только
  тем, что изменены файлы вне области записи поручения или защищённые файлы
  (gates и ревью не исполнялись), возвращается в ту же сессию с точным
  списком путей: добавленные удалить, изменённые вернуть к базе работы
  (`git checkout <база> -- <путь>`). Продолжение говорит, что gates заново
  гонять не нужно, если код внутри области не менялся, — вместо прежнего
  «гоняйте gates, пока не пройдут». Слияние цели, ответ на вопрос или
  разбор ведущего в той же сдаче возвращают прежнюю последнюю строку.
- **Продолжение сессии после разбора ведущего** (R4). Разбор ведущего
  (`diagnose`, затем `retry` без `--reset`) больше не начинает новую сессию:
  следующая сдача продолжает сессию работы с текстом разбора, причиной
  отказа и хвостами проверок. Новая сессия со сводкой — как раньше после
  `retry --reset`, `--start-over` (работа заново от цели), новой постановки,
  смены runtime, у CLI без продолжения сессии и при переполнении контекста.

## Планирование

- **План для параллельных работ** (R2). Работы без пути между ними в
  `dependsOn` движок и раньше выдавал одновременно (`concurrency`), но планы
  тонкого режима выходили цепочками. Запрос плана теперь говорит: `dependsOn`
  — только настоящий интерфейс сборки или исполнения (UI зависит от
  контракта API или SDK, а не от другого UI); общая тестовая инфраструктура
  — у ранней работы контракта или у отдельной маленькой работы, две
  параллельные работы одними файлами не владеют; сквозная проверка двух
  поверхностей — задача выпуска. `plan-check` советует (не отказ)
  `THIN_CHAIN` — 3+ работы одной цепочкой, хотя области записи каких-то из
  них не пересекаются, и `THIN_SCOPE_OVERLAP` — работы, которые могут идти
  одновременно, пишут в пересекающиеся области записи.

## Классы отказа

- **Лимит провайдера codex — `provider-auth`** (P11-1). Отказ хода codex
  берёт причину из события `error` / `turn.failed` в stdout, а не из
  последней строки stderr (там бывает шум MCP-серверов): «You've hit your
  usage limit …» — отказ провайдера, не засчитанный, а не неизвестный отказ.
- **CLI ревьюера упал без ревью — `environment`** (P11-3). Ревьюер, который
  завершился отказом (таймаут провайдера, обрыв) и не вернул ревью, больше
  не засчитывает исполнителю дефект ревью: это отказ окружения, следующая
  сдача идёт без нового отказа на счету работы.

## Драйвер ведущего

- **Отказ провайдера останавливает драйвер сразу** (P11-2). Сессия ведущего,
  упавшая с кодом не 0 на отказе провайдера (событие `error` codex, `result`
  с `is_error` claude, последняя строка stderr — по тем же признакам, что у
  попыток), даёт исход `agent-error` (23) с текстом провайдера
  («лимит провайдера: …») вместо новых сессий и `no-progress` (21) с одним
  «код выхода 1». Работает и без `--log`.

## Отчёт

- **Перечень дефектов по классу отказа.** Отказ ревью или gate без записи
  провала (например, упавший ревьюер до alpha.75) в перечне — `review` или
  `test`, а не `scope`; `scope` — только нарушение области. Заголовок
  окружения считает и `environment`, и `provider-auth`.
