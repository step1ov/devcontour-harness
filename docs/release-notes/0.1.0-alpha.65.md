# devcontour-harness 0.1.0-alpha.65

0.1.0-alpha.64 и 0.1.0-alpha.65 публикуются вместе: alpha.64 отдельно в npm
не выходила, её изменения (seed хранилища зависимостей из store хоста, сеть
сборки seed, модели ролей в `doctor`) — в
[заметках alpha.64](0.1.0-alpha.64.md) и входят в этот выпуск.

`stateVersion`, `policyVersion`, `handoffVersion`, `reportVersion` и
`viewVersion` прежние; `viewRevision` — `5`. Политика получила необязательное
поле `toolchain`; представление, статус, evidence, ответы `doctor`, `init` и
`gates` расширены совместимо. Порядок обновления и отката — `docs/upgrade.md`,
раздел alpha.65.

## Изменения

### Закреплённый node для всех стадий

- `policy.toolchain.node` — абсолютный каталог `node` или версия (`24.22.3`,
  `24.22`, `24`), разрешённая по установленным версиям (каталог node, который
  запустил harness, PATH, nvm, fnm, volta, asdf, mise, Homebrew). Каталог
  ставится первым в PATH gates, `harness gates`, lifecycle и `smoke`, prepare
  и сборки зависимостей, writer, reviewers и совместной проверки — одинаково,
  кто бы ни запустил harness. Раньше проверки наследовали PATH вызывающего:
  оболочка ведущего, заново загрузившая менеджер версий, ставила первым
  другой node, и одна и та же проверка проходила на базе и падала в попытке.
- Не разрешился — отказ окружения до работы с причиной `toolchain` (попытка
  не засчитана).
- Лог каждого gate начинается строкой `# toolchain: node vX (путь)` (с pnpm —
  и его версия); то же — `toolchain` в evidence и в итоге `harness gates`.
- Провал gate под другим node, чем последний успешный прогон того же gate
  репозитория, остаётся засчитанным провалом gate (класс не угадывается), но
  текст отказа, evidence и лог называют расхождение: «node vX (…) отличается
  от последнего успешного прогона этого gate …: vY (…); закрепите
  policy.toolchain.node». Причину прежнего ложного «дефекта» снимает само
  закрепление: база и попытка исполняются одним node.
- `init` предлагает закрепление (`.nvmrc`, `.node-version`, `engines.node` или
  node, который запустил init); `doctor` называет его и предупреждает, когда
  node первым в PATH другой. Подробно — `docs/toolchains.md`, «Закреплённый node».

### Прогноз по всему выпуску

- Объём прогноза — весь выпуск: все задачи всех снимков связки и все работы
  состояния, а не последний срез `run --source`; задача, удалённая с доски до
  передачи в harness, из выпуска уходит. Раньше запуск следующей
  задачи отдельным срезом обнулял принятые («0 % → 40 % → 20 %») и «прошло».
- Готовность работы — наибольший этап, до которого дошла любая её попытка:
  повтор её не снижает. `forecast.progress.works[]` — по каждой незаконченной
  работе «WEB-2: ~60 %, попытка 2 из 3, исправляет замечания».
- «Прошло» — от первого снимка выпуска или первой попытки; когда всё принято —
  до конца последней попытки (`time.finishedAt`).
- Время: от 5 закончившихся попыток выпуска — прежний точный диапазон, при
  1–4 — грубый «осталось ~X – Y (грубо, по N попыткам)» (`time.rough`),
  «неизвестно» — только пока ни одна попытка не закончилась (`time.estimate`).
- Задача, добавленная по ходу, называется: «добавлена задача WEB-3 (задач 2 →
  3)» (`forecast.progress.added`), и в `status --human`.

### Одно определение попытки

- «Попытка» во всех строках — засчитанная в предел. Если запусков больше
  (вопрос исполнителя, отказ окружения, остановка), строка называет оба
  числа: «запусков 3, из них засчитано попыток 2; …; осталось попыток 1 из 3»,
  строка этапа — «попытка 2 из 3 (запусков 3)». В представлении —
  `works[].attempts.runs`.

### Проверка человеком в источнике задач

- Принятые работы, которые связка оставила на проверку человеку
  (`completion.mode: review-only` или колонка доставки не done), видны
  оператору: `sourceReviews[]` («ждут вашей проверки в Relay: WEB-1, WEB-2»),
  эскалации `SOURCE_REVIEW` и строка «От вас: …» в `status --human`.

### Этап настройки до init

- `view --repository <корень>` и `status --repository <корень>` читают
  состояние и политику из `.harness/project.json` при каждом вызове — панель,
  запущенная до настройки, подхватывает их без перезапуска. До настройки
  `view --repository` отдаёт документ настройки (`setupViewSchema`,
  `schemas/setup-view.schema.json`) со строками «Идёт настройка harness»,
  «Задач пока нет»; `status` — пустой статус с полем `setup` вместо
  NOT_FOUND (у `--state` — только для каталога, которого нет). `view --state`
  сохраняет прежнюю форму; обзор без работ называет этап `stage: setup`.
  Неисправности (база без привязки, явный `--policy` без файла) — прежние
  отказы.

### Навыки

- `harness` и `harness-setup`: тяжёлые команды (`smoke`, `smoke
--writer-probe`, `gates`, `run`) — строго по очереди; в итоговом отчёте —
  ссылка на панель или сайт оператора, а не на временные порты серверов,
  поднятых и остановленных самим ведущим; закрепление node при настройке.
