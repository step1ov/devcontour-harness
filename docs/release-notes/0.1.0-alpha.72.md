## Изменения

### Ведущий не ждёт внутри модели

- **`harness lead drive`.** Ждёт событий запуска без модели (как
  `harness wait`) и запускает новую короткую сессию ведущего (`--agent` —
  команда хоста, prompt на stdin: файл целей `--prompt-file` и сводка
  события) только когда нужен ведущий: отказ, удержание, вопрос, который
  ведущий вправе решить, новый вопрос владельцу (один раз — передать его
  владельцу), ответ владельца, готовность к выпуску, остановка очереди при
  оставшейся работе. Сессия ведущего — новая, без растущей истории.
  Коды выхода: 0 — выпуск завершён, 20 — нужен владелец и больше ничего
  не движется, 21 — нет продвижения, 22 — предел сессий, 23 — команда
  агента не запустилась, 16 — прерван. `--session-timeout` (60m) снимает
  зависшую сессию вместе с группой процессов; `--log` хранит prompt и
  вывод каждой сессии (0600). Ведущий сообщает «жду владельца» командой
  `harness lead end --waiting owner --reason …`.
- **`harness run --detach --log <файл>`.** Запуск отдельным процессом
  (своя группа и сессия), ответ — после подтверждения старта; если запуск
  сразу упал — отказ с кодом выхода и хвостом журнала.
- Без драйвера ведущий ждёт с самым длинным `--timeout`, который позволяет
  его оболочка, и не крутит пустые ожидания (`harness guide run`).

### Ревью выпуска: все блокеры за раунд

- Reviewer выпуска перечисляет все блокирующие находки за один проход: каждый
  сценарий против каждого критерия, ответов владельца, топологии и сбойных
  путей; пропущенный раньше блокер остаётся блокирующим. Refuter второго
  прохода ищет пропущенные блокеры.
- Чеклист сбойных путей: медленная сеть или большой payload против
  таймаутов клиента и сервера; тяжёлая синхронная обработка в запросе и
  её повтор.
- Находки одного раунда исправляются одной работой (по репозиторию).
- Не запускайте `harness gates` руками перед `review-release`: он сам
  исполняет полный прогон, когда на цели нет годного.

### Вопросы и окружение

- **Технические вопросы — ведущему (облегчённый режим).** Без
  `inputPolicy.leadAnswers` технические вопросы (в том числе о внутреннем
  `contract`/`api`) решает ведущий с `--reason`; продуктовые, приёмочные,
  видимые пользователю и без `impact` — владелец. Новое поле
  `leadAnswers.technicalAreas`; отказ — `{ "technical": false }`. Строгий
  режим прежний.
- **Тестовые секреты попытки.** `attemptEnv.secrets` — имена секретов,
  которые harness генерирует на попытку, если политика их не задаёт;
  маскируются как объявленные секреты. Только для тестовых значений.
- Исполнитель знает, что файл окружения попытки (`attempt-env.json`)
  только для чтения.

### Мелкие исправления

- Метка документации (`release.docs`) проходит через коннектор задач
  (`tasks[].labels`); `review-release`/`release done` принимают
  `--docs-work <id>`; `RELEASE_DOCS_UNMARKED` в `source-check` и `doctor`.
- Пауза очереди, поставленная ведущим, показывается как пауза ведущего
  (`pause --by lead|operator`, `control.pausedBy`).
