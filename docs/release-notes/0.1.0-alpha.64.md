# devcontour-harness 0.1.0-alpha.64

`stateVersion`, `policyVersion`, `handoffVersion`, `reportVersion` и
`viewVersion` прежние. Квитанция `dependency-store.json` и ответ `doctor`
расширены совместимо (необязательные `sources`, `models`); схема политики и
состояния не меняется. Порядок обновления и отката — `docs/upgrade.md`,
раздел alpha.64.

## Изменения

### Seed хранилища зависимостей из store хоста

- Первая сборка seed на машине, где проект уже установлен, больше не качает
  весь граф из npm. Перед `pnpm fetch` сборка импортирует пакеты принятого
  lockfile из store pnpm хоста: путь называет `pnpm store path` в checkout
  репозитория (без `store_dir` из окружения политики), формат каталога
  (`v10`, `v11`) должен совпасть с версией менеджера. Запись индекса берётся
  по integrity lockfile (`index/…json` у pnpm 10, строка `index.db` у
  pnpm 11 — база хоста сначала копируется), файлы клонируются (`clonefile` на
  APFS, иначе обычная копия только нужных файлов) и сверяются по sha512 и
  размеру копии. Несовпавший или отсутствующий файл — пакет не импортируется,
  его скачает `pnpm fetch`. Результаты сборочных скриптов хоста (`sideEffects`)
  в seed не переносятся: у pnpm 10 запись индекса копируется без них, запись
  pnpm 11 с ними не импортируется (пакет скачивает `pnpm fetch`). Ключи записи
  разбираются без прототипа, запись без файлов не импортируется.
- Store хоста только читается; store под каталогом seeds, рабочих деревьев
  или скрытых путей (кроме самого репозитория) не используется. Индексу хоста
  доверено столько же, сколько собственной установке оператора.
- Квитанция называет источники: `sources.packages`, `host`, `base`,
  `network` (скачал pnpm), `hostStore`, `hostReason`, `retries`; строка шага
  `dependency-store` в `smoke` — `hit (seed собран: из store хоста N из M, из
сети K)`.

### Сеть сборки seed

- Пока окружение политики их не задаёт, сборка seed получает
  `fetch-retries` 5, `fetch-timeout` 180 000 мс, `network-concurrency` 8,
  `prefer-offline` и `minimum-release-age` 0: pnpm 11 иначе проверяет возраст
  выпусков lockfile по метаданным реестра — тысяча запросов, которые не
  меняют store; правила проекта применяет установка в checkout.
- Обрыв по времени (`TimeoutError`, `ETIMEDOUT`, `ECONNRESET`) — один повтор
  сборки через 5 с; скачанное остаётся, докачивается остаток. Журнал
  `dependency-store.log` хранит оба прохода.
- Отказ из-за сети говорит об этом прямо: «сборка seed: сеть реестра npm
  (истёк предел запроса), а не lockfile; следующий harness smoke или harness
  gates повторит сборку сразу, попытки run — не раньше чем через 10 мин»,
  без стека JavaScript. Явные `harness smoke` и `harness gates` повторяют
  такую сборку сразу (раз за команду, пометке не меньше 10 с) вместо
  мгновенного «недавняя сборка не удалась»; попытки `run` по-прежнему ждут
  10 минут. Постоянный отказ lockfile не повторяется. Сборка, которую явная
  команда начала сама и которая упала по сети, в этом процессе тоже не
  повторяется (второй проход `--writer-probe`), а счёт повторов по обрыву
  переживает отказ основы.

### doctor: модели по ролям

- С политикой `doctor` отдаёт `models[]`: `use` (`writer <роль>`,
  `code-review <роль>`, `plan-review`, `contract-review`, запасные и
  переопределения репозитория), `runtime`, `model`, `effort`.
- Модель Codex, которой нет в `$CODEX_HOME/models_cache.json` (по умолчанию
  `~/.codex`), — предупреждение `codex-model-unknown` (Codex с учётной записью
  ChatGPT отклоняет её сразу: «model is not supported»), effort вне уровней
  модели — `codex-effort-unknown`. Нет файла — проверки нет. Это
  предупреждения, не проблемы.
