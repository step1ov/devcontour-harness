# devcontour-harness 0.1.0-alpha.71 (черновик)

`stateVersion`, `policyVersion`, `handoffVersion`, `reportVersion` и

## Изменения

### Gates: не исполнять то, что не изменилось

- **Применимость по умолчанию для gates пакетов workspace.** Gate без
  `when`, привязанный к пакету pnpm/npm/yarn workspace (`pnpm --filter`,
  `pnpm -C`, `npm --workspace`, `yarn workspace`, `cwd` внутри пакета),
  получает неявное условие: каталог пакета и каталоги его зависимостей в
  workspace (граф — из `pnpm-workspace.yaml` или `workspaces` на SHA фазы,
  из объектов Git). Если diff от последнего зелёного SHA (той же
  `gateBasis`) не задел их и неявные входы (манифесты, lockfiles,
  `.harness/`, защищённые пути, пути команды, файлы корня, кроме `*.md`),
  пишется `not-applicable` с каталогами в сводке и
  `notApplicable.derived`. Привязка неизвестна, граф не прочитан, script
  пакета ссылается выше своего каталога — gate исполняется, как прежде.
  Явные `when.paths` перекрывают условие; `when: { always: true }` —
  исполнять всегда ([slow-environments.md](../slow-environments.md#применимость-по-умолчанию-gate-пакета-workspace)).
- **Перенос на интеграцию по умолчанию (облегчённый режим).**
  `integrationReuse` без поля — `identical-tree`, если хост поддерживает
  перенос: при дереве слияния, равном дереву кандидата, PASS gates
  кандидата переносятся, а ревью интеграции не вызывается — PASS ревью
  кандидата переносится записью `review` с `reusedEvidence`. Дерево другое
  (target сдвинулся) — gates и ревью интеграции полностью. Отказ —
  `integrationReuse: "off"`; строгий режим без поля — прежний.
- **Сначала упавший gate.** Следующая попытка того же поручения исполняет
  gate, на котором упала прежняя, первым (после замыкания предпосылок):
  повторный провал виден за время самого gate.

### Ревью B+C, раунд 2

- Получатель сверяет пары записи `derived`: последняя кончается на SHA
  записи, общий зелёный SHA — предок базы (и тот самый, если известен).
- `release done` отказывает при нечитаемой цели репозитория с принятыми
  работами; `releaseDone` требует `fullGates` (каждый такой репозиторий).
- Полный прогон gates засчитывается только из состояния (`gates-runs`):
  digest файла итога и основание каждого gate; `harness gates` и
  `review-release` его записывают.
- `spawn X ENOENT` удерживает gate, только когда X — программа самого gate.
- tsconfig: все файлы дерева пакета и цепочки `extends` до конца.
- Документы-постановки Relay в договоре выпуска; без постановки —
  заметка `BRIEF_MISSING`.

### Качество: приёмка против всего брифа со сбойными путями

- **Постановка и ответы владельца в договоре выпуска.** `run --graph`
  записывает `<граф>.brief.md` рядом с графом в состояние; договор
  `review-release` получает постановки выпуска и документы-ответы
  владельца из закреплённых контекстов (`input-answer`, документы Relay с
  разделом «Ответ»). Оба входят в digest договора: новая постановка или
  ответ делают раунд устаревшим.
- **Сбойные пути.** Ревью попытки и выпуска проходят сбойные пути каждого
  сценария (потеря или таймаут ответа, повтор, нет сети, зависимость
  недоступна, просроченное состояние, конкурентный запрос) тех сценариев,
  что меняет работа; неприменимые пропускаются. Блокирует только находка с
  доказательством (путь в коде файл:строка или прогон); без него — заметка.
  Исполнитель получает тот же список до сдачи, в пределах области работы ([review-protocol.md](../review-protocol.md), §12).
- **Пробы reviewer в записываемой копии.** `run_check` reviewer попытки
  идёт в одноразовом detached-дереве того же коммита: сборка и отчёты
  пишут туда, проверяемое дерево не меняется.

### Ревью B: осторожная применимость и страховка выпуска

- Применимость по умолчанию — только у вызова pnpm/npm/yarn (и `cwd` —
  только у них); без привязки — `sh -c`, `make`, `turbo`, `nx`, `npx`,
  аргументы с `..`. Script пакета с `..`, `cd ..`, `--root ..`, `-w`, `-r`,
  `--workspaces` или вызовом другого пакета — без применимости. Пути
  зависимостей `file:`/`link:` и цели `extends`/`references`/`paths`
  tsconfig входят в замыкание; цель вне репозитория — без применимости.
  Фильтр каталога pnpm (`./dir`, `{./dir}`) — все проекты под ним.
- Gate пакета исполняется, если исполняется любая его предпосылка: её
  вывод — его вход (сгенерированный код).
- Строгий режим — только с `derivedApplicability: on`; `off` выключает везде.
- Получатель засчитывает запись `derived` по своей сверке Git
  (`derivedRecordChecks`, `ReceiverContext.derivedChecks`) или при
  `trustDerivedRecords: true`. Получатель без `harnessMode` в политике
  перенос на интеграцию не включает.
- **Полный прогон gates выпуска.** `review-release` без годного полного
  `harness gates` на цели исполняет его сам и при провале отказывает;
  `release done` без него отказывает. Строка удержания `GATE_TOOL_MISSING`
  называет отсутствующий инструмент.

### Повторы: не тратить попытки на то же самое

- **Отказ инструмента gate — не исполнителю.** Gate, чья команда не нашла
  программу или браузер (`Command "playwright" not found`, `sh: … not
found`, `spawn … ENOENT`, Playwright без браузера) или чей pnpm отказал по
  каталогу состояния (`ERR_PNPM_UNSAFE_TASK_RUN_STATE_PATH`), удерживается
  как `environment`/`gate-definition` с меткой `GATE_TOOL_MISSING`: попытка
  не засчитана, исполнителю не повторяется, ход ведущего — починить gate
  или окружение и `retry --by lead`. Только когда признак — единственный
  сигнал провала, проба harness подтвердила отсутствие инструмента, а
  изменение задачи не трогало манифесты, lockfile, файлы команды gate,
  обёртки и конфиги тестов и не добавило вызов этого имени; иначе —
  засчитанный провал с причиной.
- **Обрыв реестра — окружение.** `EOF`, таймауты TLS и ввода-вывода,
  `toomanyrequests` в одной строке с контекстом загрузки (`/v2/`,
  `registry`, `Pulling`, `docker pull`, `ERR_PNPM_FETCH`, `npm ERR!
network`) — `environment` (`dependency-network`), только до кода
  исполнителя или на шаге загрузки.
- **Тот же дефект дважды подряд** (провал gate или отклонение ревью). Тот же отпечаток отказа или та же
  блокирующая находка ревью в двух засчитанных отказах подряд: нет
  автоматического повтора, разбор ведущего обязателен при любом
  `diagnoseAfter` и требует гипотезы, следующая попытка начинается с
  чистого дерева (без продолжения патча), исполнитель видит почему.
- **Попытки съело окружение — сброс ведущего (P8-4(b), решение
  владельца).** Разбор `environment` с доказательством исправления
  (`--evidence`, например прошедший `harness smoke --writer-probe`) —
  технический, если разобранные отказы harness отнёс к окружению: ведущий сбрасывает исчерпанные попытки сам, в пределе
  `recovery.leadResets`. То же — при исчерпанном пределе незасчитанных
  отказов окружения. Отказ без повтора (gate-definition, песочница) —
  по-прежнему решение человека.
- **Самопроверка исполнителя.** Подсказка исполнителя называет точные
  команды и `cwd` gates области (без значений и имён переменных окружения; значения объявленных секретов в команде замаскированы)
  и требует сдавать работу, только когда они проходят у него. Доверенная
  проверка — по-прежнему gates harness.

### Ведущий: ждать события, читать раздел, меньше ручных повторов

- **`harness wait`.** Блокирует до следующего значимого события после
  своего начала: работа принята, упала или удержана, вопрос исполнителя,
  выпуск готов, очередь остановилась (нет controller и попыток — сразу).
  `--until` сужает исходы, `--timeout` (по умолчанию 30m) ограничивает
  ожидание. Ответ: событие, работа, следующий шаг из `explain`, строка
  состояния; коды выхода 0 accepted, 10 release-ready, 11 question, 12 held,
  13 failed, 14 stopped, 15 timeout. Читает журнал событий только на чтение
  раз в секунду, controller не опрашивает. Общая операция каталога
  `capabilities` (`waitFor`).
- **Больше повторов без ведущего.** Таймаут и зависание не считаются в
  `diagnoseAfter`: harness повторяет их сам в пределе попыток (исчерпание —
  по-прежнему разбор ведущего). Отказ окружения без повтора, удержание gate
  которого снято исправлением (определение gate или среда сменились),
  повторяется ремонтом автоматически с событием `work.retried`. Правила
  повторного дефекта и пределы владельца прежние.
- **`harness guide <topic>`.** SKILL.md ведущего — короткое оглавление
  (меньше 6000 знаков); текст разделов — `skills/harness/guide/<topic>.md`
  (setup, plan, review, run, recovery, release), тема `relay` — раздел
  «Task source» skill установки. `harness guide run` печатает раздел
  текстом, `--json` — конвертом. Оглавление строит
  `scripts/guide-index.ts`, тест сверяет его с файлами.
- **Планирование по сценариям.** Prompt планирования: одна работа на
  связный сценарий пользователя через все слои; делить — только по
  репозиторию или на независимо принимаемые части; общая тестовая
  инфраструктура первой продуктовой работы — внутри неё. Рекомендуемое
  число работ по умолчанию — 5; размеры набросков S=1, M=1–2, L=2–3.
- **Запись прогона gates при работающем controller.** Хранилище открыто в
  WAL с `busy_timeout` 20 с: `harness gates` ждёт чужую транзакцию записи,
  а не отказывает (тест).

## Совместимость

- Новые функции: `packageBinding`, `packageClosure`, `workspaceGraphAt`,
  `derivationAllowed`, `conditionalGate`, `explicitCondition`,
  `integrationReuseOn`; `pathApplicability` и `gateDecisions` принимают
  условие (`GateCondition`), `reusedEvidenceProblem` проверяет и запись
  `review`.
- `integrationReuseProblem` отказывает только при явном `identical-tree`
  без поддержки хоста.
- Новые функции: `repeatedDefect`, `repeatedDefectPending`,
  `environmentFailures`, `neutralFailuresExhausted`, `registryPullFailure`,
  `toolMissingLine`; `technicalCause` принимает `evidence`.
- Тесты, которые нарочно повторяли один текст отказа, получают остановку
  после второго: автоматический ремонт того же отпечатка — не больше одного
  повтора.
- Новые команды CLI `wait` и `guide` (схемы данных `waitDataSchema`,
  `guideDataSchema`); `wait` — общая операция каталога. Новые функции:
  `waitFor`, `waitKinds`, `WAIT_EXIT_CODES`. `repairDecision` принимает
  `holdFixed`.
- Представление оператора (`viewRevision: 10`) не меняется: перенесённое
  ревью видно как PASS ревью интеграции со сводкой «PASS взято из
  кандидата: ревью кандидата … перенесено».
