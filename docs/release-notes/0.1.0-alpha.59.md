## Изменения

### Проба исполнителя без модели: `harness smoke --writer-probe`

Поле политики `repositories[].writerProbe` перечисляет команды, которые
правила проекта требуют от исполнителя: генератор из реестра, локальный
сервер для проверок в браузере, браузерный инструмент, инструмент со
служебным каталогом в домашнем каталоге. `harness smoke --writer-probe`
после `prepare` прогоняет их в изоляции каждого исполнителя
репозитория — то же окружение и профиль инструментов, свой TMPDIR, те же
области записи и чтения, та же сеть, тот же механизм (`codex sandbox` с
профилем прав исполнителя или sandbox-runtime для Claude) — без вызова модели.
По каждой команде: `ok`, `blocked` или `failed`, причина (`listen-denied`,
`network-denied`, `write-denied`, `process-abort`, `missing-tool`, `timeout`,
`no-shell`, `environment`), строка вывода и совет простыми словами с
вариантами: разрешить в политике, выполнить в `prepare`, вынести в gate
harness, отменить правило шаблона для режима harness. Закрытый шаг — exit 4.
Навык `harness-setup` предлагает команды пробы по AGENTS.md и навыкам проекта.

Пределы точности: для Codex проба идёт через `codex sandbox` с тем же
профилем прав, но без `--ignore-user-config` (у `codex sandbox` его нет) и без
фильтра окружения shell внутри `codex exec`; для Claude — sandbox-runtime
harness с той же политикой, а не встроенная песочница Claude Code. Это тот же
класс механизма ОС; отказ в пробе почти наверняка повторится у исполнителя,
прохождение — сильный, но не абсолютный признак.

### Временный каталог исполнителя всегда доступен

Вызов исполнителя получает свой короткий временный каталог вне каталога
состояния, открытый ему на запись (`TMPDIR`, `TMP`,
`TEMP`, `TMPPREFIX`): here-document zsh и инструменты, пишущие во временный
каталог, больше не получают отказ песочницы. Каталог убирается после вызова.

### «Сначала код, потом вопрос»

Запрос исполнителя и оверлей controller-mode v2 велят: если окружение
закрыло обязательный шаг, сначала написать код и запустить то, что можно, а
затем задать технический вопрос (`impact: technical`) с названием шага и
ошибкой — не останавливаться с `completed=false` до кода. Оверлей v2 —
новый файл `AGENTS.controller.v2.md`; закреплённые пакеты v1 не меняются.

### Без слепых повторов

- Исполнитель, остановившийся с `completed=false` и назвавший причиной
  окружение (сеть, сервер, инструмент, источник), — ход ведущего: класс
  `needs-lead`, причина `writer-environment`, попытка не засчитана (тратится
  предел незасчитанных отказов), автоматического повтора в той же песочнице
  нет. Обычная незавершённость по-прежнему продолжается черновиком.
- Итог исполнителя своими словами виден в `lastFailure` (`status`, `harness
view`) и в `explain`: «не доделано — исполнитель не доделал работу: «…»».
- Сообщение шага `exit=1; timeout=false` больше не попадает в корзину
  «время»; обрыв загрузки пакетов («terminated» с кадром прерванного
  fetch/TLS-сокета) — сетевой отказ окружения, попытку не тратит.
- Тот же упавший testcase в двух отказах gate подряд перед последней
  попыткой останавливает повтор:
  решение ведущего вместо последней попытки.

### Ведущий внутри песочницы

`harness doctor` и `harness init` распознают запуск внутри песочницы
(вложенная песочница не создаётся, `ps` запрещён, `.git` репозитория или
каталог состояния закрыты на запись) и печатают объяснение и точные флаги
Codex для ведущего. Навыки `harness` и `harness-setup` называют требования
явно.

### Навыки

Навык `harness`: только публичные команды CLI, никаких вызовов внутренностей
библиотеки; правило кеша зависимостей (замер `smoke` сразу после `init`,
`dependencyStore` через `lean`, без собственного кеша в аргументах шагов,
без платного `run`, пока подготовка долгая); остановка исполнителя из-за
окружения — ход ведущего через `smoke --writer-probe` и `retry`.

### Хранилище зависимостей для pnpm 10.27+ и pnpm 11

Проверенный диапазон pnpm — `>=9.15.0 <12.0.0`. Тесты хранилища
настоящим pnpm прошли на 10.12.3, 10.34.9 и 11.25.0 (весь набор) и на
11.0.0 и 11.28.13 (сценарий pnpm 11, `DS42`). Разные major-версии pnpm в PATH и в `packageManager` — хранилище не
применяется (формат store разный). Различия версий учтены в хранилище: ссылку
`<store>/v10|v11/projects/<hash>` от `pnpm fetch` seed не переносит;
окружение checkout и сборки — `npm_config_*` и `pnpm_config_*` (pnpm 11
читает только вторые); store pnpm 11 — каталог `v11` с базой `index.db`,
которая сверяется по манифесту, как остальные файлы; отказ патча pnpm 11
(`ERR_PNPM_PATCH_FILE_PATH_MISSING`) — неизбежный отказ сборки. Тест
`DS42` гоняет pnpm 11 из `HARNESS_TEST_PNPM11_DIR` (или из PATH) и
пропускается без него.

### Громкая диагностика хранилища

`doctor`, `init` и `lean` предупреждают `DEPENDENCY_STORE_UNSUPPORTED`
(закреплённый pnpm вне проверенных версий: хранилище не применяется,
каждый checkout ставит пакеты из сети) и `DEPENDENCY_CACHE_PATH` (свой
store/кэш pnpm в командах или окружении политики — внутри рабочей копии или
по общему абсолютному пути — с исправлением через `harness lean`).
Одинаковые предупреждения печатаются один раз.

### Подготовка — своя стадия

Шаги `prepare` — стадия `prepare` с замером (`integration-prepare` на
integration): `status`, `view` и `explain` говорят «подготовка», а не
«исполнитель пишет код». Стадия `dependency-store` без seed отмечена
`unused: true` («не используется»). `viewRevision` — `3`.

### Повторное согласование с записью

`harness reapprove --by --reason` привязывает согласование к изменённой
политике по последнему раунду ревью и записывает, кто и почему. Правка
изоляции, сети, профилей инструментов (и выбора профиля ролями и правилами
ревью), окружения, `protectedPaths`, шагов на хосте, `mode` или
`approvalMode` требует нового
`review-plan`: её
не покрывает ни `approve`, ни `reapprove`, ни `Engine.approve`.
`review-plan` не возвращает раунд, проведённый под другой политикой.
