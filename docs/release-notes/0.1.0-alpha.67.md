# devcontour-harness 0.1.0-alpha.67

`stateVersion`, `policyVersion`, `handoffVersion`, `reportVersion` и
`viewVersion` прежние; `viewRevision` — `7` (`works[].kind`,
`stage.progress`). Политика получила необязательное поле
`repositories[].infra`, поручение — `kind` и `gateChanges`, draft
самостоятельного проекта — те же два поля; журнал — событие
`environment.reconciled`; запись окружения (`environment.json`) —
`containerEnv`, `containerIdentity`, `trusted`, `trustedCheckout`,
`trustedLeftovers`. Ответы `status` (`setupProgress`, `runner.ready`,
`runner.readyWorks`, `runner.heldByQuestion`), `explain` (`queue`) и
`cleanup` (`reconciled[]`) расширены совместимо — только новые
необязательные поля. Политики, графы и поручения без новых полей сохраняют
digest байт в байт. Порядок обновления и отката — `docs/upgrade.md`, раздел
alpha.67.

Работы инфраструктуры прошли четыре раунда независимого ревью. Итог —
граница доверия, закрытая по умолчанию: где harness не может доказать, что
шаг на хосте исполняет принятый код или что демон тот же, он отказывает
(`scope-violation`, `NOT_READY`, ошибка политики), а не угадывает.
Гарантии и их пределы — [работы инфраструктуры](../infra-works.md#что-гарантирует-граница-доверия),
раздел «Что гарантирует граница доверия» и «Чего граница не обещает».

## Изменения

### Работы инфраструктуры и бюджет настройки

- Новый вид работы `kind: infra` ([работы инфраструктуры](../infra-works.md)):
  мосты окружения, обёртки gates, приёмочные тесты в `.harness/` пишет
  исполнитель обычным циклом — попытки, gates, ревью кода, прогноз, путь
  работы, — а не ведущий во время настройки.
- `repositories[].infra.paths` — область инфраструктуры: только работы
  инфраструктуры её меняют, продуктовые — нет (защищённый путь). Политика
  отклоняет область, которая покрывает корни доверия (политика, профиль,
  связка, manifest, обновления, пакет контекста, установленный пакет) или
  файлы, которые называет argv шагов на хосте (`lifecycle`,
  `workspaceLifecycle`, `prepare`, `dependencyBuild`, `preflight`,
  генераторы, превью). Область входит в `isolationDigest`; превью
  репозитория с областью — в digest исполнения (их смена делает
  согласование устаревшим; маршрут прежний). Digest без области прежний.
- Граница доверия ([что гарантируется](../infra-works.md#что-гарантирует-граница-доверия)):
  teardown после исполнителя исполняется в отдельном чистом checkout
  доверенной базы (и при повторе очистки по записи; свой компонент в
  `*_COMPONENTS_JSON` — checkout; путь checkout — в записи окружения до
  создания; уборка — только записанных путей, в том числе у записи `cleaned`),
  дерево кандидата не меняется; teardown репозитория с областью — мост с
  явным проектом (`compose-bridge.mjs`) или compose с `-p`/`--project-name`,
  иное — ошибка политики (`infraIssues`: `validate`, `doctor --policy`),
  потому что в checkout базы нет зависимостей дерева и файлов setup; повтор teardown по записи сверяет демон с
  записанной идентичностью и не исполняется у другого демона или при
  недописанной идентичности (`{pending: true}`); кандидат работы инфраструктуры повторно не берётся; генераторы
  с изменёнными входами не исполняются; воспроизведение находки на
  кандидате — `inconclusive`. Любой существующий файл области (gate,
  помощник, данные), новый файл разрешения (`package.json`, `node_modules/`,
  файл с точкой, `*.config.*`, конфигурация Python) и новый файл, затеняющий
  файл или каталог базы рядом, работа меняет, только если
  поручение называет его в `gateChanges` (входит в digest графа — изменение
  согласует ревью плана); символические ссылки работа не добавляет; файлы
  шагов на хосте сверяются и по цели ссылок базы. Иначе — `scope-violation`.
  Определение gate остаётся в политике.
- Продуктовые работы графа обязаны зависеть от работ инфраструктуры своих
  репозиториев (и связанных, `relatedRepositories`; `plan-check`/`validate`);
  открытая работа инфраструктуры прежнего графа держит выдачу продуктовых
  работ тех же репозиториев. Область роли работу инфраструктуры не сужает
  ни в runner, ни в `validate`/`plan-check`.
- Writer, reviewer кода и reviewer плана получают строку о виде работы и
  согласованных изменениях gates.
- Skill `harness-setup`: настройка — только конфигурация; новый код и
  унаследованные долги настройки — работы инфраструктуры первого плана;
  мягкий бюджет настройки 30 минут.
- Ход настройки: пока работ нет, `harness view` (`stage.progress`, обзор и
  документ настройки) и `harness status` (`setupProgress`, строка в
  `--human`) показывают шаги профиль, init, doctor, smoke, проба
  исполнителя, gates на HEAD, связка — с состоянием, временем и
  длительностью — и время настройки против бюджета. `doctor --policy`
  предупреждает `SETUP_OVER_BUDGET`, пока `run` не начинался, а настройка
  идёт дольше бюджета. `harness smoke` пишет итог рядом с логами
  (`<state>/gates-at/LS-*/result.json`).
- Представление: `works[].kind: 'infra'` у работы инфраструктуры.
- Ход настройки: испорченная длительность итога (отрицательная, нечисловая,
  больше года) не показывается; из многих записей берутся последние 500 по
  времени.

### Очистка записей smoke

- `harness cleanup --run LS-…` принимает ID запуска smoke: повторяет
  teardown окружения, пока рабочее дерево на месте (селекторы демона —
  записанные фазой). Если дерева нет, запись `cleanup-failed` сверяется в
  `cleaned` с событием `environment.reconciled` (`reconciled[]` в ответе),
  только когда это доказано: шаги lifecycle вызывают `docker`/`podman` сами
  (или мост `compose-bridge.mjs`) без глобальных параметров и выбора демона
  в argv; идентичность демона, записанная фазой (`containerIdentity`:
  `docker info` ID, у podman — хост и хранилище), совпала с полученной
  сейчас по записанному окружению (`containerEnv`: каждый селектор явно,
  отсутствующий — `null`, плюс `PATH`, `HOME`); ресурсов с меткой
  `devcontour.harness.run` нет. Иначе — `NOT_READY` с причиной, запись не
  меняется, в том числе для записей до alpha.67 (без идентичности).
  Команда ничего не удаляет.

### Вопрос держит только свою работу

- `status`: когда никто не запущен, у строки очереди `runner.ready` —
  сколько работ выдаст новый запуск — та же проверка, что у выдачи
  (`Engine.claimableWork`: удержание, зависимость, вопрос, бюджет по
  нынешнему расчёту, ожидание инфраструктуры; упавшая — если её повторит
  controller); при паузе, которую run не снимает, — ни одной;
  `runner.readyWorks` — их ID,
  `runner.heldByQuestion` — работы,
  которые держит только вопрос исполнителя, и строка «Очередь стоит — никто
  не запущен: запустите harness run: готово N задач, вопрос блокирует только
  X (ведущий).»
- `explain`: `queue {actor: lead, action: start-run, ready, heldByQuestion?,
line}`; в `--human` — первой строкой.
- Панель: та же строка; вопрос владельцу в источнике задач
  (`sourceQuestions[].tasks`) при готовых работах тоже называет запуск ходом
  ведущего; работы его задач и зависящие от них из готовых вычитаются.
- `explain`: продуктовая работа, которую держит открытая работа
  инфраструктуры прежнего графа (в том числе draft или исчерпанная),
  называет её и её диагноз (`actor: null`, `wait`); движок её не отменяет.
- Skill `harness`: ведущий запускает `run` для готовых работ, прежде чем
  закончить сессию в ожидании ответа владельца.

### Прочее

- Повтор teardown по записи окружения (`harness cleanup`, восстановление
  после падения) — у любой работы: селекторы демона и конфигурация docker
  фазы восстанавливаются; запись с идентичностью демона перечитывает её, и
  у другого или молчащего демона teardown не исполняется.
- Воспроизведение находки ревью на кандидате работы инфраструктуры —
  `inconclusive` (иначе lifecycle и prepare исполнились бы по непринятому
  коду).

## Совместимость

- Без `repositories[].infra` поведение прежнее; новые правила (область,
  teardown, `gateChanges`, порядок инфраструктуры) действуют только у
  репозитория с областью инфраструктуры.
- Записи smoke до alpha.67 (без идентичности демона) `cleanup --run LS-…`
  не сверяет: `NOT_READY`, ресурсы по метке проверяются вручную.
- Новое событие `environment.reconciled`: alpha.66 читает его как `unknown`.
- Хост с собственным draft (`planDraft(..., {keyOrder})`): общая форма задачи
  draft не менялась; `kind`/`gateChanges` — только в draft самостоятельного
  проекта.
- Хост, отображающий виды транзакций: новый вид `environment.reconciled`.
