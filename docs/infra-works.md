# Работы инфраструктуры и бюджет настройки

С 0.1.0-alpha.67 настройка harness остаётся конфигурацией, а исполняемый код
инфраструктуры проекта под harness — мосты окружения, обёртки gates,
валидаторы, приёмочные тесты в `.harness/` — пишется **работами
инфраструктуры** (`kind: infra`): обычным циклом исполнитель → gates → ревью
кода → интеграция, с попытками, бюджетом и прогнозом, как продуктовые работы.

## Почему

До alpha.67 такой код писал ведущий прямо во время настройки: исполнителю
`.harness/` недоступен (`init` кладёт его в `protectedPaths`). Настройка
становилась разработкой вне цикла: без предела попыток, без срока, без
прогноза; панель показывала только «Идёт настройка harness», продуктовые
задачи ждали, а раунды ревью кода находили всё новое в коде, который никто не
планировал.

## Настройка — только конфигурация

Настройка (`skills/harness-setup`) делает: профиль стека, `harness init`,
правку политики по решениям, связку с источником задач, `doctor`, `smoke`
(и пробу исполнителя), gates на HEAD. Новый исполняемый код ведущий в
настройке не пишет:

- код, которого нет, — работа инфраструктуры первого плана;
- унаследованные долги настройки (известный дефект моста, недостающий
  приёмочный тест, обёртка gate) — тоже работы инфраструктуры, а не молча
  взятые на себя правки ведущего;
- копирование готовых файлов примера (`examples/turbo-starter/harness/`) и
  правка их параметров под проект — конфигурация, а не новый код.

**Бюджет настройки** — мягкий, 30 минут (`SETUP_BUDGET_MS`). Время — от
самой ранней записи настройки (файлы `.harness/`, первый `smoke` или
`gates`) до регистрации первого графа. Превышение ничего не останавливает:
`doctor` печатает предупреждение `SETUP_OVER_BUDGET: …`, `status` и панель —
строку хода настройки с «бюджет 30 мин — превышен» и советом вынести код в
работы инфраструктуры.

## Ход настройки

Пока работ нет, `harness view` (обзор и документ настройки, ревизия 7) и
`harness status` отдают ход настройки (`stage.progress`, `setupProgress`):
шаги по порядку, у каждого состояние, время записи и длительность прохода.

| Шаг         | Откуда                                                                   |
| ----------- | ------------------------------------------------------------------------ |
| `profile`   | `.harness/profile.json` или встроенный профиль в `.harness/project.json` |
| `init`      | `.harness/project.json` и `.harness/policy.json`                         |
| `doctor`    | итог не записывается (`doctor` только читает) — всегда `unknown`         |
| `smoke`     | последний `<state>/gates-at/LS-*/result.json` (пишет `harness smoke`)    |
| `probe`     | последний smoke с пробой исполнителя: `writerProbe.ok`                   |
| `gates`     | последний `<state>/gates-at/GA-*/result.json` (пишет `harness gates`)    |
| `connector` | нет `.harness/connector.json` — `skipped`; есть база связки — `done`     |

Состояния: `done`, `failed`, `pending`, `skipped`, `unknown`. Ход настройки
считается только по файлам на диске; база состояния не открывается. В токен
представления входят начало, бюджет, превышение и шаги, а не прошедшее время.

## Работа инфраструктуры

**Область инфраструктуры** объявляет политика репозитория:

```json
"protectedPaths": [".github/", ".harness/", ".harness-tools/"],
"infra": { "paths": [".harness/acceptance/", ".harness/infra/"] }
```

Правила области (`policyIssues`, `infraIssues`):

- пути лежат внутри `protectedPaths` — продуктовой работе они недоступны тем
  же механизмом защищённых путей;
- пути не покрывают **корни доверия**: `.harness/policy.json`,
  `profile.json`, `connector.json`, `project.json`, `updates.json`,
  `.gitignore`, `README.md`, `.harness/work/`, `.harness-tools/`, `.git/`,
  `.devcontour/`. Политику, связку и manifest не меняет ни одна работа;
- пути не покрывают **файлы шагов на хосте**, которые называет argv команд
  `lifecycle` (репозитория и политики), `workspaceLifecycle`, `prepare`,
  `dependencyBuild`, `preflight`, генераторов (команда, `tool`, `inputs`) и
  превью (`build`, `start`): относительные пути от `cwd` шага, части значений
  со списком (`--env шаблон:имя`, `--x=a,b`), неизменный каталог шаблона
  glob (шаблон без каталога — каталог шага, у корня — всё дерево). Новая
  версия такого файла пишется рядом (`bridge-next.mjs`) и включается правкой
  политики, которая проходит новое ревью плана. Это ранняя проверка по argv:
  файлы, которые шаг читает сам (импорты, файлы по умолчанию, скрипты
  package manager, строка `sh -c`), она не видит — от них защищает
  исполнение шагов по доверенной базе (ниже);
- область входит в `isolationDigest`: её смена — новое ревью плана. Gates,
  генераторы и (у репозитория с областью) превью входят в digest исполнения:
  их смена делает согласование устаревшим, и тихо не проходит — маршрут
  прежний (`reapprove` или новое ревью, как для любой правки gates). У
  репозитория без области digest прежний байт в байт.

**Поручение** (`WorkOrder`): `kind: "infra"` (нет поля — продуктовая работа;
поле без умолчания, digest прежних поручений не меняется) и, только у работы
инфраструктуры, `gateChanges[]` — существующие файлы области (файлы gates,
их помощники и данные) и новые файлы разрешения, которые работа меняет. Draft самостоятельного проекта несёт те же поля (`kind`,
`gateChanges`); общая форма draft хоста не меняется.

Проверки графа (`crossIssues`, `plan-check`):

- область записи работы инфраструктуры — внутри области инфраструктуры
  репозитория, `["."]` недопустим; репозиторий без области — отказ; область
  роли работу инфраструктуры не сужает (как у runner);
- `gateChanges` — только у работы инфраструктуры и внутри её области записи;
- **инфраструктура раньше продукта**: продуктовая работа графа, у
  репозитория которой (своего или связанного — `relatedRepositories`) в том
  же графе есть работа инфраструктуры, зависит от каждой такой работы (прямо
  или через другие работы). Между графами — правило выдачи: продуктовая
  работа не выдаётся, пока открыта (не принята и не отменена) работа
  инфраструктуры её репозиториев из графа, зарегистрированного раньше
  (блокировка «Ждёт работы инфраструктуры прежнего графа»).

## Что гарантирует граница доверия

Работа инфраструктуры пишет код, который потом исполняется вне песочницы
исполнителя (шаги на хосте) и которым проверяются другие работы (gates).
Гарантии — закрытые по умолчанию, без разбора того, что читает команда:

1. **Шаги на хосте не исполняют непринятый код области.** Дерево попытки
   начинается с доверенной базы (target ref): `setup`, `ready`, `prepare`,
   хранилище зависимостей исполняются до черновика и до исполнителя.
   Кандидат работы инфраструктуры повторно не берётся (иначе дерево
   начиналось бы с непринятого кандидата). Teardown после исполнителя —
   принятый или отклонённый кандидат, сбой, повтор очистки по записи
   окружения (`harness cleanup`) — исполняется не в дереве кандидата, а в
   отдельном чистом checkout доверенной базы (`git worktree add --detach`
   рядом с записью окружения, убирается после шага, и при отказе тоже) с тем
   же окружением процесса: ID прогона, репозиторий, порты, каталог окружения
   (`HARNESS_ENVIRONMENT_DIR`). Дерево кандидата harness не меняет: черновик
   следующей попытки видит его целиком. Файлы, которые setup создал в дереве
   кандидата, в checkout базы нет: teardown, которому они нужны (а не
   каталог окружения), откажет — запись станет `cleanup-failed`, очистку
   доведут `harness cleanup` и сверка ресурсов по меткам. Это осознанный
   отказ закрытым: мосту лучше хранить состояние в каталоге окружения.
   Воспроизведение находки ревью (`confirm`) на кандидате работы
   инфраструктуры не исполняется (оно исполнило бы lifecycle и prepare по
   непринятому коду): исход `inconclusive`.
   Генераторы, чьи входы или инструмент изменила работа инфраструктуры, не
   исполняются: `scope-violation`. Интеграция, превью и совместная проверка
   исполняют код после ревью кода кандидата.
2. **Существующие файлы области меняются только по согласованию плана.**
   Любой файл области, который есть в доверенной базе кандидата, — файл
   gate, его помощник (импорт), файл по умолчанию, данные — работа меняет,
   переименовывает или удаляет, только если поручение называет его (или его
   каталог) в `gateChanges`; иначе — `scope-violation` («Изменены файлы gates
   доверенной базы без согласования планом»). Это не зависит от того, как
   gate его читает (`node x.mjs`, `npm run accept`, `sh -c`, ссылка из
   другого каталога). Новые файлы добавлять можно, кроме двух видов, которые
   меняют, как инструменты читают прежние файлы, и тоже требуют
   `gateChanges`:
   - файлы разрешения: `package.json`, `node_modules/`, `__mocks__/`, файлы
     с точкой (`.mocharc`, `.npmrc`, `.env`), `*.config.*`,
     `tsconfig*.json`, `conftest.py`, `pytest.ini`, `tox.ini`, `setup.cfg`,
     `setup.py`, `pyproject.toml`, `Makefile`, `justfile`, `*.pth`,
     `sitecustomize`/`usercustomize`;
   - затеняющие: новый путь, чей первый новый сегмент совпадает основой
     имени с файлом или каталогом базы рядом (`lib.js` рядом с `lib/`,
     `util/` рядом с `util.mjs`).
3. **Ссылки.** Работа инфраструктуры не добавляет и не меняет символические
   ссылки (`scope-violation`). Файлы шагов на хосте сверяются и по цели
   ссылок доверенной базы (ссылка `.harness/bridge.mjs` →
   `.harness/infra/bridge.mjs` защищает цель).
4. **Определение gate** (команда, отчёт, `when`, тайм-аут) — в политике,
   применённой при согласовании графа; политика — корень доверия.
   `gateChanges` входит в digest графа: reviewer плана одобряет такую
   работу, только если поручение говорит, что проверяет новое определение и
   что оно не слабее прежнего. Ревью кода дополнительно проверяет, что gate
   не ослаблен.
5. **Продуктовые работы исполняют определение из принятой ревизии
   инфраструктуры**: они зависят от работ инфраструктуры своих
   репозиториев, получают базу с принятым коммитом и сами область
   инфраструктуры не меняют (защищённый путь).

Чего граница не обещает — это остаётся ревью кода: новый файл области
(новый тест, новый помощник) может быть ошибочным или лишним; новый файл,
который инструмент находит по своим правилам, не перечисленным выше
(собственный загрузчик проекта, плагин по шаблону имени, `--import` по
glob), может изменить проверку; мост, который выбирает демон контейнеров
сам (`--context` внутри скрипта), сверка по меткам не видит; файлы вне области
инфраструктуры по-прежнему меняют продуктовые работы по своим правилам
(генераторы продуктовых работ исполняют их код на хосте, как и до
alpha.67).

Исполнение (runner, `scopeViolations`, `infraViolations`):

- продуктовой работе область инфраструктуры — защищённый путь
  (`scope-violation`, «Изменены защищённые файлы»);
- работа инфраструктуры пишет только внутри области инфраструктуры и своей
  области записи; область роли её не сужает; прочие защищённые пути и
  закреплённые контекст и артефакты контрактов остаются закрыты;
- изменённый файл шага на хосте, ссылка или существующий файл области без
  `gateChanges` — `scope-violation`;
- writer и reviewer получают строку о виде работы: reviewer отклоняет
  ослабление gates.

## Прогноз и путь работы

Работа инфраструктуры — обычная работа: этап, попытки, путь (`track`),
прогноз и лента — как у продуктовой. В представлении у неё
`works[].kind: "infra"` (ревизия 7), панель может показать её отдельной
меткой.

## Вопрос держит только свою работу

Блокирующий вопрос исполнителя (или вопрос владельцу в источнике задач)
держит только свою работу: независимые готовые работы выдаются. Когда никто
не запущен, а готовые работы есть, `status` (`runner.ready`,
`runner.readyWorks`, `runner.heldByQuestion`), `explain` (`queue: {actor:
lead, action: start-run}`) и представление (`progress.queue.line`) говорят:
«запустите harness run: готово N задач, вопрос блокирует только X» — ход
ведущего. Готова работа, которую выдаст новый запуск: готовая без
блокировок выдачи (удержание операцией, gate или ведущим, зависимость,
вопрос, бюджет — не готова) или упавшая, которую controller повторит. Пауза,
которую run не снимает сам (оператор, отказ провайдера, проверка базы,
операция политики), — готовых нет. Вопрос владельцу в источнике вычитает из
готовых работы своих задач и зависящие от них. Ведущий
запускает `harness run` для готовых работ, прежде чем закончить сессию в
ожидании ответа владельца.
