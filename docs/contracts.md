# Договоры devcontour-harness

Источник истины — Zod-схемы в `src/contracts`. TypeScript-типы экспортируются
из `devcontour-harness` и `devcontour-harness/contracts`.

## JSON Schema и семантическая проверка

`schemas/<имя>.schema.json` генерируется из тех же схем (`npm run schemas`);
`npm run check` падает, если закоммиченные файлы устарели, а тест паритета
сверяет вердикты Zod и JSON Schema (Ajv, draft 2020-12) на положительных и
отрицательных примерах.

Harness не нормализует значения: строки вроде `title`, `goal`, критериев и
значений ресурсов обязаны быть уже без пробелов по краям — правило выражено
регулярным выражением и одинаково в Zod и JSON Schema.

Программная проверка доступна из `devcontour-harness`: `validateInputs`
(то же, что `harness validate`) и отдельные функции ниже.

JSON Schema выражает всё, что относится к одному значению: типы,
обязательность, закрытость объектов, пределы, регулярные выражения путей и
refs, варианты исходов. Связи **между** значениями проверяются только
функциями пакета и `harness validate`:

| Функция         | Что проверяет                                                                                                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `graphIssues`   | Повтор ID, неизвестная зависимость, цикл графа                                                                               |
| `policyIssues`  | Циклы компонентов и gates, test gate у репозитория, ресурсы, профили инструментов, `effort`, `fixture`, пары writer/reviewer |
| `crossIssues`   | Связь поручений с политикой: роль, ресурсы, область записи и доказательства, требования, потребители, предпосылки            |
| `contextIssues` | Содержимое снимка контекста совпадает с digests и пределами                                                                  |
| `reviewIssues`  | Ответ reviewer согласован с историей находок предмета                                                                        |

Опубликованы: `work-order`, `work-graph`, `execution-policy`,
`context-snapshot`, `contract-document`, `run-result`, `result-envelope`,
`run-event`, `review-record`, `joint-verification`, `execution-document`.

## Версии

| Версия        | Значение                           | Поле / константа            |
| ------------- | ---------------------------------- | --------------------------- |
| Пакет         | `0.1.0-alpha.N` до стабильного API | `HARNESS_VERSION`           |
| Публичный API | `devcontour-harness/v1alpha1`      | `apiVersion`, `API_VERSION` |
| Политика      | `1`                                | `policyVersion`             |
| Состояние     | `1`                                | `stateVersion`              |

Версии независимы. Пакет читает только перечисленные в
`SUPPORTED_*_VERSIONS`; неизвестная версия входа, политики или состояния
отклоняется до любой мутации и до выдачи claim. Для `0.x`: patch — совместимые
исправления, minor — отдельно описанные изменения договора, включая
несовместимые. Выпущенная версия неизменяема.

Digests (`workGraphDigest`, `policyDigest`, `sourceDigest`, `findingId`) —
SHA-256 канонического JSON (`canonicalJson`: ключи по порядку, `undefined`
опускается). Формула — часть договора; тесты закрепляют эталонные значения.

## Входы

### WorkOrder

Исполняемое поручение — снимок постановки, а не редактируемая задача. Лишние
поля отклоняются: поручение не несёт статуса, результата или согласования.

| Поле               | Смысл                                                                                                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `apiVersion`, `id` | Версия договора и ID                                                                                                                                                                                                     |
| `source`           | `{connector, ref, revision}` — откуда и какая редакция                                                                                                                                                                   |
| `title`, `goal`    | Название и цель                                                                                                                                                                                                          |
| `acceptance[]`     | Критерии приёмки (1–30)                                                                                                                                                                                                  |
| `role`             | Роль из политики                                                                                                                                                                                                         |
| `repositoryId`     | Репозиторий из политики; `relatedRepositories[]` — поручение уровня workspace (минимум два)                                                                                                                              |
| `writeScope[]`     | Область записи: относительные пути без glob, `.`/`..`; пересекается с областью роли; `["."]` — весь репозиторий (только как единственный элемент; защищённые, генерируемые пути и область роли по-прежнему ограничивают) |
| `dependsOn[]`      | Поручения графа или подтверждённые предпосылки                                                                                                                                                                           |
| `gates[]`          | Область доказательства: gates и группы `@имя`, замкнута по `dependsOn`, содержит test gate; нет поля — все gates                                                                                                         |
| `consumers[]`      | Потребители (зависят от репозитория поручения) и их gates                                                                                                                                                                |
| `properties[]`     | Свойства договора проверки, подтверждаемые сейчас                                                                                                                                                                        |
| `resources[]`      | Ресурсы политики                                                                                                                                                                                                         |
| `requirements[]`   | Требование: текст, его SHA-256, test gate из области, testcase                                                                                                                                                           |
| `contracts[]`      | `{id, digest}` закреплённых контрактов                                                                                                                                                                                   |
| `context[]`        | ID обязательных источников контекста                                                                                                                                                                                     |

### WorkGraph

`{apiVersion, id, source, orders[], prerequisites[]}` — неизменяемый снимок
состава и зависимостей одного согласования; `workGraphDigest` закрепляет
согласование. Предпосылка — `{id, repositoryId, resultSha, receipt}`,
`receipt` — `{kind: 'engine', runId}` или `{kind: 'trusted', issuer, digest}`.
Доверие к `trusted` решает `WorkSource.trusts`: `Harness.run({ source })`
спрашивает источник графа (его `id` обязан совпасть с `graph.source.connector`);
без источника доверенных receipt нет. В обоих случаях движок проверяет, что
result SHA доступен в target ref. Коннектор задач выдаёт `trusted` и для
явной записи человека (`baseline`, см. [connectors.md](connectors.md)): форма
предпосылки та же, происхождение (`proof: 'receipt' | 'baseline'`) записано в
manifest снимка и в необязательном поле `baseline` ответов `source-snapshot`,
`source-status` и `run --source`.

### ExecutionPolicy

| Поле                                                         | Смысл                                                                                                                                                                                                                                                                                |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `policyVersion`, `mode`                                      | `1`; `live` или `fixture` (runtime `fixture` только в нём)                                                                                                                                                                                                                           |
| `repositories[]`                                             | ID, путь, `targetRef` по правилам `git check-ref-format`, `dependsOn`, gates (`test` с обязательным JUnit внутри worktree, `check`), группы gates (≤100), защищённые и генерируемые пути, среда, lifecycle, шаги подготовки, сборки зависимостей и preflight                         |
| `workspaceGates[]`, `verificationMode`, `workspaceLifecycle` | Gates совместной проверки комбинации репозиториев; `all` или `affected`; окружение совместной проверки                                                                                                                                                                               |
| `roles{}`                                                    | `writer`, `writePaths`, своё правило `review` кода, `requiresContract`                                                                                                                                                                                                               |
| `review.code / plan / contract`                              | `{reviewer, vendor}`; reviewer задан явно                                                                                                                                                                                                                                            |
| `approvalMode`                                               | `agent` или `operator` для технического согласования                                                                                                                                                                                                                                 |
| `isolation`                                                  | `{mode: 'os' \| 'none', domains[]}`, по умолчанию `os`                                                                                                                                                                                                                               |
| `toolProfiles{}`, `environment`, `lifecycle`, `resources[]`  | Инструменты (у профиля — встроенные инструменты claude, shell и сеть codex, MCP-серверы `mcp{}`: stdio-команда или http-адрес, только перечисленные `tools`, учётные данные — именами переменных `env`/`bearerTokenEnv`, передаются CLI по имени), среда, ресурсы (порты 1024–65535) |
| `concurrency`, `leaseMs`, `runTimeoutMs`, `reviewProbes`     | Пределы исполнения                                                                                                                                                                                                                                                                   |
| `maxAttempts`, `repairBudget`, `reuseImplementation`         | Повторы и повторное использование кандидата                                                                                                                                                                                                                                          |
| `reviewProtocolRetries`                                      | Необязательное: дополнительные вызовы reviewer кода при ошибке протокола ответа (0–2; нет поля — 1, умолчание не подставляется и digest политики не меняет), [review-protocol.md](review-protocol.md)                                                                                |
| `budgets{work, group, total, onUnknown}`, `prices[]`         | Пределы USD и/или времени; тарифы                                                                                                                                                                                                                                                    |

Переменные `HARNESS_*` и `DEVCONTOUR_*` политика задать не может.

`policyDigest(policy)` — digest загруженной политики целиком: им сверяются
применённая политика (`control.appliedPolicy`) и запрос операции
`control.reconfigure`. `executionDigest(policy)` — digest исполнительной
части без `budgets` и `prices`: основание согласования графа
(`GraphState.policyDigest`) и fencing попыток (`AttemptState.policyDigest`
у standalone-хоста). Поднятый предел бюджета поэтому согласования не
сбрасывает.

Хост, который строит политику из собственной конфигурации, может передать
движку своё тождество применённой политики (`EngineOptions.policyIdentity`,
digest по формуле хоста — например, файла конфигурации). Тогда применённая
политика и запрос операции сверяются с ним, а не с `policyDigest(policy)`;
изменение политики в памяти после создания движка по-прежнему проверяется по
её содержимому.

`EngineOptions.recordPolicyOnLead: false` — хост сам записывает применённую
политику при запуске своего планировщика; получение роли controller (в том
числе для прямой выдачи попытки) её тогда не записывает.

Автор (`--author`): `codex`, `claude`, `fixture` или `external` — человек или
инструмент вне harness; вендор `external` не совпадает ни с одним runtime.

**Выбор reviewer** — только `selectReviewer(policy, kind, writer, role)`:
`different-vendor` (умолчание) отклоняет reviewer того же вендора
(`REVIEWER_SAME_VENDOR`), `same-vendor-allowed` разрешает его. Неявного
«противоположного runtime» нет. Проверка входов отклоняет такую политику
целиком; хост, ведущий движок без неё, получает блокер
`REVIEWER_SAME_VENDOR` только у поручений этой роли — остальная очередь
выдаётся.

Правило может перечислить запасных reviewer (`alternates`, по порядку):
берётся первый из `[reviewer, ...alternates]`, допустимый правилом вендора
для этого автора. Так хост явно задаёт «reviewer другого вендора, чем
автор», не полагаясь на неявный выбор. Запасные reviewer проверяются
`policyIssues` так же, как основной.

**Раунд технического ревью** плана или контракта — `technicalReview(engine,
policy, adapters, input)`: та же реализация, что у `Harness.review`. Хост
передаёт предмет (ID, digest, автор), свои разделы запроса, рабочий каталог
reviewer и учёт вызова; harness выбирает reviewer, вызывает его под
бюджетом, требует состояние каждой прежней открытой находки и записывает
`ReviewRecord`. Предел раундов (`maxRounds`) задаёт вызывающий:
`Harness.review` — `2 × maxAttempts`.
Хост, который вёл раунды предмета до harness и хранит их сам, передаёт их
как `history: {rounds, findings[]}`: пока у предмета нет раундов в движке,
первый раунд получает номер `rounds + 1`, а находки последнего прежнего
раунда — прежние открытые находки, состояние которых reviewer обязан назвать.
Это только история: прежним раундам не приписываются digest, назначение
reviewer или одобрение. Дальше нумерация идёт подряд от первого раунда
движка, и `history` больше не учитывается.

### ContextSnapshot

`{apiVersion, sources[], missing[]}`. Источник —
`{id, kind, version, repositoryId?, revision?, required, files[], references[], digest, hostDigest?}`;
файл — `{path, digest, bytes, content: {encoding: 'utf8' | 'base64', data}}`.
Содержимое передаётся в снимке: источник может не быть Git, и движок обязан
получить ровно те байты, на которые выдан digest. `contextIssues` сверяет
SHA-256 и размер каждого файла и `sourceDigest` источника; `pinnedBytes`
отдаёт байты только после проверки. Пределы: 2 МиБ на файл, 16 МиБ на снимок.
Снимок попытки сохраняется по digest (`context-snapshots`) и используется
после рестарта без повторного чтения источника.

### ContractDocument

`{apiVersion, id, repositoryId?, title, content, artifacts?, checks?}` — вход
`review-contract`. `artifacts` — закреплённые файлы контракта (`{path, blob}`,
Git blob в репозитории `repositoryId`); `checks` — договор проверки
(`checkDeclarationSchema`, `version: 1`): gate, обязательства по property ID
(требования, тип обещания, область входов, правила ответа, способ проверки и
его файлы, семейства и минимальные выборки, корпус) и политика расширения
корпуса. Прошедший ревью документ хранится по digest (`contract-documents`):
из него движок строит манифест генеративного gate поручения.

#### Способы исполнения обязательства: `property` и `reference`

Обязательство исполняют его gates: `obligations[].gates` (1–10 ID) или, без
поля, `checks.gate`. Способ — `verification`:

- `property` (поле не указано) — генеративная проверка, как прежде: каждый gate
  обязательства генеративный (`gate.property`), отчёт свойств каждого
  подтверждает полное покрытие обязательства (`coverage.minCases` и
  семейства), корпус пополняет только gate договора;
- `reference` — сверка с закреплёнными эталонными наборами. Ответы
  независимого эталона (точный решатель, полный перебор, таблица DP)
  получены заранее, сверены с другим способом и закреплены артефактами
  контракта; gate сверяет с ними реализацию. Генератор не нужен, поэтому gate
  может быть обычным test-gate без `property`.

`reference` описывает:

| Поле                                                            | Смысл                                                                                                                                                 |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `oracle.description`, `oracle.limits`                           | эталон, его версия и пределы (время решения, что исключено из наборов)                                                                                |
| `crossChecks[]` `{family, against, matches, total, artifacts?}` | сверка эталона с другим способом на семействе входов; `matches < total` — отказ; `artifacts` — закреплённый скрипт или журнал, воспроизводящий сверку |
| `sets[]` `{gate, artifacts, minCases, families}`                | набор: gate, файлы набора (артефакты контракта), доля входов и семейств этого gate                                                                    |
| `gaps`                                                          | чего наборы не доказывают: обобщение за пределы входов, классы вне наборов                                                                            |

Структурные правила (`declarationProblems`, до вызова модели): у каждого gate
обязательства есть набор, gate набора — среди gates обязательства, файлы
наборов — артефакты контракта, сумма `sets[].minCases` не меньше
`coverage.minCases`, сумма долей каждого семейства покрытия не меньше его
`minCases`, семейства набора объявлены в покрытии и не превышают минимум
набора, сверка эталона без расхождений, файлы сверки (`crossChecks[].artifacts`)
— артефакты контракта; корпус у эталонного обязательства не включается.
Требование генеративного gate к `reference` не применяется; остальные
правила (`method`, бюджеты, spike) те же. Обязательство `property` любого
обещания (и `invariant`, и `functional`) на gate без `property` отклоняется:
поручение такое свойство выбрать не может (`orderPropertyProblems`), и
договор был бы мёртвым.

Доказательство — тот же отчёт свойств. Для gate, которому манифест поручения
назначает эталонное свойство, controller задаёт путь отчёта
(`DEVCONTOUR_PROPERTY_REPORT`) и селектор (`DEVCONTOUR_PROPERTIES`) и без
`gate.property`. Запись манифеста эталонного свойства — доля этого gate:
сумма `minCases` и семейств его наборов и `reference.artifacts` (файлы
наборов); поле есть только у эталонных свойств, так что digest прежних
манифестов не меняется. Gate проходит, только если отчёт называет свойство
со статусом `passed`, числом проверенных входов и семейств не меньше доли и
testcase с тем же ID в JUnit; зелёный JUnit и код 0 без отчёта — отказ
(«Проверка по эталонным наборам не отчиталась»). Приёмка требует решающую
запись обеих фаз с манифестом от каждого gate обязательства. Файлы наборов —
артефакты контракта, поэтому попытка не может их изменить (защищённые пути).

Reviewer контракта получает эталонные обязательства отдельно (`referenceNote`):
эталон, сверку, наборы и `gaps`. Обещание, которое опирается только на
`gaps`, без другого способа (генеративного свойства, инварианта,
аналитического основания), — блокирующая находка. Сверка без `artifacts` —
непроверенное утверждение автора, и reviewer оценивает её так.

Ответы наборов лежат в рабочем дереве, поэтому реализация могла бы читать их
или повторять их ответы и проходить каждый набор. Защита в два слоя:
writer и reviewer кода получают список файлов наборов (`referenceSetFiles`,
`referenceCodeNote`), и для reviewer чтение файлов наборов из кода
реализации, вшитые ответы или особые случаи для входов наборов — блокирующая
находка; controller отклоняет кандидата (`scope-violation`, до gates), если
изменённый файл называет файл набора внутри строкового литерала (`'…'`,
`"…"`, `` `…` ``): имя файла набора целым токеном — по краям нет буквы,
цифры, `_`, `-` или `.`, так что путь и `../имя` совпадают, а `data.json` с
набором `a.json` или `testcases.json` с `cases.json` — нет (`setFileReference`).
Комментарии `//` и `/* */` и файлы без кода (`.md`, `.txt`, `.rst`, `.adoc`,
каталог `docs/`) не проверяются. Тесты исполнителя, которые не артефакты
контракта, проверяются тем же правилом: через них ответы тоже можно подать
реализации. Остаточный риск: имя, собранное во время исполнения
(`` `${name}-golden.json` ``), копия ответов без имени файла и обобщение,
подогнанное под входы, механически не ловятся — их ловит ревью кода; строка
кода, которая законно называет набор (не артефакт контракта), отклоняется.

Пределы проверки долей: controller сверяет, что доли наборов покрывают
общий минимум и минимумы семейств и что gate отчитался своей долей, но не
сравнивает доли с размером файлов набора (сколько входов в нём на самом деле)
и не проверяет, что входы различны. Reviewer контракта видит минимумы
обязательства и семейств рядом с наборами (`referenceNote`) и оценивает это
сам.

#### ID testcase и отчёта

Свойство, `testId` отчёта и testcase JUnit — один ID. ID testcase — это
`classname.name` (без `classname` — `name`). Генератор отчёта задаёт
`classname` по-своему: node:test (`--test-reporter=junit`) всегда пишет
`classname="test"`, и тест `test('knapsack-optimal', …)` получает ID
`test.knapsack-optimal` — таким должен быть и property ID; JUnit-отчёт
собственного checker (как `harness.mjs` в примерах) пишет только `name`, и ID
совпадает с именем. Если testcase с ID свойства нет, а есть
`<classname>.<ID>`, отказ называет найденный ID.

Совместимость: поля `gates`, `verification`, `reference` необязательны, договор
без них разбирается, проверяется и даёт тот же манифест, digest и основание
корпуса (`suiteBasis` включает новые поля, только когда они объявлены;
`gates`, равные gate договора, — то же основание, что без поля, а digest
документа контракта при этом другой).
Версия договора остаётся `version: 1`; прежние версии harness договор с
новыми полями отклоняют строгой схемой.

## Модель исполнения

## Ответы исполнителей

Runtime возвращает сырой ответ; движок разбирает его
`implementationResultSchema` и `reviewResultSchema`. Ответ вне схемы — отказ,
а не самооценка writer. Reviewer называет состояние каждой прежней открытой
находки (`previous[]`); `reviewIssues` отклоняет `approved` при блокирующей
находке, в том числе прежней открытой, неназванную прежнюю находку и ссылку на
неизвестную. Идентичность находки плана/контракта — `findingId(subject, {rule, message})`;
невалидный ответ раунд не применяет (переходы и новые находки не записываются).

Ревью кода ведёт историю находок поручения с ID, выданными controller
(`codeReviewHistory`, `checkCodeReview`): reviewer называет ровно один переход
каждой открытой находки, ошибка протокола (`REVIEW_PROTOCOL_INVALID`,
причина и путь поля, например `previous[0].id`) отделена от содержательного
отказа (`REVIEW_REJECTED`) и даёт ограниченный повтор только reviewer
(`reviewProtocolRetries`, 0–2, по умолчанию 1). Evidence ревью несёт
аддитивное поле `reviewRound`, находки — `id`/`status`, ссылки результата —
`review`. Правила — [docs/review-protocol.md](review-protocol.md).

Ответ runtime ограничен на границе приёма. В `reviewResultSchema` — не больше
500 элементов в `findings` и в `previous` (`REVIEW_ITEMS_LIMIT`; те же
`maxItems` объявляет wire-схема CLI runtime); файл ответа codex — не больше
4 МиБ (`CODEX_RESULT_LIMIT`), читается с границей, без перехода по symlink, а
файл больше предела удаляется: он не прошёл маскирование. Сверх предела — обычный
отказ попытки: у reviewer ошибка протокола `schema`, у исполнителя класс
`unknown` без автоматического повтора. Записанное прежними версиями читается
без этих пределов: `review.json` — `storedReviewResultSchema`, а `ReviewRecord`
и evidence пределов не получили.

## Выходы

### RunResult

Варианты по `outcome`:

- `accepted` — `shas{base, candidate, integration, result}` все обязательны
  (result = integration; он уже в target ref);
- `rejected | blocked | cancelled | stopped` — `stopReason{code, message}` с
  кодом из договора ошибок; result SHA нет.

Общие поля: `workOrderId`, `graphId`, `source`, `runId`, `attempt`,
`repositoryId`, `targetRef`, `inputs` (версии harness и потребителя, версия
состояния, digests поручения, графа, политики, контекста, версия проверок),
`checked` (снимки зависимостей, их свежесть, проверенная комбинация каждого
потребителя), `evidence[]`, `findings[]`, `limitations[]`, `finishedAt`.
Свежесть записывается, а не запрещает приёмку. Необязательные поля
доказательства: `inputs.corpus` (закреплённая версия корпуса),
`inputs.requiredGates` (раскрытые при выдаче gates), `inputs.writer` (writer
попытки), у ссылки на evidence —
`checks` (версия проверок записи), `property{level, manifest}` (уровень и
манифест генеративного gate), `tests[]`/`testsTruncated` (выполненные тесты
собственной проверки интеграции — доказательство названного testcase).
Получатель проверяет результат `resultProblems(result, context)` /
`assertResult`. Всё, что результат утверждает о поручении, области, входах и
ревью, сверяется с тем, что получатель знает сам, а не с другими полями того
же результата: согласованная сама с собой подделка иначе проходила бы.

**Контекст получателя** (`ReceiverContext`):

- `order` — постановка поручения у получателя; `graphId` — граф, в котором
  он её держит; `contracts` — документы договоров поручения;
- `policy` — политика получателя (`repositories`, `roles`, `review`): по ней
  раскрываются область поручения и потребителей, замыкания зависимостей,
  target ref, writer роли и назначенный reviewer с правилом вендора;
- `contextDigest` — снимок контекста, закреплённый согласованием графа
  (`null` — без контекста);
- `suite`, `checkVersion` — корпус по копии получателя и закреплённая за
  поручением версия (`null` — без корпуса; у поручения с договором проверки
  обязательна); `specDigest` — digest согласованной постановки (по
  умолчанию digest поручения);
- `unobserved` — результат прежнего формата хоста, в котором входы попытки
  не наблюдались: `dependencies` — нет снимков собственных зависимостей и их
  свежести, `consumers` — нет свежести потребителей. Такие пустые списки не
  сверяются с замыканием (их нет, и проверке они не подлежат); непустые
  списки, снимки зависимостей потребителя и провайдер сверяются как обычно.
  Какой результат имеет прежний формат, решает хост по своим правилам формата.
- `assignment` — чем подтверждено ревью: `current` (по умолчанию) — writer и
  reviewer назначены текущей политикой получателя; `recorded` — результат
  несёт своё назначение, и хост перепроверяет его позже, когда назначение
  ролей могло смениться: writer и reviewer — записанные, оба должны быть
  runtime политики получателя, правило вендора роли соблюдено.

Чего нет в контексте (репозиторий, потребитель, зависимость или роль не
описаны в политике получателя), — отказ, а не PASS. Результат прежнего
формата (без версии проверок, области и writer) читается на прежнем уровне
только у поручения без договора проверки.

**Модель доверия** — категория каждого поля принятого результата
(`receiptTrust` в `src/verification/acceptance.ts`):

- _ожидание получателя_ — сверяется с ожиданием, вычисленным из контекста;
- _согласованность_ — сверяется с другими полями результата (SHA фаз,
  свежесть со снимками, уникальность записей);
- _сведение_ — ничего не доказывает, вердикт на него не опирается;
- _схема_ — значение фиксировано схемой.

Подлинность SHA, деревьев, artifacts и записей (их наличие в Git и в
хранилище исполнителя) получатель не удостоверяет — это транспорт хоста.

### DeliveryState и ResultEnvelope

Доставка — отдельно от исхода: `{sink, key, revision, status: pending |
delivered | failed | conflict, attempts, lastError?, currentRevision?,
receipt?, updatedAt}`. `harness result` выдаёт `{apiVersion, result,
delivery[]}`.

### JointVerification

Совместная проверка закреплённой комбинации SHA нескольких репозиториев:
`{id, status, policyDigest, specDigest, workIds[], manifest{repo: {sha, tree}},
manifestDigest, impact?, evidence[], error?}`. Смена любого SHA делает
результат устаревшим; атомарность продвижения нескольких репозиториев не
заявляется. Продуктовое принятие комбинации решает хост. Пока manifest не
закреплён, `impact` может нести только ссылку на базовую проверку
(`baseline`), выбранную хостом для режима `affected`.

### RunEvent

`{apiVersion, seq, at, type, graphId?, workId?, runId?, attempt?, payload}`.
`seq` строго возрастает. Нагрузка каждого из типов (`eventPayloads`) — закрытая
схема: лишних полей нет, поэтому токен владения, секрет или объект попытки в
событие не попадает.

`transactionKinds` — имена транзакций исполнения; совпадают с сохранёнными
типами событий журнала хоста (`run.claimed`, `task.done`, `run.failed`,
`scheduler.error`, …). `workflow.updated` пишет только локальные записи
технической очереди (`workflow-jobs`) и событий журнала не создаёт.
`usage.recorded` пишет только локальные записи учёта вызовов (`usage`): начало
вызова вместе с проверкой бюджетов, ход и итог вызова, закрытие прерванных,
закрепление атрибуции прежних записей; событий журнала не создаёт.
`checks.recorded` пишет только локальные записи корпуса (`check-suites`):
начало, продление и завершение операции подтверждения, решение и новую
версию. `checks.spike` пишет только локальную запись эксперимента
выполнимости (`spikes`). `checks.adopted`, `checks.awaiting-operator` и
`checks.adoption-abandoned` меняют принятую поручением версию корпуса и
удержание выдачи (`work.held`, `corpus.adopted`). Эпизод по свойству меняется
транзакциями `recovery.*`, отказом и выдачей (`work.recovery`).
`workspace.verification.started`, `workspace.manifest`, `workspace.evidence`,
`workspace.verified`, `workspace.failed` — транзакции совместной проверки
(`joint.started`, `joint.finished`). `config.started`, `config.reconfigure-*`
и `config.reconfigured` меняют применённую политику и запрос операции
(`policy.applied`, `policy.reconfigure`). `base.moved` — проверка владения
операцией и CAS-сдвиг ref базы; записей и событий не создаёт.

`Runner` принимает от хоста: `context(work)` — снимок контекста, в том числе
асинхронно; `stateDirFor(repositoryId)` — каталог артефактов попыток
репозитория (без него — `stateDir`), а при прежнем размещении и их рабочих
деревьев; `checkoutRoot` — корень рабочих деревьев, снимков зависимостей и
деревьев проверок потребителей (`<checkoutRoot>/<repositoryId>/worktrees/<runId>`
и т. д.; так же — `checkoutRoot` у `Harness`, `JointRunner`, `runGatesAt` и
`moveBase`). Без него корень выбирает `chooseCheckoutRoot`: каталог состояния
внутри репозитория политики или закрытого песочницей пути — кэш пользователя
вне дерева (macOS `~/Library/Caches/devcontour-harness/<hash>`, Linux
`$XDG_CACHE_HOME` или `~/.cache/devcontour-harness/<hash>`, `<hash>` —
устойчивый хэш каталога состояния), иначе прежнее место. Кэш на другом томе,
чем репозиторий, корень внутри репозитория, закрытого пути или каталога
состояния, каталог-ссылка или чужой каталог — прежнее место и пояснение
(`note`; заданный хостом такой корень — `INVALID_INPUT`). Корень закрыт
песочнице целиком, свои деревья проверки открыты; корни кэша не убираются при
переносе workspace — их удаляют вручную; `Runner.checkoutRoot()`
и `doctor` называют действующий корень. Корень лучше держать на томе
репозиториев: менеджеры пакетов ставят зависимости жёсткими ссылками и reflink;
`hooks` — точки расширения, которые добавляют сведения хоста, но не решают
приёмку: `prepared({work, attempt, baseSha})` — база известна, работа не
начата (отказ — отказ попытки, `BlockedError` — отказ окружения);
`notes({work, attempt, review})` — дополнения запроса writer или reviewer;
`implemented({attempt, output, sha})` — отчёт writer закоммичен кандидатом;
`failed({attempt, kind, message})` — отказ записан движком. `settled()` ждёт
выданные попытки — хост ведёт свой цикл поверх `tick`. `Engine.expire(at)`
снимает владение, истекающее к моменту `at`. Попытка записывает замеры стадий
(`implementation`, `<фаза>-test:<gate>`, `<фаза>-consumer:<репозиторий>:<gate>`,
`<фаза>-review`, `<фаза>-environment:<шаг>`, `integration-wait`) и сохраняет
снимок контекста артефактом `implementation/context.json`. Отказ приёмки с
кодом `GATE_FAILED`, `REVIEW_REJECTED`, `REVIEW_PROTOCOL_INVALID`,
`SCOPE_VIOLATION` или `BUDGET_EXHAUSTED` записывается классом отказа этого
правила.

Хост, ведущий движок поверх своего хранилища, собирает исполнение из
экспортов корня пакета: `Engine`, `Runner`, `WorkflowQueue`, `JointRunner`,
`moveBase`/`fencedRefMove`, `runGate`/`runCheck` (и разбор отчёта
`junitSummary`, `prepareReportPath`, `sandboxBlockedHosts`), `unprovenReason`,
`ReviewProbes`, маскирование (`redactor`, `redactDeep`, `redactError`),
git хоста над checkout с чужим кодом (`hostGitArgs`, `assertTrustedCheckout`,
`UntrustedCheckoutError`, `gitHardening`, учёт деревьев `rememberWorktree`/
`forgetWorktree`/`worktreeKey`/`worktreeAddPath`, `resetGitTrust` для тестов),
корпус (`CorpusStore`, подтверждение случая `submitCase` с `ConfirmContext`),
ограниченный разбор по свойству (`analyzeRecovery`, `applyCases`,
`recoveryBrief`; назначение хоста — модель и профиль ведущего — передаётся
`binding`, его дополнительные границы — `boundary`), проверка
переносимого результата (`resultProblems`), классы и правила отказов
(`BlockedError`, `TaskFailure`, `classifyFailure`, `failureFingerprint`,
`repairPolicy`, `repairDecision`), раунд технического ревью
(`technicalReview`), точка сбоя подтверждения корпуса для тестов
(`caseHooks`). Глубокие импорты `lib/...` не поддерживаются.

Очередь технических заданий хоста — `new WorkflowQueue(store, policy, now,
subjects)`: `subjects.input(kind, id, view)` задаёт digest входа и владельца
задания для предметов хоста (доска, набор изменений); задание хранится за
этим владельцем, недопустимый вход (`HarnessError`) отклоняет постановку его
текстом и делает поставленное задание устаревшим, смена владельца — тоже.
Число стадий задаёт `finish(job, wait, stages)`.

### StackProfile

Переносимый профиль стека (`schemas/stack-profile.schema.json`):
`{id, version, extends[], capabilities[], gates[], prepare[], environment?, lifecycle?, protectedPaths[], generatedPaths[], concurrency?, runTimeoutMs?, roles{}, contextPacks[]}`.
`extends` — встроенный ID (`profiles/<id>.json` пакета) или относительный
`./file.json` внутри репозитория; не глубже 16 слоёв и не больше 32 файлов,
без symlink и выхода за корень, файл до 128 KiB. `resolveProfile` только
читает манифесты: gates, подготовка, возможности и пути складываются,
окружение и lifecycle задаёт один слой (иначе конфликт), параллельность —
наименьшая, время попытки — наибольшее, роли и `contextPacks` — по ID.
Итог обязан иметь test gate с JUnit; `requirement-source` зарезервирован.
Файлы локальных слоёв становятся защищёнными путями. Digest: один встроенный
файл — sha256 его байтов (так закреплены прежние потребители, встроенные
профили перенесены побайтно), иначе — sha256 замыкания `[{ref, digest}]`.
`repositoryFromProfile` собирает описание репозитория политики (собственные
значения сильнее, переопределённые поля названы в `shadowed`),
`profileRoles` — роли в форме политики. Хост, у которого закреплены профили
своей формы (другие runtime ролей, свои поля, нестрогие вложенные объекты),
передаёт `resolveProfile(ref, { layerSchema })` — схему Zod своего файла:
она разбирает каждый слой вместо `StackProfile`, а gates, шаги, роли и
`contextPacks` остаются в её форме. Безопасность файлов, обход `extends`,
сложение слоёв, проверки gates (в том числе путь JUnit — относительный, внутри
worktree) и digest — прежние; слой, который не даёт
полей сложения (`ProfileLayer`), и не-Zod `layerSchema` — `INVALID_INPUT`.
`contextPacks` — инструкции стека для
хоста: harness их не читает, закрепляет их `ContextSource`. Встроенные
профили сохраняют имена скриптов проекта, которые закреплены у прежних
потребителей (например, `npm run test:devcontour`); для другого проекта
подходит локальный профиль.

Полная форма каждой команды — `cliCommands` (аргументы, обязательность,
идемпотентность, отказы exit 3). Все команды реализованы. `run` принимает `--author` (по умолчанию `external`) — автора графа для ревью плана. `HARNESS_CODEX_BIN` и `HARNESS_CLAUDE_BIN` подменяют исполняемые файлы runtime (fixture executables в тестах).
`init --plan` ничего не пишет (exit 3 при конфликтах или неготовом toolchain). `--human` принимают только `init`, `explain` и `plan-request` (печатает prompt): успешный ответ — текст для человека, отказ — тот же JSON-конверт, exit code одинаков; у прочих команд флаг — `INVALID_INPUT`. `plan-check` с проблемами отвечает `ok: true` с данными, exit — по классу первой проблемы; draft — `schemas/plan-draft.schema.json` (`planDraftSchema`). Маршрут самостоятельного проекта и планирование — [standalone](standalone.md).

**Общие операции и граница транспорта.** `init`, `explain`, `plan-request`,
`plan-check` и `capabilities` — общие операции агентского слоя
(`sharedOperations`): описание, `readOnly` (= `!writes`), вход (по `args`) и
схема ответа (`cliDataSchemas`) берутся из одной декларации — договора CLI;
`capabilities` возвращает их каталог (`operationCatalog`, тот же построитель,
что у каталога хоста). У этих команд CLI проверяет UTF-8 байты: значения
аргументов больше `maxInputBytes` (100000) — `INVALID_INPUT` с путём `argv`;
конверт ответа больше `maxResultBytes` (1048576) — `RESPONSE_TOO_LARGE`, exit
2, данные не усекаются, и с `--human` тот же JSON. Содержимое файлов-входов и
прочие команды граница не ограничивает. Усечение строк (`clipText`,
`clipDeep`) — отдельная операция и размер объекта не ограничивает; страницы с
cursor — `pageItems`, байты — `jsonBytes`/`checkJsonBytes`/`utf8Bytes`.
После приёмки договора имена и параметры меняются только совместимо или
отдельным согласованным изменением.
