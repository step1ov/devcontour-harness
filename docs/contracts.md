# Договоры devcontour-harness

Источник истины — Zod-схемы в `src/contracts`. TypeScript-типы экспортируются
из `devcontour-harness` и `devcontour-harness/contracts`.

## JSON Schema и семантическая проверка

`schemas/<имя>.schema.json` генерируется из тех же схем (`npm run schemas`);
`npm run check` падает, если закоммиченные файлы устарели, а тест паритета
сверяет вердикты Zod и JSON Schema (Ajv, draft 2020-12) на положительных и
отрицательных примерах.

Harness не нормализует значения: строки вроде `title`, `goal`, критериев и
значений ресурсов обязаны быть уже без пробелов по краям — правило выражено
регулярным выражением и одинаково в Zod и JSON Schema.

Программная проверка доступна из `devcontour-harness`: `validateInputs`
(то же, что `harness validate`) и отдельные функции ниже.

JSON Schema выражает всё, что относится к одному значению: типы,
обязательность, закрытость объектов, пределы, регулярные выражения путей и
refs, варианты исходов. Связи **между** значениями проверяются только
функциями пакета и `harness validate`:

| Функция         | Что проверяет                                                                                                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `graphIssues`   | Повтор ID, неизвестная зависимость, цикл графа                                                                               |
| `policyIssues`  | Циклы компонентов и gates, test gate у репозитория, ресурсы, профили инструментов, `effort`, `fixture`, пары writer/reviewer |
| `crossIssues`   | Связь поручений с политикой: роль, ресурсы, область записи и доказательства, требования, потребители, предпосылки            |
| `contextIssues` | Содержимое снимка контекста совпадает с digests и пределами                                                                  |
| `reviewIssues`  | Ответ reviewer согласован с историей находок предмета                                                                        |

Опубликованы: `work-order`, `work-graph`, `execution-policy`,
`context-snapshot`, `contract-document`, `run-result`, `result-envelope`,
`run-event`, `review-record`, `joint-verification`, `execution-document`,
`value-report` (отчёт `harness report`, см. «ValueReport»), `handoff-pack`
(пакет `harness handoff`, см. «HandoffPack»).

## Версии

| Версия        | Значение                           | Поле / константа            |
| ------------- | ---------------------------------- | --------------------------- |
| Пакет         | `0.1.0-alpha.N` до стабильного API | `HARNESS_VERSION`           |
| Публичный API | `devcontour-harness/v1alpha1`      | `apiVersion`, `API_VERSION` |
| Политика      | `1`                                | `policyVersion`             |
| Состояние     | `1`                                | `stateVersion`              |

Версии независимы. Пакет читает только перечисленные в
`SUPPORTED_*_VERSIONS`; неизвестная версия входа, политики или состояния
отклоняется до любой мутации и до выдачи claim. Для `0.x`: patch — совместимые
исправления, minor — отдельно описанные изменения договора, включая
несовместимые. Выпущенная версия неизменяема.

Digests (`workGraphDigest`, `policyDigest`, `sourceDigest`, `findingId`) —
SHA-256 канонического JSON (`canonicalJson`: ключи по порядку, `undefined`
опускается). Формула — часть договора; тесты закрепляют эталонные значения.

## Входы

### WorkOrder

Исполняемое поручение — снимок постановки, а не редактируемая задача. Лишние
поля отклоняются: поручение не несёт статуса, результата или согласования.

| Поле               | Смысл                                                                                                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `apiVersion`, `id` | Версия договора и ID                                                                                                                                                                                                     |
| `source`           | `{connector, ref, revision}` — откуда и какая редакция                                                                                                                                                                   |
| `title`, `goal`    | Название и цель                                                                                                                                                                                                          |
| `acceptance[]`     | Критерии приёмки (1–30)                                                                                                                                                                                                  |
| `role`             | Роль из политики                                                                                                                                                                                                         |
| `repositoryId`     | Репозиторий из политики; `relatedRepositories[]` — поручение уровня workspace (минимум два)                                                                                                                              |
| `writeScope[]`     | Область записи: относительные пути без glob, `.`/`..`; пересекается с областью роли; `["."]` — весь репозиторий (только как единственный элемент; защищённые, генерируемые пути и область роли по-прежнему ограничивают) |
| `dependsOn[]`      | Поручения графа или подтверждённые предпосылки                                                                                                                                                                           |
| `gates[]`          | Область доказательства: gates и группы `@имя`, замкнута по `dependsOn`, содержит test gate; нет поля — все gates                                                                                                         |
| `consumers[]`      | Потребители (зависят от репозитория поручения) и их gates                                                                                                                                                                |
| `properties[]`     | Свойства договора проверки, подтверждаемые сейчас                                                                                                                                                                        |
| `resources[]`      | Ресурсы политики                                                                                                                                                                                                         |
| `requirements[]`   | Требование: текст, его SHA-256, test gate из области, testcase                                                                                                                                                           |
| `contracts[]`      | `{id, digest}` закреплённых контрактов                                                                                                                                                                                   |
| `context[]`        | ID обязательных источников контекста                                                                                                                                                                                     |

### WorkGraph

`{apiVersion, id, source, orders[], prerequisites[]}` — неизменяемый снимок
состава и зависимостей одного согласования; `workGraphDigest` закрепляет
согласование. Предпосылка — `{id, repositoryId, resultSha, receipt}`,
`receipt` — `{kind: 'engine', runId}` или `{kind: 'trusted', issuer, digest}`.
Доверие к `trusted` решает `WorkSource.trusts`: `Harness.run({ source })`
спрашивает источник графа (его `id` обязан совпасть с `graph.source.connector`);
без источника доверенных receipt нет. В обоих случаях движок проверяет, что
result SHA доступен в target ref. Коннектор задач выдаёт `trusted` и для
явной записи человека (`baseline`, см. [connectors.md](connectors.md)): форма
предпосылки та же, происхождение (`proof: 'receipt' | 'baseline'`) записано в
manifest снимка и в необязательном поле `baseline` ответов `source-snapshot`,
`source-status` и `run --source`.

Переменные `HARNESS_*` и `DEVCONTOUR_*` политика задать не может.

`repositories[].dependencyStore` — необязательное хранилище зависимостей
репозитория: `{manager: 'pnpm', lockfile, maxBytes, timeoutMs}`. Умолчания:
`pnpm-lock.yaml`, 8 ГиБ, 600 000 мс. Без поля поведение и digest политики прежние.
С полем harness сам держит seed по lockfile `targetRef` и разворачивает его в
каждый checkout: попытка, integration, потребители, `runGatesAt`, проверка
примера, снимки с `dependencyBuild` и совместная проверка, где `prepare` нет.
Проекту не нужны ни свой скрипт, ни шаг `prepare`, ни запись в `.gitignore`;
gate установки остаётся обычным `pnpm install --frozen-lockfile`.
Подробности и граница доверия — [toolchains](toolchains.md#хранилище-зависимостей).

`repositories[].writerDependencies` — необязательное: `false` выключает установку зависимостей
в дереве исполнителя до его работы (gates установки попытки под изоляцией gate, без evidence,
стадия `writer-dependencies` в `timings`). Нет поля — включено, умолчание не подставляется и
digest политики не меняет. Подробно — [toolchains](toolchains.md#зависимости-исполнителя).

Квитанция `dependency-store.json` лежит в артефактах фазы: `outcome`
(`hit` — lockfile checkout равен lockfile seed; `partial` — seed другого
lockfile, установка докачивает разницу; `miss` — обычная установка), `seed`,
`mode` (`clone` или `copy`), `built`, `files`, `bytes`, `durationMs`, `reason`,
`refused[]`. Попытка получает этап `dependency-store` в `timings`. Экспорт:
`materializeStore`, `dependencyStoreRoot`, типы `StoreContext`, `StoreReceipt`. `StoreContext.deadline` — момент окончания времени фазы, `phaseMs` — полная длина её предела: сборка и ожидание чужой сборки занимают не больше трети остатка.
Исключение `materializeStore` бросает только при отмене переданного `signal`. Коды `doctor`:
предупреждения `LOCKFILE_MISSING`, `TOOL_MISSING`, `DEPENDENCY_STORE`.

`repositories[].gates[].artifacts` — необязательный список (1–16) путей
относительно корня дерева: файлы или каталоги, которые gate оставляет как
доказательство (например, снимки экрана визуального теста). Без поля поведение
и digest политики прежние. Повторы и пути внутри уже объявленного каталога
объединяются. После gate — и при успехе, и при провале — harness копирует
подходящие файлы в `<артефакты фазы>/<gate>.artifacts/<путь>` (в ID gate точки
нет, поэтому каталог не совпадает с каталогами других gates и фаз; прежние
копии этого gate в нём заменяются) и пишет в evidence поле `artifactFiles`:
`dir`, `files[]` (`path`, `sha256`, `bytes`, `redacted` — в текстовой копии
замаскирован секрет окружения) и `skipped[]` (`path`, `reason`, `detail`) с
`skippedMore` для пропусков сверх 100. Копируются только обычные файлы `.png`,
`.json`, `.txt`, `.xml`, `.log` с одной жёсткой ссылкой: не больше 64 файлов,
8 МБ на файл и 20 МБ всего, обход каталогов — до 4096 записей. Ссылки не
разыменовываются (ни сам путь, ни его компоненты, ни записи каталога); файл,
который перед чтением разрешается вне дерева, не копируется (`outside`).
Остаточный риск: между этой проверкой и открытием файла каталог-предок можно
подменить ссылкой наружу. Сделать это может только процесс, переживший gate;
потомков gate harness завершает до копирования в обоих режимах изоляции.
Секрет окружения в текстовой копии маскируется по байтам; файл, в котором
секрет остался после маски (например, текст в UTF-16), не текстовый файл с
секретом в байтах и файл с секретом в имени не копируются (`secret`).
Отменённая проверка не копирует ничего и прежние копии не удаляет. Причины
пропуска: `missing`, `symlink`, `outside`, `not-regular`, `hardlink`,
`secret`, `extension`, `file-limit`, `total-limit`, `count-limit`,
`scan-limit`, `copy-failed` (в том числе отмена проверки). Исход gate от
копирования не зависит: превышение пределов и отказ записи не делают
проваленный gate прошедшим и прошедший — проваленным, а названы в evidence.
Каталог копий, совпадающий с деревом проверки, содержащий его или лежащий
внутри него, не удаляется: отказ записывается как `copy-failed`.
`workspaceGates[].artifacts` по-прежнему обязаны существовать и хешируются в
`artifacts[]`; их копии с теми же правилами пишутся в `artifactFiles` записи
совместной проверки (`<каталог проверки>/<gate>.artifacts/`).

`policyDigest(policy)` — digest загруженной политики целиком: им сверяются
применённая политика (`control.appliedPolicy`) и запрос операции
`control.reconfigure`. `executionDigest(policy)` — digest исполнительной
части без `budgets` и `prices`: основание согласования графа
(`GraphState.policyDigest`) и fencing попыток (`AttemptState.policyDigest`
у standalone-хоста). Поднятый предел бюджета поэтому согласования не
сбрасывает.

Хост, который строит политику из собственной конфигурации, может передать
движку своё тождество применённой политики (`EngineOptions.policyIdentity`,
digest по формуле хоста — например, файла конфигурации). Тогда применённая
политика и запрос операции сверяются с ним, а не с `policyDigest(policy)`;
изменение политики в памяти после создания движка по-прежнему проверяется по
её содержимому.

`EngineOptions.recordPolicyOnLead: false` — хост сам записывает применённую
политику при запуске своего планировщика; получение роли controller (в том
числе для прямой выдачи попытки) её тогда не записывает.

Автор (`--author`): `codex`, `claude`, `fixture` или `external` — человек или
инструмент вне harness; вендор `external` не совпадает ни с одним runtime.

**Выбор reviewer** — только `selectReviewer(policy, kind, writer, role)`:
`different-vendor` (умолчание) отклоняет reviewer того же вендора
(`REVIEWER_SAME_VENDOR`), `same-vendor-allowed` разрешает его. Неявного
«противоположного runtime» нет. Проверка входов отклоняет такую политику
целиком; хост, ведущий движок без неё, получает блокер
`REVIEWER_SAME_VENDOR` только у поручений этой роли — остальная очередь
выдаётся.

Правило может перечислить запасных reviewer (`alternates`, по порядку):
берётся первый из `[reviewer, ...alternates]`, допустимый правилом вендора
для этого автора. Так хост явно задаёт «reviewer другого вендора, чем
автор», не полагаясь на неявный выбор. Запасные reviewer проверяются
`policyIssues` так же, как основной.

**Раунд технического ревью** плана или контракта — `technicalReview(engine,
policy, adapters, input)`: та же реализация, что у `Harness.review`. Хост
передаёт предмет (ID, digest, автор), свои разделы запроса, рабочий каталог
reviewer и учёт вызова; harness выбирает reviewer, вызывает его под
бюджетом, требует состояние каждой прежней открытой находки и записывает
`ReviewRecord`. Предел раундов (`maxRounds`) задаёт вызывающий:
`Harness.review` — `2 × maxAttempts`.
Хост, который вёл раунды предмета до harness и хранит их сам, передаёт их
как `history: {rounds, findings[]}`: пока у предмета нет раундов в движке,
первый раунд получает номер `rounds + 1`, а находки последнего прежнего
раунда — прежние открытые находки, состояние которых reviewer обязан назвать.
Это только история: прежним раундам не приписываются digest, назначение
reviewer или одобрение. Дальше нумерация идёт подряд от первого раунда
движка, и `history` больше не учитывается.

### ContextSnapshot

`{apiVersion, sources[], missing[]}`. Источник —
`{id, kind, version, repositoryId?, revision?, required, files[], references[], digest, hostDigest?}`;
файл — `{path, digest, bytes, content: {encoding: 'utf8' | 'base64', data}}`.
Содержимое передаётся в снимке: источник может не быть Git, и движок обязан
получить ровно те байты, на которые выдан digest. `contextIssues` сверяет
SHA-256 и размер каждого файла и `sourceDigest` источника; `pinnedBytes`
отдаёт байты только после проверки. Пределы: 2 МиБ на файл, 16 МиБ на снимок.
Снимок попытки сохраняется по digest (`context-snapshots`) и используется
после рестарта без повторного чтения источника.

### ContractDocument

`{apiVersion, id, repositoryId?, title, content, artifacts?, checks?}` — вход
`review-contract`. `artifacts` — закреплённые файлы контракта (`{path, blob}`,
Git blob в репозитории `repositoryId`); `checks` — договор проверки
(`checkDeclarationSchema`, `version: 1`): gate, обязательства по property ID
(требования, тип обещания, область входов, правила ответа, способ проверки и
его файлы, семейства и минимальные выборки, корпус) и политика расширения
корпуса. Прошедший ревью документ хранится по digest (`contract-documents`):
из него движок строит манифест генеративного gate поручения.

#### Способы исполнения обязательства: `property` и `reference`

Обязательство исполняют его gates: `obligations[].gates` (1–10 ID) или, без
поля, `checks.gate`. Способ — `verification`:

- `property` (поле не указано) — генеративная проверка, как прежде: каждый gate
  обязательства генеративный (`gate.property`), отчёт свойств каждого
  подтверждает полное покрытие обязательства (`coverage.minCases` и
  семейства), корпус пополняет только gate договора;
- `reference` — сверка с закреплёнными эталонными наборами. Ответы
  независимого эталона (точный решатель, полный перебор, таблица DP)
  получены заранее, сверены с другим способом и закреплены артефактами
  контракта; gate сверяет с ними реализацию. Генератор не нужен, поэтому gate
  может быть обычным test-gate без `property`.

`reference` описывает:

| Поле                                                            | Смысл                                                                                                                                                 |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `oracle.description`, `oracle.limits`                           | эталон, его версия и пределы (время решения, что исключено из наборов)                                                                                |
| `crossChecks[]` `{family, against, matches, total, artifacts?}` | сверка эталона с другим способом на семействе входов; `matches < total` — отказ; `artifacts` — закреплённый скрипт или журнал, воспроизводящий сверку |
| `sets[]` `{gate, artifacts, minCases, families}`                | набор: gate, файлы набора (артефакты контракта), доля входов и семейств этого gate                                                                    |
| `gaps`                                                          | чего наборы не доказывают: обобщение за пределы входов, классы вне наборов                                                                            |

Структурные правила (`declarationProblems`, до вызова модели): у каждого gate
обязательства есть набор, gate набора — среди gates обязательства, файлы
наборов — артефакты контракта, сумма `sets[].minCases` не меньше
`coverage.minCases`, сумма долей каждого семейства покрытия не меньше его
`minCases`, семейства набора объявлены в покрытии и не превышают минимум
набора, сверка эталона без расхождений, файлы сверки (`crossChecks[].artifacts`)
— артефакты контракта; корпус у эталонного обязательства не включается.
Требование генеративного gate к `reference` не применяется; остальные
правила (`method`, бюджеты, spike) те же. Обязательство `property` любого
обещания (и `invariant`, и `functional`) на gate без `property` отклоняется:
поручение такое свойство выбрать не может (`orderPropertyProblems`), и
договор был бы мёртвым.

Доказательство — тот же отчёт свойств. Для gate, которому манифест поручения
назначает эталонное свойство, controller задаёт путь отчёта
(`DEVCONTOUR_PROPERTY_REPORT`) и селектор (`DEVCONTOUR_PROPERTIES`) и без
`gate.property`. Запись манифеста эталонного свойства — доля этого gate:
сумма `minCases` и семейств его наборов и `reference.artifacts` (файлы
наборов); поле есть только у эталонных свойств, так что digest прежних
манифестов не меняется. Gate проходит, только если отчёт называет свойство
со статусом `passed`, числом проверенных входов и семейств не меньше доли и
testcase с тем же ID в JUnit; зелёный JUnit и код 0 без отчёта — отказ
(«Проверка по эталонным наборам не отчиталась»). Приёмка требует решающую
запись обеих фаз с манифестом от каждого gate обязательства. Файлы наборов —
артефакты контракта, поэтому попытка не может их изменить (защищённые пути).

Reviewer контракта получает эталонные обязательства отдельно (`referenceNote`):
эталон, сверку, наборы и `gaps`. Обещание, которое опирается только на
`gaps`, без другого способа (генеративного свойства, инварианта,
аналитического основания), — блокирующая находка. Сверка без `artifacts` —
непроверенное утверждение автора, и reviewer оценивает её так.

Ответы наборов лежат в рабочем дереве, поэтому реализация могла бы читать их
или повторять их ответы и проходить каждый набор. Защита в два слоя:
writer и reviewer кода получают список файлов наборов (`referenceSetFiles`,
`referenceCodeNote`), и для reviewer чтение файлов наборов из кода
реализации, вшитые ответы или особые случаи для входов наборов — блокирующая
находка; controller отклоняет кандидата (`scope-violation`, до gates), если
изменённый файл называет файл набора внутри строкового литерала (`'…'`,
`"…"`, `` `…` ``): имя файла набора целым токеном — по краям нет буквы,
цифры, `_`, `-` или `.`, так что путь и `../имя` совпадают, а `data.json` с
набором `a.json` или `testcases.json` с `cases.json` — нет (`setFileReference`).
Комментарии `//` и `/* */` и файлы без кода (`.md`, `.txt`, `.rst`, `.adoc`,
каталог `docs/`) не проверяются. Тесты исполнителя, которые не артефакты
контракта, проверяются тем же правилом: через них ответы тоже можно подать
реализации. Остаточный риск: имя, собранное во время исполнения
(`` `${name}-golden.json` ``), копия ответов без имени файла и обобщение,
подогнанное под входы, механически не ловятся — их ловит ревью кода; строка
кода, которая законно называет набор (не артефакт контракта), отклоняется.

Пределы проверки долей: controller сверяет, что доли наборов покрывают
общий минимум и минимумы семейств и что gate отчитался своей долей, но не
сравнивает доли с размером файлов набора (сколько входов в нём на самом деле)
и не проверяет, что входы различны. Reviewer контракта видит минимумы
обязательства и семейств рядом с наборами (`referenceNote`) и оценивает это
сам.

#### ID testcase и отчёта

Свойство, `testId` отчёта и testcase JUnit — один ID. ID testcase — это
`classname.name` (без `classname` — `name`). Генератор отчёта задаёт
`classname` по-своему: node:test (`--test-reporter=junit`) всегда пишет
`classname="test"`, и тест `test('knapsack-optimal', …)` получает ID
`test.knapsack-optimal` — таким должен быть и property ID; JUnit-отчёт
собственного checker (как `harness.mjs` в примерах) пишет только `name`, и ID
совпадает с именем. Если testcase с ID свойства нет, а есть
`<classname>.<ID>`, отказ называет найденный ID.

Совместимость: поля `gates`, `verification`, `reference` необязательны, договор
без них разбирается, проверяется и даёт тот же манифест, digest и основание
корпуса (`suiteBasis` включает новые поля, только когда они объявлены;
`gates`, равные gate договора, — то же основание, что без поля, а digest
документа контракта при этом другой).
Версия договора остаётся `version: 1`; прежние версии harness договор с
новыми полями отклоняют строгой схемой.

## Ответы исполнителей

Runtime возвращает сырой ответ; движок разбирает его
`implementationResultSchema` и `reviewResultSchema`. Ответ вне схемы — отказ,
а не самооценка writer. Reviewer называет состояние каждой прежней открытой
находки (`previous[]`); `reviewIssues` отклоняет `approved` при блокирующей
находке, в том числе прежней открытой, неназванную прежнюю находку и ссылку на
неизвестную. Идентичность находки плана/контракта — `findingId(subject, {rule, message})`;
невалидный ответ раунд не применяет (переходы и новые находки не записываются).

Ревью кода ведёт историю находок поручения с ID, выданными controller
(`codeReviewHistory`, `checkCodeReview`): reviewer называет ровно один переход
каждой открытой находки, ошибка протокола (`REVIEW_PROTOCOL_INVALID`,
причина и путь поля, например `previous[0].id`) отделена от содержательного
отказа (`REVIEW_REJECTED`) и даёт ограниченный повтор только reviewer
(`reviewProtocolRetries`, 0–2, по умолчанию 1). Evidence ревью несёт
аддитивное поле `reviewRound`, находки — `id`/`status`, ссылки результата —
`review`. Правила — [docs/review-protocol.md](review-protocol.md).

Ответ runtime ограничен на границе приёма. В `reviewResultSchema` — не больше
500 элементов в `findings` и в `previous` (`REVIEW_ITEMS_LIMIT`; те же
`maxItems` объявляет wire-схема CLI runtime); файл ответа codex — не больше
4 МиБ (`CODEX_RESULT_LIMIT`), читается с границей, без перехода по symlink, а
файл больше предела удаляется: он не прошёл маскирование. Сверх предела — обычный
отказ: у reviewer кода ошибка протокола `schema`, у исполнителя класс `unknown`
без автоматического повтора, у ревью плана и контракта — `RUNTIME_UNAVAILABLE`
с причиной. Записанное прежними версиями читается
без этих пределов: `review.json` — `storedReviewResultSchema`, а `ReviewRecord`
и evidence пределов не получили.

## Выходы

### RunResult

Варианты по `outcome`:

- `accepted` — `shas{base, candidate, integration, result}` все обязательны
  (result = integration; он уже в target ref);
- `rejected | blocked | cancelled | stopped` — `stopReason{code, message}` с
  кодом из договора ошибок; result SHA нет.

Общие поля: `workOrderId`, `graphId`, `source`, `runId`, `attempt`,
`repositoryId`, `targetRef`, `inputs` (версии harness и потребителя, версия
состояния, digests поручения, графа, политики, контекста, версия проверок),
`checked` (снимки зависимостей, их свежесть, проверенная комбинация каждого
потребителя), `evidence[]`, `findings[]`, `limitations[]`, `finishedAt`.
Свежесть записывается, а не запрещает приёмку. Необязательные поля
доказательства: `inputs.corpus` (закреплённая версия корпуса),
`inputs.requiredGates` (раскрытые при выдаче gates), `inputs.writer` (writer
попытки), у ссылки на evidence —
`checks` (версия проверок записи), `property{level, manifest}` (уровень и
манифест генеративного gate), `tests[]`/`testsTruncated` (выполненные тесты
собственной проверки интеграции — доказательство названного testcase).
Получатель проверяет результат `resultProblems(result, context)` /
`assertResult`. Всё, что результат утверждает о поручении, области, входах и
ревью, сверяется с тем, что получатель знает сам, а не с другими полями того
же результата: согласованная сама с собой подделка иначе проходила бы.

**Контекст получателя** (`ReceiverContext`):

- `order` — постановка поручения у получателя; `graphId` — граф, в котором
  он её держит; `contracts` — документы договоров поручения;
- `policy` — политика получателя (`repositories`, `roles`, `review`): по ней
  раскрываются область поручения и потребителей, замыкания зависимостей,
  target ref, writer роли и назначенный reviewer с правилом вендора;
- `contextDigest` — снимок контекста, закреплённый согласованием графа
  (`null` — без контекста);
- `suite`, `checkVersion` — корпус по копии получателя и закреплённая за
  поручением версия (`null` — без корпуса; у поручения с договором проверки
  обязательна); `specDigest` — digest согласованной постановки (по
  умолчанию digest поручения);
- `unobserved` — результат прежнего формата хоста, в котором входы попытки
  не наблюдались: `dependencies` — нет снимков собственных зависимостей и их
  свежести, `consumers` — нет свежести потребителей. Такие пустые списки не
  сверяются с замыканием (их нет, и проверке они не подлежат); непустые
  списки, снимки зависимостей потребителя и провайдер сверяются как обычно.
  Какой результат имеет прежний формат, решает хост по своим правилам формата.
- `assignment` — чем подтверждено ревью: `current` (по умолчанию) — writer и
  reviewer назначены текущей политикой получателя; `recorded` — результат
  несёт своё назначение, и хост перепроверяет его позже, когда назначение
  ролей могло смениться: writer и reviewer — записанные, оба должны быть
  runtime политики получателя, правило вендора роли соблюдено.

Чего нет в контексте (репозиторий, потребитель, зависимость или роль не
описаны в политике получателя), — отказ, а не PASS. Результат прежнего
формата (без версии проверок, области и writer) читается на прежнем уровне
только у поручения без договора проверки.

**Модель доверия** — категория каждого поля принятого результата
(`receiptTrust` в `src/verification/acceptance.ts`):

- _ожидание получателя_ — сверяется с ожиданием, вычисленным из контекста;
- _согласованность_ — сверяется с другими полями результата (SHA фаз,
  свежесть со снимками, уникальность записей);
- _сведение_ — ничего не доказывает, вердикт на него не опирается;
- _схема_ — значение фиксировано схемой.

Подлинность SHA, деревьев, artifacts и записей (их наличие в Git и в
хранилище исполнителя) получатель не удостоверяет — это транспорт хоста.

### DeliveryState и ResultEnvelope

Доставка — отдельно от исхода: `{sink, key, revision, status: pending |
delivered | failed | conflict, attempts, lastError?, currentRevision?,
receipt?, updatedAt}`. `harness result` выдаёт `{apiVersion, result,
delivery[]}`.

### JointVerification

Совместная проверка закреплённой комбинации SHA нескольких репозиториев:
`{id, status, policyDigest, specDigest, workIds[], manifest{repo: {sha, tree}},
manifestDigest, impact?, evidence[], error?}`. Смена любого SHA делает
результат устаревшим; атомарность продвижения нескольких репозиториев не
заявляется. Продуктовое принятие комбинации решает хост. Пока manifest не
закреплён, `impact` может нести только ссылку на базовую проверку
(`baseline`), выбранную хостом для режима `affected`.

### Зависшие попытки

Controller, ведущий очередь, раз в `stallSweep.intervalMs` (не меньше 1000 мс
и не больше `quietMs`) обходит исполняющиеся попытки. Движение попытки —
начало и конец её команды (вызов агента, gate, шаг среды, прочие команды),
вывод в stdout/stderr, граница стадии (`attempt.stage`) и прирост
процессорного времени дерева процессов исполняющихся команд (сумма
положительных приростов по каждому процессу, новый — от нуля) не меньше 1 %
прошедшего времени. Смена состава дерева сама движением не считается: цикл
ожидания (`until nc -z db 5432; do sleep 1; done`) рождает процессы, не
продвигаясь. Один `ps` на обход, общий для одновременных обходов; перерыв
от конца прошлого обхода дольше трёх интервалов (сон машины, занятый event
loop) начинает отсчёт заново, но не больше двух раз подряд.

Состояния: `active`; `quiet` — нет движения дольше `quietMs`; `stalled` —
дольше `stalledMs` (`quietMs < stalledMs`). Без данных `ps` о процессах
(отказ, Windows, нет времени процесса) оценка идёт только по выводу и не
поднимается выше `quiet` (`cpuUnavailable` в событии). Попытка без
исполняющейся команды (ждёт hook, ресурс, интеграцию) оценивается от последнего
движения с порогом `stalledMs` и тоже не выше `quiet`. Переход пишется в
`AttemptState.liveness` и событием `attempt.liveness` одной транзакцией под
fencing; само состояние между переходами не перезаписывается, а незаписанный
временным отказом переход повторяет следующий обход (не больше пяти раз;
отказ движка или схемы не повторяется). На `stalled` — снимок процессов
исполняющихся команд (pid, родитель, процессорное время, команда под маской
среды; команда без маски не сохраняется) и хвост вывода: в
`artifacts/<runId>/stall-<эпизод>.json` (один на эпизод, записывается первым) и в событии (≤ 20
процессов, ≤ 2000 символов). Дальше — `action`: `report` только сообщает
(попытка идёт до своего предела времени, движение вернёт `active`), `stop`
останавливает попытку отказом класса `stalled`: повтор или правка среды, а не
правка кода (`repairPolicy.stalled`, бюджет попыток он тратит, как `timeout`);
при `stop` зависшая попытка останавливается, даже если переход не записан.
Совместная проверка и gates на SHA вне попытки (`runGatesAt`) ведут свой
обход: переходы проверки — событие `joint.liveness` под её fencing, переходы
`runGatesAt` — `onLiveness` хоста и `liveness[]` результата (нагрузка как у
`attempt.liveness`, без файла снимка); при `stop` они останавливаются с
текстом зависания. `stallSweep` — надзор, а не условие
исполнения: в digest исполнения (основания попыток и reuse) он не входит.

`status` показывает `works[].liveness` (`quiet`/`stalled`) у активной попытки
без движения, `status --detail` — `detail.attempts[].liveness` (`state`,
`since`, `lastMovementAt`, `idleMs`, `activity`, `action`), `explain` —
причину `stalled` у работающего поручения: при `report` действует человек
(`fix-environment`), при `stop` — controller.

### Нехватка окна контекста

Отказ класса `context-exhausted` — исполнителю или reviewer не хватило окна
контекста модели внутри попытки. Класс ставится по признаку, который сообщил
сам runtime, а не по тексту причины: адаптер claude читает `terminal_reason`
итогового события `result` потока `stream-json` и выставляет
`RuntimeResponse.diagnostics.contextExhausted` — предел окна
(`ContextLimit`). Записанные на живом CLI признаки:

- `prompt_too_long` на первом ходе (`num_turns` ≤ 1) → `prompt-too-long` —
  запрос отклонён: уже подсказка с контекстом больше окна, сжимать нечего.
  Тот же признак после ходов работы или без `num_turns` (не записан, вывод
  инструментов заполнил окно) → `blocking-limit`;
- `blocking_limit` → `blocking-limit` — CLI сам остановил ход у предела окна.
  Записан с выключенным автоматическим сжатием через `DISABLE_AUTO_COMPACT=1`.
  `autoCompactEnabled: false` в `--settings` сжатие тоже выключает (проверено),
  но исход у предела окна с ним не записан; путь «сжатие включено, но не
  помогло» не проверен.

В обоих случаях CLI выходил с кодом 1, `is_error: true`, текст `result`
начинался с `Prompt is too long`; признак учитывается и при коде 0. Текст
отказа попытки постоянный (`claude: не хватило окна контекста модели`), предел
— данными (`AttemptState.contextLimit`), текст runtime — в журнале вызова:
отпечаток один при любом пределе и любых числах токенов, а «401» или «429» в
числах токенов текстовый разбор принял бы за отказ провайдера. Успешное
автоматическое сжатие (`system`/`compact_boundary`) — не отказ: вызов
продолжается и завершается своим исходом; число сжатий и `terminal_reason`
пишутся в `runtime.json` вызова (`compactions`, `terminalReason`). У codex
признак пока не распознаётся: его отказ классифицируется как прежде.

Попытка засчитывается в `maxAttempts`: отказ говорит о размере задачи, а не
об окружении, и выдачу не останавливает. Повторы (`repairRepeats`): у
`blocking-limit` — один (`repairPolicy['context-exhausted'].repeats`), и
следующая попытка writer получает в подсказке указание держать контекст малым
(читать только нужные файлы и строки, не выводить большие файлы и длинный
вывод команд); у `prompt-too-long` — ни одного: повтор только удлинил бы
подсказку. Предел берётся у последней попытки с отказом
(`lastContextLimit`); отпечаток у обоих пределов один. Дальше задачу нужно разделить или сократить её контекст:
код остановки `CONTEXT_EXHAUSTED` (класс `refused`), `explain` — ведущий,
`diagnose-failure`. Корзина отчёта — `incomplete`; разбор свойства
(`property-recovery`) такой отказ не считает, кандидат после отказа reviewer
переиспользуется (`reusableFailures`). Причина `attempt.diagnosed` — `none`,
`counted: true`.

### Вопрос исполнителя

Writer, которому для продолжения нужно решение человека или ведущего,
отвечает `completed: false` и вопросом `inputRequest` (`inputQuestionSchema`:
текст до 1500 знаков, до шести вариантов с последствием, рекомендуемый
вариант, самооценка серьёзности 1–10, основание, затронутые критические
области `contract | acceptance | product | api | migration`). Развилки,
которые он решил сам, — `assumptions[]` (вопрос, выбор, основание,
серьёзность, области; до 20). `completed: true` вместе с вопросом невалиден.
Поля необязательны: ответ прежнего формата — ответ без вопроса и допущений.
Wire-схема CLI runtime объявляет оба поля (`inputRequest` — объект или
`null`).

**Политика вопросов** — `ExecutionPolicy.inputPolicy`
(`{threshold: 1–11, criticalPaths: []}`; нет поля — порог 7 без критических
путей, умолчание в политику не подставляется). Порог закрепляется в попытке
при выдаче (`AttemptState.inputPolicy`) и в `executionDigest` не входит: смена
порога действует со следующей попытки без нового согласования. Порог и шкала
называются в запросе writer. Действующая серьёзность — самооценка, поднятая
до 10 минимумами, которые модель понизить не может: вопрос или допущение
называет критическую область или сам оценён потолком 10 (`declared`) либо попытка изменила путь из
`criticalPaths` (`critical-path`).

Исход ответа writer (`evaluateInput`) — после проверок защищённых путей,
HEAD и области записи: нарушение области остаётся `scope-violation` и не
прячется за вопрос.

| Ответ                                       | Исход                                                                                                                                        |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `completed: false`, вопрос не ниже порога   | `needs-input`: попытка не засчитана, черновик — `AttemptState.partial`, запрос `pending` в той же транзакции, что отказ                      |
| `completed: false`, вопрос ниже порога      | `unfinished` (нарушение запроса); вопрос записан отклонённым (`cancelled`, `closed.by: controller`) и работу не держит                       |
| `completed: false` без вопроса              | `unfinished`, как прежде                                                                                                                     |
| `completed: true`, допущение не ниже порога | `needs-input` без кандидата: самое серьёзное допущение становится вопросом (вариант `chosen` — выбор исполнителя)                            |
| `completed: true`, допущения ниже порога    | Допущения пишутся в попытку (`AttemptState.assumptions`), запрос reviewer их перечисляет; работа идёт дальше                                 |
| Порог 11 (автономный режим)                 | Остановок нет; все допущения записаны; критические — неблокирующие запросы ведущему (`kind: follow-up`); согласованное состояние не меняется |

`needs-input` — класс отказа без автоматического повтора
(`repairPolicy['needs-input']`: `stop`, выдачу не останавливает), корзина
отчёта `input`, код остановки `INPUT_REQUIRED` (класс `refused`). Остановка
вопросом возвращает попытку в предел `maxAttempts` и не тратит предел
незасчитанных отказов: ответ на вопрос последней попытки применяется без
сброса. Возврат ограничен: поручение получает не больше `maxAttempts`
остановок вопросом, возвращающих попытку, за всю жизнь (счёт — по записям
попыток с `failureKind: needs-input`, кроме прерванных остановкой
controller; сброс попыток его не обнуляет). Следующая остановка вопросом
засчитывается как обычная попытка (`counted: true`), поэтому цикл «вопрос →
ответ → применение» и обход вопроса отменой с повтором кончаются
исчерпанием попыток, даже если отвечает модель. Остановка, вернувшая
попытку, и её продолжение имеют один номер попытки; различает их
`failureKind: needs-input` записи и `counted` в `attempt.diagnosed`.

**Канонический запрос** (`InputRequest`, `schemas/input-request.schema.json`)
хранится в локальном пространстве `input-requests` у владельца — репозитория
поручения. ID (`IR-<24 hex>`) выдаёт controller детерминированно от попытки.
Вопрос и основание исходной попытки (`originBasis`: источник, digests графа,
постановки, политики, снимок контекста или `null`, база, закреплённая
`inputPolicy`) неизменяемы; ответы (`answers[]`, до 20) только дополняются;
`version` — CAS записи. Эти правила проверяет движок (записи — только через
его операции); от хранилища договор (`executionStoreContract`) требует хранить
запись целиком и отдавать её в списке без владельца с `owner` и `key`.
Жизненный цикл: `pending → answered → applied`,
альтернативные окончания — `cancelled` и `superseded` (с `successor`).

**Блокировка.** Блокирующий запрос в `pending` или `answered` сам держит
работу: claim его не выдаёт (и после новой редакции графа с согласованием),
`retry` — в том числе со сбросом — отказывает `INPUT_REQUIRED`, `repairDecision`
такую работу не чинит и не останавливает ею восстановление группы, приёмка
(`finish`) отказывает. `WorkState.hold` не занимается: снятие чужого
удержания ожидание ответа не обходит. Отмена работы закрывает её открытые
запросы.

**Продолжение.**

1. `answerInput(id, {text, optionId?, kind, actor, messageRef?},
expectedVersion)` — новая версия ответа с `answerDigest`; работу ответ не
   возобновляет. Тот же текст, вариант и вид — прежний ответ без записи.
   `kind: requirement-change` — изменение требований: старый запрос
   заменяется (`supersedeInput`) ссылкой на новую ревизию, а не
   продолжается.
2. `Harness.inputContext(id, {messages?})` — неизменяемый снимок: действующий
   снимок графа и источник `input-answer` (`inputContextSource`): файл
   `input/<id>.md` (вопрос, варианты, ответ) и справка
   `input/<id>.manifest.json` (`{requestId, answerDigest, revision,
messages[{id, revision, digest}]}`). Версия ответа — в `version`
   источника (`r<N>`), не в `revision`. Снимок хранится по digest, но не
   активируется.
3. Ревью этого снимка — обычный `review-plan --context`. Согласование им не
   меняется: попытки графа сохраняют своё. `approve` со снимком, где ответ не
   применён, — `INPUT_REQUIRED`; `run` с таким снимком отказывает тем же кодом
   до вызова модели.
4. `proposeTarget(id, contextDigest)` — основание продолжения (только чтение)
   и причины, по которым применение сейчас откажет.
5. `applyInput(id, {answerDigest, expectedVersion, contextDigest,
targetDigest, actor, reset?})` — одна транзакция: точная версия запроса и
   последний ответ, вид `clarification`, работа всё ещё в исходной остановке
   (последняя попытка — попытка вопроса), неизменные граф и постановка,
   политика процесса применена, снимок несёт ровно этот ответ (manifest),
   проверки `approve` (`approvalCheck`: раунд ревью этого снимка, в режиме
   `agent` одобренный, актёр — режим политики) и пересчитанное основание
   совпадает с `targetDigest`. Затем — активация согласования снимка, запрос
   `applied` с `target` и обычный повтор (`retryIn`: те же правила, без
   сброса, если сброс не назван). Модель не вызывается; пауза оператора и
   чужие удержания остаются. Идут попытки графа или совместная проверка —
   `{applied: false, active}`, запрос и согласование не меняются; исчерпаны попытки или бюджет —
   `{applied: false, blocker}`, запрос остаётся `answered`. Повтор того же
   применения — `{applied: true, changed: false}`.
6. Claim закрепляет действующий снимок (`pinned.contextDigest`) и связывает
   ответ с попыткой (`AttemptState.input`) только при совпадении применённого
   основания с основанием выдачи. Runner загружает снимок по закреплению:
   writer и оба reviewer видят одни и те же байты. «Передано исполнителю»
   (`delivered`, событие `input.delivered`) — только по началу вызова writer
   этой попытки, один раз, под fencing; apply и claim доставку не
   подтверждают.

**Исходная остановка** держится, пока работа на попытке вопроса
(остановлена `needs-input` или готова после устаревшего применения) и её
собственная постановка прежняя — по содержанию без ревизии источника
(`originBasis.contentDigest`, у цели — `target.contentDigest`): пересинхронизация
трекера одной ревизией ни остановку, ни применённый ответ не обесценивает. Граф целиком не
сравнивается: согласование или добавление другой работы того же графа (у
DevContour граф — активная ревизия доски) остановку и применённый ответ не
обесценивает.

**Устаревшее применение.** Если до выдачи попытки с ответом сменились
постановка работы, политика или действующий снимок (новый снимок не несёт
этот ответ), транзакция claim возвращает запрос в `answered` с причиной
(`stale.reason`: `order | policy | context`, событие `input.stale`; значение
`graph` больше не ставится): работа не выдаётся без ответа и ждёт нового
снимка, ревью и `applyInput` (готовая работа на исходной попытке применяется
так же, как остановленная). Снимок, который несёт тот же ответ (например, с
ответом на второй вопрос графа), основание не обесценивает.

**Новая редакция постановки.** Если постановка самой работы изменилась,
продолжение исходной остановки невозможно (`applyInput` и `proposeTarget`
называют выход). Выход с сохранением ответа: `supersedeInput` (преемник —
новая редакция работы), затем `inputContext` (принимает заменённый вопрос с
ответом), `review-plan` со снимком и перенос: `carryInput(id, {contextDigest,
actor})` — одна транзакция с правилом переноса, отсутствием неприменённых
ответов в снимке, барьером политики, ревью и актёром по правилам хоста
(`InputHost.review`) или `approvalRules`, без идущих попыток графа
(`{carried: false, active}`), пределами попыток и бюджета до активации
(`{carried: false, blocker}`), активацией (`InputHost.activate` с `mode:
'carry'` или согласование графа), записью цели в заменённый запрос и обычным
повтором работы, остановленной вопросом (иной отказ остаётся по своим
правилам). Перенесённый ответ связывается с попыткой при выдаче и
подтверждается вызовом writer, как применённый; если до выдачи согласование
ушло на снимок без него, цель снимается, `stale` записывается (состояние
`carry-stale`), и работа ждёт: выходы — новый перенос или снять перенесённый
ответ (`cancelInput`), тогда работа продолжится без него; запись замены
(преемник, `carry`, причина) остаётся в `closed.previous`. Изменение требований сравнивается по содержанию постановки
без ревизии источника (`originBasis.contentDigest`). Экспортированный
`unappliedInputs` требует правило переноса движка (`mayCarry`, проще —
`Engine.unappliedInputs`). У standalone тот же снимок можно согласовать и
обычным `approve`/`run`. Перенос решается в момент переноса
(`Engine.carryAllowed`), а не замены: уточнение — когда исходная остановка
уже не держится, изменение требований — только когда изменилась постановка
самой работы; только последняя версия ответа. Порядок «замена, затем новая
редакция» тоже ведёт к переносу; `closed.carry` — сведение о моменте замены.
Пока остановка держится, продолжение — только `applyInput`. Снимок с новым
ответом не становится действующим и через `approve`/`run`, пока в графе идут
попытки (`NOT_READY`; `run` отказывает до ревью). `inputContext` отказывает
для неблокирующих и закрытых без замены запросов.

**Закреплённый снимок.** У попытки с `pinned.contextDigest` записанный
снимок контекста обязан совпасть с закреплённым — при записи контекста
runner и при приёмке (`APPROVAL_STALE`): загрузчик хоста, не учитывающий
закрепление, отказывает до вызова writer; не найденный закреплённый снимок —
отказ этой работы при загрузке (`needs-lead`, причина `preflight`, попытка не
засчитана, очередь не останавливается; explain — фаза `preflight` и неполные
входы работы, `StopInput.work.preflight`). `InputHost.contextDigestOf`:
`null` — снимок «без контекста» (загрузчик обязан вернуть пусто),
`undefined` — хост не связывает согласование с контекстом (проверки нет).

**Вопрос вне схемы.** Пределы вопроса называются в запросе writer; схема
договора строгая. Ответ вне схемы, в котором есть вопрос, controller приводит
к схеме (усекает текст, исправляет ID вариантов, оставляет шесть вариантов,
ограничивает серьёзность) и решает как обычно; что исправлено — в поле запроса
`normalized`. Ответ вне схемы без вопроса — отказ, как прежде. Вопрос и
допущения маскируются полным окружением вызова до записи; решения взятого
кандидата переоцениваются по политике новой попытки, решения продолжаемого
черновика видят writer и reviewer.

События `input.requested`, `input.answered`, `input.applied`,
`input.closed`, `input.delivered` и `attempt.assumptions` несут ID, digests и
числа — без текста вопросов, ответов и допущений.

**Проекции.** `status`: у поручения `input {requestId, state, version,
severity}` (`awaiting-answer | answered-not-applied | applied-awaiting-claim
| delivered`) и число неблокирующих запросов `followUps`. `explain`:
ожидание ответа — человек, `answer-input`; ответ без применения — ведущий,
`apply-input` с причиной, по которой применение сейчас откажет; сообщение
называет усечённый вопрос, варианты, версию и digest ответа, число решений
исполнителя; неблокирующие запросы — отдельные диагнозы ведущего. Пакет
передачи — блок `inputs` (усечённый вопрос, варианты, версия, digest и
начало ответа до 500 знаков, digests основания). Отчёт — только числа
(`inputs`): ответ целиком в отчёт не попадает.

### RunEvent

`{apiVersion, seq, at, type, graphId?, workId?, runId?, attempt?, payload}`.
`seq` строго возрастает. Нагрузка каждого из типов (`eventPayloads`) — закрытая
схема: лишних полей нет, поэтому токен владения, секрет или объект попытки в
событие не попадает.

`attempt.stage` — граница стадии попытки: `{timingId, stage, phase:
'started'|'finished', at, durationMs?, outcome?: 'passed'|'failed'}`, конверт
несёт `graphId`, `workId`, `runId`, `attempt`. Стадии — те же, что замеры
`AttemptState.timings`: `dependency-store`, `implementation` /
`implementation-reuse`, `candidate-environment:<шаг>`, `integration-wait`,
`<фаза>-test:<gate>`, `<фаза>-consumer:<репозиторий>:<gate>`,
`<фаза>-recheck:<gate>`, `<фаза>-review`, `integration-environment:<шаг>`,
`integration-consumer-environment:<репозиторий>:<шаг>`. На стадию — одно
`started` и не больше одного `finished` (у него `durationMs` и `outcome`);
`at` и `durationMs` — по часам движка и совпадают с замером. Событие пишется
в той же транзакции `run.timing.started`/`run.timing.finished`, что и замер,
под fencing: утративший владение не пишет ни замера, ни события. Повторное
закрытие замера ничего не меняет и событий не создаёт.

`attempt.liveness` — переход живости попытки по обходу controller:
`{state, previous, lastMovementAt, idleMs, activity?: {kind:
'agent'|'gate'|'step'|'command', label}, cpuUnavailable?, action?:
'stop'|'report', snapshot?}`; `joint.liveness` — то же с `verificationId`; `action` и `snapshot` — только у `stalled` (см. «Зависшие
попытки»).

`work.retried` — поручение возвращено в очередь `engine.retry`: `{by:
'operator'|'recovery'|'host', reset, spent?, reasonLength?}`. `by` — третий
аргумент `retry(workId, reset?, by?)`: CLI `retry` передаёт `operator`,
восстановление очереди (`repair`, эпизод по свойству) — `recovery`, хост без
актёра — `host` (по умолчанию). `reset` — сброс исчерпанного предела; `spent` —
засчитанные попытки до сброса (сброс обнуляет `WorkState.attempt`),
`reasonLength` — длина причины сброса; текста причины в событии нет. Повтор
без изменения (поручение уже в очереди) и отказ повтора событий не создают.

`work.cancelled` — поручение отменено: `{by: 'operator'|'host'|'graph',
hadAttempt}`. `engine.cancel(workId, reason?, by?)` (CLI `cancel` — `operator`,
по умолчанию `host`); `graph` — новая редакция графа убрала поручение.
`hadAttempt` — отменена и активная попытка: её `attempt.cancelled` идёт в той
же транзакции перед `work.cancelled`, у которого тогда те же `runId` и
`attempt`. Повторная отмена отменённого событий не создаёт.

`base.moved` — сдвиг ref базы `fencedRefMove(store, fence, timeoutMs?, by?)`:
`{by: 'operator'|'controller'|'host'}` (по умолчанию `host`), одно событие на
репозиторий, в той же транзакции, что проверка владения и `git update-ref`.
Отказ проверки или Git (CAS) отменяет и событие. `moveBase` без `move` событий
не пишет: у него нет хранилища.

`attempt.diagnosed` — причина отказа попытки: `{failureKind, cause, counted}`,
конверт несёт `graphId`, `workId`, `runId`, `attempt`. Пишется сразу за
`attempt.failed` (и `attempt.expired`) в той же транзакции под fencing.
`cause` (`environmentCauses`): `sandbox-launch`, `sandbox-network`,
`sandbox-filesystem`, `sandbox-policy`, `dependency-network` — ставит gate в
точке обнаружения (`TaskFailure.diagnosis`); `transport`, `preflight`
(`BlockedError` до работы), `provider-auth`, `provider-limit`, `stalled`,
`shutdown` (прерывание штатной остановкой), `lease-expired` — по классу отказа
и его признакам; `other` — отказ окружения без известной причины; `none` —
отказ не окружения. Хост, вызывающий `engine.fail`, может передать
`options.cause`; движок приводит её к классу (у отказа не окружения — всегда
`none`). `counted` — отказ засчитан в предел попыток (`maxAttempts`): не
засчитаны отказы до работы (`blocked`), окружения и провайдера, остановка
вопросом (`needs-input`) в пределах своего предела, истёкшее владение и
прерывание остановкой;
зависание (`stalled`) засчитано. Отчёт
считает попытки засчитанными по тому же правилу; остановку вопросом — по
`counted` её `attempt.diagnosed` (без события — засчитана). Отказ до работы с классом
не окружения получает причину `preflight`. Текста отказа в событии
нет.

`finished` может не прийти: поздний finish владельца, утратившего срок,
отклоняется (runner его не повторяет), упавший процесс его не пишет, а `adopt`
и recovery открытые замеры прежнего владельца не закрывают. Такая стадия
остаётся открытой и в замере, и в журнале; её конец — событие конца попытки
(`attempt.expired`, `attempt.failed`, `attempt.cancelled`,
`attempt.recovered`, `work.accepted`). Потребитель журнала обязан обрабатывать
незакрытые стадии.

Чтение журнала терпимо к типам более новых версий: событие типа, которого нет
в `eventPayloads`, возвращается как `UnknownRunEvent` —
`{apiVersion, seq, at, graphId?, workId?, runId?, attempt?, type: 'unknown',
original}` (исходный тип, не длиннее 200 символов; нагрузка не возвращается).
`RunEvent` = известные события (`KnownRunEvent`) | `UnknownRunEvent`: нагрузка
доступна после сужения по `type` (`e.type !== 'unknown'`) или у
`KnownRunEvent`. Тип `ExecutionStore.events()` прежний (`RunEvent[]`), поэтому
хранилища хоста, возвращающие или делегирующие события, компилируются без
изменений. Разбор — `readRunEvent`, схема чтения — `readRunEventSchema`. Запись строгая
(`runEventSchema`, опубликованная `run-event`): `unknown` записать нельзя;
известный тип с нарушенной нагрузкой при чтении — отказ.

`transactionKinds` — имена транзакций исполнения; совпадают с сохранёнными
типами событий журнала хоста (`run.claimed`, `task.done`, `run.failed`,
`scheduler.error`, …). `workflow.updated` пишет только локальные записи
технической очереди (`workflow-jobs`) и событий журнала не создаёт.
`usage.recorded` пишет только локальные записи учёта вызовов (`usage`): начало
вызова вместе с проверкой бюджетов, ход и итог вызова, закрытие прерванных,
закрепление атрибуции прежних записей; событий журнала не создаёт.
`checks.recorded` пишет только локальные записи корпуса (`check-suites`):
начало, продление и завершение операции подтверждения, решение и новую
версию. `checks.spike` пишет только локальную запись эксперимента
выполнимости (`spikes`). `checks.adopted`, `checks.awaiting-operator` и
`checks.adoption-abandoned` меняют принятую поручением версию корпуса и
удержание выдачи (`work.held`, `corpus.adopted`). Эпизод по свойству меняется
транзакциями `recovery.*`, отказом и выдачей (`work.recovery`).
`workspace.verification.started`, `workspace.manifest`, `workspace.evidence`,
`workspace.verified`, `workspace.failed` — транзакции совместной проверки
(`joint.started`, `joint.finished`). `config.started`, `config.reconfigure-*`
и `config.reconfigured` меняют применённую политику и запрос операции
(`policy.applied`, `policy.reconfigure`). `base.moved` — проверка владения
операцией и CAS-сдвиг ref базы; записей не создаёт, событие — `base.moved`.

### ValueReport

Отчёт об эффекте (`harness report`, `valueReport` из `devcontour-harness/report`
и корня пакета; `reportVersion: 1`, `valueReportSchema`,
`schemas/value-report.schema.json`). Отвечает на вопрос «что дал harness на
этом проекте» данными самого проекта: только наблюдения (счёт и
длительности), без «сэкономленных часов» и сравнения «с harness и без»
(базы до harness в состоянии нет).

Вход (`ValueReportInput`) — те же формы, что у `ExecutionView`: `works`,
`attempts`, `calls` (`locals('usage')`), `reviews` (`locals('reviews')`),
`events`, `graphs`. `collectReportInput(store)` собирает его из любого
`ExecutionStore` одним `read` и страницами `events` по 500; `Harness.report()`
— то же по каталогу состояния. Параметры: `since` (включительно; ISO-время с
поясом, дата `YYYY-MM-DD` или `Nd`/`Nw` до `asOf`), `until` (не
включительно), `asOf`, `noTitles`, `label`, `stateDir`, `harnessVersion`.
`reportMarkdown(report)` и `reportHtml(report)` — чистые рендеры: те же
разделы и числа; HTML — один файл без скриптов, шрифтов, изображений и
внешних ссылок (CSP `default-src 'none'; style-src 'unsafe-inline'; img-src
data:`), светлая и тёмная схема по `prefers-color-scheme`, таблицы
прокручиваются на ширине телефона, столбики недель (inline SVG) — от 3
активных недель. Модуль `devcontour-harness/report` без `node:*` и без zod. Запись
файла отчёта (`report --out`) — `writeReportFile(out, stateDir, text)` из
корня пакета (не из `./report`: она использует `node:fs`): текст пишется во
временный файл каталога цели и переименовывается поверх цели, без записи
сквозь symlink и жёсткие ссылки; цель внутри каталога состояния, symlink,
не обычный файл или файл с `nlink > 1` — `PATH_CONFLICT`, недоступный
каталог — `INVALID_INPUT`; права прежнего файла сохраняются, новый —
`REPORT_FILE_MODE` (`0600`).

**Детерминизм.** Тот же вход и параметры — те же байты JSON, Markdown и HTML
при любом порядке входных массивов, часах и часовом поясе. `asOf` по
умолчанию — последняя метка времени в данных (событие, начало или конец
попытки и вызова, раунд ревью), не часы; с `until` раньше неё — `until`.
Время — UTC ISO, недели — ISO (понедельник, UTC), числа без локали.

**Определения.**

- Принятое поручение — `WorkState.status = done` с успешной попыткой;
  принявшая попытка — последняя `succeeded`. Поручение `done` без успешной
  попытки не имеет времени приёмки и не входит в принятые ни в каком окне
  (`coverage.doneWithoutAttempt`). В окно входят: принятые — по времени
  приёмки, попытки и вызовы — по началу, раунды ревью и события — по своему
  времени.
- Попытки поручения считаются по записям попыток, а не по
  `WorkState.attempt` (сброс возвращает счётчик к 0).
- Корзины отказа попытки (`failureBucketOf`): `defect` (`gate`, `review`,
  `scope-violation`), `incomplete` (`empty-result`, `unfinished`,
  `needs-lead`, `context-exhausted`), `integration` (`stale-base`, `merge`), `environment`
  (`environment`, `provider-auth`, `blocked`, истёкшее владение), `time-limit`
  (`timeout`), `tool` (`review-protocol`), `operator` (`cancelled`), `budget`,
  `unknown`, `unclassified` (попытка без класса — записана до
  классификации; не «дефект»). Прерванная штатной остановкой
  (`interrupted: shutdown`) — не отказ, считается отдельно.
- Первая попытка — у принятого поручения засчитанная попытка одна
  (засчитанные — без `environment` и прерываний); если, кроме принявшей,
  засчитаны только отказы без класса, — неизвестно (`unknown`, `bound:
lower`). `firstPassRaw` — попытка вообще одна.
- Возвращено (`sentBack`) — принятое поручение с попыткой `defect` до
  принявшей. Поручения, у которых до приёмки только отказы без класса
  (`unknown`, `unclassified`), не считаются, а идут в `unknown`: тогда
  `bound: lower` («≥ N», «M more without a class»). Без них, но если часть
  поручений вернули только отказы gate подготовки (установка зависимостей,
  возможна сеть; `sentBackSetupOnly`), — `bound: upper`; оба сомнения
  сразу — `bound: unknown` и диапазон `sentBackRange` («1–3 of 5»); иначе
  `exact`.
- Ревью после зелёных gates (`afterGreenGates`) — ревью кандидата отклонило,
  хотя каждый обязательный gate прошёл на том же SHA (и той же версии
  проверок); диагностика, не точность reviewer.
- Срок от согласования до приёмки — от `wait.approvedAt` первой попытки
  (иначе `WorkState.approvedAt`, его переписывает повторное согласование —
  `leadTimeFallback`) до конца принявшей попытки; включает очередь и паузы.
- Расход: известная цена — правило `knownCost`; на принятое поручение —
  известный расход окна / принятые окна. `callsRecorded` попытки значит
  «учёт её вызовов полон», а не «вызовы есть»: записи вызовов попытки без
  флага входят в её расход, но лишь нижней границей
  (`attemptsPartialCalls`); без флага и без записей расход неизвестен
  (`attemptsWithoutCalls`). `bound: exact` — только если все вызовы окна
  завершены с полными счётчиками и ценой и у всех попыток окна учёт полон;
  иначе `lower` («≥»); без единой известной цены при неизвестных —
  `unknown` (`value: null`), не `$0`. Расход отклонённых попыток
  (`cost.rejected`) и расход отказов окружения (`environment.neutral`) —
  одна и та же атрибуция по всем завершённым попыткам окна. `environment.neutral`
  — вся корзина `environment`, включая зависания (`stalled`), хотя они
  засчитаны в предел попыток.
- Пробел записи определяется по порядку журнала (`seq`), а не по времени:
  `at` события — часы записи, время попытки — часы движка.
- Действия человека — только записи с актёром-человеком: решения recovery
  с источником `operator`, повторы и отмены с `by: operator` (`work.retried`,
  `work.cancelled`). Удержания (`work.held`) актёра не называют (удерживают и
  операции хоста, например смена контракта): они показаны отдельно (`holds`)
  и в действия человека не входят; так же `cancelledAttempts` — отменённые
  попытки по записям попыток. Повторы восстановлением (`recovery`), сдвиги
  базы controller и отмены новой редакцией графа — автоматические.
- Вмешательства по событиям (`actions.recorded`): числа в окне по актёрам —
  повторы, сбросы, отмены (и отмены без активной попытки), сдвиги базы.
  Запись начинается с первого события версии, которая их пишет
  (`work.retried`, `work.cancelled`, `base.moved`, `attempt.diagnosed`;
  `recorded.from`); раньше него действие могло быть, но не записано. Нет ни
  одного такого события в журнале — `recorded: null`, `withAction` — нижняя
  граница, «без действий человека» (`withoutAction`) не измеримо (`value:
null`, `bound: unknown`). С записью: `recorded.bound: lower`, если в окне
  есть попытки, события или принятые поручения раньше `from` или пробел записи
  (`gaps`: новая попытка после отказа или отмены без `work.retried` и без новой
  редакции графа между ними — работала версия без этих событий, например
  после отката и повторного обновления), иначе `exact`. Пробел, не оставивший
  такой попытки, не обнаруживается — это постоянное ограничение. Суммы
  `retries`/`resets` — только при `bound: exact`, иначе `null` (числа по
  актёрам с границей — в `recorded`). Сдвиги базы — всегда нижняя граница
  (`baseMovesBound: lower`, сумма `baseMoves` всегда `null`): перенос вне
  `fencedRefMove` (`moveBase` без `move`) не пишется; к поручениям они не
  относятся.
- Поручение «без действий человека» известно, если оно начато не раньше
  `from` (начало — согласование первой попытки `wait.approvedAt`, иначе
  `WorkState.approvedAt`, иначе начало первой попытки), без пробела записи,
  и у него нет действий без актёра: повтора или отмены хостом (`host`) и
  удержания (`work.held` — его ставят и человек, и операции хоста). Прочие
  принятые без действия оператора идут в `unknown` обеих мер (`bound:
lower`).
- Подпричины окружения (`environment.causes`): отказы окружения окна по
  `attempt.diagnosed` своей попытки — строки `{cause, count, counted}` (по
  убыванию числа); отказ без события (записан раньше) — `undiagnosed`, тогда
  `bound: lower`. Нет ни одного `attempt.diagnosed` в журнале — `causes:
null`.
- Отказы окружения (`environment.share`) — среди классифицированных; если
  есть отказы только в gates подготовки (`setupCheckFailures`), доля —
  нижняя граница («at least», «M more may be environment»).
- Паузы — `control.paused` до следующего `control.resumed` (открытая — до
  `asOf`); время паузы — её пересечение с окном. Согласования — события
  `graph.approved` для графов, у которых такие события есть; для прочих —
  текущее согласование графа в состоянии (`source: state` или `mixed`); нет
  ни того ни другого — `source: none`, число неизвестно, а не ноль.

**Малые выборки и неизвестное.** `ReportMeasure` — `{value, n, unknown,
bound}`, `bound` — `exact | lower | upper | unknown`; неизвестное не
показывается нулём. Процент — только при знаменателе от 20, иначе «k of n».
Медиана и p75 — от 5 значений, иначе `null` и значения в `values`. Меньше 3
принятых поручений в окне — `summary.status: not-enough-data` (сырые
счётчики вместо заголовочных чисел). Сводка — не больше 5 чисел (принятые и
первая попытка, возвращено, срок, расход на принятое, отказы окружения),
каждое с предложением и основанием (`basis`). Раздел `limitations` есть
всегда: постоянные ограничения и найденные в данных (попытки без класса,
без замеров, без учёта вызовов, вызовы без цены, начало событий, смена
версии движка, усечения).

**Приватность и пределы.** В отчёт попадают только перечисленные поля: нет
prompt, вывода runtime, текстов находок, ошибок и причин, fencing-токенов.
Пути evidence — относительно `stateDir`; путь вне него — `…/<имя файла>`,
домашний каталог не печатается. `noTitles` убирает заголовки поручений и
метку проекта. Пределы (`REPORT_LIMITS`): 50 строк поручений (новые сверху),
50 ссылок evidence, 12 активных недель (ранние свёрнуты в `earlier`,
недели без активности — `gap`), 50 строк gates и стадий; JSON ≤ 512 КБ,
HTML ≤ 1 МБ. Усечение отмечено флагом и ограничением.

### HandoffPack

Пакет передачи контекста (`harness handoff`, `handoffPack(source, options)`
и `handoffMarkdown(pack)` из корня пакета; `handoffVersion: 1`,
`handoffPackSchema`, `schemas/handoff-pack.schema.json`). Ведущий агент хоста,
который ведёт доску через много попыток, начинает новую сессию с пакета, а не
с пересказа предыдущей: факты собираются из хранилища теми же проекциями, что
`status --detail` и `explain`, и только читают состояние.

- `summary`, `limits` — счёт поручений по статусам, `maxAttempts` и
  `repairBudget` политики;
- `queue`, `controller` — пауза выдачи, её причина и кто её снимает
  (`queueStop`, `queuePause`), операция, держащая паузу (`operation`), и
  классы отказа паузы runtime (`failures`); держатель роли controller и
  свежесть срока;
- `active` — идущие попытки: стадия и её длительность, heartbeat, gates
  текущей фазы (`attemptView`); `unfinished` — незакрытые записи попыток с
  истёкшим владением или такие, которые поручение уже не ведёт;
- `works` — открытые поручения (идущие, упавшие, план, остальные): класс и
  причина провала, удержание, эпизод восстановления с предложением,
  блокировки (без общей паузы очереди; сверх предела — `blockersTruncated`) и
  `next` — кто и что делает (по диагнозу `explain`; стадия и свойство — по
  `nextAction`);
- `stops` — диагнозы `explain` без проб runtime, кроме `action: none`.
  Отменённая работа (и упавшая с классом `cancelled`) — остановка
  (`CANCELLED`, lead `replan-dependents`), только пока от неё прямо зависит
  незавершённая работа (не `done` и не `cancelled`); ждущую через
  отменённую же промежуточную ведёт диагноз той. Без таких работ у
  отменённой действия нет (`action: none`): в общий `explain` и пакет она не
  входит, explain этой работы (`--work`) её показывает. Упавшая отменой
  открыта, а движок её не повторяет: без ждущих — решение человека (user
  `user-decision`: `harness retry` или отмена), шаг `nextAction` —
  `cancelled`. Любая отмена в группе останавливает её автоматическое
  восстановление: диагноз упавшей сестры называет отменённую работу.
  Остановка выдачи общей паузой очереди — одна запись с `queue: true` без
  `workId`; одинаковые остановки на выдаче у разных поручений тоже
  свёрнуты; `works` — первые 20 затронутых, `worksCount` — сколько всего.
  Решения (`actor` lead или user и действие не `wait`) идут первыми;
- `failures` — последние провалившиеся и истёкшие попытки, новые первыми:
  `failureKind`, код (`stopCodeOf`), текст ошибки и текущий статус
  поручения (`workStatus`);
- `budgets` — общий бюджет и бюджеты групп (с `--graph` — только его
  группа), бюджеты поручений — только с расходом или не в пределах и со
  своими вызовами (попытки, вызовы о поручении). Вызов о группе (ревью и
  проверка плана) засчитывается целиком бюджету каждого её открытого
  поручения (так действует ограничение поручения), но в строках группы и
  `total` — один раз; поручение, весь расход которого — такие вызовы, не
  перечисляется (`truncated.budgetsShared`), если только его строка не
  держит выдачу (превышена или не определена при `onUnknown: stop`): тогда
  она показана как ограничение поручения. Строка бюджета:
  сообщено (`reportedUsd`) и оценено (`estimatedUsd`) против предела, время,
  `complete` и причины неполноты (вызовы без стоимости, незавершённые,
  брошенные, попытки без учёта); при неполном расходе сумма — нижняя граница
  («≥ $X (неполно: …)» в Markdown), остаток — `null`. `repairs` —
  восстановления незавершённых заданий графов;
- `next` — следующий шаг доски: первое решение; иначе идущая попытка со
  свежим сроком владения — ждать (без controller — до `leaseUntil`); попытка
  с истёкшим сроком или очередь без controller — `command: "harness run"` (run истечёт брошенную
  попытку и продолжит очередь); пауза оператора — `"harness resume"`; иначе
  первый открытый шаг поручения;
- `intentions` — единственный текст не из хранилища: намерения агента.

Пределы (`HANDOFF_LIMITS`): 50 открытых поручений, 30 остановок (после
свёртки) с 5 ссылками evidence каждая, 10 провалов, 20 незавершённых
попыток, 3 блокировки на поручение, 20 строк бюджетов, 10 заданий, 20
намерений по 1000 знаков. Тексты из хранилища и намерения очищаются от
escape-последовательностей терминала (ANSI CSI, OSC), серия управляющих
символов заменяется пробелом; строки фактов усечены до 300 знаков, имена и
идентификаторы — до 200, с «…» и без разрыва суррогатной пары. Пакет не
больше `HANDOFF_MAX_BYTES` (256 КБ UTF-8): сверх него записи отбрасываются в
порядке «намерения с конца, старые провалы, поручения без решения,
остановки без решения, незавершённые попытки, остальные поручения и
остановки, строки бюджетов» (`truncated.bySize`), отказа по размеру нет.
Сколько записей каждого списка не вошло — `truncated`; бюджеты поручений в
пределах и без расхода не показываются намеренно и считаются отдельно
(`budgetsWithin`), как и бюджеты поручений только с расходом вызовов о
группе (`budgetsShared`), усечённые и отброшенные намерения — `intentions` и
`intentionsDropped`. Тексты из хранилища маскируются по значениям секретов
политики из окружения читающего процесса (`policySecrets`, как у
коннектора): секрет, которого в этом окружении нет, маска не знает —
библиотеке можно передать свою `redact`. Fencing-токены в пакет не
попадают.

**Хост.** Источник пакета — `HandoffSource`: `{ engine, policy, workflows }`,
где `engine` — `Engine` над хранилищем хоста, `policy` — его
`ExecutionPolicy`, `workflows` — `list()` заданий (пакет и диагнозы берут
задания `kind: "graph"`) и `continues(job, view, { reconfigureApplies })`,
продолжит ли очередь задание сама. `Harness` удовлетворяет типу структурно;
хост со своим движком передаёт свой адаптер заданий без экземпляра
`Harness`. Состояние доски над тем же источником — `statusOf(source,
graphId?, { detail })` (`Harness.status` — та же функция).

Параметры `handoffPack`: `graphId`, `intentions`, `redact`, а также
`maxBytes` — предел хоста в байтах UTF-8, целое от `HANDOFF_MIN_BYTES`
(4 КБ) до `HANDOFF_MAX_BYTES` (по умолчанию), иначе `INVALID_INPUT`; порядок
отбрасывания и счётчики `truncated` те же, что у предела по умолчанию, а
`bySize` значит «записи отброшены ради предела», а не «пакет уложился».
Сводка, очередь, идущие попытки, задания и `next` не отбрасываются, поэтому
уложиться не гарантируется: размер результата хост проверяет сам.
`HANDOFF_MIN_BYTES` — нижняя граница, ниже которой не помещается даже обычный
минимальный пакет, а не гарантия. `measure` — что укладывается в предел: `json` (по умолчанию) —
сериализованный пакет; `markdown` — и JSON, и `handoffMarkdown(pack)`
(Markdown бывает длиннее JSON: «|» в ячейке экранируется). Свой раздел
Markdown хост учитывает, уменьшая `maxBytes`. Маску из секретов политики и
своих значений хост составляет из `policySecrets(policy, env?)`,
`redactor` и `composeRedactors` корня пакета.

**Диагноз по состоянию.** `stopInputsOf(source, { maxAttempts,
repairBudget, workId?, workIds? })` из корня пакета (источник тот же —
`StopSource`) даёт входы `explainStop` за одно чтение. Без выбора — доска:
отменённая работа, которую никто не ждёт, в неё не входит. `workId` — одна
работа (её показывает и отменённую). `workIds` — набор: входы каждой работы
те же, что у вызова с её `workId` (в том числе отменённой без ждущих), в
порядке состояния независимо от порядка в запросе; вход роли controller —
первым, запросы ведущему — после работ. Неизвестная работа — `NOT_FOUND`,
`workId` вместе с `workIds` — `INVALID_INPUT`, пустой набор — без работ.
Общее для работ (прогноз групп, обратные зависимости, запросы, попытки,
записи вызовов, статусы бюджетов) читается один раз за вызов: набор и доска
линейны по числу работ. Порты хоста по-прежнему спрашиваются о каждой
работе: `basis.orderDigest`, `guards.claimable`, `budgets.groupOf` при
пределе группы и `budgets.members` для прежних записей вызовов без
закреплённой группы (`subjectId` без `groupId`, которые не закрепил
`pinLegacyCalls`). Бюджетные блоки многих работ хост получает из
`Engine.budgetBlocksOf(workIds | undefined, view)`: за одно чтение, для
набора или (без `workIds`) всех работ вида — `Map` работа → причина или
`undefined`, по каждой то же, что `budgetBlockOf(workId, view)` на момент
вызова. `budgetBlockOf(workId, view, records?)` принимает уже прочитанные
записи вызовов, `repairDecision(view, works, { budgetLeft, maxAttempts,
blocking? })` — вопрос, держащий работу (по умолчанию `blockingRequest`).
`Engine.budgetBlockers(view)` и `Engine.approvalStaleness(view)` —
внутренние помощники диагноза: функция, которую они возвращают, считает
общее один раз на момент создания (`at` бюджетов фиксирован) и верна
только внутри того же чтения; хост их не держит между чтениями и
пользуется `budgetBlocksOf` и `stopInputsOf`.

Весь пакет — один снимок хранилища: `handoffPack` выполняет status,
диагнозы и чтение заданий графов внутри одного `read`
(`SqliteExecutionStore.read` вложенным чтением использует снимок внешнего,
без второго `BEGIN`). Попытка со свежим сроком владения без живого
controller — `next` «ждать до `leaseUntil` или проверить процесс-владелец»
без команды; `harness run` называется только для попытки с истёкшим сроком.

`Runner` принимает от хоста: `context(work)` — снимок контекста, в том числе
асинхронно; `stateDirFor(repositoryId)` — каталог артефактов попыток
репозитория (без него — `stateDir`), а при прежнем размещении и их рабочих
деревьев; `checkoutRoot` — корень рабочих деревьев, снимков зависимостей и
деревьев проверок потребителей (`<checkoutRoot>/<repositoryId>/worktrees/<runId>`
и т. д.; так же — `checkoutRoot` у `Harness`, `JointRunner`, `runGatesAt` и
`moveBase`). Без него корень выбирает `chooseCheckoutRoot`: каталог состояния
внутри репозитория политики или закрытого песочницей пути — кэш пользователя
вне дерева (macOS `~/Library/Caches/devcontour-harness/<hash>`, Linux
`$XDG_CACHE_HOME` или `~/.cache/devcontour-harness/<hash>`, `<hash>` —
устойчивый хэш каталога состояния), иначе прежнее место. Кэш на другом томе,
чем репозиторий, корень внутри репозитория, закрытого пути или каталога
состояния, каталог-ссылка или чужой каталог — прежнее место и пояснение
(`note`; заданный хостом такой корень — `INVALID_INPUT`). Корень закрыт
песочнице целиком, свои деревья проверки открыты; корни кэша не убираются при
переносе workspace — их удаляют вручную; `Runner.checkoutRoot()`
и `doctor` называют действующий корень. Корень лучше держать на томе
репозиториев: менеджеры пакетов ставят зависимости жёсткими ссылками и reflink;
`hooks` — точки расширения, которые добавляют сведения хоста, но не решают
приёмку: `prepared({work, attempt, baseSha})` — база известна, работа не
начата (отказ — отказ попытки, `BlockedError` — отказ окружения);
`notes({work, attempt, review})` — дополнения запроса writer или reviewer;
`implemented({attempt, output, sha})` — отчёт writer закоммичен кандидатом;
`failed({attempt, kind, message})` — отказ записан движком. `settled()` ждёт
выданные попытки — хост ведёт свой цикл поверх `tick`. `Engine.expire(at)`
снимает владение, истекающее к моменту `at`. Попытка записывает замеры стадий
(`implementation`, `<фаза>-test:<gate>`, `<фаза>-consumer:<репозиторий>:<gate>`,
`<фаза>-review`, `<фаза>-environment:<шаг>`, `integration-wait`) и сохраняет
снимок контекста артефактом `implementation/context.json`. Отказ приёмки с
кодом `GATE_FAILED`, `REVIEW_REJECTED`, `REVIEW_PROTOCOL_INVALID`,
`SCOPE_VIOLATION` или `BUDGET_EXHAUSTED` записывается классом отказа этого
правила.

Хост, ведущий движок поверх своего хранилища, собирает исполнение из
экспортов корня пакета: `Engine`, `Runner`, `WorkflowQueue`, `JointRunner`,
`moveBase`/`fencedRefMove`, `runGate`/`runCheck` (и разбор отчёта
`junitSummary`, `prepareReportPath`, `sandboxBlockedHosts`), `unprovenReason`,
`ReviewProbes`, маскирование (`redactor`, `redactDeep`, `redactError`),
git хоста над checkout с чужим кодом (`hostGitArgs`, `assertTrustedCheckout`,
`UntrustedCheckoutError`, `gitHardening`, учёт деревьев `rememberWorktree`/
`forgetWorktree`/`worktreeKey`/`worktreeAddPath`, `resetGitTrust` для тестов),
корпус (`CorpusStore`, подтверждение случая `submitCase` с `ConfirmContext`),
ограниченный разбор по свойству (`analyzeRecovery`, `applyCases`,
`recoveryBrief`; назначение хоста — модель и профиль ведущего — передаётся
`binding`, его дополнительные границы — `boundary`), проверка
переносимого результата (`resultProblems`), классы и правила отказов
(`BlockedError`, `TaskFailure`, `classifyFailure`, `failureFingerprint`,
`repairPolicy`, `repairRepeats` — повторы одного отпечатка с учётом предела
окна контекста, `lastContextLimit` — предел последней попытки с отказом,
`repairDecision`), раунд технического ревью
(`technicalReview`), точка сбоя подтверждения корпуса для тестов
(`caseHooks`). Глубокие импорты `lib/...` не поддерживаются.

Очередь технических заданий хоста — `new WorkflowQueue(store, policy, now,
subjects)`: `subjects.input(kind, id, view)` задаёт digest входа и владельца
задания для предметов хоста (доска, набор изменений); задание хранится за
этим владельцем, недопустимый вход (`HarnessError`) отклоняет постановку его
текстом и делает поставленное задание устаревшим, смена владельца — тоже.
Число стадий задаёт `finish(job, wait, stages)`.

### StackProfile

Переносимый профиль стека (`schemas/stack-profile.schema.json`):
`{id, version, extends[], capabilities[], gates[], prepare[], environment?, lifecycle?, protectedPaths[], generatedPaths[], concurrency?, runTimeoutMs?, roles{}, contextPacks[]}`.
`extends` — встроенный ID (`profiles/<id>.json` пакета) или относительный
`./file.json` внутри репозитория; не глубже 16 слоёв и не больше 32 файлов,
без symlink и выхода за корень, файл до 128 KiB. `resolveProfile` только
читает манифесты: gates, подготовка, возможности и пути складываются,
окружение и lifecycle задаёт один слой (иначе конфликт), параллельность —
наименьшая, время попытки — наибольшее, роли и `contextPacks` — по ID.
Итог обязан иметь test gate с JUnit; `requirement-source` зарезервирован.
Файлы локальных слоёв становятся защищёнными путями. Digest: один встроенный
файл — sha256 его байтов (так закреплены прежние потребители, встроенные
профили перенесены побайтно), иначе — sha256 замыкания `[{ref, digest}]`.
`repositoryFromProfile` собирает описание репозитория политики (собственные
значения сильнее, переопределённые поля названы в `shadowed`),
`profileRoles` — роли в форме политики. Хост, у которого закреплены профили
своей формы (другие runtime ролей, свои поля, нестрогие вложенные объекты),
передаёт `resolveProfile(ref, { layerSchema })` — схему Zod своего файла:
она разбирает каждый слой вместо `StackProfile`, а gates, шаги, роли и
`contextPacks` остаются в её форме. Безопасность файлов, обход `extends`,
сложение слоёв, проверки gates (в том числе путь JUnit — относительный, внутри
worktree) и digest — прежние; слой, который не даёт
полей сложения (`ProfileLayer`), и не-Zod `layerSchema` — `INVALID_INPUT`.
`contextPacks` — инструкции стека для
хоста: harness их не читает, закрепляет их `ContextSource`. Встроенные
профили сохраняют имена скриптов проекта, которые закреплены у прежних
потребителей (например, `npm run test:devcontour`); для другого проекта
подходит локальный профиль.

Полная форма каждой команды — `cliCommands` (аргументы, обязательность,
идемпотентность, отказы exit 3). Все команды реализованы. `run` принимает `--author` (по умолчанию `external`) — автора графа для ревью плана. `HARNESS_CODEX_BIN` и `HARNESS_CLAUDE_BIN` подменяют исполняемые файлы runtime (fixture executables в тестах).
`init --plan` ничего не пишет (exit 3 при конфликтах или неготовом toolchain). `--human` принимают только `init`, `explain` и `plan-request` (печатает prompt): успешный ответ — текст для человека, отказ — тот же JSON-конверт, exit code одинаков; у прочих команд флаг — `INVALID_INPUT`. `plan-check` с проблемами отвечает `ok: true` с данными, exit — по классу первой проблемы; draft — `schemas/plan-draft.schema.json` (`planDraftSchema`). Маршрут самостоятельного проекта и планирование — [standalone](standalone.md).

**`report`.** Читает каталог состояния только для чтения и строит
`ValueReport` (`valueReport`); `binding.json` не нужен. Чтение однократное
(`SqliteExecutionStore.readOnce`): база без журнала (`-wal`, `-journal`)
открывается неизменяемой (`immutable=1`) — в каталоге не появляется ни одного
файла; после чтения проверяется, что журнал не появился, а размер и время
основного файла прежние, иначе (писатель начал работу или журнал уже был)
чтение повторяется обычным открытием только для чтения. Долгоживущие
дескрипторы (`status`, `events`, `result`, `explain`, `Harness.open` с
`readOnlyState`) открываются обычным чтением: с блокировками SQLite они
видят новые фиксации, а у WAL-базы появляются пустые служебные
`-wal`/`-shm` (данных в них нет). `--format json` (по умолчанию) — обычный конверт. `--format
md|html` — документированное исключение, как `--human`: успешный ответ
печатается текстом без конверта (данные перед этим проверены схемой), отказ
— тот же JSON-конверт и тот же exit code. `--out F` записывает отчёт
выбранного формата во временный файл того же каталога и переименовывает
его поверх цели (запись не идёт сквозь symlink или жёсткую ссылку; права
прежнего файла сохраняются, новый — `0600`; при неполной записи временный
файл удаляется);
`PATH_CONFLICT` — цель не обычный файл, symlink, файл с несколькими жёсткими
ссылками или путь внутри каталога состояния; отсутствующий каталог —
`INVALID_INPUT`; stdout — конверт `{out, format, bytes, asOf}`. Неверное
окно (`--since` не раньше `--until`, время без пояса) — `INVALID_INPUT`;
нет каталога — `NOT_FOUND`, каталог не создаётся. Флаги `--since`,
`--until`, `--as-of`, `--no-titles` принимает только `report` (`--format` — ещё
`handoff`, со значениями json и md).
Пределы размера (JSON 512 КБ, HTML и Markdown 1 МБ) проверяют сами
`valueReport` и рендеры (`assertReportBytes`, `INTERNAL`).

**`handoff`.** Открывает каталог состояния только для чтения (политика — из
`binding.json`, как у `status`) и строит `HandoffPack`. `--format json` (по
умолчанию) — обычный конверт; `--format md` — документированное исключение,
как у `report`: успешный ответ печатается Markdown без конверта. Отказ —
JSON-конверт в обоих режимах; нет каталога — `NOT_FOUND`, каталог не
создаётся; неизвестный `--graph` — `NOT_FOUND`; больше 20 `--intent` или
`--format` не json/md — `INVALID_INPUT`. `--intent` принимает только
`handoff`, `--format` — `report` и `handoff`.

**Причина отказа окружения `dependency-network`.** Установка зависимостей,
упавшая на сети или реестре пакетов, получает класс `environment`, а не `gate`
(правило — [архитектура](architecture.md#что-гарантируется), «Сеть и реестр при установке зависимостей»). Отдельного поля
причины нет: схема состояния прежняя, а `failureKind` — `environment`.
Причину несёт начало текста отказа: `<фаза>/<gate>: dependency-network: …` у
gate, `dependency-network: … Шаг <id>: …` у шага `prepare`. Текст
попадает в `WorkState.failure`, `AttemptState.error`, `summary` evidence gate и в
`message` диагноза `explain` (`cause: environment`, `action: fix-environment`).
У reviewer probe такой gate — `status: error`, `failure: environment`, `note`
начинается с `dependency-network:`. Хост, который сам вызывает `runGate`,
передаёт базу попытки в необязательном `GateRun.trustedBase`: без неё
классификации нет и отказ остаётся `gate`. То же поле есть в описании probe
(`trustedBase`).

**`status --detail`.** Без флага ответ `status` прежний. С флагом добавляется
`detail: {at, queue, attempts}` — снимок наблюдателя по часам движка:

- `queue` — почему стоит выдача: `paused`, `reason` и `detail` (`queueStop`;
  у паузы отказа runtime `detail` — сообщение последнего отказа её классов),
  `since`, `operation`, `failures` (классы отказа паузы runtime) и кто и что её
  снимает — `code`, `cause`, `actor`, `action` (`queuePause`, то же
  рассуждение, что у `explain` на claim). Паузу, которую снимет следующий
  run (очередь ещё не запускали, штатная остановка, применимый запрос
  политики), `explain` считает снятой; `queue` показывает её с
  `liftedByRun: true` и тем же диагнозом, что у готового поручения в
  `explain`: `NOT_READY`, `not-ready`, `controller`, `wait`.
- `attempts[]` — активные попытки (`attemptView`): `runId`, `workId`,
  `attempt`, `phase`, `runtime`, `model?`, `startedAt`, `elapsedMs`; `stage`
  — последний незакрытый замер (`name`, `family` — имя до `:`, `startedAt`,
  `elapsedMs`; при равном начале — позже записанный); `lease` — `owner`,
  `leaseUntil`, `leaseMs`, `sinceHeartbeatMs` (от последнего heartbeat,
  `leaseUntil − leaseMs`; нет при сроке `0` — владение отозвано) и `stale`
  (срок истёк). `leaseMs` — из политики процесса, который читает: у CLI —
  `binding.json` каталога состояния. `gates` — обязательные gates текущей фазы
  (интеграции в `integrating`, иначе кандидата) по последней записи каждого на
  текущем SHA фазы, без проверок потребителей: `passed + failed + remaining =
required`.

`attemptView` и `queuePause` — чистые проекции `devcontour-harness/projections`:
хост строит тот же вид по своей попытке.

**Общие операции и граница транспорта.** `init`, `explain`, `plan-request`,
`plan-check` и `capabilities` — общие операции агентского слоя
(`sharedOperations`): описание, `readOnly` (= `!writes`), вход (по `args`) и
схема ответа (`cliDataSchemas`) берутся из одной декларации — договора CLI;
`capabilities` возвращает их каталог (`operationCatalog`, тот же построитель,
что у каталога хоста). У этих команд CLI проверяет UTF-8 байты: значения
аргументов больше `maxInputBytes` (100000) — `INVALID_INPUT` с путём `argv`;
конверт ответа больше `maxResultBytes` (1048576) — `RESPONSE_TOO_LARGE`, exit
2, данные не усекаются, и с `--human` тот же JSON. Содержимое файлов-входов и
прочие команды граница не ограничивает. Усечение строк (`clipText`,
`clipDeep`) — отдельная операция и размер объекта не ограничивает; страницы с
cursor — `pageItems`, байты — `jsonBytes`/`checkJsonBytes`/`utf8Bytes`.
После приёмки договора имена и параметры меняются только совместимо или
отдельным согласованным изменением.
