# Договоры devcontour-harness

Источник истины — Zod-схемы в `src/contracts`. TypeScript-типы экспортируются
из `devcontour-harness` и `devcontour-harness/contracts`.

## JSON Schema и семантическая проверка

`schemas/<имя>.schema.json` генерируется из тех же схем (`npm run schemas`);
`npm run check` падает, если закоммиченные файлы устарели, а тест паритета
сверяет вердикты Zod и JSON Schema (Ajv, draft 2020-12) на положительных и
отрицательных примерах.

Harness не нормализует значения: строки вроде `title`, `goal`, критериев и
значений ресурсов обязаны быть уже без пробелов по краям — правило выражено
регулярным выражением и одинаково в Zod и JSON Schema.

Программная проверка доступна из `devcontour-harness`: `validateInputs`
(то же, что `harness validate`) и отдельные функции ниже.

JSON Schema выражает всё, что относится к одному значению: типы,
обязательность, закрытость объектов, пределы, регулярные выражения путей и
refs, варианты исходов. Связи **между** значениями проверяются только
функциями пакета и `harness validate`:

| Функция         | Что проверяет                                                                                                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `graphIssues`   | Повтор ID, неизвестная зависимость, цикл графа                                                                               |
| `policyIssues`  | Циклы компонентов и gates, test gate у репозитория, ресурсы, профили инструментов, `effort`, `fixture`, пары writer/reviewer |
| `crossIssues`   | Связь поручений с политикой: роль, ресурсы, область записи и доказательства, требования, потребители, предпосылки            |
| `contextIssues` | Содержимое снимка контекста совпадает с digests и пределами                                                                  |
| `reviewIssues`  | Ответ reviewer согласован с историей находок предмета                                                                        |

Опубликованы: `work-order`, `work-graph`, `execution-policy`,
`context-snapshot`, `contract-document`, `run-result`, `result-envelope`,
`run-event`, `review-record`, `joint-verification`, `execution-document`,
`value-report` (отчёт `harness report`, см. «ValueReport»), `handoff-pack`
(пакет `harness handoff`, см. «HandoffPack»).

## Версии

| Версия        | Значение                           | Поле / константа            |
| ------------- | ---------------------------------- | --------------------------- |
| Пакет         | `0.1.0-alpha.N` до стабильного API | `HARNESS_VERSION`           |
| Публичный API | `devcontour-harness/v1alpha1`      | `apiVersion`, `API_VERSION` |
| Политика      | `1`                                | `policyVersion`             |
| Состояние     | `1`                                | `stateVersion`              |

Версии независимы. Пакет читает только перечисленные в
`SUPPORTED_*_VERSIONS`; неизвестная версия входа, политики или состояния
отклоняется до любой мутации и до выдачи claim. Для `0.x`: patch — совместимые
исправления, minor — отдельно описанные изменения договора, включая
несовместимые. Выпущенная версия неизменяема.

Digests (`workGraphDigest`, `policyDigest`, `sourceDigest`, `findingId`) —
SHA-256 канонического JSON (`canonicalJson`: ключи по порядку, `undefined`
опускается). Формула — часть договора; тесты закрепляют эталонные значения.

## Входы

### WorkOrder

Исполняемое поручение — снимок постановки, а не редактируемая задача. Лишние
поля отклоняются: поручение не несёт статуса, результата или согласования.

| Поле               | Смысл                                                                                                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `apiVersion`, `id` | Версия договора и ID                                                                                                                                                                                                     |
| `source`           | `{connector, ref, revision}` — откуда и какая редакция                                                                                                                                                                   |
| `title`, `goal`    | Название и цель                                                                                                                                                                                                          |
| `acceptance[]`     | Критерии приёмки (1–30)                                                                                                                                                                                                  |
| `role`             | Роль из политики                                                                                                                                                                                                         |
| `repositoryId`     | Репозиторий из политики; `relatedRepositories[]` — поручение уровня workspace (минимум два)                                                                                                                              |
| `writeScope[]`     | Область записи: относительные пути без glob, `.`/`..`; пересекается с областью роли; `["."]` — весь репозиторий (только как единственный элемент; защищённые, генерируемые пути и область роли по-прежнему ограничивают) |
| `dependsOn[]`      | Поручения графа или подтверждённые предпосылки                                                                                                                                                                           |
| `gates[]`          | Область доказательства: gates и группы `@имя`, замкнута по `dependsOn`, содержит test gate; нет поля — все gates                                                                                                         |
| `consumers[]`      | Потребители (зависят от репозитория поручения) и их gates                                                                                                                                                                |
| `properties[]`     | Свойства договора проверки, подтверждаемые сейчас                                                                                                                                                                        |
| `resources[]`      | Ресурсы политики                                                                                                                                                                                                         |
| `requirements[]`   | Требование: текст, его SHA-256, test gate из области, testcase                                                                                                                                                           |
| `contracts[]`      | `{id, digest}` закреплённых контрактов                                                                                                                                                                                   |
| `context[]`        | ID обязательных источников контекста                                                                                                                                                                                     |
| `kind`             | alpha.67: `infra` — работа инфраструктуры harness в `repositories[].infra.paths` ([работы инфраструктуры](infra-works.md)); нет поля — продуктовая работа, digest прежних поручений не меняется                          |
| `gateChanges[]`    | alpha.67, только `kind: infra`: существующие файлы gates, которые работа меняет; входит в digest графа — изменение определения gate согласует ревью плана                                                                |

### WorkGraph

`{apiVersion, id, source, orders[], prerequisites[]}` — неизменяемый снимок
состава и зависимостей одного согласования; `workGraphDigest` закрепляет
согласование. Предпосылка — `{id, repositoryId, resultSha, receipt}`,
`receipt` — `{kind: 'engine', runId}` или `{kind: 'trusted', issuer, digest}`.
Доверие к `trusted` решает `WorkSource.trusts`: `Harness.run({ source })`
спрашивает источник графа (его `id` обязан совпасть с `graph.source.connector`);
без источника доверенных receipt нет. В обоих случаях движок проверяет, что
result SHA доступен в target ref. Коннектор задач выдаёт `trusted` и для
явной записи человека (`baseline`, см. [connectors.md](connectors.md)): форма
предпосылки та же, происхождение (`proof: 'receipt' | 'baseline'`) записано в
manifest снимка и в необязательном поле `baseline` ответов `source-snapshot`,
`source-status` и `run --source`.

Переменные `HARNESS_*` и `DEVCONTOUR_*` политика задать не может.

`repositories[].dependencyStore` — необязательное хранилище зависимостей
репозитория: `{manager: 'pnpm', lockfile, maxBytes, timeoutMs}`. Умолчания:
`pnpm-lock.yaml`, 8 ГиБ, 600 000 мс. Без поля поведение и digest политики прежние.
С полем harness сам держит seed по lockfile `targetRef` и разворачивает его в
каждый checkout: попытка, integration, потребители, `runGatesAt`, проверка
примера, снимки с `dependencyBuild` и совместная проверка, где `prepare` нет.
Проекту не нужны ни свой скрипт, ни шаг `prepare`, ни запись в `.gitignore`;
gate установки остаётся обычным `pnpm install --frozen-lockfile`.
Подробности и граница доверия — [toolchains](toolchains.md#хранилище-зависимостей).

`repositories[].writerDependencies` — необязательное: `false` выключает установку зависимостей
в дереве исполнителя до его работы (gates установки попытки под изоляцией gate, без evidence,
стадия `writer-dependencies` в `timings`). Нет поля — включено, умолчание не подставляется и
digest политики не меняет. Подробно — [toolchains](toolchains.md#зависимости-исполнителя).

`repositories[].writerProbe` — необязательный список (не больше 20) шагов `{id, command[],
timeoutMs?}`: команды, которые правила проекта требуют от исполнителя. Их прогоняет только
`harness smoke --writer-probe` в изоляции исполнителя, без модели; попытки и gates на них не
смотрят. Нет поля — digest политики прежний.

`repositories[].previews` — необязательный список (до 10, ID без повторов) превью результата
`{id, title?, build?[], start[], cwd?, env?, services?, health?, readyTimeoutMs?, ttlMs?,
idleMs?}`: как собрать и запустить приложение на принятом коммите, чтобы человек посмотрел
результат. Запускает только оператор (`harness preview-start`), никогда — `run`, попытка или
gate. В `executionDigest` и `isolationDigest` не входит; нет поля — digest политики прежний.
Подробно — [превью](previews.md).

`repositories[].infra` — необязательная область инфраструктуры `{paths[]}` (до 32 путей,
alpha.67): пути, которые меняют только работы `kind: infra`. Пути лежат внутри
`protectedPaths`, не покрывают корни доверия (`.harness/policy.json`, `profile.json`,
`connector.json`, `project.json`, `updates.json`, `.harness/work/`, `.harness-tools/` и др.) и
файлы шагов на хосте (`lifecycle`, `prepare`, `dependencyBuild`, `preflight`, генераторы).
Входит в `isolationDigest` (смена — новое ревью плана); нет поля — digest политики прежний.
Подробно — [работы инфраструктуры](infra-works.md).

`toolProfiles.<id>.network` — необязательная сеть исполнителя профиля: `none`, `loopback` или
`full`. Нет поля — прежнее: codex — по `codexNetwork` (`true` — вся сеть, иначе закрыта), claude —
домены `isolation.domains` и локальные порты; умолчание не подставляется и digest политики не
меняет. Поле входит в `isolationDigest`: его смена требует нового ревью плана, `approve` и
`reapprove` под прежним одобрением отказывают. Ревьюер сети профиля не получает.

| Режим      | codex                                                                                                                                                                                                    | claude                                                         |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `none`     | `network={enabled=false}`                                                                                                                                                                                | без доменов, `allowLocalBinding: false`                        |
| `loopback` | `features.network_proxy=true` и `network={enabled=true, mode="limited", domains={}, allow_local_binding=true, allow_upstream_proxy=false, …}`: прокси сети codex без доменов, listen/connect на loopback | без доменов, `allowLocalBinding: true`                         |
| `full`     | `network={enabled=true}`, как `codexNetwork: true`                                                                                                                                                       | отклоняется: внешние адреса claude — через `isolation.domains` |

`loopback` — локальный сервер для проверок (dev-сервер и браузер против него) без интернета:
listen и connect на 127.0.0.1 и ::1, внешние адреса закрыты и в обход прокси. Проверка
политики (`INVALID_INPUT`) отклоняет `network: none` или `loopback` вместе с `codexNetwork: true` и
`network: full` у claude. Codex без функции `network_proxy` (её нет в `codex features list` или она
`removed`) прочёл бы `enabled=true` как всю сеть, а неизвестную функцию пропускает молча: такой
вызов исполнителя отклоняется до запуска, проба исполнителя (`--writer-probe`) называет шаги
`blocked` с причиной `environment`. Определённый ответ `codex features list` запоминается на
процесс; сбой запуска, предел времени или ненулевой код называются сбоем проверки (вызов тоже не
запускается) и при следующем вызове проверяются заново. Проба сообщает режим в
`writers[].networkMode` (`none`, `loopback`, `full`; `legacy` — профиль без поля `network`: граница прежняя, сетевые инструменты runtime явно не закрыты), а у исполнителя codex с
`loopback` первой строкой исполняет проверку границы `harness-loopback-check` (без модели) в
`codex sandbox` с теми же аргументами: локальный сервер на 127.0.0.1 должен отвечать, а
соединение с внешним IP напрямую и `CONNECT` через прокси из окружения — не проходить. Открытый
внешний адрес — `blocked` с причиной `network-open`; закрытый loopback — `listen-denied`. Без
сети у хоста проверка внешнего адреса ничего не доказывает и проходит.

Пустой список доменов codex задаётся явно (`domains={}` заменяет домены из другого слоя
конфигурации), с режимом прокси `limited` и без цепочки к прокси хоста (`allow_upstream_proxy=false`).
Запретить всё правилом нельзя: codex 0.165 не принимает `"*"="deny"`. Поэтому граница опирается на
смысл пустого списка у прокси codex. Вызов исполнителя идёт с `--ignore-user-config`, и
пользовательская конфигурация codex доменов не добавит. Управляемые требования организации
(`requirements.toml`) и будущая версия codex, у которой пустой список значит «всё разрешено», —
вне контроля harness. Их ловит только проверка границы в `--writer-probe`, а при попытках она не
повторяется: после обновления codex прогоните пробу снова.

Режимы `none` и `loopback` закрывают и встроенные сетевые инструменты runtime, которые работают
мимо песочницы shell: codex получает `web_search="disabled"`, claude — `--disallowedTools
WebFetch,WebSearch`; правило `WebFetch` или `WebSearch` в `claudeAllowedTools` такого профиля
отклоняется проверкой политики. Без поля `network` вызов прежний. MCP-серверы профиля (`mcp{}`)
— вне этой границы: их процессы запускает CLI runtime вне песочницы shell, и сеть они получают
как процессы хоста. Режим сети их не ограничивает: в профиль без интернета включайте только
серверы, которым сеть не нужна или чья граница задана самим сервером.

Пределы по платформам. **macOS (Seatbelt):** `loopback` открывает bind на любом локальном адресе и
connect только на loopback — сервер, поднятый одной командой или процессом хоста, доступен
следующей; `none` закрывает и listen. **Linux (bubblewrap):** у команды своя сеть с одним
loopback: сервер и клиент должны быть в одном процессном дереве (одна команда shell); сервер хоста
и сервер из прошлой команды исполнителя недоступны, а `none` не закрывает loopback внутри
команды. У codex на Linux режим `loopback` в harness не проверен: результат показывает
`harness smoke --writer-probe`. Gates harness, как прежде, исполняются со своими локальными
портами.

`repositories[].generators` — необязательный список (не больше 10) генераторов
закоммиченных выходов: `{id, command[], cwd?, timeoutMs?, inputs[], outputs[], tool[]}`.
Нет поля — поведение и digest политики прежние; умолчание не подставляется.
Генератор нужен, когда выход генерации лежит в области записи другой роли:
данные правит одна роль, модуль из них строит скрипт другой, а общий gate
сверяет их между собой.

- **Поля.** `id` — `[A-Za-z0-9_-]{1,60}`; `command` — непустой argv; `cwd` —
  каталог команды относительно корня дерева (нет — корень); `timeoutMs` —
  предел команды (по умолчанию 120 000 мс, поднимается `gateTimeoutFloorMs`);
  `inputs` (1–64), `outputs` (1–64), `tool` (0–64, по умолчанию `[]`) — пути
  относительно корня репозитория. Совпадение — путь или префикс каталога, как
  у `writePaths`.
- **Согласованность** (`policyIssues`, отдельно — `generatorIssues(repo, path?)`,
  код `INVALID_INPUT`): ID уникальны; выходы разных генераторов не
  пересекаются; выход не пересекает вход или инструмент любого генератора
  (цепочек нет: порядок исполнения не влияет на результат), `protectedPaths` и
  служебные каталоги `.devcontour`, `.harness`, `.git`. Пересечение
  сравнивается без учёта регистра (`pathsOverlap`). Выход внутри
  `generatedPaths` допустим: исполнитель его не правит, а генератор пишет.
- **Кандидат.** После ответа исполнителя controller индексирует дерево
  (`git add -A`) и выбирает генераторы, чьи `inputs`, `tool` или `outputs`
  задевает настоящий diff. Только для готовой работы: при вопросе или
  незавершённости генераторы не исполняются, и ручная правка выхода
  проверяется областью как любая правка исполнителя. Каждый выбранный — по
  порядку политики, с изоляцией и окружением gate фазы (`runCheck`: запись
  только в дерево, граница, сеть `isolation.domains`, сверка защищённых
  путей), стадия `generate:<id>` в `timings`. Перед генерацией предел времени
  фазы (`runTimeoutMs`) начинается заново: генерация не расходует время
  исполнителя. Поэтому общий предел попытки с генератором выше на одну фазу:
  реализация, генерация, проверки и ревью кандидата, интеграция — каждая со
  своим `runTimeoutMs`.
  Зависимости проекта генератор получает от установки в дереве исполнителя
  (`writerDependencies`); при `writerDependencies: false` — только от
  `prepare` или `dependencyStore`. Перед запуском отслеживаемые файлы
  выходов удаляются: выход — целиком результат генератора, ручная правка
  исполнителя и лишний файл в каталоге выхода перезаписываются. Затем дерево
  сравнивается с деревом до генератора. Сверка видит отслеживаемые и
  неигнорируемые пути: путь вне `outputs` — `scope-violation` «Генератор <id>
  изменил пути вне своих выходов: …»; файл внутри `outputs`, скрытый
  `.gitignore` (в коммит он бы не попал), который генератор создал или изменил
  (сверка содержимого до и после запуска), — `gate` «Генератор <id> записал в
  выход файлы, скрытые .gitignore …»; игнорируемое, бывшее в выходе до
  генератора (`node_modules` пакета workspace от gate установки, кэши сборки),
  отказом не считается, а игнорируемый каталог сверяется только наличием:
  запись внутрь уже существующего не видна; символическая ссылка в выходе —
  `scope-violation`. Игнорируемые файлы вне выходов (кэши, `node_modules`)
  не сверяются. Выходы исполненных генераторов снимают для этих путей
  проверку `protectedPaths`/`generatedPaths` и области поручения и роли;
  закреплённый контекст и артефакты контрактов остаются защищёнными.
  Остальное проверяется как прежде; кандидат — по-прежнему один коммит.
- **Отказы команды.** Ненулевой код выхода — `gate` «Генератор <id> не
  выполнился: exit=N: …»; превышение предела и отсутствующий в дереве `cwd` —
  `gate`; песочница не запустила команду — `environment`/`sandbox-launch`;
  созданный защищённый путь или сменённый HEAD (коммит генератора) —
  `scope-violation`; отмена — как у прочих стадий.
- **Взятый кандидат и integration.** На взятом кандидате (стадия
  `generate:<id>`) и после слияния на integration (стадия
  `integration-generate:<id>`) генераторы, выбранные по diff кандидата,
  исполняются заново сразу после последнего применимого gate установки
  зависимостей фазы и обязаны не изменить выходы. Без применимого gate
  установки (его нет или он пропущен по `when.paths`) проверка идёт до первого
  gate, и зависимости генератор получает только от `prepare` или
  `dependencyStore`. Свежесть выхода сверяется только в этой точке: gate,
  поставленный в порядке области до установки, видит ещё не проверенный выход
  и при устаревшем выходе отказывает классом `gate`, а не `merge`. Генератор
  изменил выход — отказ класса `merge` «Генератор <id>: закоммиченный
  выход устарел на этой базе …»: повтор по таблице восстановления
  ответвляется от новой базы, переносит правку исполнителя черновиком и
  строит выход заново. Индекс после проверки при любом исходе возвращается
  к коммиту фазы; неотслеживаемые файлы подготовки остаются
  неотслеживаемыми.
- **Наблюдаемость.** `<артефакты попытки>/<candidate|integration>/generate/`:
  журнал `<id>.log` (первая строка — cwd, argv и режим) и квитанция
  `generators.json` `{mode: 'write' | 'verify', generators: [{id, changed[],
exitCode, durationMs}]}`. Запрос исполнителя называет генераторы и их выходы.
- **Экспорт.** Схема `generatorSchema`, тип `GeneratorPolicy`,
  `MAX_GENERATORS`, `generatorIssues`, `pathsOverlap`; исполнение —
  `selectGenerators`, `runGenerators`, `generatorNote`, типы
  `GeneratorOutcome`, `GeneratorsRun`; решение области — `scopeViolations`,
  `ScopeRules`.

Квитанция `dependency-store.json` лежит в артефактах фазы: `outcome`
(`hit` — lockfile checkout равен lockfile seed; `partial` — seed другого
lockfile, установка докачивает разницу; `miss` — обычная установка), `seed`,
`mode` (`clone` или `copy`), `built`, `files`, `bytes`, `durationMs`, `reason`,
`refused[]`, `sources` (alpha.64, у seed, собранного этим вызовом: `packages`, `host`, `base`,
`network`, `hostStore`, `hostReason`, `retries` — [toolchains](toolchains.md#пакеты-из-store-хоста-alpha64)).
`GatesAtContext.retryStoreNetworkFailure` (и `retryStoreNetworkFailure` у `smokeLifecycle` и
`checkGates`; CLI `smoke` и `gates` его задают) — сборка, недавно упавшая из-за сети реестра,
повторяется сразу. Попытка получает этап `dependency-store` в `timings`. Экспорт:
`materializeStore`, `dependencyStoreRoot`, типы `StoreContext`, `StoreReceipt`. `StoreContext.deadline` — момент окончания времени фазы, `phaseMs` — полная длина её предела: сборка и ожидание чужой сборки занимают не больше трети остатка.
Исключение `materializeStore` бросает только при отмене переданного `signal`. Коды `doctor`:
предупреждения `LOCKFILE_MISSING`, `TOOL_MISSING`, `DEPENDENCY_STORE`.

`repositories[].gates[].artifacts` — необязательный список (1–16) путей
относительно корня дерева: файлы или каталоги, которые gate оставляет как
доказательство (например, снимки экрана визуального теста). Без поля поведение
и digest политики прежние. Повторы и пути внутри уже объявленного каталога
объединяются. После gate — и при успехе, и при провале — harness копирует
подходящие файлы в `<артефакты фазы>/<gate>.artifacts/<путь>` (в ID gate точки
нет, поэтому каталог не совпадает с каталогами других gates и фаз; прежние
копии этого gate в нём заменяются) и пишет в evidence поле `artifactFiles`:
`dir`, `files[]` (`path`, `sha256`, `bytes`, `redacted` — в текстовой копии
замаскирован секрет окружения) и `skipped[]` (`path`, `reason`, `detail`) с
`skippedMore` для пропусков сверх 100. Копируются только обычные файлы `.png`,
`.json`, `.txt`, `.xml`, `.log` с одной жёсткой ссылкой: не больше 64 файлов,
8 МБ на файл и 20 МБ всего, обход каталогов — до 4096 записей. Ссылки не
разыменовываются (ни сам путь, ни его компоненты, ни записи каталога); файл,
который перед чтением разрешается вне дерева, не копируется (`outside`).
Остаточный риск: между этой проверкой и открытием файла каталог-предок можно
подменить ссылкой наружу. Сделать это может только процесс, переживший gate;
потомков gate harness завершает до копирования в обоих режимах изоляции.
Секрет окружения в текстовой копии маскируется по байтам; файл, в котором
секрет остался после маски (например, текст в UTF-16), не текстовый файл с
секретом в байтах и файл с секретом в имени не копируются (`secret`).
Отменённая проверка не копирует ничего и прежние копии не удаляет. Причины
пропуска: `missing`, `symlink`, `outside`, `not-regular`, `hardlink`,
`secret`, `extension`, `file-limit`, `total-limit`, `count-limit`,
`scan-limit`, `copy-failed` (в том числе отмена проверки). Исход gate от
копирования не зависит: превышение пределов и отказ записи не делают
проваленный gate прошедшим и прошедший — проваленным, а названы в evidence.
Каталог копий, совпадающий с деревом проверки, содержащий его или лежащий
внутри него, не удаляется: отказ записывается как `copy-failed`.
`workspaceGates[].artifacts` по-прежнему обязаны существовать и хешируются в
`artifacts[]`; их копии с теми же правилами пишутся в `artifactFiles` записи
совместной проверки (`<каталог проверки>/<gate>.artifacts/`).

`repositories[].gates[].when` — необязательное условие применимости gate
задачи: `{ paths: [...] }` или (alpha.71) `{ always: true }` — gate
исполняется всегда, без применимости по умолчанию (ниже). `paths` — 1–64 шаблона путей **от корня репозитория**
(POSIX-glob: `**` целым сегментом — любое число сегментов, `*` и `?` — внутри
сегмента, `{a,b}` без вложенности; без `..` и `.` (в том числе внутри `{}`),
пустых сегментов, ведущего `/`, `\`, `[]` и отрицания). Шаблон привязан к
корню, как не принято в gitignore: `*.md` задевает только файлы корня, для
любой глубины — `**/*.md`; `**` внутри `{}` целым сегментом не считается.
Шаблон задевает всё внутри совпавшего каталога (`web` и `web/` задевают
`web/a.ts`), а изменённый путь, который сам — каталог-предок буквального
префикса шаблона, задевает его (`vendor/lib/**` — gitlink `vendor/lib`, файл
`vendor` на месте каталога), как и путь, чьи сегменты совпадают с первыми
сегментами шаблона до `**` (`packages/*/src/**` — gitlink `packages/ui`).
Подмодули и ссылки под `**` называют в `when.paths` явно. Сравнение — без учёта регистра и в NFC: лишнее
совпадение только чаще исполняет gate. Без поля digest политики прежний.
`policyIssues` отклоняет репозиторий, у которого нет ни одного test
gate без `when.paths` (`when.always` считается безусловным), и `when.paths` у генеративного gate (`property`). У
`workspaceGates` поля нет (строгая схема его отклоняет). В режиме порядка
массива (gate без `dependsOn`) каждый более ранний check gate — предпосылка
следующих, поэтому `when` у check gate перед безусловным test gate не
действует: gate исполняется всегда.

Решение принимает runner в каждой фазе попытки по настоящему diff Git, а не по
отчёту исполнителя. Опора — **последний зелёный SHA** gate: integration SHA
принятой попытки этого репозитория, где gate прошёл под тем же основанием
`gateBasis` (определение `gateDigest`, описания его ресурсов, определения и
ресурсы его предпосылок `gatePrerequisites` транзитивно, окружение,
lifecycle, `prepare`, хранилище зависимостей и toolchain репозитория,
изоляция, версия harness) и который — предок базы попытки. Нет такого SHA —
gate исполняется. Diff кандидата — `зелёный..candidate`, интеграции — ещё и
`зелёный..integration`: всё, что попало в target после зелёного SHA (другие
задачи, задачи с суженной областью, коммиты мимо harness), входит в решение.
Diff — `git diff --no-renames --no-ext-diff --no-textconv --no-relative
--ignore-submodules=none --name-only` с `--no-replace-objects` (его несёт
`gitHardening`, то есть каждый вызов git хоста через `hostGitArgs`); переименование даёт оба пути, удаление, смена
режима и gitlink — свои пути. Есть `refs/replace/*` или `info/grafts` — diff
неполон. Условный gate **исполняется**, если: он назван требованием
поручения, договором проверки (свойство, эталон, обязательство) или это
`requirement-source` (`proofGates`); зелёного SHA нет; diff не прочитан,
неполон, больше 5000 путей или пуст (попытка без изменений); diff задевает
шаблон `when.paths`; diff задевает неявный вход — `protectedPaths`, каталог
`.harness/`, в любом каталоге манифест, lockfile, файл версии инструментов
или настройка checkout (`package.json`, lockfiles npm/pnpm/yarn/bun, `.npmrc`,
`.nvmrc`, `Cargo.*`, `go.mod`/`go.sum`/`go.work`, `pyproject.toml`,
`poetry.lock`, `uv.lock`, `Pipfile*`, `requirements*.txt`, `Gemfile*`,
`composer.*`, `.gitattributes`, `.gitmodules`, `.lfsconfig`) или путь,
названный в argv команды gate (с учётом `cwd`); с зелёного SHA сдвинулась
база провайдеров (`providerMovement`): у провайдера из `dependsOn`
репозитория или из снимков зависимостей (`AttemptState.dependencies`, в том
числе транзитивного) другой SHA, чем у принятой попытки зелёного SHA, либо
снимка нет у одной из попыток — изменение провайдера меняет вход gate
потребителя, даже если diff потребителя не задел его путей (artifacts
провайдера, пересобираемые в каждой попытке, не сравниваются: при том же SHA
невоспроизводимая сборка не должна отключать условные gates; смену
`dependencyBuild` провайдера при том же SHA правило не видит); он —
предпосылка (`gatePrerequisites`) исполняемого gate области. Отключить это
правило у gate нельзя. Общие настройки инструментов
неявными входами **не** считаются — их перечисляют в `when.paths` сами:
корневые `tsconfig*.json`, `eslint.config.*`, `vitest/jest/playwright.config.*`,
`Makefile`, `Dockerfile`, `.env*`, скрипты, вызванные косвенно (например из
`package.json`). Иначе gate не исполняется, а runner пишет запись evidence
вида `not-applicable` (`passed: false`, `exitCode: -1`, без команды и лога) с
полем `notApplicable`: `gateDigest`, `patterns`, `ranges[]` `{from, to}`
(`ranges[0].from` — зелёный SHA, последний `to` — SHA фазы), `count`, первые
50 путей не длиннее 1000 символов `files`, `pathsDigest` — SHA-256
отсортированного полного списка, разделённого NUL. Событие `attempt.gate`
такой записи несёт `notApplicable: true`. Исполненный условный gate пишет в
свою запись `test` поле `gateBasis`.

**Применимость по умолчанию (alpha.71).** Gate без `when`, привязанный к
пакету workspace, условен и без `when.paths`. Привязку читает
`packageBinding(gate)` из определения: `pnpm --filter <имя>` / `-F`
(суффикс `...` допустим; `./каталог` и `{./каталог}` — каталог), `pnpm -C
<каталог>`, `npm --workspace <имя|каталог>` / `-w`, `npm --prefix
<каталог>`, `yarn workspace <имя>`, иначе `cwd` gate не в корне — пакет, в
котором он лежит; ведущий `env` с присваиваниями пропускается. Привязки нет
(gate корня, `pnpm -r`, `-w`, `--workspaces`, фильтры зависимых `...x` и
`^`, шаблоны имён) — gate исполняется, как прежде. Граф пакетов
(`workspaceGraphAt`) читается из объектов Git на SHA фазы: `packages:`
`pnpm-workspace.yaml` или `workspaces` корневого `package.json` (`!`
исключает, `node_modules` — никогда), не больше 500 пакетов. Условие gate —
каталоги его пакетов и их зависимостей в workspace (`dependencies`,
`devDependencies`, `peerDependencies`, `optionalDependencies`, транзитивно;
`packageClosure`), не больше 64. Gate исполняется, если граф не прочитан,
пакет не найден, в замыкании корневой пакет или script пакета замыкания
ссылается выше своего каталога (`../`). Неявные входы — те же, что у
`when.paths`, и, кроме того, любой файл корня репозитория, кроме `*.md`
(общие `tsconfig*.json`, `eslint.config.*`, `turbo.json`). Смена любого
`package.json` или `pnpm-workspace.yaml` — неявный вход, поэтому граф на SHA
фазы тот же, что на зелёном SHA. Опора — тот же последний зелёный SHA под
`gateBasis`; исполненный такой gate пишет `gateBasis`. Применимость по
умолчанию не действует у gate с `when` (явные `paths` — свои пути,
`always` — всегда), у генеративного gate и у test gate, если в репозитории
не остаётся test gate, который исполняется всегда. Запись `not-applicable`
несёт `notApplicable.derived: { packages }` (пакеты привязки), `patterns` —
каталоги замыкания; сводка называет их. Приёмка и получатель засчитывают
такую запись только gate без `when`, которому применимость по умолчанию
разрешена по их политике (`derivationAllowed`); покрытие набора
(`uncoveredGates`) решает её по объединению `patterns` записей с тем же
правилом неявных входов. Функции: `packageBinding`, `packageClosure`,
`workspaceGraphAt`, `derivationAllowed`, `conditionalGate`,
`explicitCondition`; `pathApplicability` и `gateDecisions` принимают
условие (`GateCondition`).

Неприменимость — не PASS. `Engine.evidence` принимает её только на SHA фазы
попытки (diff кончается на нём) и только пока на этом SHA нет записи `test`
того же gate. Приёмка (`finish`) и получатель receipt (`resultProblems`)
решают по записи `test`, если она есть, и засчитывают неприменимость
обязательному gate только без неё и только когда: у gate в их политике есть
`when` с тем же `gateDigest`; gate не из `proofGates` поручения; ни один
исполненный gate той же фазы не опирается на него как на предпосылку.
Доказательство требования (`requirementProof`, testcase) и договора проверки
(`propertyProofProblem`) читает только записи `test`. Receipt перечисляет
неприменимые gates ссылками evidence вида `not-applicable` с `notApplicable`.
Функции: `changedPaths`, `coverageChanges`, `gateBasis`, `gateDecisions`,
`pathApplicability`, `matchingPaths`, `gatePathRegExp`, `proofGates`,
`providerMovement`, `notApplicableProblem`, `gateDigest`. У `gateDecisions`
вход `providersMoved` необязателен: без него провайдеры считаются не
сдвинувшимися — вызывающий ручается, что `changedFor` даёт зелёный SHA только
под теми же SHA провайдеров (runner передаёт его всегда). Основание включает версию harness:
после обновления пакета каждый условный gate исполняется один раз. Не входят
в основание образ контейнера по изменяемому тегу и переменные окружения
хоста, передаваемые по имени (`environment.inherit`): их смену gate не видит.
`matchingPaths` и `gatePathRegExp` намеренно расширяют совпадение (регистр,
NFC, каталоги-предки) и годятся только там, где совпадение исполняет
проверку, а не разрешает запись.

Покрытие набора поручений (`uncoveredGates(repositories, works, changes?)`,
`Engine.uncoveredGates(workIds, changes?, finalShas?)`): gate с `when`, признанный
неприменимым на integration хотя бы одним поручением, решается по
объединённому diff набора `changes[repositoryId]`. Его строит
`coverageChanges(repoPath, evidence, finalSha)`: от зелёного SHA каждой такой
записи (`notApplicable.ranges[0].from`) до итогового SHA. Diff засчитывается,
только если он полон, у всех пар один конец — итоговый SHA репозитория из
`finalShas` — и среди начал есть зелёный SHA
каждой записи неприменимости gate; иначе он считается отсутствующим. Задетый
diff — или без `changes`, или под другим определением gate — gate непокрыт,
даже если другое поручение его прошло, и хост исполняет его один раз на
итоговом SHA (`runGatesAt`); не задетый — не пробел. Для политики без `when`
правило прежнее. Совместная проверка (`workspaceGates`, `JointRunner`) не
меняется.

#### Перенос evidence кандидата на интеграцию

`integrationReuse: 'identical-tree'`; с alpha.71 без поля — то же в облегчённом
режиме, если хост объявил `capabilities.integrationReuse` (`integrationReuseOn`);
`'off'` и строгий режим без поля — каждый gate и ревью на интеграции. Runner сравнивает дерево
integration-коммита (`git rev-parse <integration>^{tree}`) с деревом
кандидата. Перенос возможен, только если деревья равны (target не
сдвинулся с базы кандидата), кандидат не пустой, `policyDigest` попытки
равен текущему, версия движка попытки — текущая и снимок провайдеров
попытки равен их текущим головам (`providerMovement`). Тогда каждый gate,
решающая запись которого на кандидате — PASS, пишется на интеграции записью
`test` с `passed: true`, SHA интеграции и полем
`reusedEvidence: {evidenceId, phase: 'candidate', sha, tree}` (ID записи
кандидата, его SHA и общее дерево); список тестов и `gateBasis` копируются,
сводка начинается с «PASS взято из кандидата». Не переносятся и исполняются
как прежде: gates доказательств (`proofGates`: требования, свойства,
договоры — им нужен свой манифест и testcase на каждой фазе), gates с
`artifacts`, записи со сведениями о свойствах, gates, не прошедшие или
неприменимые на кандидате, и предпосылки (`gatePrerequisites`) любого
исполняемого gate. Проверка генераторов при переносе не нужна: дерево —
дерево кандидата. Если исполнять нечего (или оставшиеся
неприменимы) и у поручения нет потребителей, окружение интеграции —
lifecycle, хранилище зависимостей, `prepare`, проверка генераторов — не
поднимается: дерево и его выходы те же, что у кандидата. С потребителями
окружение поднимается всегда: их проверка снимает провайдера с дерева
интеграции и ждёт его подготовки и сервисов lifecycle. Проверки
потребителей и источник требований идут как прежде. Ревью интеграции
(alpha.71) не вызывается, если решающая запись ревью кандидата под той же
версией проверок — PASS: пишется запись `review` интеграции с
`passed: true`, без находок и с `reusedEvidence` на эту запись (сводка
«PASS взято из кандидата: ревью кандидата … перенесено»); история находок
остаётся у записи кандидата. Иначе ревью интеграции идёт как прежде.
Принятый остаточный риск: разрешение зависимостей хранилищем вне lockfile
(например, смена ответа registry между фазами) при переносе не
перепроверяется — ни исполнением перенесённого gate, ни проверкой
генераторов, которая при переносе не идёт. Поле `reusedEvidence` не путать с
`AttemptState.reusedFrom` (кандидат прежней попытки вместо новой
реализации).

**Правило доверия** (`reusedEvidenceProblem`, одно для `Engine.evidence`,
`finish`, recovery и получателя): запись — PASS интеграции, только если она
собственная (не потребителя) запись `test` интеграции на result SHA с
`passed: true`, без сведений о свойствах и копий artifacts; ссылается на SHA
кандидата; её gate объявлен, не доказательство и без `artifacts`; запись
`evidenceId` существует, это собственная проверка того же gate на кандидате,
PASS, под той же версией проверок и решающая (последняя) для gate; деревья
кандидата и результата равны и равны `reusedEvidence.tree`. Для записи
`review` (alpha.71): PASS ревью интеграции на result SHA, ссылка на SHA
кандидата, запись `evidenceId` — собственное (не перенесённое) ревью
кандидата, PASS, под той же версией проверок и решающее (последнее); деревья
— как выше. Деревья сверяет
тот, кто владеет Git: controller при записи и recovery (`rev-parse ^{tree}`
обоих SHA до `adopt`), получатель — своим Git: `ReceiverContext.trees:
{candidate, result}` — деревья `shas.candidate` и `shas.result`,
вычисленные получателем. Проверка остаётся чистой; без `trees` запись,
взятая из кандидата, не PASS («получатель не передал деревья»).
`Engine.evidence` принимает `reusedEvidence` только под политикой, где
перенос включён (`integrationReuseOn(policy, host)`); получатель — только
когда он включён его политикой (`integrationReuseOn(policy)`: явное
`identical-tree` или облегчённый режим без поля), иначе запись не PASS. Удалённая ссылка превращает запись в обычное утверждение
об исполнении, подлинность которого получатель не удостоверяет (как у любой
записи); подмена ссылки или дерева — отказ.

Событие `attempt.gate` такой записи несёт `reusedFrom` (ID записи
кандидата), проекция попытки — `gates.reused`, отчёт об эффекте —
`environment.reused` (число таких записей в окне; нет поля — не было).

`policyDigest(policy)` — digest загруженной политики целиком: им сверяются
применённая политика (`control.appliedPolicy`) и запрос операции
`control.reconfigure`. `executionDigest(policy)` — digest исполнительной
части без `budgets` и `prices`: основание согласования графа
(`GraphState.policyDigest`) и fencing попыток (`AttemptState.policyDigest`
у standalone-хоста). Поднятый предел бюджета поэтому согласования не
сбрасывает.

Хост, который строит политику из собственной конфигурации, может передать
движку своё тождество применённой политики (`EngineOptions.policyIdentity`,
digest по формуле хоста — например, файла конфигурации). Тогда применённая
политика и запрос операции сверяются с ним, а не с `policyDigest(policy)`;
изменение политики в памяти после создания движка по-прежнему проверяется по
её содержимому.

`EngineOptions.recordPolicyOnLead: false` — хост сам записывает применённую
политику при запуске своего планировщика; получение роли controller (в том
числе для прямой выдачи попытки) её тогда не записывает.

Автор (`--author`): `codex`, `claude`, `fixture` или `external` — человек или
инструмент вне harness; вендор `external` не совпадает ни с одним runtime.

**Выбор reviewer** — только `selectReviewer(policy, kind, writer, role)`:
`different-vendor` (умолчание) отклоняет reviewer того же вендора
(`REVIEWER_SAME_VENDOR`), `same-vendor-allowed` разрешает его. Неявного
«противоположного runtime» нет. Проверка входов отклоняет такую политику
целиком; хост, ведущий движок без неё, получает блокер
`REVIEWER_SAME_VENDOR` только у поручений этой роли — остальная очередь
выдаётся. `reviewVendorConflicts(policy)` перечисляет роли, чьё правило ревью
кода так отказывает writer роли (тем же `selectReviewer`): `doctor` называет
каждую проблемой `review-vendor-conflict: …` (где записано правило и как
исправить), `init` — предупреждением `review-vendor-conflict`.

Правило может перечислить запасных reviewer (`alternates`, по порядку):
берётся первый из `[reviewer, ...alternates]`, допустимый правилом вендора
для этого автора. Так хост явно задаёт «reviewer другого вендора, чем
автор», не полагаясь на неявный выбор. Запасные reviewer проверяются
`policyIssues` так же, как основной.

**Раунд технического ревью** плана или контракта — `technicalReview(engine,
policy, adapters, input)`: та же реализация, что у `Harness.review`. Хост
передаёт предмет (ID, digest, автор), свои разделы запроса, рабочий каталог
reviewer и учёт вызова; harness выбирает reviewer, вызывает его под
бюджетом, требует состояние каждой прежней открытой находки и записывает
`ReviewRecord`. Предел раундов (`maxRounds`) задаёт вызывающий:
`Harness.review` — `2 × maxAttempts`.

**Что тратит предел раундов (0.1.0-alpha.68).** Предел считает засчитанные
раунды текущей эпохи (`roundBudget`). Раунд не засчитан (`counted: false`),
если прежний раунд предмета одобрен, а план тот же: `planDigest`
(`planContentDigest` — граф без ревизии источника набора; поручения с их
ревизиями постановок входят), политика (`executionDigest`), назначение
reviewer и автор те же — изменились только контекст (ответ на вопрос,
документы) или ревизия источника. Точно: прежний раунд предмета одобрен,
`planDigest` (граф без ревизии источника набора: поручения с ревизиями
постановок, зависимости, предпосылки), `policyDigest`, назначение reviewer
и автор равны прежним; снимок контекста может отличаться в любых источниках
любого вида (ответы на вопросы, документы задач, пакеты, документы,
написанные ведущим), ревизия источника набора — любая. Такой раунд —
настоящее ревью с вызовом reviewer, он может отклонить план, но предел
изменённого плана он не тратит. Таких раундов в эпохе не больше предела;
при исчерпанном пределе они проводятся, изменённый план — нет
(`ATTEMPTS_EXHAUSTED` с причиной). Эпоха начинается с последней доработки
принятой работы графа со своим пределом попыток (`rework.fresh`, не
`resumed`): у доработки свой счёт раундов. Каждый раунд записывает, что
изменилось против прежнего (`changes: {plan, policy, reviewer, context:
{added, removed, changed}}`). Хост передаёт `planDigest` и `roundEpoch`
сам; без них предел считается как прежде, по засчитанным раундам.
**Что тратит предел раундов (0.1.0-alpha.69).** Предел тратит только
настоящее изменение плана. Хост передаёт состав плана `planOrders`
(`planOrderDigests(graph)`: ID поручения → digest значимого содержания —
всех полей постановки, кроме версии API и источника `source` с ревизией; у
требований без digest документа-источника, у контрактов — только ID), и
раунд засчитан, только если против прежнего одобренного раунда (и против
последнего, если он отклонён) добавлено, убрано или изменено поручение,
работа которого не принята. Изменение поручения, работа которого принята
(`done`) или дорабатывается после приёмки, — доработка: предел не тратит
(`changes.orders.rework`). Указания ведущего (ревизия источника, документы и
заметки в контексте), ответы владельца, политика и reviewer предел тоже не
тратят. Эпоха доработки остаётся (свой счёт для изменений плана после неё),
но израсходована она, только когда первый раунд после неё засчитан —
бесплатная доработка эпоху не тратит. Защита от круга: бесплатных раундов
подряд после последнего одобренного — не больше предела; дальше раунд
неизменённого плана засчитан (`freeRoundsSinceApproved`). Без `planOrders`
у прежнего раунда или во входе — сравнение `planDigest`, как в alpha.68.
В облегчённом режиме (`harnessMode: light`) счёта раундов нет:
`technicalReview` не отказывает по пределу раундов (`maxRounds` не
действует), `reviewRoundCap` — `null`, строка — «раундов N, без предела
(облегчённый режим; бюджет — время/стоимость выпуска)»; предел выпуска —
`budgets.group`/`budgets.total`, исчерпание — `BUDGET_EXHAUSTED`, решает
владелец. Без этих бюджетов `doctor` предупреждает строкой `light-no-budget`.
Хост, который вёл раунды предмета до harness и хранит их сам, передаёт их
как `history: {rounds, findings[]}`: пока у предмета нет раундов в движке,
первый раунд получает номер `rounds + 1`, а находки последнего прежнего
раунда — прежние открытые находки, состояние которых reviewer обязан назвать.
Это только история: прежним раундам не приписываются digest, назначение
reviewer или одобрение. Дальше нумерация идёт подряд от первого раунда
движка, и `history` больше не учитывается.

### ContextSnapshot

Digest снимка (`contextDigest`, 0.1.0-alpha.68) считается по канонической
форме: источники и `missing` упорядочены по ID, поэтому те же источники в
другом порядке — тот же digest и то же согласование. Порядок файлов внутри
источника входит в его digest. Digest прежнего правила
(`legacyContextDigest`) узнаётся при сверке (`contextDigestMatches`):
раунды и согласования прежних версий остаются в силе после обновления.

`{apiVersion, sources[], missing[]}`. Источник —
`{id, kind, version, repositoryId?, revision?, required, files[], references[], digest, hostDigest?}`;
файл — `{path, digest, bytes, content: {encoding: 'utf8' | 'base64', data}}`.
Содержимое передаётся в снимке: источник может не быть Git, и движок обязан
получить ровно те байты, на которые выдан digest. `contextIssues` сверяет
SHA-256 и размер каждого файла и `sourceDigest` источника; `pinnedBytes`
отдаёт байты только после проверки. Пределы: 2 МиБ на файл, 16 МиБ на снимок.
Снимок попытки сохраняется по digest (`context-snapshots`) и используется
после рестарта без повторного чтения источника.

### ContractDocument

`{apiVersion, id, repositoryId?, title, content, artifacts?, checks?}` — вход
`review-contract`. `artifacts` — закреплённые файлы контракта (`{path, blob}`,
Git blob в репозитории `repositoryId`); `checks` — договор проверки
(`checkDeclarationSchema`, `version: 1`): gate, обязательства по property ID
(требования, тип обещания, область входов, правила ответа, способ проверки и
его файлы, семейства и минимальные выборки, корпус) и политика расширения
корпуса. Прошедший ревью документ хранится по digest (`contract-documents`):
из него движок строит манифест генеративного gate поручения.

#### Способы исполнения обязательства: `property` и `reference`

Обязательство исполняют его gates: `obligations[].gates` (1–10 ID) или, без
поля, `checks.gate`. Способ — `verification`:

- `property` (поле не указано) — генеративная проверка, как прежде: каждый gate
  обязательства генеративный (`gate.property`), отчёт свойств каждого
  подтверждает полное покрытие обязательства (`coverage.minCases` и
  семейства), корпус пополняет только gate договора;
- `reference` — сверка с закреплёнными эталонными наборами. Ответы
  независимого эталона (точный решатель, полный перебор, таблица DP)
  получены заранее, сверены с другим способом и закреплены артефактами
  контракта; gate сверяет с ними реализацию. Генератор не нужен, поэтому gate
  может быть обычным test-gate без `property`.

`reference` описывает:

| Поле                                                            | Смысл                                                                                                                                                 |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `oracle.description`, `oracle.limits`                           | эталон, его версия и пределы (время решения, что исключено из наборов)                                                                                |
| `crossChecks[]` `{family, against, matches, total, artifacts?}` | сверка эталона с другим способом на семействе входов; `matches < total` — отказ; `artifacts` — закреплённый скрипт или журнал, воспроизводящий сверку |
| `sets[]` `{gate, artifacts, minCases, families}`                | набор: gate, файлы набора (артефакты контракта), доля входов и семейств этого gate                                                                    |
| `gaps`                                                          | чего наборы не доказывают: обобщение за пределы входов, классы вне наборов                                                                            |

Структурные правила (`declarationProblems`, до вызова модели): у каждого gate
обязательства есть набор, gate набора — среди gates обязательства, файлы
наборов — артефакты контракта, сумма `sets[].minCases` не меньше
`coverage.minCases`, сумма долей каждого семейства покрытия не меньше его
`minCases`, семейства набора объявлены в покрытии и не превышают минимум
набора, сверка эталона без расхождений, файлы сверки (`crossChecks[].artifacts`)
— артефакты контракта; корпус у эталонного обязательства не включается.
Требование генеративного gate к `reference` не применяется; остальные
правила (`method`, бюджеты, spike) те же. Обязательство `property` любого
обещания (и `invariant`, и `functional`) на gate без `property` отклоняется:
поручение такое свойство выбрать не может (`orderPropertyProblems`), и
договор был бы мёртвым.

Доказательство — тот же отчёт свойств. Для gate, которому манифест поручения
назначает эталонное свойство, controller задаёт путь отчёта
(`DEVCONTOUR_PROPERTY_REPORT`) и селектор (`DEVCONTOUR_PROPERTIES`) и без
`gate.property`. Запись манифеста эталонного свойства — доля этого gate:
сумма `minCases` и семейств его наборов и `reference.artifacts` (файлы
наборов); поле есть только у эталонных свойств, так что digest прежних
манифестов не меняется. Gate проходит, только если отчёт называет свойство
со статусом `passed`, числом проверенных входов и семейств не меньше доли и
testcase с тем же ID в JUnit; зелёный JUnit и код 0 без отчёта — отказ
(«Проверка по эталонным наборам не отчиталась»). Приёмка требует решающую
запись обеих фаз с манифестом от каждого gate обязательства. Файлы наборов —
артефакты контракта, поэтому попытка не может их изменить (защищённые пути).

Reviewer контракта получает эталонные обязательства отдельно (`referenceNote`):
эталон, сверку, наборы и `gaps`. Обещание, которое опирается только на
`gaps`, без другого способа (генеративного свойства, инварианта,
аналитического основания), — блокирующая находка. Сверка без `artifacts` —
непроверенное утверждение автора, и reviewer оценивает её так.

Ответы наборов лежат в рабочем дереве, поэтому реализация могла бы читать их
или повторять их ответы и проходить каждый набор. Защита в два слоя:
writer и reviewer кода получают список файлов наборов (`referenceSetFiles`,
`referenceCodeNote`), и для reviewer чтение файлов наборов из кода
реализации, вшитые ответы или особые случаи для входов наборов — блокирующая
находка; controller отклоняет кандидата (`scope-violation`, до gates), если
изменённый файл называет файл набора внутри строкового литерала (`'…'`,
`"…"`, `` `…` ``): имя файла набора целым токеном — по краям нет буквы,
цифры, `_`, `-` или `.`, так что путь и `../имя` совпадают, а `data.json` с
набором `a.json` или `testcases.json` с `cases.json` — нет (`setFileReference`).
Комментарии `//` и `/* */` и файлы без кода (`.md`, `.txt`, `.rst`, `.adoc`,
каталог `docs/`) не проверяются. Тесты исполнителя, которые не артефакты
контракта, проверяются тем же правилом: через них ответы тоже можно подать
реализации. Остаточный риск: имя, собранное во время исполнения
(`` `${name}-golden.json` ``), копия ответов без имени файла и обобщение,
подогнанное под входы, механически не ловятся — их ловит ревью кода; строка
кода, которая законно называет набор (не артефакт контракта), отклоняется.

Пределы проверки долей: controller сверяет, что доли наборов покрывают
общий минимум и минимумы семейств и что gate отчитался своей долей, но не
сравнивает доли с размером файлов набора (сколько входов в нём на самом деле)
и не проверяет, что входы различны. Reviewer контракта видит минимумы
обязательства и семейств рядом с наборами (`referenceNote`) и оценивает это
сам.

#### ID testcase и отчёта

Свойство, `testId` отчёта и testcase JUnit — один ID. ID testcase — это
`classname.name` (без `classname` — `name`). Генератор отчёта задаёт
`classname` по-своему: node:test (`--test-reporter=junit`) всегда пишет
`classname="test"`, и тест `test('knapsack-optimal', …)` получает ID
`test.knapsack-optimal` — таким должен быть и property ID; JUnit-отчёт
собственного checker (как `harness.mjs` в примерах) пишет только `name`, и ID
совпадает с именем. Если testcase с ID свойства нет, а есть
`<classname>.<ID>`, отказ называет найденный ID.

Совместимость: поля `gates`, `verification`, `reference` необязательны, договор
без них разбирается, проверяется и даёт тот же манифест, digest и основание
корпуса (`suiteBasis` включает новые поля, только когда они объявлены;
`gates`, равные gate договора, — то же основание, что без поля, а digest
документа контракта при этом другой).
Версия договора остаётся `version: 1`; прежние версии harness договор с
новыми полями отклоняют строгой схемой.

## Ответы исполнителей

Runtime возвращает сырой ответ; движок разбирает его
`implementationResultSchema` и `reviewResultSchema`. Ответ вне схемы — отказ,
а не самооценка writer. Reviewer называет состояние каждой прежней открытой
находки (`previous[]`); `reviewIssues` отклоняет `approved` при блокирующей
находке, в том числе прежней открытой, неназванную прежнюю находку и ссылку на
неизвестную. Идентичность находки плана/контракта — `findingId(subject, {rule, message})`;
невалидный ответ раунд не применяет (переходы и новые находки не записываются).

Ревью кода ведёт историю находок поручения с ID, выданными controller
(`codeReviewHistory`, `checkCodeReview`): reviewer называет ровно один переход
каждой открытой находки, ошибка протокола (`REVIEW_PROTOCOL_INVALID`,
причина и путь поля, например `previous[0].id`) отделена от содержательного
отказа (`REVIEW_REJECTED`) и даёт ограниченный повтор только reviewer
(`reviewProtocolRetries`, 0–2, по умолчанию 1). Evidence ревью несёт
аддитивное поле `reviewRound`, находки — `id`/`status`, ссылки результата —
`review`. Правила — [docs/review-protocol.md](review-protocol.md).

Ответ runtime ограничен на границе приёма. В `reviewResultSchema` — не больше
500 элементов в `findings` и в `previous` (`REVIEW_ITEMS_LIMIT`; те же
`maxItems` объявляет wire-схема CLI runtime); файл ответа codex — не больше
4 МиБ (`CODEX_RESULT_LIMIT`), читается с границей, без перехода по symlink, а
файл больше предела удаляется: он не прошёл маскирование. Сверх предела — обычный
отказ: у reviewer кода ошибка протокола `schema`, у исполнителя класс `unknown`
без автоматического повтора, у ревью плана и контракта — `RUNTIME_UNAVAILABLE`
с причиной. Записанное прежними версиями читается
без этих пределов: `review.json` — `storedReviewResultSchema`, а `ReviewRecord`
и evidence пределов не получили.

### Предложения, разбор в начале попытки и исследование (0.1.0-alpha.70)

Ответ writer (`implementationResultSchema`) получил необязательные поля;
негодное значение каждого отбрасывается, а не весь ответ:

- `followUpTasks[]` — задачи-продолжения на остаток вне критериев работы
  (`title`, `goal`, `acceptance`, `reason`, `evidence`). Сдать работу
  можно только с выполненными критериями: reviewer видит предложения и
  отклоняет критерий, перенесённый в продолжение.
- `triage` — разбор в начале попытки: `implement`, `split` (2–8 частей
  `parts`, код не пишется, `completed: false`) или `ask` (вопрос —
  `inputRequest`). Разделение останавливает попытку без засчёта
  (`needs-lead`, причина `writer-split`, `AttemptState.writerSplit`).
- `research` — исследование задачи (`summary`, `files`, `approach`,
  `constraints`): сохраняется у работы (`WorkState.research`,
  замаскированным, до 8000 знаков) и попадает в запрос следующих попыток
  этой работы и работ, зависящих от неё, сразу после постановки
  (стабильный префикс — кеш подсказки). Адаптер с
  `RuntimeCapabilities.sessionFork` получает `session: {kind: 'fork', id}`
  от сессии исследования; reviewer — всегда новая сессия и исследования
  не видит. Встроенный адаптер CLI `sessionFork` пока не объявляет.

Разделение после отклонённого ведущим — засчитанная незавершённость
(`unfinished`), а не новое предложение; у разделений свой предел записей
на работу (10), задачи-продолжения его не занимают. Предложения и решения
по ним переживают новые редакции графа; исследование — только у той же
постановки, и в зависимые работы — только того же репозитория. Тексты
задач-продолжений reviewer получает как непроверенные данные исполнителя.

Предложения — `WorkState.proposals[]` (`P-<12 hex>`, `kind:
follow-up|split`, `status: proposed|accepted|rejected`, `decision`).
Принимает или отклоняет только ведущий (или оператор): `harness proposal
--state D --work W --proposal P --decision accept|reject --reason R [--by
lead|operator]`. Принятие граф не меняет: принятое ведущий вносит в план
обычным ревью плана.

`WorkOrder` получил `labels` (метки: security/payments/auth — второй проход
ревью всегда, `docs` — документация выпуска) и `criteriaSources`
(источник каждого критерия, который написал ведущий: `brief`,
`owner-answer`, `review-finding`, `context`). Ревью плана помечает критерий
без источника находкой `unsourced-criterion`.

## Выходы

### RunResult

Варианты по `outcome`:

- `accepted` — `shas{base, candidate, integration, result}` все обязательны
  (result = integration; он уже в target ref);
- `rejected | blocked | cancelled | stopped` — `stopReason{code, message}` с
  кодом из договора ошибок; result SHA нет.

Общие поля: `workOrderId`, `graphId`, `source`, `runId`, `attempt`,
`repositoryId`, `targetRef`, `inputs` (версии harness и потребителя, версия
состояния, digests поручения, графа, политики, контекста, версия проверок),
`checked` (снимки зависимостей, их свежесть, проверенная комбинация каждого
потребителя), `evidence[]`, `findings[]`, `limitations[]`, `finishedAt`.
Свежесть записывается, а не запрещает приёмку. Необязательные поля
доказательства: `inputs.corpus` (закреплённая версия корпуса),
`inputs.requiredGates` (раскрытые при выдаче gates), `inputs.writer` (writer
попытки), у ссылки на evidence —
`checks` (версия проверок записи), `property{level, manifest}` (уровень и
манифест генеративного gate), `tests[]`/`testsTruncated` (выполненные тесты
собственной проверки интеграции — доказательство названного testcase).
Получатель проверяет результат `resultProblems(result, context)` /
`assertResult`. Всё, что результат утверждает о поручении, области, входах и
ревью, сверяется с тем, что получатель знает сам, а не с другими полями того
же результата: согласованная сама с собой подделка иначе проходила бы.

**Контекст получателя** (`ReceiverContext`):

- `order` — постановка поручения у получателя; `graphId` — граф, в котором
  он её держит; `contracts` — документы договоров поручения;
- `policy` — политика получателя (`repositories`, `roles`, `review`): по ней
  раскрываются область поручения и потребителей, замыкания зависимостей,
  target ref, writer роли и назначенный reviewer с правилом вендора;
- `contextDigest` — снимок контекста, закреплённый согласованием графа
  (`null` — без контекста);
- `suite`, `checkVersion` — корпус по копии получателя и закреплённая за
  поручением версия (`null` — без корпуса; у поручения с договором проверки
  обязательна); `specDigest` — digest согласованной постановки (по
  умолчанию digest поручения);
- `unobserved` — результат прежнего формата хоста, в котором входы попытки
  не наблюдались: `dependencies` — нет снимков собственных зависимостей и их
  свежести, `consumers` — нет свежести потребителей. Такие пустые списки не
  сверяются с замыканием (их нет, и проверке они не подлежат); непустые
  списки, снимки зависимостей потребителя и провайдер сверяются как обычно.
  Какой результат имеет прежний формат, решает хост по своим правилам формата.
- `assignment` — чем подтверждено ревью: `current` (по умолчанию) — writer и
  reviewer назначены текущей политикой получателя; `recorded` — результат
  несёт своё назначение, и хост перепроверяет его позже, когда назначение
  ролей могло смениться: writer и reviewer — записанные, оба должны быть
  runtime политики получателя, правило вендора роли соблюдено.

Чего нет в контексте (репозиторий, потребитель, зависимость или роль не
описаны в политике получателя), — отказ, а не PASS. Результат прежнего
формата (без версии проверок, области и writer) читается на прежнем уровне
только у поручения без договора проверки.

- `trees` — деревья кандидата и результата, вычисленные получателем своим
  Git (`git rev-parse <sha>^{tree}`); нужны только результату с записями,
  взятыми из кандидата (`evidence[].reusedEvidence`, [правило
  доверия](#перенос-evidence-кандидата-на-интеграцию)): без них такая запись
  не PASS.

**Модель доверия** — категория каждого поля принятого результата
(`receiptTrust` в `src/verification/acceptance.ts`):

- _ожидание получателя_ — сверяется с ожиданием, вычисленным из контекста;
- _согласованность_ — сверяется с другими полями результата (SHA фаз,
  свежесть со снимками, уникальность записей);
- _сведение_ — ничего не доказывает, вердикт на него не опирается;
- _схема_ — значение фиксировано схемой.

Подлинность SHA, деревьев, artifacts и записей (их наличие в Git и в
хранилище исполнителя) получатель не удостоверяет — это транспорт хоста.

### DeliveryState и ResultEnvelope

Доставка — отдельно от исхода: `{sink, key, revision, status: pending |
delivered | failed | conflict, attempts, lastError?, currentRevision?,
receipt?, updatedAt}`. `harness result` выдаёт `{apiVersion, result,
delivery[]}`.

Отдельная доставка того же результата (`Harness.deliver(workId, sink,
{ runId, variant })`) пишет свою запись с ключом
`<sink>:<variant>:<workId>:<runId>`; прежняя подтверждённая доставка не
меняется. Коннектор задач так выполняет повторное доказательство критериев
принятого результата (`source-deliver --reprove`, вариант `reprove-<digest
привязок>`): ответ `source-deliver` получает `reprove: true` и
`skipped[] {workId, reason}` (поручения без принятого результата),
`source-status` — `tasks[].proof {reprovable, unproven[] {title, reason},
next?}` для принятого поручения с незакрытой задачей. Ревизия поручения
из коннектора (`source.revision`) — semantic digest v2: без привязок
критериев и необязательных документов (см.
[connectors.md](connectors.md), «Идентичность и снимок»).

### JointVerification

Совместная проверка закреплённой комбинации SHA нескольких репозиториев:
`{id, status, policyDigest, specDigest, workIds[], manifest{repo: {sha, tree}},
manifestDigest, impact?, evidence[], error?}`. Смена любого SHA делает
результат устаревшим; атомарность продвижения нескольких репозиториев не
заявляется. Продуктовое принятие комбинации решает хост. Пока manifest не
закреплён, `impact` может нести только ссылку на базовую проверку
(`baseline`), выбранную хостом для режима `affected`.

### Зависшие попытки

Controller, ведущий очередь, раз в `stallSweep.intervalMs` (не меньше 1000 мс
и не больше `quietMs`) обходит исполняющиеся попытки. Движение попытки —
начало и конец её команды (вызов агента, gate, шаг среды, прочие команды),
вывод в stdout/stderr, граница стадии (`attempt.stage`) и прирост
процессорного времени дерева процессов исполняющихся команд (сумма
положительных приростов по каждому процессу, новый — от нуля) не меньше 1 %
прошедшего времени. Смена состава дерева сама движением не считается: цикл
ожидания (`until nc -z db 5432; do sleep 1; done`) рождает процессы, не
продвигаясь. Один `ps` на обход, общий для одновременных обходов; перерыв
от конца прошлого обхода дольше трёх интервалов (сон машины, занятый event
loop) начинает отсчёт заново, но не больше двух раз подряд.

Состояния: `active`; `quiet` — нет движения дольше `quietMs`; `stalled` —
дольше `stalledMs` (`quietMs < stalledMs`). Без данных `ps` о процессах
(отказ, Windows, нет времени процесса) оценка идёт только по выводу и не
поднимается выше `quiet` (`cpuUnavailable` в событии). Попытка без
исполняющейся команды (ждёт hook, ресурс, интеграцию) оценивается от последнего
движения с порогом `stalledMs` и тоже не выше `quiet`. Переход пишется в
`AttemptState.liveness` и событием `attempt.liveness` одной транзакцией под
fencing; само состояние между переходами не перезаписывается, а незаписанный
временным отказом переход повторяет следующий обход (не больше пяти раз;
отказ движка или схемы не повторяется). На `stalled` — снимок процессов
исполняющихся команд (pid, родитель, процессорное время, команда под маской
среды; команда без маски не сохраняется) и хвост вывода: в
`artifacts/<runId>/stall-<эпизод>.json` (один на эпизод, записывается первым) и в событии (≤ 20
процессов, ≤ 2000 символов). Дальше — `action`: `report` только сообщает
(попытка идёт до своего предела времени, движение вернёт `active`), `stop`
останавливает попытку отказом класса `stalled`: повтор или правка среды, а не
правка кода (`repairPolicy.stalled`, бюджет попыток он тратит, как `timeout`);
при `stop` зависшая попытка останавливается, даже если переход не записан.
Совместная проверка и gates на SHA вне попытки (`runGatesAt`) ведут свой
обход: переходы проверки — событие `joint.liveness` под её fencing, переходы
`runGatesAt` — `onLiveness` хоста и `liveness[]` результата (нагрузка как у
`attempt.liveness`, без файла снимка); при `stop` они останавливаются с
текстом зависания. `stallSweep` — надзор, а не условие
исполнения: в digest исполнения (основания попыток и reuse) он не входит.

`status` показывает `works[].liveness` (`quiet`/`stalled`) у активной попытки
без движения, `status --detail` — `detail.attempts[].liveness` (`state`,
`since`, `lastMovementAt`, `idleMs`, `activity`, `action`), `explain` —
причину `stalled` у работающего поручения: при `report` действует человек
(`fix-environment`), при `stop` — controller.

### Нехватка окна контекста

Отказ класса `context-exhausted` — исполнителю или reviewer не хватило окна
контекста модели внутри попытки. Класс ставится по признаку, который сообщил
сам runtime, а не по тексту причины: адаптер claude читает `terminal_reason`
итогового события `result` потока `stream-json` и выставляет
`RuntimeResponse.diagnostics.contextExhausted` — предел окна
(`ContextLimit`). Записанные на живом CLI признаки:

- `prompt_too_long` на первом ходе (`num_turns` ≤ 1) → `prompt-too-long` —
  запрос отклонён: уже подсказка с контекстом больше окна, сжимать нечего.
  Тот же признак после ходов работы или без `num_turns` (не записан, вывод
  инструментов заполнил окно) → `blocking-limit`;
- `blocking_limit` → `blocking-limit` — CLI сам остановил ход у предела окна.
  Записан с выключенным автоматическим сжатием через `DISABLE_AUTO_COMPACT=1`.
  `autoCompactEnabled: false` в `--settings` сжатие тоже выключает (проверено),
  но исход у предела окна с ним не записан; путь «сжатие включено, но не
  помогло» не проверен.

В обоих случаях CLI выходил с кодом 1, `is_error: true`, текст `result`
начинался с `Prompt is too long`; признак учитывается и при коде 0. Текст
отказа попытки постоянный (`claude: не хватило окна контекста модели`), предел
— данными (`AttemptState.contextLimit`), текст runtime — в журнале вызова:
отпечаток один при любом пределе и любых числах токенов, а «401» или «429» в
числах токенов текстовый разбор принял бы за отказ провайдера. Успешное
автоматическое сжатие (`system`/`compact_boundary`) — не отказ: вызов
продолжается и завершается своим исходом; число сжатий и `terminal_reason`
пишутся в `runtime.json` вызова (`compactions`, `terminalReason`). У codex
признак пока не распознаётся: его отказ классифицируется как прежде.

Попытка засчитывается в `maxAttempts`: отказ говорит о размере задачи, а не
об окружении, и выдачу не останавливает. Повторы (`repairRepeats`): у
`blocking-limit` — один (`repairPolicy['context-exhausted'].repeats`), и
следующая попытка writer получает в подсказке указание держать контекст малым
(читать только нужные файлы и строки, не выводить большие файлы и длинный
вывод команд); у `prompt-too-long` — ни одного: повтор только удлинил бы
подсказку. Предел берётся у последней попытки с отказом
(`lastContextLimit`); отпечаток у обоих пределов один. Дальше задачу нужно разделить или сократить её контекст:
код остановки `CONTEXT_EXHAUSTED` (класс `refused`), `explain` — ведущий,
`diagnose-failure`. Корзина отчёта — `incomplete`; разбор свойства
(`property-recovery`) такой отказ не считает, кандидат после отказа reviewer
переиспользуется (`reusableFailures`). Причина `attempt.diagnosed` — `none`,
`counted: true`.

### Вопрос исполнителя

Writer, которому для продолжения нужно решение человека или ведущего,
отвечает `completed: false` и вопросом `inputRequest` (`inputQuestionSchema`:
текст до 1500 знаков, до шести вариантов с последствием, рекомендуемый
вариант, самооценка серьёзности 1–10, основание, затронутые критические
области `contract | acceptance | product | api | migration`). Развилки,
которые он решил сам, — `assumptions[]` (вопрос, выбор, основание,
серьёзность, области; до 20). `completed: true` вместе с вопросом невалиден.
Поля необязательны: ответ прежнего формата — ответ без вопроса и допущений.
Wire-схема CLI runtime объявляет оба поля (`inputRequest` — объект или
`null`).

**Влияние вопроса** (0.1.0-alpha.55). Вопрос несёт необязательное `impact`:
`technical` — ни один вариант не меняет того, что видит и получает
пользователь продукта (выбор внутри реализации), `user-visible` — меняет.
Нет поля или `null` — `user-visible` (консервативно: вопрос человеку). Вариант
несёт необязательное `forUser` — одну строку простыми словами (до 300 знаков)
«что изменится для пользователя». Запрос writer называет правило
классификации («в сомнении — `user-visible`»). Wire-схема объявляет оба поля
обязательными с `null`; `null` в каноническую запись не попадает, поэтому
запрос без них — тот же, что запрос прежней версии. Значение `impact` вне
перечня приводится к отсутствию поля (`normalized`); область `affects`,
названная строкой, читается как список из неё, иным значением — как
нераспознанная (минимум `declared`, вопрос человеку).

**Политика вопросов** — `ExecutionPolicy.inputPolicy`
(`{threshold: 1–11, criticalPaths: [], leadAnswers?: {maxSeverity?: 1–10,
technical?: boolean}}`; нет поля — порог 7 без критических путей, умолчание в
политику не подставляется). `leadAnswers` — явное согласие человека, что
ведущий агент отвечает на блокирующие вопросы сам: `maxSeverity` — до этой
серьёзности (критический вопрос поднят до 10); `technical: true` — только
на технические вопросы (`impact: technical`) без минимумов, с обязательной
причиной. Нужно хотя бы одно из двух (схема — объединение двух вариантов,
JSON Schema — `anyOf`). С `technical: true` вопрос, меняющий результат для
пользователя, и вопрос с минимумом (`declared`, `critical-path`) остаются
человеку при любом `maxSeverity`; `maxSeverity` тогда лишь дополнительно
ограничивает серьёзность технических вопросов. Без `technical` — правило
`maxSeverity` alpha.54. Согласие действует по текущей политике
процесса и в попытку и основание вопроса не закрепляется. `doctor`
(`questions`) и `init --plan` (`questions`) называют действующее правило
простыми словами (`line`, `lineEn`); `init --lead-technical-answers` пишет
`leadAnswers.technical: true` в новую политику. Порог закрепляется в попытке
при выдаче (`AttemptState.inputPolicy`) и в `executionDigest` не входит: смена
порога действует со следующей попытки без нового согласования. Порог и шкала
называются в запросе writer. Действующая серьёзность — самооценка, поднятая
до 10 минимумами, которые модель понизить не может: вопрос или допущение
называет критическую область или сам оценён потолком 10 (`declared`) либо попытка изменила путь из
`criticalPaths` (`critical-path`).

Исход ответа writer (`evaluateInput`) — после проверок защищённых путей,
HEAD и области записи: нарушение области остаётся `scope-violation` и не
прячется за вопрос.

| Ответ                                       | Исход                                                                                                                                        |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `completed: false`, вопрос не ниже порога   | `needs-input`: попытка не засчитана, черновик — `AttemptState.partial`, запрос `pending` в той же транзакции, что отказ                      |
| `completed: false`, вопрос ниже порога      | `unfinished` (нарушение запроса); вопрос записан отклонённым (`cancelled`, `closed.by: controller`) и работу не держит                       |
| `completed: false` без вопроса              | `unfinished`, как прежде                                                                                                                     |
| `completed: true`, допущение не ниже порога | `needs-input` без кандидата: самое серьёзное допущение становится вопросом (вариант `chosen` — выбор исполнителя)                            |
| `completed: true`, допущения ниже порога    | Допущения пишутся в попытку (`AttemptState.assumptions`), запрос reviewer их перечисляет; работа идёт дальше                                 |
| Порог 11 (автономный режим)                 | Остановок нет; все допущения записаны; критические — неблокирующие запросы ведущему (`kind: follow-up`); согласованное состояние не меняется |

`needs-input` — класс отказа без автоматического повтора
(`repairPolicy['needs-input']`: `stop`, выдачу не останавливает), корзина
отчёта `input`, код остановки `INPUT_REQUIRED` (класс `refused`). Остановка
вопросом возвращает попытку в предел `maxAttempts` и не тратит предел
незасчитанных отказов: ответ на вопрос последней попытки применяется без
сброса. Возврат ограничен: поручение получает не больше `maxAttempts`
остановок вопросом, возвращающих попытку, за всю жизнь (счёт — по записям
попыток с `failureKind: needs-input`, кроме прерванных остановкой
controller; сброс попыток его не обнуляет). Следующая остановка вопросом
засчитывается как обычная попытка (`counted: true`), поэтому цикл «вопрос →
ответ → применение» и обход вопроса отменой с повтором кончаются
исчерпанием попыток, даже если отвечает модель. Остановка, вернувшая
попытку, и её продолжение имеют один номер попытки; различает их
`failureKind: needs-input` записи и `counted` в `attempt.diagnosed`.

**Канонический запрос** (`InputRequest`, `schemas/input-request.schema.json`)
хранится в локальном пространстве `input-requests` у владельца — репозитория
поручения. ID (`IR-<24 hex>`) выдаёт controller детерминированно от попытки.
Вопрос и основание исходной попытки (`originBasis`: источник, digests графа,
постановки, политики, снимок контекста или `null`, база, закреплённая
`inputPolicy`) неизменяемы; ответы (`answers[]`, до 20) только дополняются;
`version` — CAS записи. Эти правила проверяет движок (записи — только через
его операции); от хранилища договор (`executionStoreContract`) требует хранить
запись целиком и отдавать её в списке без владельца с `owner` и `key`.
Жизненный цикл: `pending → answered → applied`,
альтернативные окончания — `cancelled` и `superseded` (с `successor`).

**Блокировка.** Блокирующий запрос в `pending` или `answered` сам держит
работу: claim его не выдаёт (и после новой редакции графа с согласованием),
`retry` — в том числе со сбросом — отказывает `INPUT_REQUIRED`, `repairDecision`
такую работу не чинит и не останавливает ею восстановление группы, приёмка
(`finish`) отказывает. `WorkState.hold` не занимается: снятие чужого
удержания ожидание ответа не обходит. Отмена работы закрывает её открытые
запросы.

**Продолжение.**

1. `answerInput(id, {text, optionId?, kind, actor, messageRef?},
expectedVersion)` — новая версия ответа с `answerDigest`; работу ответ не
   возобновляет. Тот же текст, вариант, вид, актёр, причина и правило приёма —
   прежний ответ без записи.
   Блокирующий вопрос (`kind: question`, `blocking`) адресован человеку:
   ответ с `actor.kind: lead` отклоняется `OPERATOR_ANSWER_REQUIRED` (класс
   `refused`, без записи, и до проверки повтора), если текущая политика не
   разрешила его `inputPolicy.leadAnswers`: при `technical: true` — вопрос не
   технический, с минимумом или серьёзнее `maxSeverity`; без него —
   серьёзнее `maxSeverity`. Правило `technical` требует причины (`reason`, до 1000 знаков; нет — `INVALID_INPUT`
   `reason-required`). Принятый ответ ведущего на блокирующий вопрос несёт
   `basis: technical | severity` и `reason` (в `answerDigest` не входят;
   `basis` — только у ответа ведущего, `technical` — только с причиной: это
   держат Zod и движок, JSON Schema описывает форму полей);
   `technical` показывается как «решено ведущим (технический вопрос)» в
   `status` (`works[].input.answerBasis`; `impact`, `leadMay` — правило, по
   которому ведущий может ответить на ждущий вопрос), `explain` (тогда
   `actor: lead`, `answer-input`), пакете передачи (`inputs[].impact`,
   `inputs[].answer.basis/reason`) и отчёте (`inputs.answeredBy.leadTechnical`).
   Неблокирующий запрос ведущему в ожидании
   (`kind: follow-up`) ведущий отвечает без разрешения; вопрос ниже порога
   записан закрытым и ответа не принимает; `operator` и `host` —
   как прежде. Кто ответил (актёр последнего ответа) показывают `status`
   (`works[].input.answeredBy`, `--human` — «ответил оператор»), сообщение
   `explain` («(ответил: …)»), пакет передачи (`inputs[].answer.by` и
   Markdown) и отчёт (`inputs.answeredBy {operator, lead, host}` и строка
   раздела Autonomy в md/html).
   `kind: requirement-change` — изменение требований: старый запрос
   заменяется (`supersedeInput`) ссылкой на новую ревизию, а не
   продолжается.
2. `Harness.inputContext(id, {messages?})` — неизменяемый снимок: действующий
   снимок графа и источник `input-answer` (`inputContextSource`): файл
   `input/<id>.md` (вопрос, варианты, ответ) и справка
   `input/<id>.manifest.json` (`{requestId, answerDigest, revision,
messages[{id, revision, digest}]}`). Версия ответа — в `version`
   источника (`r<N>`), не в `revision`. Снимок хранится по digest, но не
   активируется.
3. Ревью этого снимка — обычный `review-plan --context`. Согласование им не
   меняется: попытки графа сохраняют своё. `approve` со снимком, где ответ не
   применён, — `INPUT_REQUIRED`; `run` с таким снимком отказывает тем же кодом
   до вызова модели.
4. `proposeTarget(id, contextDigest)` — основание продолжения (только чтение)
   и причины, по которым применение сейчас откажет.
5. `applyInput(id, {answerDigest, expectedVersion, contextDigest,
targetDigest, actor, reset?})` — одна транзакция: точная версия запроса и
   последний ответ, вид `clarification`, работа всё ещё в исходной остановке
   (последняя попытка — попытка вопроса), неизменные граф и постановка,
   политика процесса применена, снимок несёт ровно этот ответ (manifest),
   проверки `approve` (`approvalCheck`: раунд ревью этого снимка, в режиме
   `agent` одобренный, актёр — режим политики) и пересчитанное основание
   совпадает с `targetDigest`. Затем — активация согласования снимка, запрос
   `applied` с `target` и обычный повтор (`retryIn`: те же правила, без
   сброса, если сброс не назван). Модель не вызывается; пауза оператора и
   чужие удержания остаются. Идут попытки графа или совместная проверка —
   `{applied: false, active}`, запрос и согласование не меняются; исчерпаны попытки или бюджет —
   `{applied: false, blocker}`, запрос остаётся `answered`. Повтор того же
   применения — `{applied: true, changed: false}`.
6. Claim закрепляет действующий снимок (`pinned.contextDigest`) и связывает
   ответ с попыткой (`AttemptState.input`) только при совпадении применённого
   основания с основанием выдачи. Runner загружает снимок по закреплению:
   writer и оба reviewer видят одни и те же байты. «Передано исполнителю»
   (`delivered`, событие `input.delivered`) — только по началу вызова writer
   этой попытки, один раз, под fencing; apply и claim доставку не
   подтверждают.

**Исходная остановка** держится, пока работа на попытке вопроса
(остановлена `needs-input` или готова после устаревшего применения) и её
собственная постановка прежняя — по содержанию без ревизии источника
(`originBasis.contentDigest`, у цели — `target.contentDigest`): пересинхронизация
трекера одной ревизией ни остановку, ни применённый ответ не обесценивает. Граф целиком не
сравнивается: согласование или добавление другой работы того же графа (у
DevContour граф — активная ревизия доски) остановку и применённый ответ не
обесценивает.

**Устаревшее применение.** Если до выдачи попытки с ответом сменились
постановка работы, политика или действующий снимок (новый снимок не несёт
этот ответ), транзакция claim возвращает запрос в `answered` с причиной
(`stale.reason`: `order | policy | context`, событие `input.stale`; значение
`graph` больше не ставится): работа не выдаётся без ответа и ждёт нового
снимка, ревью и `applyInput` (готовая работа на исходной попытке применяется
так же, как остановленная). Снимок, который несёт тот же ответ (например, с
ответом на второй вопрос графа), основание не обесценивает.

**Новая редакция постановки.** Если постановка самой работы изменилась,
продолжение исходной остановки невозможно (`applyInput` и `proposeTarget`
называют выход). Выход с сохранением ответа: `supersedeInput` (преемник —
новая редакция работы), затем `inputContext` (принимает заменённый вопрос с
ответом), `review-plan` со снимком и перенос: `carryInput(id, {contextDigest,
actor})` — одна транзакция с правилом переноса, отсутствием неприменённых
ответов в снимке, барьером политики, ревью и актёром по правилам хоста
(`InputHost.review`) или `approvalRules`, без идущих попыток графа
(`{carried: false, active}`), пределами попыток и бюджета до активации
(`{carried: false, blocker}`), активацией (`InputHost.activate` с `mode:
'carry'` или согласование графа), записью цели в заменённый запрос и обычным
повтором работы, остановленной вопросом (иной отказ остаётся по своим
правилам). Перенесённый ответ связывается с попыткой при выдаче и
подтверждается вызовом writer, как применённый; если до выдачи согласование
ушло на снимок без него, цель снимается, `stale` записывается (состояние
`carry-stale`), и работа ждёт: выходы — новый перенос или снять перенесённый
ответ (`cancelInput`), тогда работа продолжится без него; запись замены
(преемник, `carry`, причина) остаётся в `closed.previous`. Изменение требований сравнивается по содержанию постановки
без ревизии источника (`originBasis.contentDigest`). Экспортированный
`unappliedInputs` требует правило переноса движка (`mayCarry`, проще —
`Engine.unappliedInputs`). У standalone тот же снимок можно согласовать и
обычным `approve`/`run`. Перенос решается в момент переноса
(`Engine.carryAllowed`), а не замены: уточнение — когда исходная остановка
уже не держится, изменение требований — только когда изменилась постановка
самой работы; только последняя версия ответа. Порядок «замена, затем новая
редакция» тоже ведёт к переносу; `closed.carry` — сведение о моменте замены.
Пока остановка держится, продолжение — только `applyInput`. Снимок с новым
ответом не становится действующим и через `approve`/`run`, пока в графе идут
попытки (`NOT_READY`; `run` отказывает до ревью). `inputContext` отказывает
для неблокирующих и закрытых без замены запросов.

**Закреплённый снимок.** У попытки с `pinned.contextDigest` записанный
снимок контекста обязан совпасть с закреплённым — при записи контекста
runner и при приёмке (`APPROVAL_STALE`): загрузчик хоста, не учитывающий
закрепление, отказывает до вызова writer; не найденный закреплённый снимок —
отказ этой работы при загрузке (`needs-lead`, причина `preflight`, попытка не
засчитана, очередь не останавливается; explain — фаза `preflight` и неполные
входы работы, `StopInput.work.preflight`). `InputHost.contextDigestOf`:
`null` — снимок «без контекста» (загрузчик обязан вернуть пусто),
`undefined` — хост не связывает согласование с контекстом (проверки нет).

**Вопрос вне схемы.** Пределы вопроса называются в запросе writer; схема
договора строгая. Ответ вне схемы, в котором есть вопрос, controller приводит
к схеме (усекает текст, исправляет ID вариантов, оставляет шесть вариантов,
ограничивает серьёзность) и решает как обычно; что исправлено — в поле запроса
`normalized`. Ответ вне схемы без вопроса — отказ, как прежде. Вопрос и
допущения маскируются полным окружением вызова до записи; решения взятого
кандидата переоцениваются по политике новой попытки, решения продолжаемого
черновика видят writer и reviewer.

События `input.requested`, `input.answered`, `input.applied`,
`input.closed`, `input.delivered` и `attempt.assumptions` несут ID, digests и
числа — без текста вопросов, ответов и допущений.

**Проекции.** `status`: у поручения `input {requestId, state, version,
severity}` (`awaiting-answer | answered-not-applied | applied-awaiting-claim
| delivered`) и число неблокирующих запросов `followUps`. `explain`:
ожидание ответа — человек, `answer-input`; ответ без применения — ведущий,
`apply-input` с причиной, по которой применение сейчас откажет; сообщение
называет усечённый вопрос, варианты, версию и digest ответа, число решений
исполнителя; неблокирующие запросы — отдельные диагнозы ведущего. Пакет
передачи — блок `inputs` (усечённый вопрос, варианты, версия, digest и
начало ответа до 500 знаков, digests основания). Отчёт — только числа
(`inputs`): ответ целиком в отчёт не попадает.

### RunEvent

`{apiVersion, seq, at, type, graphId?, workId?, runId?, attempt?, payload}`.
`seq` строго возрастает. Нагрузка каждого из типов (`eventPayloads`) — закрытая
схема: лишних полей нет, поэтому токен владения, секрет или объект попытки в
событие не попадает.

`attempt.stage` — граница стадии попытки: `{timingId, stage, phase:
'started'|'finished', at, durationMs?, outcome?: 'passed'|'failed'}`, конверт
несёт `graphId`, `workId`, `runId`, `attempt`. Стадии — те же, что замеры
`AttemptState.timings`: `dependency-store`, `implementation` /
`implementation-reuse`, `candidate-environment:<шаг>`, `integration-wait`,
`<фаза>-test:<gate>`, `<фаза>-consumer:<репозиторий>:<gate>`,
`<фаза>-recheck:<gate>`, `<фаза>-review`, `integration-environment:<шаг>`,
`integration-consumer-environment:<репозиторий>:<шаг>`. На стадию — одно
`started` и не больше одного `finished` (у него `durationMs` и `outcome`);
`at` и `durationMs` — по часам движка и совпадают с замером. Событие пишется
в той же транзакции `run.timing.started`/`run.timing.finished`, что и замер,
под fencing: утративший владение не пишет ни замера, ни события. Повторное
закрытие замера ничего не меняет и событий не создаёт.

`attempt.liveness` — переход живости попытки по обходу controller:
`{state, previous, lastMovementAt, idleMs, activity?: {kind:
'agent'|'gate'|'step'|'command', label}, cpuUnavailable?, action?:
'stop'|'report', snapshot?}`; `joint.liveness` — то же с `verificationId`; `action` и `snapshot` — только у `stalled` (см. «Зависшие
попытки»).

`work.retried` — поручение возвращено в очередь `engine.retry`: `{by:
'operator'|'recovery'|'host', reset, spent?, reasonLength?}`. `by` — третий
аргумент `retry(workId, reset?, by?)`: CLI `retry` передаёт `operator`,
восстановление очереди (`repair`, эпизод по свойству) — `recovery`, хост без
актёра — `host` (по умолчанию). `reset` — сброс исчерпанного предела; `spent` —
засчитанные попытки до сброса (сброс обнуляет `WorkState.attempt`),
`reasonLength` — длина причины сброса; текста причины в событии нет. Повтор
без изменения (поручение уже в очереди) и отказ повтора событий не создают.

`work.reopened` — новая редакция графа изменила постановку уже принятого
поручения (доработка после приёмки, `WorkState.rework`): `{revision, budget:
'fresh'|'carried', acceptedSha, spent}`. `revision` — номер доработки (1 —
первая), `acceptedSha` — результат прежней приёмки, `spent` — засчитанные
попытки принятой редакции. `fresh` — у доработки свой предел попыток
(`WorkState.attempt` и `neutralFailures` с нуля): это следующее изменение, а
не повтор проваленного договора. Своих пределов у доработок поручения не
больше `MAX_REWORK_BUDGETS` (3); дальше — `carried`, счётчик прежней
редакции переносится, и исчерпание снова снимает только `retry --reset`
человека. Каждую доработку открывает новое согласование графа, то есть
раунд ревью плана нового digest. Изменённая постановка **непринятого**
поручения события не пишет и счётчик (`attempt`, `neutralFailures`) не
трогает: новой редакцией предел не обойти. Поручение с новым ID — новая
задача со своим счётчиком (так было и раньше); от переименования ради
попыток защищает раунд ревью плана, который согласует новую редакцию. Пишется сразу за
`graph.registered` той же транзакции.

`work.rework-abandoned` (0.1.0-alpha.66) — доработка после приёмки
оставлена: `{by: 'operator'|'host'|'graph', revision, acceptedSha, restored,
hadAttempt}`. `cancel` открытой доработки (и повтор `cancel` для доработки,
отменённой alpha.65 и старше, — состояние `cancelled` с `WorkState.rework`)
или новая редакция графа, убравшая поручение с открытой доработкой, не
отменяют задачу: работа возвращается к принятой редакции — `done`, результат
`acceptedSha`, засчитанные попытки принятой редакции; идущая попытка
доработки отменяется (`attempt.cancelled`, `hadAttempt: true`). `restored` —
поручению возвращена принятая постановка (`WorkState.rework.acceptedOrder`,
пишется с alpha.66 при открытии доработки); у доработки прежней версии
постановки нет, остаётся текущая, а `WorkState.rework.abandoned.orderDigest`
помнит её содержание: та же постановка в новой редакции графа снова
открывает доработку, принятая — нет. Счёт доработок со своим пределом
(`budgets`) сохраняется: отказом и новой доработкой предел не обойти.
Решение — `cancel`, а не отдельная команда: принятый результат `cancel` и так
не отменяет (`NOT_READY`), и у ведущего, который отменяет ненужную доработку,
не остаётся способа потерять приёмку (прежде отмена доработок выводила
принятые работы из выпуска). Ответ `cancel` — `abandoned: true`, `status:
done`.

`work.cancelled` — поручение отменено: `{by: 'operator'|'host'|'graph',
hadAttempt}`. `engine.cancel(workId, reason?, by?)` (CLI `cancel` — `operator`,
по умолчанию `host`); `graph` — новая редакция графа убрала поручение.
`hadAttempt` — отменена и активная попытка: её `attempt.cancelled` идёт в той
же транзакции перед `work.cancelled`, у которого тогда те же `runId` и
`attempt`. Повторная отмена отменённого событий не создаёт.

`base.moved` — сдвиг ref базы `fencedRefMove(store, fence, timeoutMs?, by?)`:
`{by: 'operator'|'controller'|'host'}` (по умолчанию `host`), одно событие на
репозиторий, в той же транзакции, что проверка владения и `git update-ref`.
Отказ проверки или Git (CAS) отменяет и событие. `moveBase` без `move` событий
не пишет: у него нет хранилища.

`attempt.diagnosed` — причина отказа попытки: `{failureKind, cause, counted}`,
конверт несёт `graphId`, `workId`, `runId`, `attempt`. Пишется сразу за
`attempt.failed` (и `attempt.expired`) в той же транзакции под fencing.
`cause` (`environmentCauses`): `sandbox-launch`, `sandbox-network`,
`sandbox-filesystem`, `sandbox-policy`, `sandbox-process-list`,
`sandbox-signal`, `sandbox-browser`, `dependency-network` — ставит gate в
точке обнаружения (`TaskFailure.diagnosis`; `sandbox-process-list`,
`sandbox-signal`, `sandbox-browser` — см. «Список процессов в песочнице
проверок» ниже); `transport`, `preflight`
(`BlockedError` до работы), `provider-auth`, `provider-limit`, `stalled`,
`shutdown` (прерывание штатной остановкой), `lease-expired` — по классу отказа
и его признакам; `process-reap` — потомков сдерживаемой команды (gate,
вызова runtime) не удалось остановить или пересчитать (`ReapFailure`):
проверка не пройдена и на том же дереве не повторяется;
`cleanup` — ресурсы попытки не освобождены: не убраны временные каталоги
завершившейся проверки или не завершилась очистка окружения (lifecycle
teardown) без отказа самой работы; при отказе работы класс и причина — его
(`CleanupFailure.original`); `resource-busy` — порт ресурса аренды занят до
начала фазы процессом, который не записан как переживший остановку прежней
попытки (или записанный не удалось остановить), см. «Ресурсы `port`» ниже;
`other` — отказ окружения без известной причины; `none` —
отказ не окружения. Хост, вызывающий `engine.fail`, может передать
`options.cause`; движок приводит её к классу (у отказа не окружения — всегда
`none`). `counted` — отказ засчитан в предел попыток (`maxAttempts`): не
засчитаны отказы до работы (`blocked`), окружения и провайдера, остановка
вопросом (`needs-input`) в пределах своего предела, истёкшее владение и
прерывание остановкой;
зависание (`stalled`) засчитано. Отчёт
считает попытки засчитанными по тому же правилу; остановку вопросом — по
`counted` её `attempt.diagnosed` (без события — засчитана). Отказ до работы с классом
не окружения получает причину `preflight`. Текста отказа в событии
нет.

`finished` может не прийти: поздний finish владельца, утратившего срок,
отклоняется (runner его не повторяет), упавший процесс его не пишет, а `adopt`
и recovery открытые замеры прежнего владельца не закрывают. Такая стадия
остаётся открытой и в замере, и в журнале; её конец — событие конца попытки
(`attempt.expired`, `attempt.failed`, `attempt.cancelled`,
`attempt.recovered`, `work.accepted`). Потребитель журнала обязан обрабатывать
незакрытые стадии.

Чтение журнала терпимо к типам более новых версий: событие типа, которого нет
в `eventPayloads`, возвращается как `UnknownRunEvent` —
`{apiVersion, seq, at, graphId?, workId?, runId?, attempt?, type: 'unknown',
original}` (исходный тип, не длиннее 200 символов; нагрузка не возвращается).
`RunEvent` = известные события (`KnownRunEvent`) | `UnknownRunEvent`: нагрузка
доступна после сужения по `type` (`e.type !== 'unknown'`) или у
`KnownRunEvent`. Тип `ExecutionStore.events()` прежний (`RunEvent[]`), поэтому
хранилища хоста, возвращающие или делегирующие события, компилируются без
изменений. Разбор — `readRunEvent`, схема чтения — `readRunEventSchema`. Запись строгая
(`runEventSchema`, опубликованная `run-event`): `unknown` записать нельзя;
известный тип с нарушенной нагрузкой при чтении — отказ.

`transactionKinds` — имена транзакций исполнения; совпадают с сохранёнными
типами событий журнала хоста (`run.claimed`, `task.done`, `run.failed`,
`scheduler.error`, …). `workflow.updated` пишет только локальные записи
технической очереди (`workflow-jobs`) и событий журнала не создаёт.
`usage.recorded` пишет только локальные записи учёта вызовов (`usage`): начало
вызова вместе с проверкой бюджетов, ход и итог вызова, закрытие прерванных,
закрепление атрибуции прежних записей; событий журнала не создаёт.
`checks.recorded` пишет только локальные записи корпуса (`check-suites`):
начало, продление и завершение операции подтверждения, решение и новую
версию. `checks.spike` пишет только локальную запись эксперимента
выполнимости (`spikes`). `checks.adopted`, `checks.awaiting-operator` и
`checks.adoption-abandoned` меняют принятую поручением версию корпуса и
удержание выдачи (`work.held`, `corpus.adopted`). Эпизод по свойству меняется
транзакциями `recovery.*`, отказом и выдачей (`work.recovery`).
`workspace.verification.started`, `workspace.manifest`, `workspace.evidence`,
`workspace.verified`, `workspace.failed` — транзакции совместной проверки
(`joint.started`, `joint.finished`; у прерванной до результата gates —
`interrupted: true`). `workspace.budget-reset` — явный сброс бюджета
совместных проверок набора: запись `joint-budget-resets` и событие
`joint.budget-reset`. Договор хранилища (`executionStoreContract`)
проверяет, что адаптер сохраняет `interrupted` совместной проверки и
пространство `joint-budget-resets`; хост, который заводит проверку своей
операцией, передаёт её в необязательном `startVerification`. `config.started`, `config.reconfigure-*`
и `config.reconfigured` меняют применённую политику и запрос операции
(`policy.applied`, `policy.reconfigure`). `base.moved` — проверка владения
операцией и CAS-сдвиг ref базы; записей не создаёт, событие — `base.moved`.

### ValueReport

Отчёт об эффекте (`harness report`, `valueReport` из `devcontour-harness/report`
и корня пакета; `reportVersion: 1`, `valueReportSchema`,
`schemas/value-report.schema.json`). Отвечает на вопрос «что дал harness на
этом проекте» данными самого проекта: только наблюдения (счёт и
длительности), без «сэкономленных часов» и сравнения «с harness и без»
(базы до harness в состоянии нет).

Вход (`ValueReportInput`) — те же формы, что у `ExecutionView`: `works`,
`attempts`, `calls` (`locals('usage')`), `reviews` (`locals('reviews')`),
`events`, `graphs`. `collectReportInput(store)` собирает его из любого
`ExecutionStore` одним `read` и страницами `events` по 500; `Harness.report()`
— то же по каталогу состояния. Параметры: `since` (включительно; ISO-время с
поясом, дата `YYYY-MM-DD` или `Nd`/`Nw` до `asOf`), `until` (не
включительно), `asOf`, `noTitles`, `label`, `stateDir`, `harnessVersion`.
`reportMarkdown(report)` и `reportHtml(report)` — чистые рендеры: те же
разделы и числа; HTML — один файл без скриптов, шрифтов, изображений и
внешних ссылок (CSP `default-src 'none'; style-src 'unsafe-inline'; img-src
data:`), светлая и тёмная схема по `prefers-color-scheme`, таблицы
прокручиваются на ширине телефона, столбики недель (inline SVG) — от 3
активных недель. Модуль `devcontour-harness/report` без `node:*` и без zod. Запись
файла отчёта (`report --out`) — `writeReportFile(out, stateDir, text)` из
корня пакета (не из `./report`: она использует `node:fs`): текст пишется во
временный файл каталога цели и переименовывается поверх цели, без записи
сквозь symlink и жёсткие ссылки; цель внутри каталога состояния, symlink,
не обычный файл или файл с `nlink > 1` — `PATH_CONFLICT`, недоступный
каталог — `INVALID_INPUT`; права прежнего файла сохраняются, новый —
`REPORT_FILE_MODE` (`0600`).

**Детерминизм.** Тот же вход и параметры — те же байты JSON, Markdown и HTML
при любом порядке входных массивов, часах и часовом поясе. `asOf` по
умолчанию — последняя метка времени в данных (событие, начало или конец
попытки и вызова, раунд ревью), не часы; с `until` раньше неё — `until`.
Время — UTC ISO, недели — ISO (понедельник, UTC), числа без локали.

**Определения.**

- Принятое поручение — `WorkState.status = done` с успешной попыткой;
  принявшая попытка — последняя `succeeded`. Поручение `done` без успешной
  попытки не имеет времени приёмки и не входит в принятые ни в каком окне
  (`coverage.doneWithoutAttempt`). В окно входят: принятые — по времени
  приёмки, попытки и вызовы — по началу, раунды ревью и события — по своему
  времени.
- Попытки поручения считаются по записям попыток, а не по
  `WorkState.attempt` (сброс возвращает счётчик к 0). Отчёт, пакет передачи
  и «принято с первой попытки» — цифры за всю жизнь поручения, вместе с
  попытками прежних редакций доработки после приёмки (`WorkState.rework`);
  `status`, `explain` и `harness view` считают только попытки текущей
  редакции.
- Корзины отказа попытки (`failureBucketOf`): `defect` (`gate`, `review`,
  `scope-violation`), `incomplete` (`empty-result`, `unfinished`,
  `needs-lead`, `context-exhausted`), `integration` (`stale-base`, `merge`), `environment`
  (`environment`, `provider-auth`, `blocked`, истёкшее владение), `time-limit`
  (`timeout`), `tool` (`review-protocol`), `operator` (`cancelled`), `budget`,
  `unknown`, `unclassified` (попытка без класса — записана до
  классификации; не «дефект»). Прерванная штатной остановкой
  (`interrupted: shutdown`) — не отказ, считается отдельно.
- Первая попытка — у принятого поручения засчитанная попытка одна
  (засчитанные — без `environment` и прерываний); если, кроме принявшей,
  засчитаны только отказы без класса, — неизвестно (`unknown`, `bound:
lower`). `firstPassRaw` — попытка вообще одна.
- Возвращено (`sentBack`) — принятое поручение с попыткой `defect` до
  принявшей. Поручения, у которых до приёмки только отказы без класса
  (`unknown`, `unclassified`), не считаются, а идут в `unknown`: тогда
  `bound: lower` («≥ N», «M more without a class»). Без них, но если часть
  поручений вернули только отказы gate подготовки (установка зависимостей,
  возможна сеть; `sentBackSetupOnly`), — `bound: upper`; оба сомнения
  сразу — `bound: unknown` и диапазон `sentBackRange` («1–3 of 5»); иначе
  `exact`.
- Ревью после зелёных gates (`afterGreenGates`) — ревью кандидата отклонило,
  хотя каждый обязательный gate прошёл на том же SHA (и той же версии
  проверок); диагностика, не точность reviewer.
- Срок от согласования до приёмки — от `wait.approvedAt` первой попытки
  (иначе `WorkState.approvedAt`, его переписывает повторное согласование —
  `leadTimeFallback`) до конца принявшей попытки; включает очередь и паузы.
- Расход: известная цена — правило `knownCost`; на принятое поручение —
  известный расход окна / принятые окна. `callsRecorded` попытки значит
  «учёт её вызовов полон», а не «вызовы есть»: записи вызовов попытки без
  флага входят в её расход, но лишь нижней границей
  (`attemptsPartialCalls`); без флага и без записей расход неизвестен
  (`attemptsWithoutCalls`). `bound: exact` — только если все вызовы окна
  завершены с полными счётчиками и ценой и у всех попыток окна учёт полон;
  иначе `lower` («≥»); без единой известной цены при неизвестных —
  `unknown` (`value: null`), не `$0`. Расход отклонённых попыток
  (`cost.rejected`) и расход отказов окружения (`environment.neutral`) —
  одна и та же атрибуция по всем завершённым попыткам окна. `environment.neutral`
  — вся корзина `environment`, включая зависания (`stalled`), хотя они
  засчитаны в предел попыток.
- Пробел записи определяется по порядку журнала (`seq`), а не по времени:
  `at` события — часы записи, время попытки — часы движка.
- Действия человека — только записи с актёром-человеком: решения recovery
  с источником `operator`, повторы и отмены с `by: operator` (`work.retried`,
  `work.cancelled`). Удержания (`work.held`) актёра не называют (удерживают и
  операции хоста, например смена контракта): они показаны отдельно (`holds`)
  и в действия человека не входят; так же `cancelledAttempts` — отменённые
  попытки по записям попыток. Повторы восстановлением (`recovery`), сдвиги
  базы controller и отмены новой редакцией графа — автоматические.
- Вмешательства по событиям (`actions.recorded`): числа в окне по актёрам —
  повторы, сбросы, отмены (и отмены без активной попытки), сдвиги базы.
  Запись начинается с первого события версии, которая их пишет
  (`work.retried`, `work.cancelled`, `base.moved`, `attempt.diagnosed`;
  `recorded.from`); раньше него действие могло быть, но не записано. Нет ни
  одного такого события в журнале — `recorded: null`, `withAction` — нижняя
  граница, «без действий человека» (`withoutAction`) не измеримо (`value:
null`, `bound: unknown`). С записью: `recorded.bound: lower`, если в окне
  есть попытки, события или принятые поручения раньше `from` или пробел записи
  (`gaps`: новая попытка после отказа или отмены без `work.retried` и без новой
  редакции графа между ними — работала версия без этих событий, например
  после отката и повторного обновления), иначе `exact`. Пробел, не оставивший
  такой попытки, не обнаруживается — это постоянное ограничение. Суммы
  `retries`/`resets` — только при `bound: exact`, иначе `null` (числа по
  актёрам с границей — в `recorded`). Сдвиги базы — всегда нижняя граница
  (`baseMovesBound: lower`, сумма `baseMoves` всегда `null`): перенос вне
  `fencedRefMove` (`moveBase` без `move`) не пишется; к поручениям они не
  относятся.
- Поручение «без действий человека» известно, если оно начато не раньше
  `from` (начало — согласование первой попытки `wait.approvedAt`, иначе
  `WorkState.approvedAt`, иначе начало первой попытки), без пробела записи,
  и у него нет действий без актёра: повтора или отмены хостом (`host`) и
  удержания (`work.held` — его ставят и человек, и операции хоста). Прочие
  принятые без действия оператора идут в `unknown` обеих мер (`bound:
lower`).
- Подпричины окружения (`environment.causes`): отказы окружения окна по
  `attempt.diagnosed` своей попытки — строки `{cause, count, counted}` (по
  убыванию числа); отказ без события (записан раньше) — `undiagnosed`, тогда
  `bound: lower`. Нет ни одного `attempt.diagnosed` в журнале — `causes:
null`.
- Отказы окружения (`environment.share`) — среди классифицированных; если
  есть отказы только в gates подготовки (`setupCheckFailures`), доля —
  нижняя граница («at least», «M more may be environment»).
- Паузы — `control.paused` до следующего `control.resumed` (открытая — до
  `asOf`); время паузы — её пересечение с окном. Согласования — события
  `graph.approved` для графов, у которых такие события есть; для прочих —
  текущее согласование графа в состоянии (`source: state` или `mixed`); нет
  ни того ни другого — `source: none`, число неизвестно, а не ноль.

**Малые выборки и неизвестное.** `ReportMeasure` — `{value, n, unknown,
bound}`, `bound` — `exact | lower | upper | unknown`; неизвестное не
показывается нулём. Процент — только при знаменателе от 20, иначе «k of n».
Медиана и p75 — от 5 значений, иначе `null` и значения в `values`. Меньше 3
принятых поручений в окне — `summary.status: not-enough-data` (сырые
счётчики вместо заголовочных чисел). Сводка — не больше 5 чисел (принятые и
первая попытка, возвращено, срок, расход на принятое, отказы окружения),
каждое с предложением и основанием (`basis`). Раздел `limitations` есть
всегда: постоянные ограничения и найденные в данных (попытки без класса,
без замеров, без учёта вызовов, вызовы без цены, начало событий, смена
версии движка, усечения).

**Приватность и пределы.** В отчёт попадают только перечисленные поля: нет
prompt, вывода runtime, текстов находок, ошибок и причин, fencing-токенов.
Пути evidence — относительно `stateDir`; путь вне него — `…/<имя файла>`,
домашний каталог не печатается. `noTitles` убирает заголовки поручений и
метку проекта. Пределы (`REPORT_LIMITS`): 50 строк поручений (новые сверху),
50 ссылок evidence, 12 активных недель (ранние свёрнуты в `earlier`,
недели без активности — `gap`), 50 строк gates и стадий; JSON ≤ 512 КБ,
HTML ≤ 1 МБ. Усечение отмечено флагом и ограничением.

### OperatorView

Представление оператора (`harness view`, `harnessView(options)` корня пакета;
чистые `operatorView(input, options)` и `workDetailView(input, workId, options)`
из `devcontour-harness/projections`; загрузчик для node —
`collectOperatorViewInput`). Один JSON-документ только для чтения, который
рисует панель оператора. Схемы — `operatorViewSchema`, `workDetailViewSchema`
(`schemas/operator-view.schema.json`, `schemas/work-detail-view.schema.json`).

**Версии.** `viewVersion` — мажорная (сейчас `1`): меняется, только когда поле
удалено, переименовано или меняет смысл. `viewRevision` (сейчас `5`; ревизия 3 — `unused` у стадий попытки; ревизия 4 — обновления, кто двигает очередь, порядок снятия блокировок, где применённый ответ, класс отказа попытки, связка с источником задач, варианты вопроса и прогноз выпуска; ревизия 5 — прогноз по всему выпуску, этап настройки, проверка в источнике, запуски попыток) растёт при
добавлениях: необязательное поле, новое значение перечисления с безопасным
чтением по умолчанию, новый раздел. Читатель принимает свою мажорную версию с
любой ревизией и игнорирует неизвестные поля. Выпущенная мажорная версия
держится всю линию `0.1.x`; `--view-version N` оставит прежнюю доступной ещё
минимум один минорный выпуск после появления новой. `stateVersion`
копируется как есть.

**Разделы.** `settings` (действующая политика: роли и правила ревью по
областям, пороги, бюджеты, тайм-ауты, слой `lean`, `defaulted` — пути,
взятые из умолчаний), `works[]` (порядок `status`: этап, сводка попыток,
блокировки, вопрос, расход с границей `exact | lower | unknown`, принятое),
`reviews[]` (план, контракт и код), `questions[]` (открытые состояния
`inputStates`, `answerableBy`, `impact`), `escalations[]` (остановки, которые
ждут человека или ведущего, эскалации ревью, пауза очереди), `drift[]`,
`progress` (счётчики по всем работам), `history` (ряды по интервалам окна:
нагрузка, начатые и упавшие попытки, gates пройденные, упавшие и
перенесённые, расходы и остаток до окна), `health` и `activity[]` (ревизия
2). `decisions[]` harness выдаёт с ревизии 8. Обязательные сочетания
(`decisions[]`; `verification[]`: `executed` требует `by` и `attempt`,
`reused` — `attempt`) проверяет Zod-схема; опубликованная JSON Schema их не
выражает. Поля alpha.55
(`attempts.lastFailure`, `blockers[].plain`, `verification[]`,
`questions[].impact/plain`) заполняются, когда их даёт `status`.

  связки (`basis: scope`, задачи, не переданные в harness, — с весом 0), без
  связки — работы harness (`works`); отменённые не входят. Вес: принятая
  работа — 1, работа на этапе попытки — доля этапов до текущего (`prepare`,
  `writer`, `gates`, `review`, `integration` → 0, 0,2 … 0,8), остальные — 0;
  `percent` — округлённая сумма весов к объёму. `time {elapsedMs?,
remaining?, humanWait, line}`: `elapsedMs` — от начала первой попытки работ
  объёма; `remaining {loMs, hiMs, samples, attemptsPerTask}` — незавершённая
  доля объёма × длительность попытки (p50 для нижней, p90 для верхней
  границы, ближайший ранг по закончившимся, не прерванным попыткам, не меньше
  5 образцов) × попыток на принятую задачу (без принятых — 1); нижняя граница
  делится на `concurrency` (параллельно), верхняя — нет (последовательно).
  Образцов меньше — поля `remaining` нет, строка говорит «неизвестно»; нулём
  неизвестное не показывается. `humanWait {works, ms}` — работы, которые
  сейчас ждут человека или ведущего, и сколько ждут; в прогноз не входит.
  `assumptions` — эти допущения словами на языке представления. Это
  наблюдение, а не обещание. Прошедшее время зависит от часов, поэтому в
  `source.token` входят точки отсчёта (`time.startedAt`, `humanWait.since`), а
  `elapsedMs`, `humanWait.ms` и `time.line` — нет.

**Ревизия 5 (0.1.0-alpha.65).** Добавления, все необязательные в схеме;
читатель ревизии 4 их игнорирует, смысл прежних полей не меняется, кроме
объёма прогноза (ниже):

- `forecast.progress` считает **весь выпуск**: все задачи всех снимков связки
  (доска, а не последний срез `run --source`) и все работы состояния; принятое
  — 100 %, отменённое — вне объёма. Задача, которой нет в последнем чтении
  связки и у которой нет работы harness (удалена с доски или выведена из
  области), в выпуск не входит. `basis` по-прежнему `scope` (есть связка)
  или `works`. Вес работы — наибольший этап, до которого дошла любая её
  попытка (`works[].attempts` по замерам): повтор готовность не снижает.
- `forecast.progress.added[] {key, workId?, at, before, after, line}` —
  задачи, добавленные в выпуск после его начала (первый снимок с ними позже
  первого снимка связки): «добавлена задача WEB-3 (задач 2 → 3)». Не больше 10.
- `forecast.progress.works[] {workId, key?, percent, attempt? {n, max},
retry?, line}` — готовность каждой незаконченной работы (не больше 50,
  остальные — `truncated.forecastWorks`; документ сверх предела размера теряет
  этот список первым) и её засчитанная попытка из предела; `retry: repair` — идущая попытка исправляет замечания прошлой,
  `answer` — продолжает после вопроса исполнителя. `line` — «WEB-2: ~60 %,
  попытка 2 из 3, исправляет замечания», «WEB-1: принято».
- `forecast.time.startedAt` — начало выпуска: первое появление в снимке любой
  задачи текущего выпуска или первая попытка объёма, что раньше; `finishedAt` — когда всё принято и ничего не
  идёт, конец последней попытки (`elapsedMs` тогда — до него, а не до «сейчас»).
- `forecast.time.rough {loMs, hiMs, samples, attemptsPerTask}` — при 1–4
  закончившихся попытках выпуска: разброс от самой короткой до самой долгой
  попытки, строка «осталось ~X – Y (грубо, по N попыткам)». От 5 попыток —
  прежний точный `remaining` (p50–p90). `estimate` — `precise`, `rough`,
  `unknown` (ни одной закончившейся попытки — «неизвестно») или `nothing`.
- `works[].attempts.rework {revision, fresh, acceptedSha, acceptedAt?}` —
  доработка после приёмки (как `attemptSummary.rework` у `status`); числа
  `attempts` и `line` — только её попытки. `forecast` считает такую работу
  принятой ранее: вес 1 (прогноз не падает ниже доли, принятой прежней
  редакцией), `progress.done` её включает, `progress.left` — нет;
  `progress.rework` — число открытых доработок, строка — «…, доработок после
  приёмки: 1», `percent` не выше 99, пока доработка открыта, `finishedAt`
  нет. Остаток доработки (1 − наибольший этап её попыток) входит в «осталось»
  времени. `progress.works[]` у неё — `rework: true`, `percent` — готовность
  доработки, `line` — «WEB-1: принято ранее; доработка ~40 %, попытка 1 из
  3». Поля ревизии 5, все необязательные.
- `works[].attempts.runs` — запусков всего, в том числе незасчитанных (вопрос
  исполнителя, отказ окружения, остановка), только когда их больше
  засчитанных; `used` — только засчитанные в предел `max`. «Попытка» во всех строках — засчитанная: сводка
  `attempts.line` при расхождении пишет «запусков 3, из них засчитано попыток
  2; …; осталось попыток 1 из 3», строка этапа — «попытка 2 из 3 (запусков 3)».
- `sourceReviews[] {connector, provider, tasks[] {taskId, key?, workId,
column, since}, line}` — принятые работы, оставленные в источнике задач на
  проверку человеку (`completion.mode: review-only` или колонка доставки не
  `done`): последняя операция доставки задачи (любого состояния — более
  новая идущая или конфликтная заменяет прежнюю) доставлена, принята и
  перенесла её в такую колонку,
  а по последнему чтению связки задача не закрыта и не отменена. `line` —
  «ждут вашей проверки в Relay: WEB-1, WEB-2». Каждая задача — ещё и
  эскалация `{code: SOURCE_REVIEW, actor: operator, action:
review-in-source, workId, subject: key, since}`. `status --human` печатает
  «От вас: …». Задач сверх 50 — `truncated.sourceReviews`.
- `stage {name, lines}` — `setup`, пока работ нет (`lines`: «Идёт настройка
  harness», «Задач пока нет»), иначе `work` (`lines` пусты).
- **Документ настройки** (`setupViewSchema`, `schemas/setup-view.schema.json`):
  `{viewVersion, viewRevision, generatedAt, source, stage {name: setup, lines},
setup {waitingFor}}` — ответ `view --repository`, когда harness в проекте ещё
  не настроен. `view --repository <корень>` читает состояние и политику из
  `.harness/project.json` при каждом вызове (относительный `paths.state` — от
  корня репозитория): панель, запущенная до настройки, подхватывает их, когда
  они появятся. Документ настройки отдаёт только `view --repository`: нет
  manifest (`waitingFor: project`) или manifest есть, а ни привязки, ни базы
  состояния, ни файла политики ещё нет (`policy`). `view --state` сохраняет
  прежнюю форму: с `--policy` — пустой обзор (с `stage: setup`), без привязки
  и политики — прежний отказ `POLICY_REQUIRED`. `status` до настройки — не
  NOT_FOUND, а пустой статус с полем `setup {waitingFor: project | state,
lines, linesEn}`: `--repository` без manifest или с manifest, но без базы
  состояния; `--state` — только каталог, которого нет совсем. Неисправности
  остаются прежними отказами: база состояния без привязки (NOT_FOUND у
  `status`, POLICY_REQUIRED у `view`), существующий пустой каталог `--state`,
  явный `--policy` без файла. Договор CLI и `harness capabilities` называют
  `--repository` у `view` и `status`, а `--state` там — необязательный (одно
  из двух нужно): поддержку видно по флагу, без разбора схемы ответа.

**Токен.** `source.token` — SHA-256 канонических байтов документа без часов
проекции — `generatedAt` и границ окна `history.from`, `history.to` (окно
кончается в момент запроса) — и без самого `source.token` (ключи
отсортированы). Договор: при тех же языке, окне (`--window`, `--bucket`),
работе (`--work`) и `--no-titles` равный токен ⇔ то же содержимое; два
запуска над неизменным состоянием дают один токен (с 0.1.0-alpha.56; в
alpha.55 токен менялся при каждом запуске). Время остановки без начала
этапа (`escalations[].since`) берётся из хранилища (конец последней попытки
работы по времени, иначе регистрация графа), а не из часов; только у паузы
записи прежней версии без `pausedAt` времени нет и в хранилище — тогда
`since` (обязательный в версии 1) — момент запроса, и токен такого состояния
идёт за часами. Содержимое, которое честно
зависит от часов, меняет токен без записи в хранилище: истечение аренды
controller, живость, время идущей попытки (ряд `load`,
`history.totals.wallMs`/`attemptMs`), запись, вышедшая из окна, и запись,
которая с ходом окна переехала в соседний интервал ряда (раз в `bucketMs`:
история скользящая, ряды привязаны к концу окна).

**Политика и отсутствующее состояние.** Без `--policy` — привязанная к
состоянию; нет состояния и нет `--policy` — `POLICY_REQUIRED` (exit 2), с
`--policy` — пустое представление по ней и предупреждение `STATE_NOT_FOUND`.
`--policy`, отличная от привязанной, — предупреждение
`POLICY_DIGEST_MISMATCH`. Каталог состояния не создаётся и не пишется: чтение
неизменяемое, как у `report`, и всё представление собирается из одного
снимка по одним часам. Если журнал WAL уже есть (идёт `run`), чтение
повторяется обычным открытием только для чтения, и SQLite может создать
служебный `-shm`, как у `status`. Неизвестный `--work`, `--view-version`,
`--lang`, окно или интервал — `INVALID_INPUT` (exit 2).

- **Решения** (`decisions[]`, схема прежняя — `{id, kind, by, at, workId?,
subject?, findingId?, requestId?, temporary, revisit?, title?, reason?}`):
  harness выдаёт список из записей хранилища и журнала событий, новые
  сверху, не больше 50 (`truncated.decisions`). Нет поля — производитель
  решения не сообщает; пустой список — решений нет. `id` —

  - `diagnosis` — разбор ведущего (`WorkState.leadRecovery.diagnoses`):
    `subject` — `D<n>`, `title` — причина и «обязательный» / «по желанию»
    (как `track.steps[].required`), `reason` — гипотеза (маска, до 400
    знаков);
  - `reset` — новый предел попыток (`leadRecovery.resets`): ведущего
    («+3 (сброс 1 из 2)», `subject` — разбор) или человека;
  - `technical-answer` — ответ ведущего на технический вопрос
    (`basis: technical`), `requestId`, `reason` — причина ведущего или
    фиксированная фраза; `answer` — прочие ответы (ведущий до порога
    серьёзности, человек, хост);
  - `accepted-limitation` / `review-continue` — решение по находке ревью
    (`findingId`): код — `WorkState.codeReviewDecisions`, план и контракт —
    `disposition` находок последнего раунда предмета (время — раунда, в
    котором решение применено); `subject` — предмет ревью;
  - `cancel`, `reopen`, `rework-abandoned` — события `work.cancelled`,
    `work.reopened`, `work.rework-abandoned`;
  - `reapproval` — `graph.approved` с `reapproval` (`subject` — граф,
    `reason` — причина `reapprove`).

  Актёр `by` (`lead` | `operator`): разбор и технический ответ — `lead`;
  сброс, ответ и решение по находке — как записаны (`host` — `operator`:
  хост передаёт команду человека); отмена и оставленная доработка
  оператором или хостом — `operator`; отмена и оставленная доработка новой
  редакцией плана (`by: graph`) и переоткрытие — актёр согласования этой
  редакции (первое `graph.approved` графа после события: `agent` —
  `lead`, `operator` — `operator`); редакция ещё не согласована — решения
  нет, актёр не придумывается; `reapprove --by` — `operator` для
  `operator`, `user`, `owner`, `human`, `host` (и русских «оператор»,
  «владелец», «человек»), иначе (`lead`, имя агента) — `lead`. Повторы без
  сброса, повторы движка (`recovery`) и правки политики без
  `reapprove` решениями не считаются: журнал не называет, что они решали.
  `temporary` пока всегда `false`: временных решений с условием пересмотра
  harness не записывает. С `--no-titles` свободного текста (гипотеза,
  причины) нет; обязательная причина технического ответа —
  фиксированной фразой. События журнала читаются выборкой по типу
  (последние 2000 событий четырёх типов). Сверх байтового предела решения
  опускаются после ленты `activity` (шаг 3).

- **Обязательность разбора** (`works[].track.steps[].required`, у шагов
  `diagnosis`): `true` — разбор держит правило восстановления (засчитанных
  отказов без решения не меньше `recovery.diagnoseAfter`,
  `DIAGNOSIS_REQUIRED`) или он нужен для сброса на исчерпании; `false` —
  повтор делает harness сам, ведущий разбирает по желанию. Пройденный
  разбор — `true`, если он разобрал не меньше `diagnoseAfter` отказов или
  по нему ведущий дал новый предел (по действующей политике `recovery`).
  В плановом остатке между попытками до `diagnoseAfter` отказов — шаг
  «повтор: harness сам, ведущий может разобрать» (`required: false`), на
  `diagnoseAfter` и перед запасным сбросом — «обязательный разбор
  ведущего» (`required: true`). Ожидающий шаг перепланирования
  (`split`) поля не имеет.
- **Переоткрытая работа** (`works[].reopened {at, by?, revision, budget,
acceptedSha, spent, reason}`): новая редакция плана изменила постановку
  принятой работы, доработка ещё не принята, не оставлена и не отменена.
  `by` — актёр согласования переоткрывшей редакции (как у `reopen`), не
  согласована — поля нет. `budget` — `fresh` (свой предел попыток) или
  `carried`; `spent` — засчитанные попытки принятой редакции; `reason` —
  «переоткрыта ведущим: доработка после приёмки (принятый результат
  <sha7> не включён)» («переоткрыта: …», когда актёр неизвестен).
- **Итог ревью по попыткам** (`works[].attemptReviews[] {attempt, phase,
verdict, findings, notes, at, earlier?}`): по попытке и фазе
  (`candidate`, `integration`) — последний применённый раунд
  независимого ревью (протокол `valid` или запись прежней версии);
  `verdict` — `approved`, `rejected` или `invalid` (только ответы не по
  протоколу или небезопасные); `findings` — открытые blocking-находки
  раунда, `notes` — прочие открытые; `earlier` — попытка прежней
  (принятой) редакции. По порядку попыток, не больше 40, сверх — самые
  ранние отброшены (`truncated.attemptReviews`). Ревью кода ведущего
  (`reviews[kind=code]`, `harness review-code`) — отдельно. Сверх
  байтового предела `reopened` и `attemptReviews` опускаются на шаге 2
  (`truncated.workFields`).

  `OUTLINE_DEFAULT_TASK_MS`) × попыток на задачу, нижняя — на

  по-прежнему — только зарегистрированные работы.

reason?, line}`): последний рост — работы или задачи, появившиеся позже

  большим объёмом (`by: outline`, `reason` — причина записи), что позже.
  `before` — готовность без добавленного (при той же готовности остального),
  `after` — текущая; строка — «план вырос: +W (было 95 % → стало 86 %)».
  Работа, заполнившая место плана, — не рост. После `release done` поля нет.

  принята или идёт; строка — «готово ~95 % — если ведущий не добавит задач
  · код принят, …» (или в конце строки в работе).

exceeded?}`): весь код принят, отчёта нет — «код принят · осталось

  ничего + работа ведущего»; `since` — конец последней попытки. Ведущий

  компонентов).

### HandoffPack

Пакет передачи контекста (`harness handoff`, `handoffPack(source, options)`
и `handoffMarkdown(pack)` из корня пакета; `handoffVersion: 1`,
`handoffPackSchema`, `schemas/handoff-pack.schema.json`). Ведущий агент хоста,
который ведёт доску через много попыток, начинает новую сессию с пакета, а не
с пересказа предыдущей: факты собираются из хранилища теми же проекциями, что
`status --detail` и `explain`, и только читают состояние.

- `summary`, `limits` — счёт поручений по статусам, `maxAttempts` и
  `repairBudget` политики;
- `queue`, `controller` — пауза выдачи, её причина и кто её снимает
  (`queueStop`, `queuePause`), операция, держащая паузу (`operation`), и
  классы отказа паузы runtime (`failures`); держатель роли controller и
  свежесть срока;
- `active` — идущие попытки: стадия и её длительность, heartbeat, gates
  текущей фазы (`attemptView`); `unfinished` — незакрытые записи попыток с
  истёкшим владением или такие, которые поручение уже не ведёт;
- `works` — открытые поручения (идущие, упавшие, план, остальные): класс и
  причина провала, удержание, эпизод восстановления с предложением,
  блокировки (без общей паузы очереди; сверх предела — `blockersTruncated`) и
  `next` — кто и что делает (по диагнозу `explain`; стадия и свойство — по
  `nextAction`, с 0.1.0-alpha.66 — с восстановлением ведущим
  `leadRecoveryStep`: на исчерпании шаг `attempts-exhausted` ведущего —
  `diagnose` или `reset-attempts`, пока бюджет его сбросов не потрачен);
- `stops` — диагнозы `explain` без проб runtime, кроме `action: none`.
  Отменённая работа (и упавшая с классом `cancelled`) — остановка
  (`CANCELLED`, lead `replan-dependents`), только пока от неё прямо зависит
  незавершённая работа (не `done` и не `cancelled`); ждущую через
  отменённую же промежуточную ведёт диагноз той. Без таких работ у
  отменённой действия нет (`action: none`): в общий `explain` и пакет она не
  входит, explain этой работы (`--work`) её показывает. Упавшая отменой
  открыта, а движок её не повторяет: без ждущих — решение человека (user
  `user-decision`: `harness retry` или отмена), шаг `nextAction` —
  `cancelled`. Любая отмена в группе останавливает её автоматическое
  восстановление: диагноз упавшей сестры называет отменённую работу.
  Остановка выдачи общей паузой очереди — одна запись с `queue: true` без
  `workId`; одинаковые остановки на выдаче у разных поручений тоже
  свёрнуты; `works` — первые 20 затронутых, `worksCount` — сколько всего.
  Решения (`actor` lead или user и действие не `wait`) идут первыми;
- `failures` — последние провалившиеся и истёкшие попытки, новые первыми:
  `failureKind`, код (`stopCodeOf`), текст ошибки и текущий статус
  поручения (`workStatus`). Попытки, прерванные штатной остановкой
  controller (`interrupted: "shutdown"`), — не провалы: они исключены до
  предела `HANDOFF_LIMITS.failures` и не вытесняют настоящие провалы, а их
  число — `interruptions` (нет поля — таких попыток нет);
- `budgets` — общий бюджет и бюджеты групп (с `--graph` — только его
  группа), бюджеты поручений — только с расходом или не в пределах и со
  своими вызовами (попытки, вызовы о поручении). Вызов о группе (ревью и
  проверка плана) засчитывается целиком бюджету каждого её открытого
  поручения (так действует ограничение поручения), но в строках группы и
  `total` — один раз; поручение, весь расход которого — такие вызовы, не
  перечисляется (`truncated.budgetsShared`), если только его строка не
  держит выдачу (превышена или не определена при `onUnknown: stop`): тогда
  она показана как ограничение поручения. Строка бюджета:
  сообщено (`reportedUsd`) и оценено (`estimatedUsd`) против предела, время,
  `complete` и причины неполноты (вызовы без стоимости, незавершённые,
  брошенные, попытки без учёта); при неполном расходе сумма — нижняя граница
  («≥ $X (неполно: …)» в Markdown), остаток — `null`. `repairs` —
  восстановления незавершённых заданий графов: `graphId`, `key` (ключ
  задания; у графа после новой редакции их несколько, и прежнее — `stale`),
  `status` задания, `used` и `budget`; с 0.1.0-alpha.58 сначала действующие
  задания (не `stale` и не замещённые более новым заданием того же графа),
  затем устаревшие, внутри группы — новые первыми: предел 10 не вытесняет
  действующее задание историей устаревших; у пакетов прежних версий `key` нет;
- `next` — следующий шаг доски: первое решение; иначе идущая попытка со
  свежим сроком владения — ждать (без controller — до `leaseUntil`); попытка
  с истёкшим сроком или очередь без controller — `command: "harness run"` (run истечёт брошенную
  попытку и продолжит очередь); пауза оператора — `"harness resume"`; иначе
  первый открытый шаг поручения;
- `intentions` — единственный текст не из хранилища: намерения агента.

Пределы (`HANDOFF_LIMITS`): 50 открытых поручений, 30 остановок (после
свёртки) с 5 ссылками evidence каждая, 10 провалов, 20 незавершённых
попыток, 3 блокировки на поручение, 20 строк бюджетов, 10 заданий, 20
намерений по 1000 знаков. Тексты из хранилища и намерения очищаются от
escape-последовательностей терминала (ANSI CSI, OSC), серия управляющих
символов заменяется пробелом; строки фактов усечены до 300 знаков, имена и
идентификаторы — до 200, с «…» и без разрыва суррогатной пары. Пакет не
больше `HANDOFF_MAX_BYTES` (256 КБ UTF-8): сверх него записи отбрасываются в
порядке «намерения с конца, старые провалы, поручения без решения,
остановки без решения, незавершённые попытки, остальные поручения и
остановки, строки бюджетов» (`truncated.bySize`), отказа по размеру нет.
Сколько записей каждого списка не вошло — `truncated`; бюджеты поручений в
пределах и без расхода не показываются намеренно и считаются отдельно
(`budgetsWithin`), как и бюджеты поручений только с расходом вызовов о
группе (`budgetsShared`), усечённые и отброшенные намерения — `intentions` и
`intentionsDropped`. Тексты из хранилища маскируются по значениям секретов
политики из окружения читающего процесса (`policySecrets`, как у
коннектора): секрет, которого в этом окружении нет, маска не знает —
библиотеке можно передать свою `redact`. Fencing-токены в пакет не
попадают.

**Хост.** Источник пакета — `HandoffSource`: `{ engine, policy, workflows }`,
где `engine` — `Engine` над хранилищем хоста, `policy` — его
`ExecutionPolicy`, `workflows` — `list()` заданий от старых к новым (пакет и диагнозы берут
задания `kind: "graph"`) и `continues(job, view, { reconfigureApplies })`,
продолжит ли очередь задание сама. `Harness` удовлетворяет типу структурно;
хост со своим движком передаёт свой адаптер заданий без экземпляра
`Harness`. Состояние доски над тем же источником — `statusOf(source,
graphId?, { detail })` (`Harness.status` — та же функция).

Параметры `handoffPack`: `graphId`, `intentions`, `redact`, а также
`maxBytes` — предел хоста в байтах UTF-8, целое от `HANDOFF_MIN_BYTES`
(4 КБ) до `HANDOFF_MAX_BYTES` (по умолчанию), иначе `INVALID_INPUT`; порядок
отбрасывания и счётчики `truncated` те же, что у предела по умолчанию, а
`bySize` значит «записи отброшены ради предела», а не «пакет уложился».
Сводка, очередь, идущие попытки, задания и `next` не отбрасываются, поэтому
уложиться не гарантируется: размер результата хост проверяет сам.
`HANDOFF_MIN_BYTES` — нижняя граница, ниже которой не помещается даже обычный
минимальный пакет, а не гарантия. `measure` — что укладывается в предел: `json` (по умолчанию) —
сериализованный пакет; `markdown` — и JSON, и `handoffMarkdown(pack)`
(Markdown бывает длиннее JSON: «|» в ячейке экранируется). Свой раздел
Markdown хост учитывает, уменьшая `maxBytes`. Маску из секретов политики и
своих значений хост составляет из `policySecrets(policy, env?)`,
`redactor` и `composeRedactors` корня пакета.

**Диагноз по состоянию.** `stopInputsOf(source, { maxAttempts,
repairBudget, workId?, workIds? })` из корня пакета (источник тот же —
`StopSource`) даёт входы `explainStop` за одно чтение. Без выбора — доска:
отменённая работа, которую никто не ждёт, в неё не входит. `workId` — одна
работа (её показывает и отменённую). `workIds` — набор: входы каждой работы
те же, что у вызова с её `workId` (в том числе отменённой без ждущих), в
порядке состояния независимо от порядка в запросе; вход роли controller —
первым, запросы ведущему — после работ. Неизвестная работа — `NOT_FOUND`,
`workId` вместе с `workIds` — `INVALID_INPUT`, пустой набор — без работ.
Общее для работ (прогноз групп, обратные зависимости, запросы, попытки,
записи вызовов, статусы бюджетов) читается один раз за вызов: набор и доска
линейны по числу работ. Порты хоста по-прежнему спрашиваются о каждой
работе: `basis.orderDigest`, `guards.claimable`, `budgets.groupOf` при
пределе группы и `budgets.members` для прежних записей вызовов без
закреплённой группы (`subjectId` без `groupId`, которые не закрепил
`pinLegacyCalls`). Бюджетные блоки многих работ хост получает из
`Engine.budgetBlocksOf(workIds | undefined, view)`: за одно чтение, для
набора или (без `workIds`) всех работ вида — `Map` работа → причина или
`undefined`, по каждой то же, что `budgetBlockOf(workId, view)` на момент
вызова. `budgetBlockOf(workId, view, records?)` принимает уже прочитанные
записи вызовов, `repairDecision(view, works, { budgetLeft, maxAttempts,
blocking? })` — вопрос, держащий работу (по умолчанию `blockingRequest`).
`Engine.budgetBlockers(view)` и `Engine.approvalStaleness(view)` —
внутренние помощники диагноза: функция, которую они возвращают, считает
общее один раз на момент создания (`at` бюджетов фиксирован) и верна
только внутри того же чтения; хост их не держит между чтениями и
пользуется `budgetBlocksOf` и `stopInputsOf`.

Весь пакет — один снимок хранилища: `handoffPack` выполняет status,
диагнозы и чтение заданий графов внутри одного `read`
(`SqliteExecutionStore.read` вложенным чтением использует снимок внешнего,
без второго `BEGIN`). Попытка со свежим сроком владения без живого
controller — `next` «ждать до `leaseUntil` или проверить процесс-владелец»
без команды; `harness run` называется только для попытки с истёкшим сроком.

### Ресурсы `port`

Ресурс `port` — порт, который поднимает сама попытка: служба lifecycle,
`prepare` или gate. Кроме блокировки в `resources.sqlite` (порт исключителен
для всех контуров машины) порт проверяется на деле: перед каждой фазой
аренды (candidate, integration, проверка потребителя, совместная проверка,
`runGatesAt`) — до lifecycle `setup`/`ready`, `prepare` и gates — controller
привязывает и сразу отпускает его на `127.0.0.1`, `::1`, `0.0.0.0` и `::`
(миллисекунды; служба, поднявшаяся сразу после пробы, ей не мешает). Внутри
окружения фазы вложенная фаза порт не проверяет: его законно держит служба
lifecycle.

- **Свободен** — ничего не меняется.
- **Занят процессом, пережившим остановку прежней попытки.** Сдерживаемая
  команда внутри аренды записывает пережившие остановку процессы
  (`ReapFailure.survivors`) с временем старта, именем машины и
  идентификатором загрузки ОС в таблицу `survivors` той же базы. Запись
  хранится 7 дней; учитываются записи только этой машины и загрузки;
  владелец записи не фильтруется — аренда порта общая для всех контуров
  машины. Держатель порта узнаётся `lsof` (`-nP -iTCP:<port> -sTCP:LISTEN`).
  Если он сам или его предок (не потомок) — такой процесс (тот же PID и
  время старта), оба останавливаются: время старта сверяется снова прямо
  перед сигналом, SIGTERM, через 2 с SIGKILL. Запись снимается, исход решает
  повторная проба порта, а не завершение процесса (зомби порт не держит);
  фаза продолжается.
- **Чужой процесс держит только wildcard-адреса** (`0.0.0.0`, `::`), а
  `127.0.0.1` и `::1` свободны — предупреждение, не отказ: служба попытки,
  слушающая `127.0.0.1`, на таком порту работает. Так на macOS выглядит
  AirPlay Receiver (ControlCenter) на портах 5000 и 7000; служба, слушающая
  все адреса, там не поднимется. Предупреждение — в `port-probe.json`
  каталога окружения фазы, стадией `port-shared:<порт>` в `timings` попытки
  (с префиксом фазы, например `candidate-environment:`) и в
  `GatesAtResult.warnings` у `runGatesAt`. Записанный переживший процесс
  рядом с ним всё равно останавливается.
- **Занят иным процессом** (или держатель не определён: нет `lsof`, процесс
  другого пользователя, переживший не освободил порт) — отказ окружения
  `environment` с причиной `resource-busy`; текст называет порт, ресурс, PID
  и имя команды. Ничего не останавливается. Попытка не засчитывается в
  `maxAttempts` (как любой отказ окружения: предел незасчитанных отказов,
  пауза выдачи по правилу класса `environment`); `runGatesAt` бросает такой
  `TaskFailure` до gates, без evidence.

Порт внешней службы, которую попытка не поднимает (общая база разработки),
объявляйте ресурсом `service`: `port` с работающей службой не пройдёт
проверку. Отказ `environment` ставит выдачу на паузу (класс в
`pauseFailures`): её снимает повтор восстановления или `harness resume`,
поручение повторяет `harness retry --work <id>`.

`harness doctor` пробует порты ресурсов политики тем же способом, без
остановки процессов: поле `ports[]` — `{id, port, status, hosts?, holder?}`,
`status` — `free`, `busy`, `wildcard-only` или `leased` (порт под арендой
идущей попытки, не пробуется). Занятый порт попадает в `problems`,
wildcard-предупреждение — в `warnings`. Проба doctor — снимок одного
момента: служба, поднявшаяся сразу после неё (или аренда, взятая между
чтением аренд и пробой), в нём не видна, а остановленная — ещё видна.
`explain` порты не пробует (без привязок и `lsof`). Предупреждение пробы
перед фазой попытки дописывается и к тексту отказа попытки
(`; предупреждение пробы портов: …`), если она затем падает.

`moveBase`). Без него корень выбирает `chooseCheckoutRoot`: каталог состояния
внутри репозитория политики или закрытого песочницей пути — кэш пользователя
вне дерева (macOS `~/Library/Caches/devcontour-harness/<hash>`, Linux
`$XDG_CACHE_HOME` или `~/.cache/devcontour-harness/<hash>`, `<hash>` —
устойчивый хэш каталога состояния), иначе прежнее место. Кэш на другом томе,
чем репозиторий, корень внутри репозитория, закрытого пути или каталога
состояния, каталог-ссылка или чужой каталог — прежнее место и пояснение
(`note`; заданный хостом такой корень — `INVALID_INPUT`). Корень закрыт
песочнице целиком, свои деревья проверки открыты; корни кэша не убираются при
переносе workspace — их удаляют вручную; `Runner.checkoutRoot()`
и `doctor` называют действующий корень. Корень лучше держать на томе
репозиториев: менеджеры пакетов ставят зависимости жёсткими ссылками и reflink;
`hooks` — точки расширения, которые добавляют сведения хоста, но не решают
приёмку: `prepared({work, attempt, baseSha})` — база известна, работа не
начата (отказ — отказ попытки, `BlockedError` — отказ окружения);
`notes({work, attempt, review})` — дополнения запроса writer или reviewer;
`implemented({attempt, output, sha})` — отчёт writer закоммичен кандидатом;
`failed({attempt, kind, message})` — отказ записан движком. `settled()` ждёт
выданные попытки — хост ведёт свой цикл поверх `tick`. `Engine.expire(at)`
снимает владение, истекающее к моменту `at`. Попытка записывает замеры стадий
(`implementation`, `<фаза>-test:<gate>`, `<фаза>-consumer:<репозиторий>:<gate>`,
`<фаза>-review`, `<фаза>-environment:<шаг>`, `integration-wait`) и сохраняет
снимок контекста артефактом `implementation/context.json`. Отказ приёмки с
кодом `GATE_FAILED`, `REVIEW_REJECTED`, `REVIEW_PROTOCOL_INVALID`,
`SCOPE_VIOLATION` или `BUDGET_EXHAUSTED` записывается классом отказа этого
правила.

Хост, ведущий движок поверх своего хранилища, собирает исполнение из
экспортов корня пакета: `Engine`, `Runner`, `WorkflowQueue`, `JointRunner`,
`moveBase`/`fencedRefMove`, `runGate`/`runCheck` (и разбор отчёта
`junitSummary`, `prepareReportPath`, `sandboxBlockedHosts`), `unprovenReason`,
`ReviewProbes`, маскирование (`redactor`, `redactDeep`, `redactError`),
git хоста над checkout с чужим кодом (`hostGitArgs`, `assertTrustedCheckout`,
`UntrustedCheckoutError`, `gitHardening`, учёт деревьев `rememberWorktree`/
`forgetWorktree`/`worktreeKey`/`worktreeAddPath`, `resetGitTrust` для тестов),
корпус (`CorpusStore`, подтверждение случая `submitCase` с `ConfirmContext`),
ограниченный разбор по свойству (`analyzeRecovery`, `applyCases`,
`recoveryBrief`; назначение хоста — модель и профиль ведущего — передаётся
`binding`, его дополнительные границы — `boundary`), проверка
переносимого результата (`resultProblems`), классы и правила отказов
(`BlockedError`, `TaskFailure`, `classifyFailure`, `failureFingerprint`,
`repairPolicy`, `repairRepeats` — повторы одного отпечатка с учётом предела
окна контекста, `lastContextLimit` — предел последней попытки с отказом,
`repairDecision`), раунд технического ревью
(`technicalReview`), точка сбоя подтверждения корпуса для тестов
(`caseHooks`). Глубокие импорты `lib/...` не поддерживаются.

Очередь технических заданий хоста — `new WorkflowQueue(store, policy, now,
subjects)`: `subjects.input(kind, id, view)` задаёт digest входа и владельца
задания для предметов хоста (доска, набор изменений); задание хранится за
этим владельцем, недопустимый вход (`HarnessError`) отклоняет постановку его
текстом и делает поставленное задание устаревшим, смена владельца — тоже.
Число стадий задаёт `finish(job, wait, stages)`.

### StackProfile

Переносимый профиль стека (`schemas/stack-profile.schema.json`):
`{id, version, extends[], capabilities[], gates[], prepare[], environment?, lifecycle?, protectedPaths[], generatedPaths[], concurrency?, runTimeoutMs?, gateTimeoutFloorMs?, roles{}, contextPacks[], previews?[]}`.
`previews` — превью результата ([превью](previews.md)): слои объединяются по ID, один ID в двух
слоях — конфликт; `repositoryFromProfile` переносит их в репозиторий политики.
`extends` — встроенный ID (`profiles/<id>.json` пакета, иначе слой
`profiles/layers/<id>.json`) или относительный
`./file.json` внутри репозитория; не глубже 16 слоёв и не больше 32 файлов,
без symlink и выхода за корень, файл до 128 KiB. `resolveProfile` только
читает манифесты: gates, подготовка, возможности и пути складываются,
окружение и lifecycle задаёт один слой (иначе конфликт), параллельность —
наименьшая, время попытки и `gateTimeoutFloorMs` — наибольшие, роли и
`contextPacks` — по ID. Встроенный слой — часть профиля без gates, сам по себе
не разрешается, gates не объявляет и в `builtinProfiles()` не входит; ID,
который есть и среди профилей, и среди слоёв, — отказ. `lean` задаёт
`concurrency: 1`, `runTimeoutMs: 1800000` и `gateTimeoutFloorMs: 240000`.
`resolveProfile(ref, { layers: ["lean"] })` складывает встроенные слои —
только из `profiles/layers/` — поверх листа (они входят в closure и digest);
`harness init --lean` делает это и записывает слои в manifest
(`profile.layers`); в подготовленном проекте слой включает и выключает
`harness lean` (`switchLean`). `generatePolicy` переносит `concurrency`, `runTimeoutMs` и
`gateTimeoutFloorMs` профиля в политику; без них политика и её digest прежние.
`runTimeoutMs` профиля или слоя — нижняя граница: если требуемый пределами
шагов с запасом (`requiredRunTimeoutMs`) больше, в политику пишется он, так
что слой не даёт срока меньше, чем профиль без слоя.
Итог обязан иметь test gate с JUnit; `requirement-source` зарезервирован.
Файлы локальных слоёв становятся защищёнными путями. Digest: один встроенный
файл — sha256 его байтов (так закреплены прежние потребители, встроенные
профили перенесены побайтно), иначе — sha256 замыкания `[{ref, digest}]`.
`repositoryFromProfile` собирает описание репозитория политики (собственные
значения сильнее, переопределённые поля названы в `shadowed`),
`profileRoles` — роли в форме политики. Хост, у которого закреплены профили
своей формы (другие runtime ролей, свои поля, нестрогие вложенные объекты),
передаёт `resolveProfile(ref, { layerSchema })` — схему Zod своего файла:
она разбирает каждый слой вместо `StackProfile`, а gates, шаги, роли и
`contextPacks` остаются в её форме. Безопасность файлов, обход `extends`,
сложение слоёв, проверки gates (в том числе путь JUnit — относительный, внутри
worktree) и digest — прежние; слой, который не даёт
полей сложения (`ProfileLayer`), и не-Zod `layerSchema` — `INVALID_INPUT`.
`contextPacks` — инструкции стека для
хоста: harness их не читает, закрепляет их `ContextSource`. Встроенные
профили сохраняют имена скриптов проекта, которые закреплены у прежних
потребителей (например, `npm run test:devcontour`); для другого проекта
подходит локальный профиль.

Полная форма каждой команды — `cliCommands` (аргументы, обязательность,
идемпотентность, отказы exit 3). Все команды реализованы. `run` принимает `--author` (по умолчанию `external`) — автора графа для ревью плана. `HARNESS_CODEX_BIN` и `HARNESS_CLAUDE_BIN` подменяют исполняемые файлы runtime (fixture executables в тестах).
`init --plan` ничего не пишет (exit 3 при конфликтах или неготовом toolchain). `lean` включает или выключает слой `lean` в подготовленном проекте: поля исполнения политики и `profile.layers` manifest, прежние значения — в записи manifest `lean`, по ней `--off` возвращает политику точно; `--plan` ничего не пишет (exit 3 при `problems`: идущий run — `CONTROLLER_BUSY`, поле изменено вручную после включения — `PATH_CONFLICT`); без manifest — `NOT_READY` ([слабая машина](standalone.md#слабая-машина)). `--human` принимают только `init`, `lean`, `status` (строка сводки попыток на поручение), `explain`, `plan-request` (печатает prompt), `gates` (таблица исходов) и `smoke` (таблица шагов, класс отказа и совет): успешный ответ — текст для человека, отказ — тот же JSON-конверт, exit code одинаков; у прочих команд флаг — `INVALID_INPUT`. `plan-check` с проблемами отвечает `ok: true` с данными, exit — по классу первой проблемы; draft — `schemas/plan-draft.schema.json` (`planDraftSchema`). Маршрут самостоятельного проекта и планирование — [standalone](standalone.md).

**`gates`.** Gates компонента на коммите вне попытки — `runGatesAt` с тем же
исполнением, что integration поручения: отдельное рабочее дерево на SHA,
снимки зависимостей, ресурсы, lifecycle и prepare, окружение фазы
`integration`, песочница. `--sha` — SHA, ref или `HEAD` checkout
репозитория; `--gate` — gates и группы через запятую (нет — все gates),
предпосылки (`gatePrerequisites`) добавляются и идут первыми; `--repository`
нужен, если в политике несколько репозиториев. Неизвестный gate —
`GATE_UNKNOWN` (exit 2) до исполнения. Провал gate проверку не останавливает
(исходы всех gates — диагностика); `--fail-fast` останавливает её на первом
провале, следующие gates — `skipped`, не провал. Все прошли — exit 0, иначе
ответ с данными и exit 3 (`GATE_FAILED`). Попытки, evidence в базе состояния и
состояние поручений не пишутся, база не открывается; логи остаются в
`<state>/gates-at/<id>` (`data.logs`), ход — в stderr. Политика — из
`--policy` или привязки каталога состояния; неизвестный репозиторий, коммит
или неинициализированный каталог — `NOT_FOUND`. Прерывание (SIGINT, SIGTERM)
или исчерпанный предел проверки `runTimeoutMs` — отказ `CANCELLED` (exit 3):
исход каждого gate — в `error.issues` (`gates.<id>`), прерванный gate —
`cancelled`, следующие — `not-run`; рабочее дерево убирается. Остановка
обходом зависших (`stallSweep: stop`) — по-прежнему провал gate.
Итог проверки записывается в `<state>/gates-at/<id>/result.json`
(`{at, data}`, `data` — ответ команды): его прикладывает `review-code` того же
SHA.
Провал gate, который gate назвал отказом среды, несёт `gates[].environment`
(причина из `environmentCauses`, например `sandbox-process-list`); `--human`
печатает её перед сообщением: `[среда: sandbox-process-list]`.

**Выжимка провала gate** (0.1.0-alpha.68). Непройденная запись `test`, чей
провал назвала команда (ненулевой код выхода или упавшие testcases), несёт
`failureSummary` (`gateFailureSummarySchema`); то же поле — у
`gates[].failureSummary` итога `harness gates`. Поля: `tests` — до 20 имён
упавших тестов (`testsTruncated` — есть ещё), `assertion` — первая строка
утверждения или ошибки (до 300 знаков), `tail` — последние строки stdout и
stderr (до 1200 знаков), `source` — откуда имена: `junit` (отчёт gate без
общих провалов обёртки вроде «Gate execution failed»), `output` (упавшие
тесты вывода `node --test` spec или TAP), `command-report` (JUnit, который
команда записала сама по пути `*.xml` из argv — `--test-reporter-destination=…`
и подобные — внутри дерева и этим запуском; путь открывается по компонентам
от настоящего корня дерева: каталоги — `O_DIRECTORY | O_NOFOLLOW`, отчёт —
`O_NOFOLLOW | O_NONBLOCK`; ссылка на любом компоненте (и внутрь дерева) и
отчёт с несколькими именами (`nlink` > 1, жёсткая ссылка) отклоняются. На
Linux каждый компонент открывается от дескриптора предыдущего каталога
(`/proc/self/fd/<fd>/<имя>`, как `openat`) — подмена родителя ссылкой после
его открытия обход не уводит; на macOS (`/dev/fd` там не обходится) после
открытия каждый префикс и сам отчёт сверяются `lstat` с открытыми
дескрипторами (каталог, не ссылка, то же устройство и inode), — подмена,
которая держится на любом вызове или снята до сверки, отклоняется; не
закрыто только переключение родителя уцелевшим процессом точно между
вызовами сверки. Тип, размер (до 5 МБ) и время берутся `fstat` открытого
дескриптора, и читается не больше предела из него); `withheld` — gate не назвал ни
теста, ни строки ошибки, а вывод говорит, что подробности скрыты (или в нём
не больше двух строк). Всё — с той же маской секретов, что лог. Имена не из
отчёта gate дописываются к тексту отказа (`упали …` или `; по выводу: …`), у
`withheld` — пометка, что gate должен печатать безопасную выжимку (это правка
команды gate, ход ведущего). Подсказка следующей попытки получает выжимку
отдельным случаем `failure-summary`; `--human` печатает под gate строку
`причина: …`. Выжимка — диагностика: класс отказа, отпечаток и приёмка от неё
не зависят.

**Список процессов в песочнице проверок.** При `isolation.mode: os` gate
исполняется в песочнице ОС (sandbox-runtime). На macOS ядро не запускает
setuid-программы из песочницы, даже при профиле `(allow default)`: `/bin/ps`
и `/usr/bin/top` отвечают EPERM («Operation not permitted», в Node —
`spawn EPERM`), а `pgrep`/`pkill` (не setuid) печатают «Cannot get process
list»: песочница открывает сведения только о процессах той же песочницы.
Ни правило Seatbelt, ни параметр sandbox-runtime этого не открывают, и
открывать по умолчанию небезопасно: `ps -E` показывает окружение каждого
процесса того же пользователя (хост harness, CLI моделей с токенами API), а
код gate пишет исполнитель. Разрешения «этот gate вне песочницы» в политике
нет: что исполняет gate, не ограничено его путями — импорты модулей,
`package.json` и скрипты менеджера пакетов, `node_modules`, неотслеживаемые
файлы дерева пишет исполнитель, и `when.paths` внутри `protectedPaths` этого
не меняет (gate применим и по неявным входам — манифестам и lockfiles), а вне
песочницы проверка читает учётные данные, ходит в сеть и пишет куда угодно.
Поэтому harness распознаёт отказ и называет его:

- gate под песочницей ОС завершился ненулевым кодом, и признак — `spawn
/bin/ps EPERM`, `spawn EPERM` без пути, `/bin/ps: Operation not permitted`,
  `execvp() of '/bin/ps' failed`, `Cannot get process list` — есть в выводе, а
  если JUnit назвал упавшие testcases, — в тексте каждого из них (не больше
  200; testcase без признака оставляет провал классом `gate`). Признак
  подтверждает собственная проба harness (`probeProcessList`: `ps -o pid= -p
1` тем же `runCheck`, что gates, одна на процесс): только при её ответе
  `unavailable` провал — `environment` с причиной `sandbox-process-list`, не
  засчитанный в `maxAttempts` (в пределах `MAX_NEUTRAL_FAILURES`, как прочие
  отказы песочницы). С 0.1.0-alpha.66 такой отказ не повторяется
  автоматически и выдачу не ставит на паузу: повтор дал бы тот же отказ.
  Попытка хранит `environmentCause: sandbox-process-list`, `repairDecision`
  сразу останавливается с объяснением, а explain называет ход ведущего:
  `RUNTIME_UNAVAILABLE`, `lead`, `fix-environment` (правило
  `environment-gate-command`, docs/principles.md). Ведущий меняет gate или
  команду. Текст evidence начинается с кода
  `GATE_SANDBOX_PROCESS_LIST` (метка текста отказа, а не код `HarnessError`:
  отказ попытки — `environment`, `harness gates` — `GATE_FAILED`) и называет строку признака и совет: тест не
  должен требовать список всех процессов хоста — свои дочерние процессы
  проверяются по pid (`process.kill(pid, 0)`) или по файлам-меткам, либо такие
  тесты выносятся из команды gate и запускаются на хосте; `isolation.mode:
none` снимает песочницу со всех проверок и не рекомендуется. Признак,
  напечатанный проверкой, делает провал лишь незасчитанным (не PASS) и
  ограничен пределом незасчитанных отказов поручения.
- `doctor` (CLI) отвечает `sandbox.processList` (`status`: `available`,
  `unavailable`, `unknown`, `not-isolated`; `command`, `detail`, `line`); при
  `unavailable` — строка `sandbox-process-list: …` в `notes` (не проблема:
  gate может не вызывать `ps`).
- `smoke` при `isolation.mode: os` отвечает `processList` (те же поля и
  `callers` — до 10 файлов дерева на SHA, которые вызывают `ps`, `pgrep`,
  `pkill` или `top`: абсолютный путь, имя строкой, вызов в shell; `*.md` не
  смотрятся). Недоступен и такие файлы есть — предупреждение
  `sandbox-process-list: <файлы> вызывают ps/pgrep/top; …`; `--human`
  печатает строку возможности или это предупреждение.

С 0.1.0-alpha.68 то же правило, только строже и закрытое по умолчанию,
классифицирует ещё два отказа песочницы ОС проверок. Причина назначается,
только когда выполнено всё: `isolation.mode: os`; след песочницы есть у
каждого упавшего теста; ни у одного нет иного провала — проваленного
утверждения, строки `…Error`/`…Exception`/`error:`, кода ошибки (`ECONNREFUSED`
и подобных), статуса HTTP 4xx/5xx, аварии (`panic`, `Segmentation fault`,
`uncaught`), — кроме точного текста самого следа и его сопровождения (след
с примыкающим `Error: `, поля объекта ошибки `kill`, кадр стека; общая
строка запуска браузера, префикс журнала Chromium, имена служб Mach рядом со
следом песочницы): из строки вырезается только этот текст, и иной признак в
остатке (`Error: HTTP status 500; cleanup: kill EPERM`) оставляет провал
засчитанным; вызов
не из добавленных строк изменения задачи; и собственная проба harness в той
же песочнице проверок (тот же `runCheck` и профиль изоляции, что у gates и у
пробы `ps`) подтвердила ограничение (`unavailable`). Проба одна на процесс
harness и причину, кешируется любой её исход, и `unknown` тоже (сбрасывает
кеш только новый процесс). Проба не подтвердила
(`available`, `unknown`, браузер не найден) — провал засчитан, а текст несёт
пометку «возможная причина окружения … не подтверждена пробой harness …».
Пробы:

- сигнал — процесс в песочнице посылает сигнал 0 процессу harness (он вне
  песочницы): EPERM — `unavailable`;
- браузер — известный браузер машины (Google Chrome, Chromium, кеш
  Playwright) стартует без окна (`--headless=new`, `--use-mock-keychain`,
  `--password-store=basic`, временный профиль, предел 30 с) и печатает
  `about:blank`: отказ со следом
  песочницы — `unavailable`, браузер отработал — `available`; браузера нет
  или отказ без следа песочницы — `unknown` (не доказано).

Ответы проб видны, как проба `ps`: `doctor` (CLI) пробует обе и отвечает
`sandbox.signal` и `sandbox.browser` (`status`, `command`, `detail`, `line`),
при `unavailable` — строка `sandbox-signal: …` / `sandbox-browser: …` в
`notes` (не проблема среды); `harness gates` отвечает `sandbox.signal` /
`sandbox.browser` — ответы проб, которые этот процесс уже получил (проба идёт,
когда провал gate несёт след класса; иначе поля нет), `--human` печатает
строку `возможность: …`.

Причины:

- `sandbox-signal` (`GATE_SANDBOX_SIGNAL`) — проверка шлёт сигнал процессу
  вне своей песочницы (обёртке gate, процессу хоста): `Error: kill EPERM`,
  `kill: (…) - Operation not permitted`, объект ошибки с `syscall: 'kill'` и
  `EPERM`. Вызов изменения — `process.kill(`, `os.kill(`, `kill` в shell.
- `sandbox-browser` (`GATE_SANDBOX_BROWSER`) — проверка запускает браузер или
  его демон, а он не стартует в песочнице: «browser daemon unavailable»,
  `bootstrap_check_in … Permission denied (1100)`, `mach_port_rendezvous`.
  Общие строки запуска («Failed to launch the browser process», «Chrome
  crashed», «Browser process exited», `BROWSER_LAUNCH`) следом не считаются:
  их даёт и сломанная настройка; строка о пути к браузеру (`executablePath`,
  `ENOENT`, «executable doesn't exist») рядом со следом оставляет провал
  засчитанным. Вызов изменения —
  `agent-browser`, `chromium.launch(`, импорт `playwright`/`puppeteer`.

Общий провал обёртки gate без своей причины, дописанный в JUnit к тестам с
признаком, классификацию не отменяет, только когда его текст — ровно строка
«Gate execution failed» (в сообщении, теле или обоих), вывод `node --test`
(spec/TAP) сам называет упавшие тесты и итог прогона сходится. Любой другой
лишний testcase (например, «HTTP status 500», «Tests failed», строка `Error`)
оставляет провал засчитанным. Признак лишь у части упавших тестов оставляет
провал засчитанным, а текст называет эту часть пометкой «часть провала —
причина окружения …» (если проба подтвердила) или «возможная причина
окружения … не подтверждена пробой harness …». Семантика — та же, что у `sandbox-process-list`: попытка не засчитана
(предел незасчитанных отказов работы), автоматического повтора нет, gate
удержан (`ENVIRONMENT_GATE_HELD`, `WorkState.environmentHold.cause`) до смены
определения gate или среды либо до `retry --by lead`; проба `ps` удержание по
этим причинам не снимает.

**`review-code`.** Технический обзор ветки, написанной вне harness: reviewer —
по правилу ревью кода роли (`--role`; одна роль репозитория — по умолчанию) и
правилу вендора относительно автора (`--author`, по умолчанию writer роли;
недопустимый — `REVIEWER_SAME_VENDOR` до вызова, `same-vendor-allowed` —
`sameVendor: true` в записи). Diff — `merge-base(base, head)..head`; пустой,
больше 4 МиБ или без общего предка — `INVALID_INPUT`, неизвестный коммит —
`NOT_FOUND`, всё до вызова модели. Reviewer читает отдельное рабочее дерево на
`head` (только чтение, состояние и исходные checkout закрыты, их `.git` открыт
на чтение); дерево убирается после вызова. Последний итог `harness gates` на
`head` из `<state>/gates-at/*/result.json` прикладывается к запросу и записи
(`gates`). Изменённое reviewer дерево (файлы, HEAD) — раунд неодобрен. Ответ reviewer проверяется как у ревью плана (§8 протокола ревью), одобрение — и по итоговым находкам (открытая блокирующая не одобряет):
невалидный — раунд неодобрен, прежние находки прежние. Предмет —
`(repositoryId, роль, --base, --head как названы)`: повтор — следующий раунд,
reviewer называет состояние прежних открытых находок; тот же одобренный `head`, автор, назначение и итог gates — тот же раунд без вызова; предел раундов —
`maxAttempts × 2`. Запись (`codeReviewRecordSchema`) хранится в `code-reviews`
у `@workspace` и в `<state>/review-code/<id>/` (запрос, `review.json`). Exit 0 —
одобрено, 3 — нет; прерывание (SIGINT, SIGTERM, предел `runTimeoutMs`) — `CANCELLED`, рабочее дерево убирается, раунд не записывается. Поручения, попытки и target ref не меняются: это не приёмка.

**Принятая версия против target ref.** `status` (`works[].target`), `result` и
`deliver` (`target`) для принятой работы и `report` (`targets`: принятые
поручения, у которых ref ушёл вперёд, переписан или не прочитан; `checked` —
сверено всего; нет поля — в каталоге нет `binding.json`, испорченный `binding.json` — отказ) отдают
`acceptedTargetSchema`: `repositoryId`, `ref`, `acceptedSha`, `head`,
`commitsSinceAccepted` (`acceptedSha..head`), `filesSinceAccepted`, `diverged`
(принятый коммит не предок ref), `unavailable` (git не ответил — не отказ
команды) и строки `line` / `lineEn`. Значения — состояние Git на момент
вызова; `status --human` печатает строку под поручением. Хост, вызывающий
`statusOf` со своим движком, поле не получает.

**`smoke`.** Только окружение репозитория на коммите — то же исполнение, что
у `gates` (`runGatesAt` с `lifecycleOnly`), но без gates и без вызовов
моделей: снимки зависимостей (`dependencies`), рабочее дерево (`worktree`),
lifecycle `setup` и `ready`, хранилище зависимостей (`dependency-store`),
`prepare` и `teardown`. Ресурсы — те, что держат gates репозитория (порт
службы lifecycle проверяется так же, как перед фазой). `data.steps[]` —
каждый шаг по порядку: `stage`, `id`, `status` (`passed`/`failed`),
`durationMs`, `exitCode`, `timedOut`, `log`; у упавшего шага — `signal`
(сигнал процесса) и `tail` (хвост вывода с маской секретов, до 600 знаков;
0.1.0-alpha.68). Отказ — данные и exit 4
(`LIFECYCLE_FAILED`): `data.failure` с классом, стадией и шагом, сообщением,
хвостом упавшего шага (`tail`) и советом. Классы: `port-busy` (порт ресурса занят до окружения), `timeout`
(шаг дольше своего `timeoutMs`, проверка дольше `runTimeoutMs` или замолкла
дольше порога `stallSweep`), `crash` (ненулевой код шага; установка, упавшая
на сети или реестре по правилу `dependency-network`, — `environment`), `missing-tool`
(нет исполняемого файла: `ENOENT`, `EACCES`, код 126/127), `cleanup` (упал
только `teardown`), `tree-changed` (подготовка изменила отслеживаемые файлы)
и `environment` (прочее: переменные и секреты окружения, сеть реестра, git).
teardown исполняется и после отказа. Прерывание сигналом — `CANCELLED`.
Логи шагов — в `<state>/gates-at/<id>` (`data.logs`), ход — в stderr.
Библиотека: `smokeLifecycle`, `classifyLifecycleFailure`.

Упавший шаг lifecycle (`setup`, `ready`, `teardown`) и `prepare` в попытке,
`gates` и `smoke` называет причину сам (0.1.0-alpha.68): текст отказа —
`Шаг <id>: exit=<код>; timeout=<true|false>[; signal=<сигнал>][; стадия
<стадия>] ⟦вывод: <хвост>⟧`, где хвост — последние строки stdout и stderr с
маской секретов (до 600 знаков). Класс отказа, его причина и отпечаток
читают текст без `⟦вывод: …⟧`: вывод службы (например, слово «timeout» в её
логе) не меняет, как судится попытка. Receipt окружения фазы
(`environment.json`) записывает первый упавший шаг до `teardown` в `failure`
и упавшие шаги `teardown` в `cleanupFailure[]`: `stage`, `step`, `exitCode`,
`signal`, `timedOut`, `aborted`, `spawnError`, `tail`, `log`.

**`preview-start`, `preview-stop`, `preview-list`.** Превью результата по
`previews[]` репозитория (0.1.0-alpha.66): своё рабочее дерево на принятом
коммите в `<state>/previews`, свободный loopback-порт приложения (`PORT`,
`{port}`) за loopback-прокси, lifecycle при `services`, готовность по
`health`; надзирающий процесс сам останавливает превью по сроку (`--ttl`,
`ttlMs`) и простою без запросов (`--idle`, `idleMs`); `--ttl` и `--idle` —
длительности с единицей `s`, `m` или `h` (`90s`, `30m`, `2h`), голое число —
`INVALID_INPUT` (кроме `--idle 0` — не по простою). `--ref accepted` (по
умолчанию) — с `--work` принятый SHA поручения, без него — вершина
`targetRef`. Не поднялось — `LIFECYCLE_FAILED` (exit 4) с причиной и логом.
Запускает только оператор: внутри попытки и gate — `NOT_READY`, `run` превью
не запускает. Receipt, остановка и сверка — [превью](previews.md).
Библиотека: `startPreview`, `stopPreviews`, `listPreviews`, `livePreviews`.

**`report`.** Читает каталог состояния только для чтения и строит
`ValueReport` (`valueReport`); `binding.json` не нужен (с ним — сверка принятых поручений с target ref, `targets`). Чтение однократное
(`SqliteExecutionStore.readOnce`): база без журнала (`-wal`, `-journal`)
открывается неизменяемой (`immutable=1`) — в каталоге не появляется ни одного
файла; после чтения проверяется, что журнал не появился, а размер и время
основного файла прежние, иначе (писатель начал работу или журнал уже был)
чтение повторяется обычным открытием только для чтения. Долгоживущие
дескрипторы (`status`, `events`, `result`, `explain`, `Harness.open` с
`readOnlyState`) открываются обычным чтением: с блокировками SQLite они
видят новые фиксации, а у WAL-базы появляются пустые служебные
`-wal`/`-shm` (данных в них нет). `--format json` (по умолчанию) — обычный конверт. `--format
md|html` — документированное исключение, как `--human`: успешный ответ
печатается текстом без конверта (данные перед этим проверены схемой), отказ
— тот же JSON-конверт и тот же exit code. `--out F` записывает отчёт
выбранного формата во временный файл того же каталога и переименовывает
его поверх цели (запись не идёт сквозь symlink или жёсткую ссылку; права
прежнего файла сохраняются, новый — `0600`; при неполной записи временный
файл удаляется);
`PATH_CONFLICT` — цель не обычный файл, symlink, файл с несколькими жёсткими
ссылками или путь внутри каталога состояния; отсутствующий каталог —
`INVALID_INPUT`; stdout — конверт `{out, format, bytes, asOf}`. Неверное
окно (`--since` не раньше `--until`, время без пояса) — `INVALID_INPUT`;
нет каталога — `NOT_FOUND`, каталог не создаётся. Флаги `--since`,
`--until`, `--as-of`, `--no-titles` принимает только `report` (`--format` — ещё
`handoff`, со значениями json и md).
Пределы размера (JSON 512 КБ, HTML и Markdown 1 МБ) проверяют сами
`valueReport` и рендеры (`assertReportBytes`, `INTERNAL`).

**`handoff`.** Открывает каталог состояния только для чтения (политика — из
`binding.json`, как у `status`) и строит `HandoffPack`. `--format json` (по
умолчанию) — обычный конверт; `--format md` — документированное исключение,
как у `report`: успешный ответ печатается Markdown без конверта. Отказ —
JSON-конверт в обоих режимах; нет каталога — `NOT_FOUND`, каталог не
создаётся; неизвестный `--graph` — `NOT_FOUND`; больше 20 `--intent` или
`--format` не json/md — `INVALID_INPUT`. `--intent` принимает только
`handoff`, `--format` — `report` и `handoff`.

**Причина отказа окружения `dependency-network`.** Установка зависимостей,
упавшая на сети или реестре пакетов, получает класс `environment`, а не `gate`
(правило — [архитектура](architecture.md#что-гарантируется), «Сеть и реестр при установке зависимостей»). Отдельного поля
причины нет: схема состояния прежняя, а `failureKind` — `environment`.
Причину несёт начало текста отказа: `<фаза>/<gate>: dependency-network: …` у
gate, `dependency-network: … Шаг <id>: …` у шага `prepare`. Текст
попадает в `WorkState.failure`, `AttemptState.error`, `summary` evidence gate и в
`message` диагноза `explain` (`cause: environment`, `action: fix-environment`).
У reviewer probe такой gate — `status: error`, `failure: environment`, `note`
начинается с `dependency-network:`. Хост, который сам вызывает `runGate`,
передаёт базу попытки в необязательном `GateRun.trustedBase`: без неё
классификации нет и отказ остаётся `gate`. То же поле есть в описании probe
(`trustedBase`).

**Сводка попыток (`status`, `explain`).** У каждого поручения `status` —
`works[].attemptSummary`, у `explain` — `attempts[]` (`workId` и те же поля;
с `--work` — одно поручение), `attemptSummarySchema`:

- `total` — записей попыток, `active` — идущие;
- `failed` и `failures[]` (`{key, count}`) — отказы по корзинам отчёта
  (`failureBucketOf`), в порядке `failureBucketNames`; `timeouts` — из них
  по превышению времени (`timeout`, корзина `time-limit`);
- `interrupted` — прерванные штатной остановкой controller
  (`interrupted: shutdown`): не отказы, работа продолжается;
- `accepted` — 1, если поручение принято (последняя успешная попытка
  принятого поручения);
- `attempts` — `used` (засчитанные, `attempt` поручения; идущая попытка
  уже засчитана, закончившаяся незасчитанным отказом возвращается), `max`
  (`maxAttempts`) и `left`; `neutral` — незасчитанные отказы
  (`neutralFailures`) и их предел `MAX_NEUTRAL_FAILURES`: на пределе повтор
  только со сбросом, и у незавершённой работы `line` называет это вместо
  остатка попыток (у принятой и отменённой — итог);
  `repairs` — `used`, `budget` (`repairBudget`) и `left` задания графа по
  правилу `explain` (`repairJobOf`: задание, которое продолжит работу, или
  новое при устаревшем согласовании в режиме agent; нет — нет поля);
- `lastFailure` — почему поручение повторяется: последний отказ (последняя
  по порядку попытка с корзиной `failureBucketOf`) — `runId`, `bucket`,
  `kind` (класс отказа, если записан), `at` и причина простыми словами
  по-русски (`plain`) и по-английски (`plainEn`), например «окружение — порт
  3000 занят», «дефект — не прошли проверки: lint, unit». Текст строится из
  класса отказа, ID упавших gates и номера занятого порта; свободный текст
  ошибки попытки (вывод команд, пути, секреты) в него не попадает; предел —
  300 символов. Нет поля — отказов нет;
- `rework {revision, fresh, acceptedSha, acceptedAt?, earlierRuns}` —
  доработка после приёмки (`WorkState.rework`, событие `work.reopened`):
  числа сводки и `attempts` — только попытки доработки (после принявшей
  попытки прежней редакции), `earlierRuns` — запусков прежних редакций (в
  сводку не входят), `fresh` — свой ли предел попыток. `line` начинается с
  «принято ранее на <sha7>; доработка N: » (`accepted earlier at <sha7>;
rework N: `; без своего предела — «доработка N (попытки перенесены)»).
  Этап `status` тоже считает только попытки доработки. Нет поля — доработок
  не было;
- `line` — та же сводка одной строкой (`attemptSummaryLine`), её же печатают
  `status --human` и `explain --human` (раздел «Попытки»). Строку собирает
  `attemptLine` (`devcontour-harness/projections`) в пределе длины (1000 у
  `status`, 200 у `harness view`): хвост — остаток попыток или «повтор —
  только со сбросом» (`retry only after a reset`) и восстановления группы —
  не обрезается; при нехватке места сначала сокращается список отказов
  («defect 1, … и ещё 5», `and 5 more`), затем начало строки.

У `explain` строк не больше 100 (`EXPLAIN_ATTEMPT_ROWS`), остальные —
числом `attemptsTruncated`. Попытки читаются одним проходом на чтение.

Числа считает `attemptSummaryOf` (`devcontour-harness/report`) — та же
функция, что строки поручений отчёта (`works.rows[].attempts`,
`rejections`): на одном состоянии они совпадают. Хост со своим движком
получает ту же сводку через `statusOf(source)`; остаток восстановлений —
если источник передаёт `workflows` (`StatusSource.workflows`, как у
`HandoffSource`). Строка — факты из хранилища, не оценка времени.

**Этап поручения для оператора (`status`, `works[].stage`).** Что сейчас
происходит с поручением простыми словами (`workStageSchema`,
`src/control/stage.ts`):

- `name` — этап: `writer` (исполнитель пишет код), `prepare` (подготовка
  зависимостей), `gates` (проверки кандидата), `review` (независимое ревью),
  `integration` (интеграция с целевой веткой, включая её gates и ревью),
  `input` (ждёт ответа или применения ответа на вопрос исполнителя), `queued`
  (просто ждёт очереди — ничего не нужно), `blocked` (не выдаётся — см.
  `blockers`), `stopped`
  (остановлено отказом), `done`, `cancelled`. У идущей попытки этап —
  по последнему открытому замеру (`attempt.stage`, `step`, например
  `candidate-test:lint`), без замера — по статусу поручения; фаза интеграции
  важнее имени замера. Окружение кандидата охватывает всю его фазу: `setup`,
  `ready` и проба портов (`candidate-environment:*`) — `prepare`, `cleanup` —
  этап по статусу поручения;
- `since`, `elapsedMs` — начало этапа и время в нём по часам движка: у идущей
  попытки — открытого замера (иначе попытки), у `stopped` и `input` — конец
  последней попытки; у `queued`, `blocked` и итога полей нет;
- `next` — оставшиеся этапы попытки (`writer`, `gates`, `review`,
  `integration`): после `writer` — три, после остановки и в очереди — все;
- `needs` — что нужно и от кого: `actor` и `action` диагноза `explain`
  (`stopInputsIn` → `explainStop`, отбор доски, в том же чтении и по тем же
  часам, что весь ответ `status`) при `StatusSource.workflows`; без заданий
  графов — только `user`/`answer-input` открытого вопроса, иначе поля нет
  (неизвестно, а не «ничего»);
- `spend` — собственные вызовы поручения (его попытки и вызовы о нём; ревью
  плана группы не входит): `calls`, `knownUsd`, `unknownCalls` (без цены),
  `durationMs`;
- `line` (по-русски) и `lineEn` (по-английски) — одна строка: этап и время,
  почему повтор, дальше, «от вас», потрачено. `status --human` печатает её
  строкой `сейчас:` под строкой сводки попыток. Почему повтор: если
  последняя закончившаяся попытка (без прерванных штатной остановкой)
  отказала или засчитано больше одной попытки, строка называет номер
  попытки из `maxAttempts` и причину отказа (`attemptSummary.lastFailure`):
  у идущей — «попытка 3 из 6; прошлая остановлена: окружение — порт 3000
  занят», у ждущей и остановленной — «попыток использовано 3 из 6;
  последняя остановлена: …». У `input` вопрос исполнителя причиной не
  повторяется, у итога и первой попытки без отказа части нет. У `queued` —
  «просто ждёт очереди — ничего не нужно», у `blocked` — «не выдаётся:» и
  первая по актёру блокировка простыми словами (`blockers[].plain`: сначала
  то, что нужно от человека, затем ход ведущего, затем harness).

**Блокировки простыми словами (`status`, `works[].blockers[]`).** К прежним
`code` и `message` у каждой блокировки `status` добавлены `plain` (по-русски),
`plainEn` и `actor` — кто её снимает (`user`, `lead`, `controller`; `null` —
никто, итог), как у диагноза `explain`. Разновидность внутри кода — по
сообщению движка и состоянию поручения (`plainBlocker`,
`src/control/blocker-plain.ts`): «ждёт зависимости a» (остановленная
зависимость — что дальше по её диагнозу `explain`, например «дальше:
повтор» ходом harness; отменённая — «нужно перепланировать зависимые»), «черновик — не утверждён», «ждёт согласования плана»
(согласует ведущий, при `approvalMode: operator` — человек), «остановлено
после отказа — дальше: <действие диагноза `explain`>» (актёр — из
`stage.needs`), «ждёт вашего ответа на вопрос исполнителя», «ответ записан —
ждёт применения ведущим», «пауза очереди: поставил оператор», «пауза
очереди: бюджет», «пауза очереди: штатная остановка — снимет следующий
запуск», «очередь ещё не запускали — снимет следующий запуск», «попытки
исчерпаны (3 из 3) — нужен ваш сброс попыток», «бюджет
исчерпан» и «бюджет не определён … (поднятие предела не поможет)»,
«процесс harness работает со старой политикой — перезапустите его»,
«удержано операцией X», «ждёт конца совместной проверки репозиториев» и
другие. Из сообщения в текст переносятся только идентификаторы, которые
подтверждает состояние поручения (его зависимость, операция удержания), и
числа попыток: сообщение хоста (`HostGuards.claimable`), даже совпавшее с
шаблоном движка, ничего своего в текст не добавляет — у него общий текст кода
(`blockerCodeText`), само сообщение остаётся в `message`. У каждого кода
`Engine.blockers` есть текст — тест падает, если код добавлен без него. У
принятого и отменённого поручения блокировки выдачи ничего не требуют:
«уже принято» / «отменено», `actor: null` (код и сообщение прежние). Ответ
`run` (`works[].blockers`) полей не несёт. `status --human` печатает строку
`не выдаётся: <простой текст> (<кто снимает>); … [коды: …]` (сначала то, что
нужно от человека) вместо прежней `блокировки: <коды>`; у блокировки без
`plain` (ответ другой версии) — общий текст кода, а не `message`.

**Что проверено и как (`status`, `explain`, `result`, `report`).** Поле
`verification` (`workVerificationSchema`, `src/contracts/verification-view.ts`;
функции `verificationOf`, `verificationRows`, `verificationLines` —
`devcontour-harness/report`, модуль без zod) — записи evidence одной попытки:
у принятого поручения — принявшей, иначе последней (`runId`); у `result` —
попытки результата. ID gates и потребителей, не подходящие под форму ID
(`[A-Za-z0-9_-]{1,80}`), выводятся постоянной меткой `unnamed`. Берутся
записи текущего SHA фазы (`candidateSha`,
`integrationSha`): запись прежнего SHA — не проверка текущего. Нет поля —
попыток нет или идущая попытка ещё ничего не записала.

- `rows[]` — строка на gate и на ревью в каждой фазе (последняя запись:
  повтор `recheck` заменяет первую): `gate` (ID, без команды), `kind`
  (`gate`, `review`), `phase`, `consumer`, `result` (`passed`, `failed`,
  `reused` — запись интеграции взята из записи кандидата при том же дереве,
  `skipped` — у закончившейся попытки обязательный gate без записи
  кандидата, а если попытка дошла до интеграции — и интеграции; gate
  потребителя без записи — строкой интеграции с `consumer`;
  `not-applicable` — gate с `when.paths` не исполнялся), `how`
  (`executed-by-harness` — команду запустил harness, `reused-evidence`,
  `read-by-reviewer` — ревью агента, `not-run` — не исполнялось, в том числе
  песочница не запустила команду: `failed` с `not-run`), `at` (момент записи
  в UTC); у ревью — `reviewer {runtime, vendor}` и `review {inspection,
commands, protocol}`: по записи controller `diff-only` — команд не
  запускал, `commands` — запускал (число), `unknown` — не записано;
  `protocol: invalid|unsafe` — ответ не по протоколу, вердикта нет. Строк не
  больше 40 (`rowsTruncated` — остальные), у отчёта — 6, и проверки всех
  поручений отчёта — не больше 64 КБ JSON: сверх предела у поручения
  остаются строки `line`/`lineEn` с `rowsTruncated`, затем поле опускается;
- `line` / `lineEn` — одна строка по gate обеих фаз: «Проверено harness
  (запущено): lint, unit; на интеграции взято из записи кандидата (то же
  дерево): lint; на интеграции не запускались: …; не прошло (запущено
  harness): …; взято из записи кандидата (то же дерево): …; ревью: прочитал
  агент openai (codex), только diff, ничего не запускал — одобрил; не
  проверялось: e2e (изменения его не задели), smoke (не запускался), x (не
  запустилась — отказ среды)». У ревью вместо «только diff, ничего не
  запускал» — «и запускал команды: N (по записи controller)» или «запуск
  команд не записан», вместо вердикта при ошибке протокола — «ответ не по
  протоколу — вердикта нет». Предел — 1000 символов, у отчёта — 500.

`status` — `works[].verification` (`status --human` — строка `проверки:`),
`explain` — `verification[]` (`workId` и те же поля, не больше 100 строк;
`explain --human` — раздел «Проверки и ревью — кто и как»), `result` и
`deliver` — `verification`, отчёт — `works.rows[].verification` (раздел
«What was verified and how» в Markdown и HTML). Текст для человека не
говорит «проверено» или "checked" без того, кто и как проверял: тест
сканирует вывод `status --human`, `explain --human`, отчёта и словари
текстов.

`status --human --watch [--interval S]` (1–3600 с, по умолчанию 5) печатает
тот же текст заново каждые S секунд, пока доска не успокоится: нет идущих
попыток с действующим владением, нет задания графа с действующей арендой
(восстановление группы) и нет открытого поручения, которое сдвинет живой
controller (`statusSettled`; статус и задания — одним снимком); Ctrl-C (SIGINT/SIGTERM) завершает с exit 0. `--watch` без
`--human` и `--interval` без `--watch` — `INVALID_INPUT`. Каждый кадр —
отдельное чтение только для чтения.

**`status --detail`.** Без флага ответ `status` прежний. С флагом добавляется
`detail: {at, queue, attempts}` — снимок наблюдателя по часам движка:

- `queue` — почему стоит выдача: `paused`, `reason` и `detail` (`queueStop`;
  у паузы отказа runtime `detail` — сообщение последнего отказа её классов),
  `since`, `operation`, `failures` (классы отказа паузы runtime) и кто и что её
  снимает — `code`, `cause`, `actor`, `action` (`queuePause`, то же
  рассуждение, что у `explain` на claim). Паузу, которую снимет следующий
  run (очередь ещё не запускали, штатная остановка, применимый запрос
  политики), `explain` считает снятой; `queue` показывает её с
  `liftedByRun: true` и тем же диагнозом, что у готового поручения в
  `explain`: `NOT_READY`, `not-ready`, `controller`, `wait`.
- `attempts[]` — активные попытки (`attemptView`): `runId`, `workId`,
  `attempt`, `phase`, `runtime`, `model?`, `startedAt`, `elapsedMs`; `stage`
  — последний незакрытый замер (`name`, `family` — имя до `:`, `startedAt`,
  `elapsedMs`; при равном начале — позже записанный); `lease` — `owner`,
  `leaseUntil`, `leaseMs`, `sinceHeartbeatMs` (от последнего heartbeat,
  `leaseUntil − leaseMs`; нет при сроке `0` — владение отозвано) и `stale`
  (срок истёк). `leaseMs` — из политики процесса, который читает: у CLI —
  `binding.json` каталога состояния. `gates` — обязательные gates текущей фазы
  (интеграции в `integrating`, иначе кандидата) по последней записи каждого на
  текущем SHA фазы, без проверок потребителей: `passed + failed + remaining =
required`.

`attemptView` и `queuePause` — чистые проекции `devcontour-harness/projections`:
хост строит тот же вид по своей попытке.

**Общие операции и граница транспорта.** `init`, `explain`, `plan-request`,
`plan-check` и `capabilities` — общие операции агентского слоя
(`sharedOperations`): описание, `readOnly` (= `!writes`), вход (по `args`) и
схема ответа (`cliDataSchemas`) берутся из одной декларации — договора CLI;
`capabilities` возвращает их каталог (`operationCatalog`, тот же построитель,
что у каталога хоста). У этих команд CLI проверяет UTF-8 байты: значения
аргументов больше `maxInputBytes` (100000) — `INVALID_INPUT` с путём `argv`;
конверт ответа больше `maxResultBytes` (1048576) — `RESPONSE_TOO_LARGE`, exit
2, данные не усекаются, и с `--human` тот же JSON. Содержимое файлов-входов и
прочие команды граница не ограничивает. Усечение строк (`clipText`,
`clipDeep`) — отдельная операция и размер объекта не ограничивает; страницы с
cursor — `pageItems`, байты — `jsonBytes`/`checkJsonBytes`/`utf8Bytes`.
После приёмки договора имена и параметры меняются только совместимо или
отдельным согласованным изменением.
