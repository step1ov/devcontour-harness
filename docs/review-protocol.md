# Протокол ревью кода: находки, переходы и ошибки протокола

Документ задаёт правила истории находок независимого ревью кода (candidate и
integration) и отделяет ошибку формата ответа reviewer от содержательного
отказа. Правила записаны до реализации и являются договором: тесты
`tests/review-*.test.ts` проверяют именно их.

## 1. Область истории

История находок ведётся **на поручение**, а не на попытку, фазу или SHA:

```
scope = digestOf({ kind: 'code-review', repositoryId, workId })
```

- Новая попытка writer, переход candidate → integration и рестарт процесса не
  начинают историю заново: история каждый раз заново собирается из evidence
  всех попыток поручения (`ExecutionView.attempts(workId)`) в порядке записи.
- Отдельного хранилища нет: состояние находок — это записи ревью в
  `EvidenceRecord` попыток (см. §5). Нового обязательного метода
  `ExecutionStore`, второй базы или нового пространства локальных записей нет.
- SHA не является идентичностью истории: после исправления SHA меняется, а
  находка — нет.
- Находка другой области (другое поручение или репозиторий) в этой истории
  неизвестна: ссылка на неё — ошибка протокола `unknown`.

## 2. Идентификатор находки

ID выдаёт controller в момент записи валидного раунда; reviewer его не
придумывает и ссылается только на выданный. Формат прежний — SHA-256 hex
(`^[0-9a-f]{64}$`), без ослабления до произвольной строки.

```
id = digestOf({ v: 1, scope, runId, phase, sha, round, index, severity, message })
```

`round` — номер валидного раунда области, `index` — позиция находки в ответе.
Повторно найденный дефект с тем же текстом в новом раунде получает **новый**
ID: дедупликации по тексту нет, поэтому повторно найденный на integration
дефект не теряется.

Находка хранит: severity, сообщение, путь/строку, статус (`open`, `closed`,
`withdrawn`), origin (runId, фаза, SHA, раунд, согласованная постановка
`spec` на момент записи) и ряд переходов (раунд, runId, фаза, SHA, from → to,
основание).

## 3. Переходы

Для каждой прежней **открытой** находки валидный ответ называет ровно одну
запись в `previous` с основанием (`basis`, не короче трёх непробельных
символов):

| Из                   | В           | Смысл                                                                                  |
| -------------------- | ----------- | -------------------------------------------------------------------------------------- |
| `open`               | `closed`    | исправление подтверждено на проверяемом SHA                                            |
| `open`               | `withdrawn` | находка ошибочна или потеряла предмет; основание объясняет почему                      |
| `open`               | `open`      | дефект остаётся                                                                        |
| `closed`/`withdrawn` | `open`      | явное повторное открытие (reopen): дефект снова есть, например в интеграционном дереве |

Закрытые и снятые находки передаются reviewer как история и не требуют
повторного закрытия. Указать для них `closed`/`withdrawn` повторно —
ошибка `not-open`.

Ответ невалиден (ошибка протокола), если:

| reason                   | path                               | условие                                                                       |
| ------------------------ | ---------------------------------- | ----------------------------------------------------------------------------- |
| `schema`                 | путь Zod, например `previous.0.id` | ответ вне схемы: не SHA-256 ID, пустое основание, неизвестный статус, поля    |
| `unknown`                | `previous.N.id`                    | ID нет в истории области (в том числе ID чужого поручения/репозитория)        |
| `duplicate`              | `previous.N.id`                    | ID назван второй раз (в том числе с другим статусом)                          |
| `not-open`               | `previous.N.status`                | закрытой/снятой находке назван не `open`                                      |
| `missing`                | `previous`                         | прежняя открытая находка не названа                                           |
| `approved-with-blocking` | `approved`                         | `approved: true` при новой blocking-находке или blocking, оставшейся открытой |

`note`, оставленная открытой явным переходом, не мешает `approved: true`.

**Пределы.** В ответе не больше 500 находок и 500 переходов
(`REVIEW_ITEMS_LIMIT`): больше — ошибка `schema` с путём `findings` или
`previous`. Файл ответа codex больше предела — ошибка `schema` с путём
`(response)`, как и нечитаемый ответ. Если открытых находок поручения больше
500, раунд не записать: попытка останавливается с `review-protocol` до вызова
reviewer.

**Атомарность.** Ответ проверяется целиком до любой записи. Невалидный ответ
не закрывает ни одной находки, не создаёт новых и не даёт PASS: он
сохраняется только как диагностика (сырой ответ — в своём `review.json`,
причины — в evidence). Валидный раунд записывается одной транзакцией
`engine.evidence` под fencing-токеном попытки: попытка, потерявшая владение,
переходов не сохраняет.

## 4. Фазы, повторное открытие и новая редакция

- Закрытие на candidate не означает одобрения integration: integration —
  отдельный раунд той же области. Reviewer integration получает открытые
  находки и историю закрытых; найденный там снова дефект блокирует приёмку
  либо явным reopen прежнего ID, либо новой находкой с новым ID.
- Приёмка по-прежнему требует последней записи ревью каждой фазы на точном SHA
  с PASS (`engine.finish`, `findLast`).
- **Новая редакция постановки/контрактов** (новое согласование того же
  поручения) не начинает историю заново и не удаляет её. Открытые находки
  переносятся в новую редакцию открытыми; в их origin видна редакция, под
  которой они записаны (`spec`). Reviewer новой редакции обязан назвать их
  состояние, как любые прежние открытые (например, `withdrawn` с основанием
  «требование удалено редакцией …»). Закрытые остаются историей. Одобрение
  прежней редакции новую не подтверждает: новая редакция исполняется новой
  попыткой, и приёмка учитывает только evidence этой попытки.
- Формулы host digests (`orderDigest`, `policyDigest`, `scopeDigest`,
  основание реализации и эпизода) не меняются: находки в них не входят.

## 5. Хранение: аддитивные поля EvidenceRecord

DevContour хранит `Evidence` как есть; все новые поля необязательны, старые
записи читаются без них.

- `findings[].id`, `findings[].status` — ID и статус находки, записанной этим
  раундом.
- `reviewRound` — сведения раунда ревью кода:
  `version: 1`, `scope`, `round`, `call` (номер вызова reviewer в логическом
  ревью), `calls` (предел вызовов), `protocol: valid | invalid`, `expected`
  (ID открытых находок, выданных reviewer), `issues` (path, reason, message —
  у невалидного), `transitions` (id, from, to, basis — у валидного), `spec`.

Результат (`RunResult`) получает аддитивно: `findings[].id/status` и у ссылок
на evidence ревью — `review` (round, call, protocol, issues, transitions).
Принятый результат несёт только решающие записи: невалидные вызовы в него не
входят отдельными ссылками, их причины видны у валидного вердикта повтора
(`review.call > 1`, `review.issues` — причины предыдущих вызовов того же
логического ревью). Непринятый результат содержит и записи невалидных
вызовов (`review.protocol: invalid` с их причинами).

- `alreadySatisfied` — у записи ревью попытки без изменений (кандидат —
  база): gates и основание, которыми reviewer подтвердил, что приёмка уже
  выполнена. Поле ответа reviewer `alreadySatisfied` (`null` — нет
  подтверждения) входит в схему только для такой попытки; обычное ревью
  отвечает прежней схемой. Одобрение без годного подтверждения записывается
  непрошедшим, отказ попытки — `empty-result`; без механического основания
  (`basis`: договор проверки или зависимость, изменившая область записи) —
  `needs-lead`.

## 6. Записи alpha.5 (legacy)

Запись ревью без `reviewRound` — запись прежней версии. Её находки (у
отклонившего ревью) получают детерминированный ID из неизменяемого origin:

```
id = digestOf({ v: 'legacy-1', scope, evidence: e.id, runId, phase, sha, index, severity, message })
```

После рестарта ID тот же. Находки открыты, пока reviewer явно не назовёт их
состояние — это явное повторное ревью вместо пустой истории. Принятые
попытки и их результаты не переписываются: новые поля у них не появляются, и
исход не меняется задним числом.

## 7. Ошибка протокола и ограниченный повтор reviewer

| Исход                                                                       | Поведение                                                                                    |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Валидный `approved: false`                                                  | `REVIEW_REJECTED`, обычный путь исправления writer                                           |
| Нарушение схемы/переходов/противоречивый approved                           | повтор reviewer; после исчерпания — `REVIEW_PROTOCOL_INVALID` (класс infrastructure, exit 4) |
| Reviewer изменил дерево/HEAD, утрачено владение, отмена, смена согласования | соответствующий отказ без протокольного повтора                                              |
| Runtime недоступен, авторизация, timeout                                    | прежняя инфраструктурная причина, без протокольного повтора                                  |

- Политика: необязательное поле `reviewProtocolRetries` (0–2). Нет поля —
  один дополнительный вызов (не более двух вызовов на логическое ревью);
  `0` отключает повтор. Отсутствующее поле не подставляется в политику, её
  digest и pins не меняются.
- Логическое ревью — (область, фаза, SHA). Повтор идёт на том же SHA, с тем же
  diff, контекстом, назначением reviewer и набором открытых находок; к запросу
  добавляется только структурированная диагностика (path, reason, message) и
  требование вернуть полный валидный вердикт. ID не подменяются «похожими»,
  `previous` не выбрасывается, `approved` не восстанавливается догадкой.
- Writer не вызывается, номер попытки не растёт. Каждый вызов проходит
  `measuredInvoke` (бюджет до вызова, учёт usage/стоимости, неизвестная
  стоимость по `budgets.onUnknown`). Повтор не получает нового предела
  времени фазы и нового бюджета probe: общий срок и остаток бюджета probe
  переходят от первого вызова.
- Каждый вызов пишет свои артефакты: первый — `<phase>/review/`, следующие —
  `<phase>/review/call-<n>/` (`review.json`, журнал runtime, probe). Каждый
  невалидный вызов записывается своим evidence (`passed: false`,
  `reviewRound.protocol: invalid`, без находок); итоговое evidence ссылается
  на байты валидного вердикта.
- Рестарт не обнуляет счётчик. Вызов засчитывается при **начале**: запись
  учёта вызова (`usage`, `CallRecord` со `stage: <фаза>-review`, `runId`)
  создаётся транзакцией `measuredInvoke` до внешнего invoke, поэтому вызов,
  прерванный падением controller, засчитан так же, как завершённый (после
  рестарта он помечается `abandoned`). Начатые вызовы того же (область, фаза,
  SHA) из попыток, прерванных до вердикта (истёкших или с отказом окружения),
  засчитываются продолжающей попытке (кандидат переиспользуется); для записей
  без учёта вызовов — по невалидным evidence. Исчерпанный счётчик — остановка
  `REVIEW_PROTOCOL_INVALID` без вызова. Номер вызова — номер фактически
  начатого вызова. Логическое ревью закрывают валидный вердикт или иное
  завершение попытки (в том числе остановка `REVIEW_PROTOCOL_INVALID`).
- Срок и бюджет проверок после рестарта не выдаются заново: срок логического
  ревью — `runTimeoutMs` от начала его первого вызова (по записи учёта);
  истёкший срок — явная остановка `REVIEW_PROTOCOL_INVALID` (класс `review-protocol`, без автоматического повтора) без вызова, а каждому вызову достаётся
  только остаток срока. Расход бюджета проверок — по журналам `probes.jsonl`
  прежних вызовов этого логического ревью. Резерв каждой проверки (её предел)
  записывается в журнал строкой `start` с fsync **до** запуска команды; без
  этой записи проверка не запускается. Завершённая проверка списывает
  фактическое время, начатая без строки исхода (controller или сервер проверок
  погиб посреди команды) — весь резерв, никогда не меньше. Новый controller
  останавливает пережившие процессы такой проверки (метка `HARNESS_PROBE_RUN`
  и их группы) и дописывает строку `abandoned`; остаток меньше секунды — вызов
  без инструмента проверок (docs/review-probes.md). Integration SHA после рестарта
  создаётся заново (новое слияние), поэтому это новое логическое ревью; его
  повторы ограничены правилами повтора попытки.
- Класс отказа попытки `review-protocol`: автоматического повтора нет
  (`repairPolicy` — stop), для эпизода восстановления по свойству он
  нейтрален (не увеличивает и не обнуляет счёт), код остановки результата —
  `REVIEW_PROTOCOL_INVALID`. Кандидат такой попытки переиспользуется
  повтором, назначенным человеком, без нового вызова writer.

## 8. План и контракт

`technicalReview` (ревью плана и контракта) применяет то же правило
атомарности: невалидный ответ (вне схемы или с нарушением `reviewIssues`)
не применяет переходы и не добавляет находок; раунд записывается
неодобренным с причинами (у ответа вне схемы — путь поля и сообщение первой
ошибки). Повторно найденная закрытая находка с тем же ID
открывается снова, а не отбрасывается как дубликат. Формат `ReviewRecord`
не меняется.

## 9. Адаптеры без протокола переходов (совместимость хостов)

Строгие правила §3 действуют, когда адаптер reviewer объявляет
`RuntimeCapabilities.reviewProtocol: 1`. Это необязательное поле; нового
обязательного метода нет. `cliAdapter` (codex, claude, в том числе fixture
executables `HARNESS_*_BIN`) поле объявляет, поэтому пилот, live и demo
работают строго. Runner читает поле асинхронно до вызова reviewer, вне
транзакций хранилища, и кэширует его на runtime. Отказ `capabilities()`
трактуется как адаптер прежней версии.

Адаптер хоста, который поля не объявляет (например, собственные
runtime-обёртки DevContour), получает семантику переходов alpha.5:

- в запросе нет раздела выданных ID, и в ответе переходы не требуются:
  ответ проверяется без прежних открытых находок, как прежний
  `reviewIssues(result, [])`. Ссылка на прежний ID — `unknown`, а
  `approved: true` с новой blocking-находкой — `approved-with-blocking`;
- находки записываются в историю открытыми с выданными ID, раунд помечен
  `reviewRound.mode: 'legacy'`. Закрытия не выдумываются: одобрение не
  закрывает прежние находки, они остаются в истории открытыми. Одобрение
  при таких находках — поведение alpha.5 для этого адаптера: прежний адаптер
  не умеет называть их состояние;
- разделение H2 сохраняется: ответ вне схемы или противоречивый `approved`
  даёт ошибку протокола с ограниченным повтором reviewer и
  `REVIEW_PROTOCOL_INVALID`, а не содержательный отказ;
- writer такого поручения не получает раздела «открытых» находок: их
  некому закрыть.

Если позже ревью ведёт адаптер с протоколом, открытые находки legacy-раундов
требуют явного перехода, как записи alpha.5 (§6).

### Что реализует собственный адаптер с протоколом

1. `capabilities()` возвращает `reviewProtocol: 1`.
2. Для `task: 'review-code'` запрос несёт `RuntimeRequest.findings`
   (`{scope, open[], closed[]}`; у находки — `id`, `severity`, `message`, `path`,
   `line`, `status`, `origin {runId, phase, sha, round}`, `basis?`). Это те же
   данные, что раздел запроса `Open review findings issued by the controller`,
   поэтому адаптеру без модели не нужно разбирать текст.
3. Ответ (`RuntimeResponse.output`, схема `reviewResultSchema` / wire
   `reviewOutputSchema`) содержит в `previous` ровно одну запись
   `{id, status: 'open' | 'closed' | 'withdrawn', basis}` на каждую находку
   `open`. `id` — выданный (SHA-256 hex), `basis` — не меньше трёх непробельных
   символов. Для `closed` допустимо только `{id, status: 'open', basis}`
   (повторное открытие). `approved: true` невозможно при blocking-находке,
   оставленной открытой, или при новой blocking-находке.
