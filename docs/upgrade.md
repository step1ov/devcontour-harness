# Обновление и откат

Документ описывает, какие форматы поддерживает пакет, как обновить установку
и как откатиться. Процедуры одинаковы для standalone-состояния harness и для
хоста, который держит состояние в своём хранилище (например, DevContour с
центральной базой или базами компонентов).

## Версии

| Что | Правило |
| --------------- | --------------------------------------------------------------------------- || --------------------
| Пакет | `0.1.0-alpha.N`; выпущенная версия неизменяема (тот же номер — те же байты) |
| Публичный API | `devcontour-harness/v1alpha1` |
| Политика | `policyVersion: 1` |
| Состояние | `stateVersion: 1` |
| Отчёты и корпус | `version: 1` (отчёт свойств, договор проверки, корпус, receipt среды) |

Для `0.x`: patch — совместимые исправления; minor — отдельно описанные
изменения договора, включая несовместимые. Неизвестная версия входа, политики
или состояния отклоняется до любой записи и до выдачи попытки.

Новые версии добавляют только необязательные поля и новые пространства
локальных записей. Схемы состояния строгие: прежняя версия отклоняет
незнакомое поле до любой записи, а не сохраняет его молча. Поэтому откат
пакета «формат совместим» возможен только для состояния без новых полей,
иначе — восстановление копии (таблица «Откат» ниже).

### alpha.2: версия движка в роли controller

Роль controller записывает версию движка (`engineVersion`). Процесс другой
версии — и процесс прежней версии, записавший роль без версии, — живую роль
не перенимает, даже под тем же именем владельца: `harness run` получает
`CONTROLLER_BUSY` с обеими версиями, выдачи нет. После истечения срока роль
переходит штатно, а активные попытки прежней версии проходят recovery без
повторного использования кандидата. Штатная остановка снимает роль целиком.

### alpha.3: версии движка в `doctor`

Формат состояния тот же, что у alpha.2 (столбец alpha.2 матрицы относится и
к alpha.3). `harness doctor --state D` читает состояние строгой схемой этой
версии и для совместимого состояния называет версии движка, записавшие его
(`state.engineVersions`: роль controller и попытки); состояние, которое эта
версия не читает, отмечается несовместимым без записи.

### alpha.4: открытие без записи и владение попыткой по версии

- Существующее состояние сначала проверяется целиком соединением только для
  чтения: версия формата и документ строгой схемой. Несовместимое состояние
  отклоняется до создания таблиц, записи автора (`meta.writer`) и смены
  journal mode — файл остаётся байт в байт прежним. `harness doctor --state`
  открывает состояние только для чтения и автором не становится.
- Операции активной попытки (продление, фаза, evidence, принятие, отказ) и
  совместной проверки выполняет только движок той версии, что их начал.
  Другая версия — и попытка без версии, записанная до её появления, — получает
  `LEASE_STALE` даже с верным token до истечения срока; продолжение — только
  через истечение и recovery с новым владением.
- Совместная проверка записывает `engineVersion`; состояние, где она есть,
  прежние версии не читают (строка матрицы выше), поэтому откат с alpha.4 на
  более раннюю версию после первой совместной проверки — только через копию.

### alpha.5: публикация в npm

Код движка, форматы состояния, политики, отчётов и публичный API те же, что
у alpha.4; меняются поставка (npm, тег `alpha`) и номер версии. Состояние
alpha.4 alpha.5 читает и пишет без преобразования, состояние alpha.5 читает
alpha.4 (новых полей нет).

Номер версии — это `engineVersion`, поэтому правила alpha.2–alpha.4
действуют и между alpha.4 и alpha.5:

- живая роль controller alpha.4 не переходит к alpha.5 (`CONTROLLER_BUSY`),
  пока не будет снята штатной остановкой или не истечёт;
- активную попытку и совместную проверку, начатые alpha.4, alpha.5 не
  продолжает даже с верным token (`LEASE_STALE`): после истечения срока
  recovery передаёт их новой версии без повторного использования кандидата
  прежней версии;
- в обратную сторону то же: после отката alpha.4 не продолжает попытки
  alpha.5.

Поэтому обновление — по общей процедуре ниже: остановить writers, сделать
копию, проверить её новой версией. У хоста, который поставлял alpha.4
архивом, переход на registry — смена зависимости на точную версию
`0.1.0-alpha.5` и обновление lock; содержимое alpha.4 под своим номером не
меняется.

### alpha.6: протокол ревью, доставка `uncertain`, toolchains

Формат `stateVersion: 1` прежний; добавлены только необязательные поля, но
строгие схемы прежних версий их не знают:

- записи ревью кода несут `reviewRound` и `findings[].id/status` (протокол
  ревью, [review-protocol](review-protocol.md)); такая запись появляется после
  первого ревью кода новой версией;
- запись доставки может иметь статус `uncertain` и поле `operation`; в журнале —
  событие `delivery.uncertain`.

Состояние alpha.5 alpha.6 читает и продолжает без преобразования: прежние
записи ревью — legacy-раунды, прежние доставки и receipts не переписываются.
Standalone-состояние, в котором есть новые поля, alpha.5 и alpha.4 не читают:
отказ `STATE_VERSION_UNSUPPORTED` до любой записи. Прежний хост DevContour
(0.4.0-alpha.7 с адаптером alpha.4) такого отказа **не даёт**: состояние alpha.6
— и без записей ревью нового протокола, и с ними (`reviewRound`,
`findings[].id/status`) — он открывает и может записать в него роль controller,
события и документ, а при готовых поручениях — выдать по ним работу; новые поля при этом сохраняются, но гарантии строгой схемы
нет. Пока действует роль controller alpha.6, прежний writer её не перехватывает
и ничего не пишет. Защиты от запуска прежнего DevContour на состоянии alpha.6
нет, поэтому откат с alpha.6 — только восстановлением копии состояния,
сделанной до обновления; прежнюю версию на текущее состояние не запускать.

Правила `engineVersion` (alpha.2–alpha.5) действуют и между alpha.5 и alpha.6:
живая роль и активные попытки alpha.5 не продолжаются до истечения срока и
recovery.

Политики: новые необязательные поля `repositories[].toolchain` и
`reviewProtocolRetries`. Политика без них сохраняет прежние `policyDigest`,
`executionDigest` и закрепления; политика с ними получает новое основание
(новое согласование). Встроенные профили alpha.5 побайтно прежние; новые
профили — новые id (`npm-ci`, `pnpm-frozen`, `go-gotestsum`, `python-uv`).

### alpha.7: учёт выполненных команд reviewer

Формат `stateVersion: 1` прежний. `inspection` в `review.json` и evidence ревью кода получает
новые значения и необязательные поля ([review-probes](review-probes.md#итог-inspection-что-reviewer-действительно-выполнил)):
`source` — также `controller-probes` и `runtime-and-controller`; `commands[].exitCode` может
быть `null`; новые `commands[].origins/status/failure/gate/note`, `context`, `total`,
`excluded`, `excludedTotal`, `invalid`. Строки исхода в `probes.jsonl` несут `started` и
`scope`; `review.json.probes` — `exitCode`, `started`, `scope`, `note`.

Направление совместимости одностороннее: alpha.7 читает записи alpha.6 и ранее без
пересчёта; строгая схема alpha.6 не принимает новый `source`, `exitCode: null` и новые поля,
поэтому состояние с такими записями alpha.6 не читает. Потребителю, разбирающему
`inspection`, нужно принять новые значения `source`, nullable `exitCode` и необязательные
поля; признак выполнения — `mode`, а не наличие кода 0. Откат — как для alpha.6: только
восстановлением копии состояния, сделанной до обновления.

### alpha.24: выбор корня и диагностика

Форматы состояния, политики и публичные поля API прежние. Диагностика
`doctor` не создаёт каталоги корня рабочих деревьев. Корень, заданный
хостом, отклоняется, если он содержит репозиторий, каталог состояния или
закрытый путь; символическая ссылка вместо корня тоже отклоняется.
Назначьте отдельный каталог рядом с ними. Новые каталоги создаются с mode
0700, существующие права не меняются. Состояние alpha.24 читает alpha.23;
при откате возвращается прежнее поведение выбора корня и классификации
отказа чтения учётных данных. Подробнее —
[заметки выпуска](release-notes/0.1.0-alpha.24.md).

### alpha.27: хранилище зависимостей

Форматы состояния и публичные поля API прежние; без
`repositories[].dependencyStore` политика и её digest не меняются. Поле
необязательно, строгая схема прежних версий его не принимает: при откате
уберите его из политики. Каталог `dependency-store` в состоянии и таблицу
`seed_pins` в `resources.sqlite` прежние версии не читают. Подробнее —
[заметки выпуска](release-notes/0.1.0-alpha.27.md) и
[хранилище зависимостей](toolchains.md#хранилище-зависимостей).

### alpha.29: запуск песочницы проверок

Форматы состояния, политики и публичные поля API прежние. sandbox-runtime
искал shell через `which` с таймаутом в секунду на каждый запуск проверки; под
нагрузкой машины поиск не успевал, и проверка не стартовала с ошибкой
«Shell 'bash' not found in PATH». Теперь процесс srt находит shell по PATH сам,
без порождения `which`, и только в абсолютных каталогах PATH; не найденный
shell по-прежнему ищет `which`. Старт команды доказывает токен, который обёртка
печатает в stderr перед `exec`; он ищется и вырезается в сыром потоке до маски
секретов: стёртая командой
метка-файл больше не выдаёт стартовавшую команду за не запущенную, и такая
команда не повторяется. Если песочница не запустила команду и после повторов
(до трёх попыток, только пока нет ни метки, ни токена), а весь stderr — только
строки известного отказа запуска srt (`Error: Shell '…' not found in PATH`,
`Failed to execute command: …`), gate не
проходит с классом `environment` и сообщением «песочница ОС не запустила
команду проверки», а не как провал проекта с кодом выхода; probe reviewer в
этом случае — `error`/`environment`. Прочие отказы srt до старта остаются
провалом проверки (`gate`). При откате возвращается прежний поиск shell и
прежняя классификация (`gate`).

### alpha.29: быстрее копия хранилища зависимостей

те же байты и права копии по тому же закреплённому манифесту. На macOS копия

версии, seeds и копии подходят обеим. Подробнее —
[хранилище зависимостей](toolchains.md#хранилище-зависимостей).

### alpha.30: события стадий

Форматы состояния (`stateVersion: 1`), политики и её digest прежние: в
документ состояния не добавлено ни одного поля. Новое в журнале и в CLI:

- **Терпимое чтение событий.** Событие типа, которого версия не знает
  (записанное более новой версией), `events` и `ExecutionStore.events`
  возвращают непрозрачным: конверт без нагрузки, `type: 'unknown'` и исходный
  тип в `original` — а не обрывают список отказом. Писатель строгий: событие
  `unknown` не записывается. Известный тип с нарушенной нагрузкой — по-прежнему
  отказ. Хост, который сам разбирает сохранённые события, использует
  `readRunEvent`. В TypeScript `RunEvent` теперь включает `UnknownRunEvent`:
  код, читающий `payload` без сужения по `type`, перестаёт компилироваться —
  сузить (`e.type !== 'unknown'` или конкретный тип) либо взять
  `KnownRunEvent`. Тип `ExecutionStore.events()` прежний: хранилища хоста не
  меняются.
- **Событие `attempt.stage`.** На каждую стадию попытки (замер
  `AttemptState.timings`) — одно `started` и не больше одного `finished` с
  `durationMs` и исходом, в той же транзакции под fencing, что и замер.
  Стадия попытки, утратившей владение или упавшей, остаётся открытой; её
  конец — событие конца попытки.
- **`status --detail`.** Поле `detail`: почему стоит выдача и активные
  попытки — стадия и её длительность, владение и его свежесть, счёт gates.
  Без флага ответ `status` прежний.

**Откат.** Прежние версии (alpha.29 и ниже) разбирают каждое событие строго:
терпимое чтение появляется только с этой версией. После отката ниже неё
`harness events` и чтение журнала хостом через прежний `ExecutionStore.events`
отказывают на первой странице, где есть `attempt.stage`; документ состояния,
`status`, `result` и работа очереди читаются как прежде. Рекомендуемый путь —
строка «Новая версия уже изменила формат» таблицы [«Откат»](#откат): остановить
writers и восстановить копию каталога состояния, снятую до обновления, вместе
с прежней версией пакета. Без копии прежняя версия продолжает работу очереди,
но журнал после первого `attempt.stage` ей не прочитать; удалять или
переписывать события ради неё нельзя.

### alpha.30: отчёт об эффекте

Форматы состояния (`stateVersion: 1`), политики, событий и их схем прежние:
отчёт только читает. Новое — аддитивно:

- **`harness report`.** Отчёт по каталогу состояния: принятые поручения и
  первая попытка, возвраты проверками и ревью, действия человека (нижняя
  граница), срок от согласования до приёмки, расход (неизвестная цена —
  «≥», а не ноль), отказы окружения, недели и ограничения. `--format
json|md|html`, `--out F`, окно `--since/--until`, `--as-of`, `--no-titles`.
  База открывается только для чтения; `binding.json` не нужен.
- **Библиотека.** `devcontour-harness/report` (`valueReport`,
  `reportMarkdown`, `reportHtml`; без `node:*`), в корне — те же функции,
  `collectReportInput(store)` и `Harness.report()`.
- **Чтение без файлов.** `report` читает состояние однократно: база без
  журнала открывается неизменяемой и в каталоге состояния не появляется
  служебных `-wal`/`-shm`; если писатель начал работу во время чтения,
  оно повторяется обычным открытием. Прочие читающие команды не менялись.
- **Схема.** `value-report` (`schemas/value-report.schema.json`,
  `reportVersion: 1`) и данные `report` в `cliDataSchemas`.

Определения, правила малых выборок и приватности — [ValueReport](contracts.md#valuereport).
Отчёт строится из истории как она записана: попытки прежних версий без класса
отказа показаны `unclassified`, без `wait` — с запасным началом срока, без
учёта вызовов — с неизвестным расходом; история не переписывается.

**Откат.** Ниже этой версии команды `report` нет; состояние она не меняла,
поэтому откат пакета копии не требует.

### alpha.30: сетевой отказ установки зависимостей

Форматы состояния и политики прежние; нового поля в состоянии нет. В
описании reviewer probe (`probe.json`) — необязательное поле `trustedBase`.
Установка зависимостей, упавшая на сети или реестре пакетов, теперь отказ
`environment`, а не `gate`; сообщение начинается с `dependency-network:`.
Условия:

- argv gate попытки или шага `prepare` сам вызывает `npm install|ci`, `pnpm
install|fetch` или `yarn install`;
- входы менеджера в дереве (`.npmrc`, `.yarnrc*`, pnpmfile, lockfiles, поля
  зависимостей и скрипты установки `package.json`) совпадают с базой попытки;
- база не исполняет кода при установке;
- менеджер вышел сам с кодом 1–127;
- его отчёт называет только сетевые коды: HTTP 403/407/408/429/5xx реестра,
  обрыв соединения, DNS, TLS.

Такой отказ не тратит попытку поручения и ставит паузу очереди `runtime`, как
любой отказ окружения. Повтор берёт того же кандидата, работу ограничивает
`MAX_NEUTRAL_FAILURES`. Отказ после правки кандидатом реестра, зависимостей
или скриптов установки, ошибки lockfile, 404, peer-зависимости и упавший скрипт
остаются `gate`. Прежде такой отказ gate давал класс `gate`, а шаг `prepare` —
`unknown`. Хосту, который считает «дефекты, найденные проверками» по
`failureKind`, новых действий не нужно: эти отказы уходят из счёта сами.
Правило — [архитектура](architecture.md#что-гарантируется). При откате
возвращается прежняя классификация; уже записанные попытки сохраняют свой
класс.

### alpha.31: обход зависаний

Номера форматов прежние (`stateVersion: 1`, `policyVersion: 1`), новое —
аддитивно:

- **Состояние.** Необязательное поле `AttemptState.liveness` (`state`, `at`,
  `lastMovementAt`, `activity`, `action`, `artifact`) и класс отказа
  `stalled` в `failureKind`. Поле пишется только на переходах живости.
- **Политика.** Необязательное поле
  `stallSweep{intervalMs, quietMs, stalledMs, action}` и
  `repairPolicy.stalled`. Без поля обход идёт с
  умолчаниями (30 000 / 180 000 / 600 000 мс, `report`); умолчание в
  политику не подставляется, digest политики и digest исполнения прежние,
  поэтому основания попыток и reuse кандидатов после обновления не меняются.
- **Журнал.** События `attempt.liveness` и `joint.liveness`. Файлы снимков
  `artifacts/<runId>/stall-<эпизод>.json` в каталоге состояния.
- **Хост.** `runGatesAt` принимает `onLiveness` и возвращает `liveness[]`;
  `status` — `works[].liveness`, `status --detail` —
  `detail.attempts[].liveness`.

**Откат.** Документ состояния и политика разбираются строго: alpha.30 и ниже
отказывают на документе, где у попытки есть `liveness` или отказ `stalled`, и
на политике с `stallSweep`. Обход включён по умолчанию, поэтому такой документ
появляется с первой затихшей попыткой. Путь — строка «Новая версия уже
изменила формат» таблицы [«Откат»](#откат): остановить writers, восстановить
копию каталога состояния, снятую до обновления, вместе с прежней версией
пакета и убрать `stallSweep` из политики. События `attempt.liveness` alpha.30
читает как `unknown`.

### alpha.32: пакет передачи контекста для хоста

Только чтение и только аддитивно: формат состояния, политики, событий и

меняется. Новое в корне пакета:

- `handoffPack(source, options)` принимает `HandoffSource`
  (`{ engine, policy, workflows: { list, continues } }`) — `Harness` ему

`handoffPack` с узким источником, `maxBytes` или `measure`, либо
импортировавший `statusOf`, `policySecrets` или `HANDOFF_MIN_BYTES`, при
откате возвращается к прежнему коду (экземпляр `Harness`, свой обход
секретов и своя подгонка размера).

### alpha.32: песочница при глубоком TMPDIR

Форматы не меняются. Раньше при глубоком TMPDIR процесса controller путь
unix-сокета sandbox-runtime превышал предел (104 байта на macOS, 108 на
Linux), srt падал до запуска команды (`listen EINVAL`), и проверка не
стартовала. Теперь srt в этом случае получает короткий каталог
`/tmp/dc-srt-<pid>-*` (`0700`, удаляется после проверки; брошенные упавшим controller каталоги, где ничего не менялось дольше суток и процесса создателя нет, убираются при создании нового). Если и он недоступен —
отказ среды (`environment`) с TMPDIR в тексте.

**Откат.** Состояние не меняется. На прежней версии при глубоком TMPDIR
проверки в песочнице снова не стартуют: задайте короткий TMPDIR.

### alpha.33: отменённые без ждущих и расход ревью плана в пакете передачи

Форматы состояния, политики и событий прежние; `handoffVersion` — 1.

- Отменённая работа (и упавшая с классом `cancelled`) — решение ведущего
  (`CANCELLED`, `replan-dependents`), только пока от неё прямо зависит
  незавершённая работа (не `done` и не `cancelled`); сообщение называет
  ждущих. Отменённая без таких работ в общий `explain` и в `stops`/`next`
  пакета передачи не входит (как принятая); `explain --work` этой работы
  показывает её с `action: none`. Упавшая отменой без ждущих — решение
  человека (user `user-decision`: `harness retry` или отмена), а не повтор:
  `nextAction` для неё — `user-decision` на шаге `cancelled`. Диагноз упавшей
  работы, чью группу движок не восстанавливает из-за отмены, называет
  отменённую.
  Раньше доска, где все зависимые отменённых тоже отменены или приняты,
  начиналась с решения «перепланировать», которое нечего было делать.
- Вызов о группе (ревью и проверка плана) по-прежнему засчитывается целиком
  бюджету каждого её открытого поручения — так действует ограничение
  поручения; в строках группы и `total` он учтён один раз, суммы не
  завышены. Пакет передачи больше не перечисляет бюджеты поручений, весь
  расход которых — такие вызовы, кроме тех, что держат выдачу (превышены
  или не определены при `onUnknown: stop`): их число — новое поле
  `truncated.budgetsShared` (в схеме необязательное, по умолчанию 0: пакеты
  прежних версий разбираются). `handoffVersion` остаётся 1, поэтому внешний
  валидатор со строгой прежней схемой пакета
  (`schemas/handoff-pack.schema.json`) обновляется вместе с harness: прежняя
  схема новое поле отклонит. `status` бюджеты поручений показывает как
  прежде.

**Откат.** Состояние не меняется; прежняя версия снова показывает такие
отменённые как решение и повторяет строку бюджета у каждого поручения.

### alpha.34: события вмешательств и причин отказа

Формат состояния (`stateVersion: 1`), политики и её digest прежние: в документ
состояния не добавлено ни одного поля. Новое в журнале (`docs/contracts.md`,
`RunEvent`):

- `work.retried {by, reset, spent?, reasonLength?}` — повтор поручения.
  `engine.retry(workId, reset?, by?)` принимает актёра: CLI `retry` —
  `operator`, восстановление очереди — `recovery`, по умолчанию `host`.
  Текста причины сброса в событии нет, только длина.
- `work.cancelled {by, hadAttempt}` — отмена поручения, в том числе без
  активной попытки и новой редакцией графа (`by: graph`).
  `engine.cancel(workId, reason?, by?)`; CLI `cancel` — `operator`.
- `base.moved {by}` — сдвиг ref базы `fencedRefMove(store, fence, timeoutMs?,
by?)`, `by` — `operator`, `controller` или `host` (по умолчанию). Хост,
  сдвигающий базу перемоткой очереди, передаёт `controller`, ручной перенос —
  `operator`. Транзакция `base.moved` теперь пишет событие: адаптер хоста,
  выполнявший её без событий, должен записать его так же, как другие
  нейтральные события без изменения документа.
- `attempt.diagnosed {failureKind, cause, counted}` — причина отказа попытки
  рядом с `attempt.failed` и `attempt.expired`. Хост, вызывающий
  `engine.fail` сам, может передать `options.cause`; `TaskFailure` принимает
  причину четвёртым аргументом (`diagnosis`).

Отчёт (`ValueReport`, `reportVersion: 1`): `autonomy.actions.recorded`
(актёры вмешательств по событиям или `null`), суммы `retries`/`resets` по
событиям — только точные (иначе `null`), `baseMoves` — всегда `null` (сдвиг
вне `fencedRefMove` не пишется, число по актёрам — нижняя граница),
`withAction`/`withoutAction` с записью — точные или нижняя граница
(удержанные поручения — неизвестны); `environment.causes` — подпричины или
`null`; предел `limitations` — 40. Засчитанные попытки (первая попытка,
попыток на принятое) считаются по правилу движка: зависание (`stalled`)
теперь засчитано. Без новых событий отчёт прежний, кроме поля `recorded:
null` и этого правила засчитанных попыток: история с зависаниями даёт
другие числа первой попытки и попыток на принятое. Читатель, проверявший отчёт

  корзина отказов `input`.
- **Порты.** Необязательный `ExecutionHost.input` (`InputHost`) для хоста,
  ведущего согласование сам; `RunnerOptions.context(work, attempt)` получает
  выданную попытку (снимок загружается по `attempt.pinned.contextDigest`);
  `measuredInvoke` — необязательный `onStart(callId)` (доставку ответа
  runner подтверждает не им, а ответом runtime, отличным от `unavailable`). Набор
  `executionStoreContract` проверяет пространство `input-requests`;
  `sampleInputRequest`/`answeredInputRequest` экспортированы из
  `devcontour-harness/testing`.

  `input-context`, `input-target`, `input-apply`, `input-cancel`,
  `input-supersede`.
- **Хост с портом согласования.** `InputHost.review` и `activate`
  получают запрос (`{id, answerDigest, mode}`); перенос ответа заменённого
  запроса — `Engine.proposeCarry` и `Engine.carryInput` (`expectedVersion`,
  `targetDigest`; `Harness.proposeCarry`/`carryInput`). Экспортированный
  `unappliedInputs` требует `mayCarry`. `originBasis.contentDigest` —
  необязательное поле запроса, `target.contentDigest` — цели; состояние
  вопроса `carry-stale` (status, handoff); `cancelInput` снимает устаревший
  перенесённый ответ. Не найденный закреплённый снимок держит только свою
  работу (`needs-lead`, не засчитана), очередь не останавливается. Исходная остановка и
  устаревание применённого ответа сравнивают постановку самой работы, а не
  digest графа. Попытка с `pinned.contextDigest` отказывает, если загрузчик
  контекста хоста вернул другой снимок. `implementationOutputSchema`
  (wire-схема ответа writer) экспортирован корнем пакета.
- **Маскирование.** Ответ writer маскируется полным окружением вызова до
  разбора: `hooks.implemented` получает уже замаскированный `output`
  (`summary`, `discoveries`). Наследуемые переменные (`environment.inherit`)
  маскируются, если значение не короче 8 знаков или имя похоже на секрет

  знаков); объявленные `secrets` — всегда. Не маскируются только наследуемые
  значения короче 8 знаков без секретного имени (`FORCE_COLOR=1`, `CI=true`):
  прежде они вырезались из каждой строки вывода проверок и ответов. Короткий
  секрет без секретного имени объявите в `secrets`.

  проверяются до решения о вопросе и незавершённости для любого ответа

  `unfinished` и продолжался с черновика в области; теперь это

- **Перенос и объяснение.** Снятие устаревшего перенесённого ответа хранит

  `preflight` (`StopInput.work.preflight`).
- **Отчёт.** `report.inputs.carryStale` — новое число; `report.inputs.closed`

`StopDiagnosis`, `RunEvent`, `RunResult` или ответа `status` отклонит новые
значения и поля: обновить схему вместе с пакетом. Хост с собственным
хранилищем (DevContour) хранит `input-requests` у владельца-компонента, а

### 0.1.0-alpha.38: вопрос не тратит попытку

Номера форматов прежние (`stateVersion: 1`, `policyVersion: 1`). Остановка
`needs-input` возвращает попытку в предел `maxAttempts` и не тратит предел
незасчитанных отказов: ответ на вопрос последней попытки применяется
(`applyInput`, `carryInput`) без `reset`. `attempt.diagnosed` такой остановки
пишет `counted: false`; отчёт считает засчитанные попытки по тому же правилу,
поэтому принятая после вопроса работа может стать «с первой попытки».
Возврат ограничен: поручение получает не больше `maxAttempts` остановок
вопросом, возвращающих попытку, за всю жизнь (счёт по записям попыток,
сброс его не обнуляет); следующая засчитывается как обычная попытка
(`counted: true`), и цикл вопросов кончается исчерпанием попыток. Новой
настройки нет. Работы, остановленные вопросом до обновления, хранят прежний
счётчик: продолжение после исчерпания по-прежнему требует сброса с
причиной; их прежние остановки вопросом входят в счёт предела. Хост,
требовавший `reset` после вопроса на последней попытке, может это требование
снять, пока предел остановок вопросом не исчерпан. Откат возможен без
изменений состояния.

    - подтверждение контрпримера — исход `inconclusive` («проверка не
      выполнилась: …»), корпус не меняется.
  - Совместная проверка рабочей области (joint) сверки подготовки не
    получает, как и сверки gate.
- Отказ ядра в удалении закреплённого каталога — отказ окружения
  `sandbox-filesystem` только тогда, когда одна строка вывода gate содержит
  и EPERM, и этот путь отдельным словом: абсолютный (в том числе `/var`
  вместо `/private/var`) или относительно `cwd` gate. Перед путём — начало
  строки, пробел, кавычка, `(`, `[`, `=` или `<`; после — конец строки,
  пробел, кавычка, `:`, `/`, `,`, `;`, `)`, `]`, `>` или точка в конце
  предложения. `.claude-old`, `.claude.bak` и `~/.claude/…` каталог
  `.claude` не называют. Иначе провал остаётся `gate`.
- Тексты отказов исполнителя и установки зависимостей говорят «создал,
  изменил или удалил защищённые пути» (прежде «создал или изменил»):
  читатель, сравнивавший текст, сверяет по `защищённые пути`.
- Откат возможен без изменений состояния.

### 0.1.0-alpha.43: исчезновение `.git` подготовки и подпись с ctime

Номера форматов прежние (`stateVersion: 1`, `policyVersion: 1`).

- Исчезновение вложенного `.git`, которым владеет подготовка, засчитывается
  только когда родители от корня до первого исчезнувшего звена — настоящие
  каталоги: родитель, заменённый символьной ссылкой или файлом, —
  `scope-violation` (во время подготовки — `sandbox-policy`). Подмодуль,
  записанный в индексе, переносом наружу не убрать: git хоста видит
  удаление отслеживаемого пути, и gate проваливается проверкой
  отслеживаемых файлов. Его уборка — дело подготовки или teardown.
- Подпись защищённого файла в сверке включает ctime: правка на месте с
  восстановленными размером и mtime (`utimes`), а также chmod/chown, новая
  жёсткая ссылка или изменение расширенных атрибутов защищённого файла во
  время работы исполнителя, установки или gate — изменение
  (`scope-violation`; во время подготовки — `sandbox-policy`). Шаги, которые
  меняют права или делают жёсткие ссылки на файлы `.idea`, `.vscode`,
  `.claude` или `.git` в дереве, держите вне проверки.
- Откат возможен без изменений состояния.

## Перед обновлением

1. **Остановить записывающих.** Запретить новые выдачи (`harness pause`),
   дождаться завершения или явно остановить активные попытки, остановить
   controller, сервер и всех остальных, кто пишет в состояние. Одной паузы
   очереди недостаточно.
2. **Зафиксировать.** Версии пакета и потребителя, конфигурацию, вершины
   target refs и result SHA принятых поручений (`git rev-parse` каждого
   target ref, `harness result` каждого поручения).
3. **Сделать копию.**
   - standalone — каталог `--state` целиком, пока controller остановлен;
   - центральная база хоста — штатная согласованная копия SQLite;
   - базы компонентов — копия **всех** баз при остановленных writers
     (команда резервной копии одной базы этого не обеспечивает).
     Git-объекты должны оставаться доступными: копия базы без объектов, на
     которые она ссылается, не восстанавливает историю.
4. **Проверить на копии.** Открыть копию новой версией в отдельном каталоге
   (`harness doctor --state <копия>`, `harness status --state <копия>`).
   Проверка несовместимой версии не должна менять данные — сравните хэши
   файлов копии до и после.

## Обновление

1. Установить новую версию точно (у хоста — смена зависимости и lock):
   - из npm — `npm install --save-exact devcontour-harness@<new>`;
   - из архива — `npm install --omit=dev --ignore-scripts ./devcontour-harness-<new>.tgz`.
2. `harness doctor --state D` — версии, runtime, песочница, совместимость и
   версии движка, записавшие состояние (`state.engineVersions`: роль
   controller и попытки).
3. Возобновить работу **одним** controller (`harness resume`, `harness run`).
4. Попытки, активные во время остановки, не продолжаются со старыми
   токенами: recovery либо принимает сохранённый integration SHA при полных
   актуальных evidence, либо завершает попытку; новая попытка получает новое
   владение и новые проверки. Кандидат попытки прежней версии движка повторно
   не используется.

Установка новой версии не меняет политику, профили, закрепления контекста,
инструкции агентам и принятые результаты.

## Откат

| Ситуация | Действие |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- || --------------------
| Изменения исходников до выкатки | Вернуться к проверенной паре коммитов/версий в отдельном checkout или revert-коммитами; страховочную ветку не переписывать |
| Только пакет, формат данных совместим | Остановить writers → вернуть прежнюю версию (архив или точную версию npm), зависимость и lock → `harness doctor` → возобновить |
| Новая версия уже изменила формат | Остановить writers → восстановить согласованную копию вместе с совместимой версией пакета → сверить Git refs и артефакты (ниже); простого понижения версии мало |

### Сверка Git после восстановления базы

База и Git не образуют одну транзакцию. Если после копии target ref ушёл
вперёд (поручение принято уже новой версией), восстановленная база не знает
об этом принятии.

1. Для каждого репозитория сравните вершину target ref с зафиксированной до
   обновления и с result SHA, известными восстановленной базе.
2. Коммиты, которых база не знает, — принятые после копии. Их нельзя молча
   «забыть»: либо повторите поручения новой попыткой (её интеграция
   продолжит текущий target ref), либо явно задокументируйте, что эти
   принятия выполнены вне восстановленного состояния.
3. Не выполняйте `git reset --hard` пользовательского репозитория и не
   переписывайте target ref ради совпадения с базой — это не откат, а потеря
   принятой работы.

Откат объявляется успешным, только когда для каждого target ref известно,
какие его коммиты учтены восстановленным состоянием.
