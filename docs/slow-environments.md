# Медленные окружения

Страница для проекта, где gates и подготовка среды дороги: установка
зависимостей идёт минутами, тесты поднимают службы, сборка мобильного
приложения или e2e занимают десятки минут. Каждая попытка платит за среду
дважды — на кандидате и на интеграции, — а повтор после отказа платит снова.
Ниже — как найти, куда уходит время, какие поля политики его сокращают и
какие пределы выставить, чтобы попытка не истекала посреди проверок.

Все поля — `ExecutionPolicy` (`.harness/policy.json`,
[contracts](contracts.md#executionpolicy)); умолчания — из схемы политики
(`schemas/execution-policy.schema.json`).

## Куда уходит время

Каждая стадия попытки — замер `timings` и событие `attempt.stage`:

| Стадия                                                  | Что это                                               |
| ------------------------------------------------------- | ----------------------------------------------------- |
| `dependency-store`                                      | копия зависимостей из хранилища (`dependencyStore`)   |
| `implementation`, `implementation-reuse`                | работа исполнителя или перенос его прежнего кандидата |
| `candidate-environment:<шаг>`                           | lifecycle `setup`/`ready` и `prepare` на кандидате    |
| `candidate-test:<gate>`, `candidate-recheck:<gate>`     | gates кандидата и повтор gate                         |
| `candidate-review`                                      | независимое ревью кандидата                           |
| `integration-wait`                                      | ожидание очереди слияния репозитория                  |
| `integration-environment:<шаг>`                         | lifecycle и `prepare` на integration-коммите          |
| `integration-test:<gate>`, `integration-recheck:<gate>` | gates интеграции и повтор                             |
| `integration-review`                                    | ревью интеграции                                      |
| `generate:<id>`, `integration-generate:<id>`            | генераторы выходов (`repositories[].generators`)      |
| `<фаза>-consumer:<репозиторий>:<gate>`                  | gates потребителей                                    |

Где смотреть:

- `harness report --state <state> --format md` — таблица стадий (раздел
  Speed): сумма, медиана, время на принятых и отклонённых попытках по
  семействам стадий (имя до `:`). Семейство `candidate-environment` или
  `integration-environment` с большой суммой — дорогая подготовка;
  `*-test` на отклонённых попытках — время, потраченное на повторы.
- `harness status --state <state> --detail` — идущая стадия и её
  длительность (`detail.attempts[].stage`); `harness status` — строка
  сводки попыток поручения: сколько отказов по времени (`timeout`) и
  прерываний.
- `harness events --state <state>` — события `attempt.stage` с
  `durationMs` и исходом.
- `harness doctor --policy .harness/policy.json` — предупреждения о сроке
  фаз (ниже) до первого запуска.

## Пределы времени

| Поле                                         | Умолчание  | Смысл                                                                                                                                                     |
| -------------------------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runTimeoutMs`                               | `900000`   | срок одной фазы попытки, мс: реализация, генерация, проверки и ревью кандидата, интеграция                                                                |
| `repositories[].gates[].timeoutMs`           | `120000`   | предел одного исполнения gate                                                                                                                             |
| `gateTimeoutFloorMs`                         | нет        | нижняя граница предела каждого gate (1000–600000), не больше `runTimeoutMs`                                                                               |
| `repositories[].prepare[].timeoutMs`         | `120000`   | предел шага `prepare`                                                                                                                                     |
| `repositories[].lifecycle.setup[].timeoutMs` | `120000`   | предел шага lifecycle (`ready` и `teardown` — так же)                                                                                                     |
| `repositories[].dependencyStore.timeoutMs`   | `600000`   | предел сборки seed хранилища зависимостей                                                                                                                 |
| `concurrency`                                | `2`        | одновременных попыток (1–4)                                                                                                                               |
| `leaseMs`                                    | `30000`    | срок владения попыткой без heartbeat                                                                                                                      |
| `stallSweep.quietMs`                         | `180000`   | без движения дольше — `quiet`                                                                                                                             |
| `stallSweep.stalledMs`                       | `600000`   | без движения дольше — `stalled`                                                                                                                           |
| `stallSweep.action`                          | `"report"` | на `stalled`: `report` только сообщает, `stop` останавливает попытку                                                                                      |
| `stallSweep.writerStallEpisodes`             | `3`        | облегчённый и тонкий режимы: столько эпизодов `stalled` в одном вызове writer без живой команды инструмента останавливают его и при `report`; `0` — выкл. |

**`runTimeoutMs` — срок фазы, а не попытки.** Срок начинается заново в
начале каждой фазы. Внутри фазы на него ложатся все её шаги: lifecycle
`setup`/`ready`, `prepare`, gates (каждый со своим пределом), один возможный
повтор самого долгого gate (`recheck`), генераторы, ревью. Если сумма
пределов шагов фазы больше `runTimeoutMs`, попытка может истечь до конца
проверок, хотя каждый шаг укладывается в свой предел: отказ `timeout`
засчитывается и тратит попытку.

**Как выбрать.** Замерьте самый долгий gate и подготовку на этой машине
(`harness gates`, ниже, или стадии `report`), возьмите предел gate с
запасом в 1.5–2 раза, затем `runTimeoutMs` — не меньше суммы фазы с запасом
25 % (так считает `init`: наибольшая сумма фазы × 1.25, вверх до 5 минут).
`timeoutMs` gate — защита от зависания, а не бюджет производительности:
бюджеты производительности проверяет сама проверка.

**`gateTimeoutFloorMs`** поднимает короткие пределы всех gates разом
(действующий предел — `max(timeoutMs, gateTimeoutFloorMs)`), не меняя
объявленные. Это для машины под нагрузкой, где проверка, обычно идущая
30 секунд, иногда идёт три минуты. Граница входит в сумму фазы.

**Предупреждения о сроке фаз.** `harness doctor --policy …` (и `--state`)
пишет в `warnings` фазу, где сумма пределов шагов больше `runTimeoutMs`, со
слагаемыми в минутах и самой длинной цепочкой `dependsOn`: если цепочка
укладывается, можно сузить области задач вместо подъёма срока. `problems` и
exit code предупреждение не меняет. `init` записывает `runTimeoutMs` в новую
политику сам, когда умолчания не хватает; уже записанная политика не
переписывается — срок поднимают вручную или `harness lean` (ниже). В
библиотеке те же числа — `timeBudgetWarnings`, `phaseBudgets`,
`requiredRunTimeoutMs`, `longestGateChain`.

## Меньше работы на попытку

### Условные gates: `when.paths`

`repositories[].gates[].when.paths` (1–64 шаблона от корня репозитория,
умолчания нет — без поля gate исполняется всегда) делает gate задачи
условным: в каждой фазе runner сравнивает настоящий diff Git от последнего
зелёного SHA этого gate с шаблонами и при непересечении пишет evidence
`not-applicable` вместо исполнения. Так дорогой e2e не запускается на
правке документации. Gate всё равно исполняется, если его называет
требование или договор проверки, зелёного SHA нет, diff неполон или
задевает неявный вход (манифесты, lockfiles, `.harness/`, защищённые
пути). У репозитория должен остаться хотя бы один test gate без `when.paths`.
Правила шаблонов — [contracts](contracts.md#executionpolicy).

### Применимость по умолчанию: gate пакета workspace

С 0.1.0-alpha.71 gate без `when`, привязанный к пакету pnpm/npm/yarn
workspace, условен и без `when.paths`: условие — каталог его пакета,
каталоги пакетов, от которых тот зависит в workspace (транзитивно), и пути,
которые они читают вне себя. Так сборка и проверки фронтенда не исполняются
заново в задаче, которая правит только backend. Включено в облегчённом
режиме; в строгом — только явным `"derivedApplicability": "on"`, выключить
везде — `"off"`. Привязка читается из определения gate:

| Определение gate                                               | Пакет                      |
| -------------------------------------------------------------- | -------------------------- |
| `pnpm --filter @app/web run build` (`-F`, `web...`)            | `@app/web`                 |
| `pnpm --filter ./apps` или `{./apps}`                          | все проекты под `apps`     |
| `pnpm -C apps/web …`                                           | пакет каталога `apps/web`  |
| `npm --workspace @app/api test` (`-w`)                         | `@app/api`                 |
| `yarn workspace api build`                                     | `api`                      |
| pnpm/npm/yarn с `cwd: apps/web`                                | пакет, в котором лежит cwd |
| корень, `pnpm -r`, `-w`, `--workspaces`, `...x`, `*`           | нет — исполняется всегда   |
| не менеджер пакетов (`node`, `sh -c`, `make`, `turbo`, `nx`)   | нет — исполняется всегда   |
| аргумент с `..` (`-C ../..`, `--root ..`), `exec turbo/sh/npx` | нет — исполняется всегда   |

Граф берётся из объектов Git на SHA фазы (`pnpm-workspace.yaml` или
`workspaces` корневого `package.json`). В замыкание входят и пути, которые
пакеты читают вне себя: каталоги зависимостей `file:`/`link:` и цели
`extends`, `references` и `compilerOptions.paths` всех `tsconfig*.json` в
дереве пакета (кроме `node_modules`), с цепочками `extends` до конца — через
каталоги и пакеты workspace (`extends` по имени пакета workspace — этот пакет
с его зависимостями; пакет registry закрепляет lockfile). Gate исполняется,
как прежде, если привязки нет, граф не прочитан, пакет не найден, такая
цель лежит вне репозитория, не найдена в дереве или tsconfig не разобран, script пакета замыкания
выходит за свой каталог или берёт весь workspace (`..`, `cd ..`,
`--root ..`, `-w`, `-r`, `--workspaces`, вызов другого пакета через
`--filter`), исполняется любая его предпосылка (`dependsOn` или более ранний
check gate: её вывод — его вход), а также если diff от последнего зелёного
SHA задел путь замыкания, неявный вход (любой `package.json`, lockfile,
`pnpm-workspace.yaml`, `.harness/`, защищённые пути, пути из команды) или
файл корня репозитория, кроме `*.md`. Запись `not-applicable` называет
пути, которые diff не задел.

Перекрыть: явный `when.paths` — свои пути вместо пакетов; `"when": {
"always": true }` — gate исполняется всегда. Нужно `always` или явные пути
gate, который читает файлы вне своего пакета другим способом — например,
относительным импортом исходника `../../shared` или конфигом тестов с
`../fixtures`: этого граф не видит (остаточный риск; его закрывает полный
прогон gates выпуска, ниже). Применимость по умолчанию не действует у
генеративного gate и у test gate, если в репозитории не останется test
gate, исполняемого всегда.

**Получатель результата** (`resultProblems`) засчитывает запись
применимости по умолчанию только по своей сверке Git
(`derivedRecordChecks` → `ReceiverContext.derivedChecks`: граф, замыкание и
diff записи пересчитаны; последняя пара кончается на SHA записи, у всех пар
один зелёный SHA, он — предок базы и, если получатель его знает, тот самый
зелёный SHA gate) или при явном `"trustDerivedRecords": true` своей
политики.

**Полный прогон gates выпуска.** Применимость по умолчанию и перенос на
интеграцию ускоряют попытки, а приёмка выпуска опирается на полный
`harness gates` на принятой цели: все gates репозитория, без
неприменимости и переноса. Засчитывается только прогон, записанный в
состоянии тем путём, который его исполнил (`harness gates` или
`review-release`): digest файла итога и основание каждого gate (определение,
ресурсы, предпосылки, окружение, lifecycle, `prepare`, хранилище
зависимостей, toolchain, изоляция, версия harness). Файл итога без записи,
подменённый файл или сменившееся основание — прогона нет.
`harness review-release` без годного прогона на цели исполняет его сам и
при провале отказывает до ревью (`NOT_READY`). `harness release done`
отказывает (`NOT_READY`) при любом правиле ревью выпуска, если у
репозитория с принятыми работами нет годного прогона на цели или цель не
читается (неверный `targetRef` или путь checkout).

**Заметка `GATE_ALWAYS_RUNS`.** `harness doctor` пишет в `notes` (не в
`problems`, exit code не меняется) по репозиторию строку `GATE_ALWAYS_RUNS
<репозиторий> (<gates>): исполняется в каждой попытке — добавьте when.paths
… или when.always` для каждого gate без `when`, не генеративного и без
привязки к пакету (`packageBinding`): такой gate исполняется в каждой
попытке, а его `dependsOn` — вместе с ним. Обычно это приёмочный или e2e
gate корня: дайте ему `when.paths` (приложения, которые он проверяет, их
зависимости в workspace и общая поддержка тестов) и `dependsOn` только на
сборки, которые он использует; gate, который действительно нужен всегда, —
`"when": { "always": true }`. Пример — skill `harness-setup`, шаг 6.

### Сначала gate, на котором упала прежняя попытка

С 0.1.0-alpha.71 следующая попытка того же поручения исполняет gate, на
котором упала прежняя, первым — после замыкания его предпосылок
(`dependsOn`, в режиме порядка массива — более ранние check gates); остальные
— в прежнем порядке. Повторный провал виден за время самого gate, а не после
всех сборок перед ним. Настройки нет.

### Предпосылки: `dependsOn` и режим графа

`repositories[].gates[].dependsOn` (умолчания нет) задаёт предпосылки gate.
Без поля у всех gates репозитория — режим порядка массива: каждый более
ранний check gate — предпосылка следующих (установка, сборка, статические
проверки), а `when` у check gate перед безусловным test gate не действует.
С полем у gate (в том числе пустым `[]`) — режим графа: предпосылки — только
названные, транзитивно. Режим графа нужен, когда gates независимы: задача,
которой нужен один test gate, не платит за все check gates перед ним, а
`harness gates --gate <id>` исполняет только этот gate и его предпосылки.
Самая длинная цепочка `dependsOn` видна в предупреждении о сроке фаз.

### Разделяемые ресурсы: `resources`

`resources[]` (умолчание `[]`) объявляет устройства, порты, учётные записи
и службы (`kind`: `device`, `port`, `account`, `service`), а
`repositories[].gates[].resources` — какие из них держит gate. Ресурс
исключителен для всех контуров машины, поэтому две попытки не делят один
симулятор или порт и не роняют друг друга. Перед каждой фазой controller
пробует привязать каждый `port`: порт, занятый процессом, пережившим прежнюю
попытку и записанным ею (таблица `survivors`), освобождается; занятый любым другим процессом, в том числе пережившим, но не записанным, — отказ `environment`
(`resource-busy`), попытка не засчитана. Порт внешней службы, которую
попытка не поднимает (заранее запущенная база), объявляйте как `service`.
`harness doctor --policy …` пробует порты до первого запуска
(`ports[]`). Подробности — [contracts](contracts.md#ресурсы-port).

### Цена lifecycle и prepare

`lifecycle` (`setup`, `ready`, `teardown`; у политики и у репозитория) и
`repositories[].prepare[]` (умолчание `[]`) исполняются **в каждой фазе**:
на кандидате, на интеграции, у проверки потребителя и в `harness gates`.
Шаг на 5 минут в `prepare` стоит не меньше 10 минут на каждую попытку и
ещё 10 на каждый повтор. Что помогает:

- держать в `prepare` только то, без чего gates не идут; сборку, нужную
  одному gate, переносить в сам gate или в check gate с `when.paths`;
- зависимости pnpm — через `repositories[].dependencyStore`
  ([хранилище зависимостей](toolchains.md#хранилище-зависимостей)): seed
  собирается один раз на lockfile, а каждое дерево получает копию вместо
  установки;
- службы (база, эмулятор) поднимать в lifecycle `setup` с проверкой
  готовности в `ready`, а не внутри каждого gate.

### Перенос evidence на интеграцию: `integrationReuse`

`integrationReuse: "identical-tree"`; с 0.1.0-alpha.71 без поля — то же в
облегчённом режиме (если хост поддерживает перенос; standalone — да).
`"off"` и строгий режим без поля — каждый gate и ревью исполняются на
интеграции. Если дерево integration-коммита равно дереву кандидата (target
не сдвинулся), а политика, версия движка и снимок провайдеров те же, gates,
прошедшие на кандидате, на интеграции не исполняются: пишется PASS со
ссылкой на запись кандидата, а при полном переносе окружение интеграции не
поднимается. Ревью интеграции того же дерева тоже не вызывается: PASS ревью
кандидата переносится записью со ссылкой на него. Доказательства
(требования, свойства, договоры) и gates с `artifacts` исполняются всегда.
Если target сдвинулся и деревья различаются — gates и ревью интеграции
полностью, как прежде. Явное поле меняет `executionDigest`: согласования
графов нужно повторить. Правила доверия —
[contracts](contracts.md#перенос-evidence-кандидата-на-интеграцию).

## Слабая машина: слой `lean`

На машине с малым запасом процессора и памяти две одновременные попытки
делят ядра, и gates упираются в пределы. Слой `lean` задаёт
`concurrency: 1`, `gateTimeoutFloorMs: 240000`, `runTimeoutMs` не меньше
1800000 (и не меньше требуемого пределами шагов) и `dependencyStore` для
pnpm-профиля. Новый проект — `init --lean`; подготовленный — `harness lean`:

```sh
harness lean --repository <repo> --plan   # что изменится, без записи
harness lean --repository <repo>          # включить
harness lean --repository <repo> --off    # вернуть прежние значения точно
```

`doctor` советует слой предупреждением `LOW_RESOURCES`. Подробности —
[standalone](standalone.md#слабая-машина).

## Проверка до долгого цикла: `harness gates --fail-fast`

Прежде чем запускать долгий цикл попыток, прогоните решающие gates на
текущем коммите:

```sh
harness gates --state <state> --policy .harness/policy.json \
  --sha HEAD --gate lint,unit --fail-fast --human
```

Команда исполняет названные gates и их предпосылки тем же исполнением, что
интеграция (рабочее дерево, ресурсы, lifecycle, `prepare`, песочница), но вне
попытки: ни попыток, ни бюджетов она не тратит. С `--fail-fast` первый
провал останавливает остальные (`skipped`). Красная база — отдельная первая
задача, а не повод для долгого цикла, в котором каждая попытка упадёт на
том же gate. Длительность всей проверки — `data.durationMs`, логи gates —
`data.logs`: это замер для выбора пределов выше (проверка ограничена тем же
`runTimeoutMs`).

## Окружение без gates и моделей: `harness smoke`

Ошибку в lifecycle, `prepare` или seed хранилища зависимостей дешевле найти
без попыток: каждая попытка с моделью платит за реализацию, а затем падает на
той же подготовке. `harness smoke` поднимает только окружение репозитория на
коммите — тем же исполнением, что фаза integration (рабочее дерево, снимки
зависимостей, ресурсы, lifecycle `setup`/`ready`, хранилище зависимостей,
`prepare`, `teardown`), без gates и без вызовов моделей:

```sh
harness smoke --state <state> --policy .harness/policy.json --sha HEAD --human
```

Каждый шаг — строка с длительностью и кодом выхода (`data.steps[]`), лог —
в `<state>/gates-at/<id>`. Хранилище зависимостей, которое не использовано
(промах, отказ или истёкший бюджет сборки seed), — не отказ окружения и не
«пройдено»: в JSON шаг `dependency-store` остаётся `status: passed` с
`unused: true` и причиной в `detail` (`miss: …`), а таблица `--human` и ход в
stderr показывают `miss` с настоящим временем и «не используется: причина». Отказ — exit 4 (`LIFECYCLE_FAILED`) и
`data.failure` с классом и советом:

| Класс          | Что случилось                                                                             |
| -------------- | ----------------------------------------------------------------------------------------- |
| `port-busy`    | порт ресурса занят до окружения (старый dev-сервер, служба прежней попытки)               |
| `timeout`      | шаг дольше своего `timeoutMs`, проверка дольше `runTimeoutMs` или замолкла (`stallSweep`) |
| `crash`        | шаг завершился ненулевым кодом (кроме установки, упавшей на сети или реестре)             |
| `missing-tool` | исполняемого файла шага нет или он не запускается (`ENOENT`, `EACCES`, код 126/127)       |
| `cleanup`      | упал только `teardown`: службы могли остаться запущенными                                 |
| `tree-changed` | подготовка изменила отслеживаемые файлы коммита                                           |
| `environment`  | прочее: переменная или секрет окружения не заданы, сеть реестра, защищённые пути, git     |

Установка зависимостей, чей вывод — сетевой отказ реестра по правилу `dependency-network` (код менеджера, обрыв «terminated» или `TimeoutError` прерванного по пределу запроса), — класс `environment`, а не `crash`; сообщение начинается с `dependency-network:`.

`teardown` исполняется и после отказа. Попыток, evidence и состояния
поручений команда не пишет.

### Проверка окружения перед запуском: `lifecyclePreflight`

`lifecyclePreflight: "cached"` (умолчания нет — без поля проверки нет)
включает ту же проверку перед `harness run`: до ревью плана и первой попытки
controller поднимает окружение каждого репозитория с незавершёнными
поручениями (всех графов очереди) на его `targetRef`; целевая ветка, если
её ещё нет, создаётся до проверки. Успех записывается в `<state>/preflight/`
по ключу из дерева базы (`targetRef^{tree}`), деревьев её зависимостей
(`dependsOn`, транзитивно), `executionDigest` политики, `stallSweep`, digest
окружения процесса (переменные и секреты политики, `PATH`, `HOME`; значения
не сохраняются) и версии harness; при том же ключе окружение больше не
поднимается. Не заданная переменная или секрет политики — отказ до кэша. Отказ
записывается для разбора, но не переиспользуется: порт, сеть и службы —
состояние машины, а не дерева, и следующий запуск проверяет снова. Отказ
останавливает `run` с `LIFECYCLE_FAILED` (exit 4) — класс, шаг, совет и
команда `harness smoke` для повтора без запуска — до любого платного
вызова. Поле не входит в `executionDigest`: включение не требует нового
согласования графа.

### Проба исполнителя: `--writer-probe`

`repositories[].writerProbe` — команды, которые правила проекта требуют от
исполнителя (генератор из реестра, локальный сервер, браузерный инструмент).
`harness smoke --sha HEAD --writer-probe --human` после `prepare` прогоняет их
в изоляции каждого исполнителя репозитория без вызова модели и
называет по каждой `ok`, `blocked` или `failed` с причиной (`listen-denied`,
`network-denied`, `write-denied`, `process-abort`, `missing-tool`, `timeout`,
`no-shell`, `environment`) и советом. Причину называет последняя значимая строка вывода: предупреждения (`[WARN]`,
`npm warn`, `Warning` Node) и безвредное чтение `~/.npmrc` pnpm под песочницей
не считаются. Браузер, умерший при старте («Daemon process exited during
startup»), — `process-abort`; EPERM без пути (сборщик на Rust,
`Operation not permitted (os error 1)`) — `write-denied` с советом, что это
может быть и локальный сокет (при `network: none` — повторить с `loopback`),
а рядом со строкой «binding to a port» (Turbopack) — `listen-denied`, если
в выводе нет отказа записи с явным путём (с ним — `write-denied`);
упавшая сама команда (`failed`) приводит последнюю строку ошибки. Закрытый шаг решается до первой платной
попытки: разрешить в политике, выполнить в `prepare`, вынести в gate или
отменить правило шаблона для режима harness. Локальному серверу исполнителя
(`listen-denied`) хватает `network: loopback` в профиле инструментов: listen
и connect на 127.0.0.1 и ::1 без интернета ([contracts](contracts.md#executionpolicy));
режим сети проба печатает у каждого исполнителя. Команды пробы не должны менять
отслеживаемые файлы: проверка дерева после smoke это заметит.

**Сеть loopback — умолчание, а не развилка.** Шаг, закрытый только локальным
портом (`listen-denied` или EPERM без пути), у исполнителя, чья сеть закрыта и
для него (codex без поля `network` или с `none`, claude с `none`), проба сама
повторяет под `network: loopback` в той же изоляции, но в свежем рабочем
дереве и со свежим TMPDIR, подготовленными как для первого прохода (кеш
сборщика, оставленный закрытым проходом, повторял бы его отказ); у codex
сначала — поддержка `network_proxy` и проверка границы
`harness-loopback-check`. Итог —
`writers[].loopback`: `resolves` (закрытые шаги проходят, прежде проходившие не
сломались), `not-enough` или `unavailable`, причина простыми словами и
`decision: "lead"`. При `resolves` проба печатает одну команду
`loopbackCommand`: `harness smoke … --writer-probe --apply-loopback` записывает
`network: "loopback"` в профиль исполнителя (нет профиля — новый
`writer-loopback` у его ролей), кладёт запись с причиной в
`writerProbe.loopbackApplied` и `loopback-receipt.json` каталога пробы и
повторяет пробу под новой политикой — тоже в свежем дереве. Итог свежего
прохода считается, только когда проход завершился целиком (teardown и
проверка дерева): иначе повтор — `unavailable` с причиной, а проба под
записанной политикой — отказ smoke. `--human`
печатает исход каждого шага повтора (`повтор <шаг>: …`). Больше ничего не меняется: интернет,
домены, области записи, `isolation.mode` и сеть ревьюера прежние. Сеть профиля
входит в `isolationDigest`, поэтому согласованные графы нужно согласовать
заново (`review-plan`). Это техническое решение ведущего, не вопрос владельцу.

**Проверки в браузере — вне исполнителя.** Шаг, в выводе которого браузер не
запустился под песочницей (агент-браузер «Daemon process exited during
startup», «Failed to launch the browser process», `browserType.launch`, Chrome
или Chromium, в том числе с `Abort trap`), — статус `outside`: ожидаемо, проба
остаётся зелёной (exit 0), если остальное доступно. Имя шага и его аргументы
этого не доказывают: `browser-bundle` или `pnpm add -D @playwright/test` с
отказом записи или сети остаются `blocked`. `doctor` с политикой, не исполняя
команд, называет в `notes` (`browser-checks …`), не в `problems`, шаги с
инструментом запуска браузера в argv (`agent-browser`, `playwright test`,
`cypress run`, скрипт `verify:browser`). Такую проверку запускайте gate harness
только если она проходит на HEAD под harness.

## Исследование: тёплый стенд между попытками

_Это исследовательская заметка, а не обязательство: в harness такого режима
нет, и решение о нём не принято._

**Идея.** Сейчас каждая фаза поднимает окружение с нуля: новое рабочее
дерево, `prepare`, lifecycle `setup`/`ready`, после фазы — `teardown`.
Тёплый стенд — переиспользовать между попытками одного репозитория уже
поднятое окружение: установленные зависимости, собранные артефакты,
запущенные службы (база с миграциями, эмулятор, dev-сервер).

**Выигрыш.** На проекте, где подготовка занимает большую часть фазы,
выигрыш близок к цене `candidate-environment` и `integration-environment`
из отчёта, умноженной на число фаз и повторов. На проекте с дешёвой
подготовкой и дорогими тестами выигрыша почти нет: тесты исполняются всё
равно. Измерять до решения — по таблице стадий `report`.

**Риски изоляции.**

- **Остаток прежней попытки.** Данные в базе, файлы кэша, сгенерированные
  артефакты, запущенные процессы прежней попытки видны следующей: gate может
  пройти благодаря состоянию, которого нет в коммите, и evidence перестаёт
  доказывать свойство кода.
- **Утечка между поручениями.** Стенд, общий для разных поручений, переносит
  данные и секреты одного поручения в попытку другого, в том числе в ввод
  модели исполнителя.
- **Расхождение с чистым окружением интеграции.** Кандидат, проверенный на
  тёплом стенде, а интеграция — на чистом, дают разные основания; если же и
  интеграция идёт на тёплом стенде, PASS интеграции больше не проверка
  «с нуля», на которую опирается приёмка.
- **Пережившие процессы и порты.** Службы стенда держат порты и файлы между
  фазами: проба портов и `teardown` перестают означать «среда пуста».

**Какие проверки понадобились бы, чтобы evidence оставалась
доказательством.**

- Снимок состояния стенда (digest данных базы, списка процессов, дерева
  кэша) до и после каждой фазы в `gateBasis`: стенд с другим снимком — не
  тот же вход, gate исполняется на чистом.
- Сброс к эталону перед фазой (пересоздание базы из миграций, очистка
  неотслеживаемых файлов) с проверкой результата, а не доверие к сбросу.
- Интеграция — всегда на чистом окружении (или периодическая сверка: тот же
  gate на чистом и тёплом стенде с одинаковым исходом), чтобы приёмка не
  зависела от стенда.
- Стенд — на одно поручение, не на репозиторий: без общих данных разных
  поручений.
- Тест на попытку, оставившую в стенде данные, которые делают gate зелёным:
  следующая попытка без этих данных в коммите обязана упасть.

Ближайшее к этому, что уже есть, — `dependencyStore` (зависимости без
состояния служб) и `integrationReuse` (перенос PASS при равных деревьях, без
общего стенда).
