# Приёмка выпуска

С 0.1.0-alpha.69 перед `harness release done` независимый reviewer
проверяет принятую цель выпуска целиком против договора выпуска. Ревью
каждой попытки смотрит одно изменение; приёмка выпуска смотрит, работает ли
всё вместе там, где будет работать: маршрутизация production, файлы
окружения, ответы владельца.

## Зачем

Ошибка маршрута — медиа по адресу порта API, а не шлюза production —
проходит все тесты, если gates ходят прямо в порт API, и все ревью
попыток, которые топологию развёртывания не видят. После развёртывания
такой выпуск отдаёт 404. Приёмка выпуска сверяет код с топологией, а gates
через шлюз ([light-mode.md](light-mode.md#gates-через-шлюз-как-в-production))
проверяют её на деле.

## Команда

```sh
harness review-release --state D [--base REF] [--head REF] [--repository ID] [--role R]
```

- `--head` — по умолчанию `targetRef` репозитория (принятая цель).
- `--base` — начало выпуска; по умолчанию база самой ранней попытки
  репозитория в состоянии. Попыток нет — назовите `--base`.
- Reviewer — по правилу ревью кода роли: другой вендор, если он есть,
  иначе запасной reviewer правила (`same-vendor-allowed`).

Договор выпуска в запросе reviewer:

1. постановка: название, цель и критерии приёмки каждой неотменённой
   работы всех графов;
2. ответы владельца: вопросы исполнителей и ответы на них;
3. топология развёртывания: содержимое каждого файла `release.topology`
   на head (нет файла — так и сказано); без `release.topology` reviewer
   ищет конфигурации шлюза и файлы окружения сам;
4. diff `base..head`.

Reviewer обязан сверить, что маршрутизация и окружение production
совпадают с тем, что проверяли тесты; расхождение — блокирующая находка.

```json
"release": {
  "review": "required",
  "topology": ["deploy/Caddyfile", "deploy/production.env.example", "compose.prod.yml"]
}
```

## Раунды и `release done`

Раунд записывается как ревью `kind: release` (рядом с `review-code`, id
`RR-…`). Новый head — новый раунд; открытые находки переносятся с
переходами closed/open/withdrawn. Тот же head и тот же договор — прежний
одобренный раунд без нового вызова; новый ответ владельца — новый раунд.

Требование: `release.review`, иначе `required` в облегчённом режиме и
`advisory` в строгом.

- `required` — `release done` отказывает (`NOT_READY`), пока у каждого
  репозитория с принятыми работами последний раунд приёмки не на текущей
  цели, не одобрен или держит открытые блокирующие находки. Находки
  исправляются обычными работами: новая принятая цель — новый раунд.
- `advisory` — `release done` проходит, ответ несёт предупреждение.

Неблокирующие находки одобренного раунда выпуск не держат: они в ответе
`release done` (`releaseReview.notes`).

Представление (ревизия 9): `forecast.progress.release.review` —
требование, состояние (`not-run`, `stale`, `findings`, `approved`), раунд,
открытые и блокирующие находки и строка; раунды — в `reviews[]` с
`kind: release`.
