# Toolchains целевого проекта

Harness — Node.js-инструмент. Исполняемому проекту не нужны package.json, npm или
JavaScript: gates и шаги подготовки — произвольные argv, каталог gate — `cwd`, окружение —
`environment`. npm и pnpm — менеджеры пакетов, Turborepo — планировщик задач, Go и
Python/uv — отдельные toolchain. Единого «типа проекта» нет: репозиторий описывается
композицией шагов.

| Что                                                             | Где в политике                                                                                                           |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Установка зависимостей (locked)                                 | `repositories[].prepare[]` — исполняется в каждом worktree попытки до writer, отдельно для candidate и integration       |
| Команды задач и проверки                                        | `repositories[].gates[]` (`check` / `test` с JUnit)                                                                      |
| Каталог                                                         | `gates[].cwd`; у шага `prepare` — собственный флаг инструмента (`pnpm --dir`, `npm --prefix`, `uv --directory`, `go -C`) |
| Окружение                                                       | `environment` политики/репозитория (`values`, `inherit`, `secrets`)                                                      |
| Проверенные версии инструментов и явный выбор менеджера пакетов | `repositories[].toolchain` (`tools`, `packageManagers`), необязательно                                                   |
| Общие пакеты между worktree без скачивания                      | `repositories[].dependencyStore`, необязательно ([хранилище зависимостей](#хранилище-зависимостей))                      |

`toolchain` — необязательное аддитивное поле: политики и профили без него сохраняют прежний
digest. `tools` — `{ "gotestsum": "1.12.3" }` (названные компоненты версии совпадают) или
`{ "go": ">=1.24" }` (не ниже). `packageManagers` — `{ ".": "pnpm", "frontend": "pnpm" }`:
явный выбор снимает неоднозначность, когда в каталоге лежат lockfiles нескольких менеджеров.

## Рецепты

Проверенный набор (macOS arm64, Darwin 24.6): Node 24.3.0, npm 11.4.2, pnpm 10.12.3,
Turbo 2.11.10 (devDependency fixture), Go 1.24.5, gotestsum v1.12.3, uv 0.11.28,
CPython 3.12.9 (выбран uv по `.python-version`), pytest 8.4.1, ruff 0.12.4.

| Вариант                        | prepare                                                                                 | gates                                                                                         | Встроенный профиль                                             |
| ------------------------------ | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Node + npm                     | `npm ci`                                                                                | `npm run check`, `npm run test` (JUnit `.reports/junit.xml`)                                  | `npm-ci@0.1.0`                                                 |
| Node + pnpm                    | `pnpm install --frozen-lockfile`                                                        | `pnpm run check`, `pnpm run test`                                                             | `pnpm-frozen@0.1.0`                                            |
| pnpm + Turborepo               | `pnpm install --frozen-lockfile`                                                        | `pnpm exec turbo run check --filter=<pkg>`, `pnpm exec turbo run test --filter=<pkg> --force` | — (фильтры проекта: политика, см. `examples/toolchains/turbo`) |
| Go                             | `go mod download`                                                                       | `go vet ./...`, `gotestsum --junitfile .reports/junit.xml -- -count=1 ./...`                  | `go-gotestsum@0.1.0`                                           |
| Python                         | `uv sync --locked`                                                                      | `uv run --no-sync ruff check .`, `uv run --no-sync pytest --junitxml=.reports/junit.xml`      | `python-uv@0.1.0`                                              |
| pnpm frontend + Go backend     | `pnpm --dir frontend install --frozen-lockfile`, `go -C backend mod download`           | gates с `cwd: frontend` / `cwd: backend`                                                      | — (`examples/toolchains/mixed-go`)                             |
| pnpm frontend + Python backend | `pnpm --dir frontend install --frozen-lockfile`, `uv sync --locked --directory backend` | gates с `cwd: frontend` / `cwd: backend`                                                      | — (`examples/toolchains/mixed-python`)                         |

Правила рецептов:

- Только locked-установка: `npm ci`, `pnpm install --frozen-lockfile`, `uv sync --locked`,
  `go mod download`. Несовместимый lockfile — отказ шага с диагностикой менеджера, lockfile
  не переписывается. `npm install`, `pnpm install` без `--frozen-lockfile`, `uv sync` без
  `--locked`, `uv run` без `--no-sync`, `go get`, `go mod tidy` — проблема preflight.
- Точные версии, без `@latest`, `npx`, `pnpm dlx` без версии, `uvx` без версии, `--if-present`.
  Отсутствующий test task не заменяется build/lint.
- Отчёт gate лежит относительно корня worktree, а не `cwd`: gate `cwd: backend` пишет JUnit в
  `../.reports/backend.xml`, gate объявляет `.reports/backend.xml`. Harness удаляет файл
  отчёта до запуска и передаёт путь в `HARNESS_REPORT_PATH`.
- Один monorepo — одна запись Git repository с разными `cwd`. `consumers` — только для
  действительно отдельных репозиториев.
- Профили языков (`go-gotestsum`, `python-uv`, прежние `go-api`, `python-api`) не наследуют
  npm-подготовку. Слои профиля с разными версиями одного инструмента или разными менеджерами
  одного каталога — отказ разрешения (`Конфликт частей профиля: toolchain.…`).
- Композиция из кода: `composeRepository(own, components, tools)` и `installRecipes` из
  opt-in entrypoint `devcontour-harness/toolchains`.

## Установка harness для Go/Python-проекта

Target-проекту package.json не нужен. Harness ставится в отдельное окружение инструмента.

npm:

```sh
mkdir -p ~/.local/share/harness-tool && cd ~/.local/share/harness-tool
npm init -y >/dev/null
npm install --save-exact devcontour-harness@<версия>
export PATH="$PWD/node_modules/.bin:$PATH"
harness doctor --policy /path/to/project-harness/policy.json
```

pnpm:

```sh
mkdir -p ~/.local/share/harness-tool && cd ~/.local/share/harness-tool
pnpm init >/dev/null
pnpm add --save-exact devcontour-harness@<версия>
export PATH="$PWD/node_modules/.bin:$PATH"
```

Политика и граф могут лежать вне target-репозитория: `repositories[].path` относителен
каталогу политики (`examples/toolchains/go/policy.json` → `"path": "repo"`).

## Cache и изменяемые каталоги

Каждая попытка исполняется в своём worktree (`<state>/repos/<repo>/worktrees/<attempt>` и
`…-integration`; если каталог состояния лежит внутри репозитория — под корнем вне дерева
`<checkoutRoot>/<repo>/worktrees/<attempt>`), и `prepare` устанавливает зависимости заново в нём. Изменяемые артефакты
одной попытки другой не видны.

| Допустимый общий cache (content-addressed, вне worktree)                                               | Изменяемое, только внутри worktree попытки                       |
| ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| npm cache (`~/.npm`), pnpm store, Go module cache (`GOMODCACHE`), Go build cache (`GOCACHE`), uv cache | `node_modules/`, `.venv/`, `.reports/`, `.turbo/`, выходы сборки |

Cache сборки допустим, но не заменяет тест:

- Во время исполнения каждый gate `kind: test` получает `TURBO_FORCE=true` и `GOFLAGS`,
  оканчивающийся на `-count=1` (после значения политики). Окружение наследуют все потомки, так
  что защита действует при любой обёртке (package script, `pnpm --filter … run`, task runner),
  в библиотечном `Harness.run`/`Runner` и в CLI одинаково. Заголовок лога gate записывает
  применённые значения (`fresh={...}`); digest лога входит в evidence. `check` gates cache
  используют как обычно.
- Turbo: preflight дополнительно требует явной свежести в самой команде — `--force`,
  `--cache=` без чтения или `TURBO_FORCE=true` — и находит turbo внутри package scripts
  (напрямую, через `pnpm run`/`npm run`, `pnpm --filter … run`, `pnpm exec`, `npx`). Без неё —
  `CACHE_REPLAY`. Script turbo-проекта, который не разбирается статически (`$(…)`, обратные
  кавычки, конвейер, `sh -c`, `eval`, `xargs`), — `SCRIPT_UNRESOLVED`: угадывать нельзя.
  Проверено T03: при входах задачи без `src` неверная реализация вне harness даёт «cache hit,
  replaying» и зелёный отчёт; тот же script через gate — «cache bypass, force executing» и
  отказ, в том числе через общий `TURBO_CACHE_DIR` и `Harness.run` без CLI.
- Go: команда без `-count=1` в test gate — предупреждение (`warnings`): прежний `go-api`
  продолжает проходить preflight, а свежесть обеспечивает `GOFLAGS` во время gate.

Isolation `os` пишет только в worktree и временный каталог проверки: для Go/uv/pnpm в
песочнице cache-каталоги (`GOCACHE`, `UV_CACHE_DIR`, store) нужно указать доступными или
использовать `isolation.mode: none`, как в примерах. Установка (`prepare`) идёт вне песочницы.

## Хранилище зависимостей

Свежий worktree в песочнице не видит общий store менеджера и скачивает все пакеты заново.
Настройка одной строкой в политике снимает это для pnpm без скрипта в проекте:

```json
{ "id": "app", "dependencyStore": { "manager": "pnpm" } }
```

Необязательные поля: `lockfile` (`pnpm-lock.yaml`), `maxBytes` (8 ГиБ), `timeoutMs` (600 000).
`timeoutMs` — верхний предел, общий для сборки и ожидания чужой сборки; действует ещё и треть
остатка времени фазы: при `runTimeoutMs` 900 000 это 300 000 мс. Проект, чьей сборке этого мало,
поднимает `runTimeoutMs`, иначе получает `miss`. Если остаётся меньше 30 000 мс или меньше трёх четвертей полного бюджета, когда он сам мал, сборка не начинается.
Seed собирается в песочнице проверок, и с alpha.61 её сеть к реестру открывает сам harness —
только для этой сборки: к `isolation.domains` добавляются хост реестра из окружения политики
(`npm_config_registry`/`pnpm_config_registry`; пока реестр по умолчанию не задан под обоими
префиксами — ещё и `registry.npmjs.org`: pnpm 10 читает `npm_config_*`, pnpm 11 — `pnpm_config_*`) и хосты `tarball:`
lockfile (git- и tarball-зависимости). Writers и gates этих доменов не получают: сборка исполняет
только `pnpm fetch --ignore-scripts` над принятым lockfile, поэтому домен в политике не нужен и
не открывает реестр остальным. Без этого `pnpm fetch` в закрытой сети повторял запросы до конца
бюджета (600 с). Другой реестр задаётся через `environment` как `npm_config_registry` и
`pnpm_config_registry`; `.npmrc` проекта в сборку не попадает, поэтому реестр, настроенный только
там (или под одним префиксом), даёт `miss` — `doctor`, `init` и `lean` предупреждают об этом
`DEPENDENCY_STORE_REGISTRY`, сравнивая адрес реестра целиком (хост, порт и путь)
(реестр области `@scope:registry` окружение политики задать не может).

Проверенные версии pnpm: от 9.15.0, ниже 12.0.0. Настоящими прогонами проверены 9.15.0, 10.12.3,
10.13.1, 10.26.0, 10.34.9, 11.0.0, 11.25.0 и 11.28.13. Различия версий учтены в хранилище: с 10.27.0
`pnpm fetch` кладёт в store символическую ссылку `v10/projects/<hash>` (у pnpm 11 — `v11/projects`),
которую seed не переносит; pnpm 11 читает настройки только из `pnpm_config_*`, поэтому окружение
checkout и сборки задаёт и `npm_config_store_dir`, и `pnpm_config_store_dir` (то же для
`userconfig`, `cache_dir`, `state_dir` сборки); store pnpm 11 — каталог `v11` с базой `index.db`,
она сверяется по манифесту, как остальные файлы. Реестр для pnpm 11 задаётся как
`pnpm_config_registry` (`npm_config_registry` он не читает). Версия берётся из PATH и из поля
`packageManager`; вне диапазона, а также
когда менеджер не найден, его версия не определена или `package.json` не читается, хранилище не меняет ни окружение, ни дерево:
установка идёт как без него, причина — в квитанции, стадия `dependency-store` отмечена `unused`
(«не используется»), а `doctor`, `init` и `lean` громко предупреждают `DEPENDENCY_STORE_UNSUPPORTED`.

Свой store или кэш pnpm в командах проверок (`--store-dir`, `--cache-dir`, `config set store-dir`)
или в окружении политики (`npm_config_*`/`pnpm_config_*` `store_dir`/`cache_dir`) — предупреждение
`DEPENDENCY_CACHE_PATH`: относительный путь лежит в рабочей копии, и каждая попытка скачивает всё
заново; абсолютный — общее изменяемое состояние попыток вне границы доверия хранилища (его байты
никто не сверяет) и непереносимый путь. Исправление — `dependencyStore` через `harness lean`; для
версии вне проверенных — находка по harness, а не общий кэш в аргументах.

Как это работает:

1. Перед `prepare` каждого checkout, а у совместной проверки — перед её gates, harness читает
   lockfile из `targetRef`; пока целевой ветки нет (до первого `run`), — из `HEAD` checkout
   репозитория, от которого `run` её создаст (квитанция называет его в `ref`), поэтому
   `harness smoke` сразу после `init` уже собирает seed и попадает в него. Проверяемый SHA ключом
   не служит: это может быть кандидат. Seed этого lockfile есть — используется, нет — собирается:
   `pnpm fetch` в каталоге только с lockfile, поэтому `.npmrc`, `.pnpmfile.cjs` и
   `pnpm-workspace.yaml` проекта не участвуют и его хуки не исполняются. Новый seed начинается с
   клона предыдущего: сдвиг lockfile докачивает только разницу. Параллельные проверки ждут одну
   сборку.
2. Seed клонируется в `<checkout>/.pnpm-store` (копия-при-записи на APFS и reflink-томах, иначе
   обычная копия, если хватает места), копия сверяется с манифестом, менеджер получает путь через
   `npm_config_store_dir` и `pnpm_config_store_dir`. Каталог скрыт от git собственным `.gitignore`.
   На macOS клон делается одним `clonefile(2)` всего каталога (через `/usr/bin/osascript`;
   если вызов не удался — `cp -c` порциями), а сверка читает и хэширует файлы копии в
   нескольких потоках: seed из 37 тысяч файлов и 430 МБ на APFS разворачивается и сверяется
   примерно за 2–3 с, а не за 8–9. Потоков — ядра минус одно, не больше 8; переменная
   `HARNESS_DIGEST_THREADS` (целое 1–8) в окружении controller задаёт их число явно, например
   `1` на слабой машине; иное значение не действует.
3. Gate установки — обычный `pnpm install --frozen-lockfile`. Он берёт пакеты из копии, а чего нет,
   скачивает через прокси песочницы.

Исполнитель и проверки ревьюера переменные `npm_config_store_dir` и `pnpm_config_store_dir` не получают: их окружение строится
отдельно. Зависимости в дерево исполнителя ставит controller до его работы
([ниже](#зависимости-исполнителя)) — в окружении фазы, то есть уже с хранилищем.

| Исход                                                                                                                             | Что происходит                                                                                                                                                                                                                                  |
| --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Seed того же lockfile                                                                                                             | `hit`: скачивать нечего                                                                                                                                                                                                                         |
| Lockfile checkout другой, или сборка нового seed не удалась                                                                       | `partial`: установка докачивает разницу                                                                                                                                                                                                         |
| Seed нет, сборка не удалась, не хватает места                                                                                     | `miss`: обычная установка; очередь не останавливается, попытка не тратится                                                                                                                                                                      |
| Отказ, зависящий от самого lockfile: патчи (`patchedDependencies`, сборка видит только lockfile), пустой seed, seed сверх предела | `miss`; этот lockfile не собирается, пока не изменится                                                                                                                                                                                          |
| Истёк бюджет хранилища: реестр висит или чужая сборка идёт долго                                                                  | `miss` или старый seed; время фазы остаётся работе, отменяет фазу только отмена попытки или оператора. Пометку об отказе ставит только сборка, начатая с полным бюджетом (не меньше трёх четвертей): опоздавшая фаза другим сборку не закрывает |
| Сборка не удалась недавно                                                                                                         | 10 минут новых сборок этого lockfile нет: отказавший реестр не отнимает `timeoutMs` у каждой попытки                                                                                                                                            |
| Сборка не удалась из-за сети реестра (alpha.64)                                                                                   | Причина начинается с «сборка seed: сеть реестра npm (…), а не lockfile»; попытки `run` ждут 10 минут, а явные `harness smoke` и `harness gates` повторяют сборку сразу (раз за команду, пометке не меньше 10 с)                                 |
| Seed изменён                                                                                                                      | Отказ с причиной в `refused`, seed удаляется и собирается заново                                                                                                                                                                                |
| `isolation.mode: none` или `.pnpm-store` уже есть в дереве                                                                        | `miss`: без границы seed не используется, в занятый путь harness не пишет                                                                                                                                                                       |

### Пакеты из store хоста (alpha.64)

Проект, уже установленный на машине, не качает граф заново: перед `pnpm fetch` сборка нового
seed импортирует пакеты своего lockfile из store pnpm хоста. Путь store называет
`pnpm store path` в checkout репозитория (конфигурация проекта и пользователя, но без
`store_dir` из окружения политики); формат каталога (`v10` у pnpm 10, `v11` у pnpm 11) должен
совпасть с версией менеджера. Для каждого integrity lockfile берётся запись индекса store
(`index/…json` у pnpm 10, строка `index.db` у pnpm 11 — база хоста сначала копируется), её файлы
клонируются (`clonefile` на APFS, иначе обычная копия только нужных файлов) в сборочный store, и
байты копии сверяются с sha512 и размером из записи; не совпало или файла нет — пакет не
импортируется, его скачает `pnpm fetch`. Результаты сборочных скриптов хоста (`sideEffects`) в seed не переносятся: запись pnpm 10 копируется без них, запись pnpm 11 с ними не импортируется. Затем `pnpm fetch` докачивает остальное, и seed
сверяется и закрепляется как прежде. В квитанции `sources`: `packages` (integrity lockfile),
`host` (импортировано), `base` (было в прежнем seed), `network` (скачал pnpm, по его выводу),
`hostStore`, `hostReason` (почему импорта нет или он неполный), `retries`; строка шага
`dependency-store` в `smoke`: `hit (seed собран: из store хоста 1103 из 1246, из сети 8)`.

Store хоста только читается: gates его не видят, в него ничего не пишется. Store под каталогом
seeds, рабочих деревьев или скрытых путей (кроме самого репозитория) не используется — туда мог
писать код кандидата. Соответствие «integrity tarball → файлы» берётся из индекса хоста: ему
доверено столько же, сколько собственной установке оператора из этого store.

Сеть сборки: пока окружение политики не задаёт настройку само (под любым префиксом), сборка
получает `fetch-retries` 5, `fetch-timeout` 180 000 мс, `network-concurrency` 8,
`prefer-offline` и `minimum-release-age` 0 — pnpm 11 иначе проверяет возраст выпусков по
метаданным реестра (тысяча запросов на большом lockfile), хотя seed lockfile не принимает: правила
проекта применяет установка в checkout. Обрыв по времени (`TimeoutError`, `ETIMEDOUT`,
`ECONNRESET`) — один повтор сборки через 5 с: скачанное остаётся в store, докачивается остаток.

Граница доверия:

- Seed строится только из lockfile целевой ветки (до её создания — `HEAD` checkout, от
  которого её создаст `run`). Сам harness не даёт кандидату запустить сборку или
  выбрать её содержимое: его lockfile лишь сравнивается с seed.
- **Условие:** шаги `prepare` и `lifecycle` идут на хосте вне песочницы, а на integration — над слитым
  деревом. Шаг, исполняющий код кандидата (скрипт из репозитория), работает с правами controller и
  может изменить seed и базу закреплений. Граница seed держится только там, где эти шаги кода
  кандидата не исполняют. `doctor` предупреждает о `dependencyStore` рядом с непустым `prepare`.
- Seeds лежат под корнем рабочих деревьев или в каталоге состояния, закрытых песочницей на чтение
  и запись. Манифест закреплён digest в базе ресурсов, вне дерева seed.
- Проверяются байты копии, а не источника: те, что прочитает менеджер. Ускорение этого не
  меняет: каждый файл копии открывается с `O_NOFOLLOW`, а хэш, права и тип берутся с того же
  дескриптора, что и байты; ссылка, каталог или канал на месте файла — отказ. `O_NOFOLLOW`
  защищает только последний компонент пути: каталог по пути к файлу, подменённый ссылкой между
  обходом и чтением, не обнаруживается. Такая подмена требует процесса, который пишет в checkout
  во время развёртывания, то есть до `prepare` и gates этого checkout; это вне модели угроз,
  как и прежде (прежние `lstat` и `readFile` следовали и по последнему компоненту). Setuid, setgid и sticky у файлов seed — отказ, BSD-флаги вроде `uchg`
  копия наследует, как и при `cp -c`, а удаление копии и seed их снимает.
- Копия принадлежит своему checkout, в seed ничего не возвращается. Integration и следующая попытка
  получают новую копию. Поэтому байты seed проверены всегда, а докачанные байты и всё, что
  исполнитель изменил в своём дереве, доверены не больше, чем его `node_modules`: они не выходят
  за пределы этого дерева.

Диск: хранятся два последних по использованию seed в пределах `maxBytes`, остальное и брошенные
сборки убираются при публикации нового. Seed больше предела размера или 150 000 файлов не публикуется. Копия лежит в checkout и входит в
сверку защищённых путей (предел 200 000 элементов), поэтому checkout, который вместе с копией превысил
бы 180 000 элементов, получает `miss`, а не отказ проверки. Сборка от прежнего seed, упёршаяся в предел, повторяется с пустого: основа копит старые пакеты. При любом пределе дерево и окружение остаются как без хранилища, если только прежний seed не подошёл как частичное попадание. Отказ по `maxBytes` действует, пока предел не изменён. Копии уходят вместе с
рабочими деревьями. Seeds лежат в `<корень>/<repo>/dependency-store`, а без корня вне дерева — в
`<state>/dependency-store/<repo>`; их можно удалить, когда harness не запущен, и они соберутся заново.

`doctor` предупреждает об отсутствии менеджера и lockfile, о версии вне диапазона и о непустом
`prepare`; это предупреждения: запуск идёт, установка обычная. Эксперимент выполнимости (`spike`)
хранилища не получает: у него нет `prepare`, его команду задаёт оператор. Что в итоге произошло в конкретной фазе, показывает
`dependency-store.json` в её артефактах. Другие менеджеры добавляются записью в таблице `managers`
(`verification/dependency-store.ts`); пока поддержан только pnpm.

## Зависимости исполнителя

Песочница Claude Code закрывает запись в `**/.idea` и `**/.vscode` от рабочего каталога исполнителя
без возможности снять запрет настройками, а у codex по умолчанию нет сети: установка пакетов
самим исполнителем не проходит, и до сдачи работы он не может собрать проект и запустить тесты.
Поэтому перед исполнителем controller сам исполняет в его дереве **gates установки** попытки —
обязательные gates, чей argv однозначно установка известным менеджером (`npm ci|install`,
`pnpm install|fetch`, `yarn`; скрипты, `npx` и shell не подходят), в их порядке:

- после `prepare`, хранилища зависимостей и наложения черновика прежней попытки (манифесты, которые
  он меняет, ставятся сразу), до снимка защищённых путей исполнителя и его вызова. `dependsOn` gate
  установки не исполняется: проверки, от которых он зависит, остаются gates кандидата. Если
  установка есть ещё и в `prepare`, менеджер запустится дважды; второй раз обычно ничего не делает;
- под той же изоляцией, что и gate, при любом `isolation.mode`: в `os` — песочница проверки с
  записью только в дерево, сетью `isolation.domains` и сверкой защищённых путей; в `none` — без
  песочницы, так же, как исполняются сами gates (выбор `none` уже разрешает gates работать на хосте);
  в окружении фазы, с `timeoutMs` gate;
- **evidence не пишется**: настоящий gate установки по-прежнему исполняется на SHA кандидата после
  сдачи работы и остаётся единственным свидетельством.

Следы установки исполнителю не вменяются и в его коммит не попадают (он коммитит дерево целиком):

- каждый новый каталог `node_modules` — в корне, в пакетах workspace и внутри каталогов, уже бывших
  неотслеживаемыми (например, созданных `prepare`), — скрывается от git собственным `.gitignore`, как
  копия хранилища. Поиск — обход дерева без перехода по ссылкам, без спуска в `node_modules` и с
  пределом в 200 000 элементов; недоделанный обход назван в квитанции (`incomplete`);
- прочие неотслеживаемые и не игнорируемые пути, которых до установки не было (сборка `dist/`,
  сгенерированный код, журналы менеджера), удаляются; пустые каталоги остаются (git их не видит).
  Пути, бывшие до установки, и содержимое прежних `node_modules` не трогаются; вложенный репозиторий
  не удаляется и называется в `kept`;
- отслеживаемые файлы (lockfile, манифест), которые установка изменила, возвращаются к прежним байтам —
  базы или наложенного черновика, — HEAD к базе; это считается отказом установки.

Заметка исполнителю при успехе: зависимости поставлены controller, установку не запускать. Фраза о
том, что lockfiles и манифесты менять нельзя, добавляется, только если все манифесты и lockfiles в
каталогах установки лежат в `protectedPaths`. Убранные пути названы числом и первыми именами. Отказ
(код выхода, сеть, timeout) попытку не роняет: исполнитель получает заметку «Dependencies were not
installed before your turn (gate "…")», в которой сводка вывода (не больше 400 символов) приведена
строкой JSON и помечена как недоверенный вывод инструмента, а не указания; стадия
`writer-dependencies` в `timings` закрывается исходом `failed`. Исключение — защищённый путь
(конфигурация IDE, shell, git или Claude), созданный или изменённый установкой: над деревом базы это
отказ среды `environment` с причиной `sandbox-policy`, над наложенным черновиком (манифесты писал
прежний исполнитель) — `scope-violation`, как у gate кандидата. Взятый кандидат прежней попытки
исполнителя не вызывает, и установки до него нет. Журналы и квитанция `writer-dependencies.json`
(`installed`, `failed`, `frozen`, `sealed`, `removed`, `removedCount`, `kept`, `incomplete`) — в
`artifacts/<попытка>/candidate/writer-dependencies/`.

Gate установки кандидата исполняется в том же дереве и переиспользует его `node_modules`, которые
исполнитель мог изменить: `pnpm install --frozen-lockfile` сверяет lockfile, но не содержимое уже
установленных пакетов. Integration исполняется в новом checkout с чистой установкой; именно она
подтверждает, что результат собирается из lockfile.

Выключить: `"writerDependencies": false` в репозитории политики. Без поля — включено, digest
политики прежний.

## Закреплённый node

`policy.toolchain.node` (необязательное поле верхнего уровня политики, с
0.1.0-alpha.65) закрепляет Node.js для всех процессов прогона. Без него
каждый процесс получает PATH того, кто запустил harness: оболочка ведущего,
которая заново загружает менеджер версий, может поставить первым другой node,
и тогда проверки на базе и в попытке исполняются разными версиями.

```json
{ "toolchain": { "node": "24.22.3" } }
```

- Значение — абсолютный каталог с исполняемым `node` (`/opt/node/24.22.3/bin`)
  либо версия `24.22.3`, `24.22` или `24`. Версию разрешает самая новая
  установленная подходящая среди: каталога node, который запустил harness,
  абсолютных элементов PATH, nvm (`$NVM_DIR`, по умолчанию `~/.nvm`), fnm,
  volta, asdf, mise, `/opt/homebrew/bin`, `/usr/local/bin`.
- Разрешённый каталог ставится первым в PATH окружения каждой фазы: gates
  попытки и интеграции, `harness gates`, lifecycle и `harness smoke`,
  `prepare` и сборка зависимостей, writer и `smoke --writer-probe`, reviewers
  и `review-code`, совместная проверка. PATH одинаков, кто бы и из какой
  оболочки ни запустил harness.
- Закреплённый node не установлен — отказ окружения до работы (попытка не
  засчитана), текст называет значение и как исправить.
- Каждый лог gate начинается строкой `# toolchain: node v24.22.3 (/…/bin/node)`
  (у команд с pnpm — и версия pnpm); то же — поле `toolchain` записи evidence
  и строки gate в итоге `harness gates`.
- Закреплённый node не разрешился — причина отказа окружения `toolchain`.
- Провал gate под другим node (версия или путь), чем последний успешный прогон
  того же gate репозитория (прежняя попытка или `harness gates`), остаётся
  засчитанным провалом gate: о коде он может говорить. Текст отказа, сводка
  evidence и лог gate получают строку «node vX (…) отличается от последнего
  успешного прогона этого gate …: vY (…); закрепите policy.toolchain.node» —
  ведущий видит, что закрепить. С закреплением обе стороны исполняются одним
  node, и расхождения нет.
- `harness init` предлагает закрепление: точную версию из `.nvmrc`,
  `.node-version` или `engines.node`, если она установлена, иначе версию node,
  который запустил init (`toolchainPin` в ответе init).
- `harness doctor` называет разрешённое закрепление (`toolchainPin`) и
  предупреждает, когда node первым в PATH его процесса другой; без
  закрепления — совет в `notes`.
- Поле не входит в `executionDigest`: закрепление на идущем выпуске не требует
  нового согласования плана; политика без поля сохраняет прежний digest.

## Диагностика: doctor и preflight

`harness doctor --policy policy.json` (или `--state`) добавляет `toolchains[]` — по
репозиторию политики:

- `plan` — каждый шаг и gate: фаза, `cwd`, argv, путь отчёта, поле конфигурации;
- `tools` — внешние инструменты из PATH (найден, версия по пробе, требования и их источник:
  `toolchain.tools`, `package.json#packageManager`, `go.mod#go`) и инструменты среды проекта
  (`turbo` из `package.json`: диапазон допустим, если lockfile закрепляет точную версию,
  иначе `UNPINNED`; `ruff`/`pytest` из `uv.lock`) — последние не запускаются;
- `lockfiles` — каталоги node-проектов, их lockfiles и выбранный менеджер;
- `reports`, `ambiguities` (с `resolvedBy`), `problems`, `warnings`, `configSource`.

Каждая проблема — код, поле (`repositories.0.gates.1.command`) и путь файла проекта:
`TOOL_MISSING`, `TOOL_VERSION`, `TOOL_VERSION_UNKNOWN`, `TOOL_NOT_LOCKED`, `MANIFEST_MISSING`,
`LOCKFILE_MISSING`, `LOCKFILE_AMBIGUOUS`, `SCRIPT_UNKNOWN`, `TASK_UNKNOWN`, `FILTER_UNKNOWN`,
`INSTALL_UNLOCKED`, `UNPINNED`, `IF_PRESENT`, `CACHE_REPLAY`, `REPORT_MISMATCH`,
`COMPOSITION_CONFLICT`, `CWD_MISSING`, `PROJECT_FILE_MISSING`, `REPOSITORY_MISSING`,
`TOOL_IN_PROJECT`, `SCRIPT_UNRESOLVED`.

Диагностика только читает файлы (package.json, pnpm-workspace.yaml, turbo.json, go.mod,
pyproject.toml, uv.lock) и запускает пробы версий внешних инструментов: `<tool> --version`
(`go version`; для Go-бинарника без метки версии — `go version -m <файл>`), в нейтральном
временном каталоге, по одной на инструмент, с пределом 10 с и одним повтором с пределом 20 с, если проба не
уложилась во время (нагрузка). Перед пробой путь инструмента
разрешается до канонического (все symlink файла и каталога PATH): файл внутри любого
репозитория политики (включая его `node_modules/.bin`, `.venv`) или каталога состояния с
worktrees не запускается — проблема `TOOL_IN_PROJECT`. Ни установки, ни генерации, ни новых
файлов.

С политикой `doctor` возвращает и `warnings` — советы, которые не делают среду негодной и не
попадают в `problems`:

- `DEPENDENCY_STORE_RECOMMENDED` — у репозитория есть `pnpm-lock.yaml`, а `dependencyStore`
  нет; совет — `harness lean --repository <корень> --plan` (вместе со слоем lean) или только
  поле в политике, для npm совета нет;
- `LOW_RESOURCES` — не больше 4 производительных ядер (macOS: `sysctl hw.perflevel0.physicalcpu`,
  иначе `os.cpus().length`) или меньше 16 ГиБ памяти при `concurrency` больше 1. Совет называет
  `harness lean --repository <корень> --plan` для подготовленного проекта (корень — над
  `.harness/` политики), `init --lean` для нового и поля слоя для политики вне проекта
  ([слабая машина](standalone.md#слабая-машина)). Ограничение частоты процессора из
  `pmset -g therm` на macOS упоминается, только когда оно меньше 100%. Известный предел: вне
  macOS считаются логические ядра, и машина с 2 физическими ядрами и hyperthreading выглядит
  как 4-ядерная;
- `LEAN_MISMATCH` — manifest проекта рядом с политикой включает слой lean, а поля, которые
  записал `harness lean`, в политике другие (прерванное переключение или ручная правка); совет —
  повторить `harness lean --plan` или `--off --plan`;
- `DIGEST_THREADS_INVALID` — `HARNESS_DIGEST_THREADS` в окружении `doctor` задана, но не целое
  1–8: значение не действует.
- срок фаз — фаза, сумма пределов шагов которой (lifecycle setup/ready, prepare, gates,
  генераторы) больше `runTimeoutMs`, названа с числами и самой длинной цепочкой `dependsOn`.

`doctor` по-прежнему информационный (exit 0, проблемы в `problems`). С политикой он требует
только runtime, назначенные политикой (`reason: "не назначен политикой"` у остальных).
`harness run` выполняет ту же диагностику как обязательный preflight: при любой проблеме —
exit 3, `NOT_READY` с issues `policy.<поле>` до записи `binding.json`, открытия состояния и
вызова runtime.
