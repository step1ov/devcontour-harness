# Облегчённый и строгий режимы

С 0.1.0-alpha.69 у harness два режима (`harnessMode` политики). Поле
называется `harnessMode`, потому что `mode` политики — режим runtime
(`live`/`fixture`).

|                                      | Облегчённый (`light`, по умолчанию)                                              | Строгий (`strict`)                                      |
| ------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------- |
| Исполнитель                          | на хосте, без песочницы runtime: Docker, сеть, браузер, порты, `ps`, сигналы     | песочница runtime с закрытым чтением и сетью по доменам |
| Gates                                | на хосте с тем же доступом                                                       | песочница ОС проверок                                   |
| Граница                              | одна: запись только в своё дерево попытки, временный каталог и кеши инструментов | чтение, запись, сеть, процессы                          |
| Изоляция попыток друг от друга       | своё дерево, своё имя проекта compose, свои порты                                | своё дерево, песочница                                  |
| Работы инфраструктуры, `gateChanges` | не нужны (доступны)                                                              | нужны для `.harness/` и gates                           |
| Ревью плана                          | раунды без предела; бюджет — время и стоимость выпуска                           | предел раундов                                          |
| Приёмка выпуска                      | обязательна перед `release done`                                                 | совет (`release.review: required` включает)             |

Политика без `harnessMode` — облегчённая. Строгий режим — явный выбор
владельца (`"harnessMode": "strict"` или `harness init --harness-mode
strict`) для чужого кода или секретов production. Строгий режим заморожен:
новых возможностей не получает и может быть убран после следующих пилотов.

## Как выбрать режим (владелец)

Режим выбирает владелец проекта при настройке; ведущий его не меняет.

- **Облегчённый** — свой код одного владельца, локальные секреты
  разработки, нужны Docker, браузер и настоящие сервисы. Так работает
  обычный разработчик; качество держат независимое ревью каждой попытки,
  gates проекта и приёмка выпуска.
- **Строгий** — код, которому нельзя доверять (чужой форк, сгенерированные
  зависимости без проверки), или на машине лежат секреты production,
  которые исполнитель не должен прочитать.

`harness doctor` первой заметкой называет режим: «режим: облегчённый (по
умолчанию); строгий — `harnessMode: strict`». Смена режима не делает
согласования графов устаревшими: поле не входит в digest исполнения и
границы.

## Что облегчённый режим отдаёт

- **Чтение не закрыто.** Исполнитель и gates читают любые файлы
  пользователя, в том числе каталоги учётных данных и состояние harness.
  Ключи production на такой машине не держите — для них строгий режим.
- **Сеть не закрыта.** Исполнитель может ходить в интернет.
- **Процессы и порты общие.** Попытки различаются деревом, именем проекта
  compose и портами; процесс одной попытки может послать сигнал процессу
  другой. Попытки не мешают друг другу, пока gates и lifecycle проекта
  берут порты и имя проекта из переменных попытки.
- **Отказов песочницы нет.** Причины `sandbox-*` (список процессов, сигнал,
  браузер, сеть) в облегчённом режиме не возникают.

## Граница записи

Исполнитель (процесс CLI runtime и все его потомки) и каждая проверка
(gate, генератор, установка зависимостей, проверки reviewer) пишут только
в:

- своё рабочее дерево попытки и свой временный каталог (`TMPDIR`);
- кеши инструментов (`DEFAULT_WRITE_GUARD_CACHES`);
- состояние своего CLI (только исполнитель: `~/.codex`, `~/.claude`,
  `~/.claude.json`).

Кеши по умолчанию: `~/.npm`, `~/.pnpm-store`, `~/Library/pnpm`,
`~/.local/share/pnpm`, `~/.yarn`, `~/.bun/install/cache`, `~/.cache`,
`~/Library/Caches` (в том числе `ms-playwright`), `~/.docker/buildx`,
`~/.maestro`, `~/Library/Developer/CoreSimulator`,
`~/Library/Logs/CoreSimulator`, `~/Library/Developer/Xcode/DerivedData`,
`~/.android`, `~/.gradle`, каталоги пользователя macOS
`$DARWIN_USER_CACHE_DIR` и `$DARWIN_USER_TEMP_DIR` (Chrome создаёт во
временном каталоге пользователя сокет профиля).

```json
"writeGuard": { "add": ["~/.cache/my-tool"] }
"writeGuard": { "replace": ["~/.npm", "$DARWIN_USER_CACHE_DIR"] }
"writeGuard": { "off": true }
```

`add` дополняет умолчания, `replace` заменяет их целиком, `off: true`
снимает границу (решение владельца; `isolation.mode: none` тоже снимает
её). `doctor` печатает механизм и действующий список (`mode.writeGuard`).

Механизм: на macOS — Seatbelt (`sandbox-exec`) с профилем «разрешено всё,
кроме записи вне путей»; `ps` (setuid) исполняется без песочницы — он
ничего не пишет. На Linux — bubblewrap: корень только на чтение,
разрешённые пути на запись, `/dev`, `/proc`, сеть, PID и IPC общие с
хостом. Нет механизма — отказ среды до запуска (`doctor` называет его
проблемой).

Браузер под границей: Chromium Playwright запускает свою песочницу только
по флагу (`chromiumSandbox: false` по умолчанию); Chrome запускайте с
`--no-sandbox` и профилем во временном каталоге попытки
(`--user-data-dir=$TMPDIR/profile`) — вложенная песочница macOS не
стартует.

## Изоляция попыток

Каждая попытка получает:

- своё рабочее дерево (как и прежде);
- `HARNESS_ATTEMPT_ID` и `COMPOSE_PROJECT_NAME=hx-<попытка>` — compose
  проекта поднимает свои контейнеры, сети и тома под этим именем;
- свои порты: каждое имя из `attemptEnv.ports` получает свободный порт из
  `attemptEnv.portRange` (по умолчанию 20000–29999) в переменной с этим
  именем. Занятость проверяется той же пробой, что у ресурсов-портов, а
  порт арендуется в базе ресурсов машины (общей с DevContour) на время
  попытки; аренда процесса, который умер, снимается при следующем
  выделении.

```json
"attemptEnv": { "ports": ["API_PORT", "WEB_PORT", "GATEWAY_PORT"] }
```

Переменные получают исполнитель, gates, lifecycle и `harness gates --sha`.
Те же значения (имя проекта compose, порты, адрес шлюза) попытка пишет в
файл `attempt-env.json` в своём каталоге артефактов; путь —
`HARNESS_ATTEMPT_ENV_FILE`. Compose-файл проекта берёт порты из переменных
(`"${API_PORT}:3000"`), teardown lifecycle — `docker compose down -v
--remove-orphans` (имя проекта уже в окружении). Потомки каждой проверки
(демоны браузера, серверы) останавливаются вместе с ней.

Советы для compose проекта: у каждого сервиса настоящий healthcheck и
`up --wait`; данные приёмки — в tmpfs; healthcheck RabbitMQ через
`rabbitmq-diagnostics` ждёт файл cookie Erlang (`test -s
/var/lib/rabbitmq/.erlang.cookie && rabbitmq-diagnostics -q ping`) —
иначе параллельные стеки попыток падают на гонке старта (`doctor`:
`compose-rabbitmq-cookie`). При настройке прогрейте инструменты: браузер
Playwright, образы compose, хранилище зависимостей — gates тогда идут без
сети и быстро.

Тестовая инфраструктура (приёмочные тесты, фикстуры, тестовые сервисы
compose) живёт с кодом продукта в продуктовых работах и проходит ревью как
код; отдельного этапа инфраструктуры нет. Работа инфраструктуры — только
для общего, что нужно нескольким работам (например, новый сервис compose).

## Gates через шлюз (как в production)

Если в production приложение доступно через шлюз (Caddy, nginx), gates
должны ходить через тот же шлюз, а не в порт API: иначе ошибка маршрута
(медиа по адресу API вместо адреса шлюза) проходит все тесты и ревью.

```json
"repositories": [{
  "gateway": {
    "url": "http://127.0.0.1:${GATEWAY_PORT}",
    "env": { "IMAGE_PUBLIC_BASE_URL": "/media", "API_URL": "/api" }
  }
}]
```

Объявлена топология production (`release.topology`), а ни один
репозиторий не ходит через шлюз — `doctor` предупреждает
`GATEWAY_MIRROR_MISSING`.

Harness передаёт `HARNESS_GATEWAY_URL` и каждой переменной из `env` адрес
шлюза с суффиксом. Шлюз поднимает lifecycle проекта — сервис compose с той
же конфигурацией, что в production (`Caddyfile` проекта), на порту
`GATEWAY_PORT`. `url` ссылается только на порты `attemptEnv.ports`
(политика это проверяет). Файлы маршрутизации production объявите в
`release.topology` — их сверяет приёмка выпуска
([release-review.md](release-review.md)).

UI-проверки (браузер, мобильные) — [ui-gates.md](ui-gates.md).
