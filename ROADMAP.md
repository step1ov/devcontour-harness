Дата: 26 октября 2026 года. Текущая версия в `master`: `0.1.0-alpha.11`.

Файл перечисляет работу, оставшуюся после выпуска alpha.11, для разбора и
передачи отдельным агентам. Каждый пункт — отдельное задание со своей
матрицей приёмки и независимым приёмщиком другой модели (см. `AGENTS.md`).
Порядок — рекомендуемый, а не обязательный.

## 1. Поставка alpha.11 — решение владельца

- Push `master` и тег `v0.1.0-alpha.11`.
- Публикация npm. Архив из `master` воспроизводим (`npm pack` даёт принятые байты).
- **A7-TAG:** куда указывает `latest`. Сейчас в registry `latest` = alpha.6 (историческое значение), `alpha` = alpha.7. Предложение: установка и проверки ставят точную версию с проверкой integrity, `latest` переносится на принятую версию отдельным решением.

## 2. Движок: зацикливание и бюджеты восстановления (FI-001…FI-004)

Найдено при H1, существует с alpha.7, вне матриц H1–H3. Диагностика `explain`
для этих состояний уже называет действие человека; сам движок не останавливается.

| ID     | Дефект                                                                                                                                | Направление исправления                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| FI-001 | `run` зацикливается после неуспешного разрешённого повтора восстановления свойства с классом `environment` (очередь на паузе runtime) | `afterDecision` возвращает «ждать» только при новом действии или идущей попытке                                                              |
| FI-002 | `advance` крутится без выдачи: эпизод `retrying` с не доказывающим отказом; эпизод `retry` при паузе, hold или budgetBlock            | повтор из эпизода снимает свою блокирующую причину как repair; `retrying` с не доказывающим отказом детерминированно завершается (`stopped`) |
| FI-003 | бюджет восстановлений списывается до отказа `recoveryReserve`                                                                         | проверять условия резервирования до списания                                                                                                 |
| FI-004 | `afterDecision` вызывает `engine.retry` при исчерпанных попытках — сырое сообщение без ID работы                                      | проверять лимит попыток до повтора; отказ — типизированный, с ID работы                                                                      |

Затрагивает `src/control/harness.ts` и `src/engine/property-recovery.ts`. Gates,
бюджеты и правила находок не ослабляются; регрессии — на `h.run`, а не только
на диагноз.

## 3. A7-LIVE — живой пилот finding/repair

Платный запуск, только по решению владельца. Цель — наблюдать живую цепочку:
содержательная находка настоящего reviewer → ID controller → исправление writer →
закрытие **того же** ID → integration gates/review → accepted. Если модель всё
сделала с первой попытки, честный исход — «repair не наблюдался»; специально
программировать отказ reviewer не нужно. Перед запуском фиксируются стенд
(commit демо), точная версия пакета с integrity, runtime и модели, бюджет.

## 4. T — Turbo Starter как основной сложный сценарий

Preset для подключения совместимой версии starter: цепочка backend → OpenAPI →
SDK → frontend и controller-mode. Новая задача не использует готовый patch
примера. Проверить холодный старт, зависимости и cache, env, Docker lifecycle,
конфликт портов, JUnit и cleanup. Режим изоляции выбирается явно, без тихого
отключения sandbox. Работает без Relay/Hindsight. Негативный несовместимый
SDK/consumer отвергается; повтор и cleanup не затрагивают чужую среду.

## 5. I — опциональные внешние подключения

Не блокирует самостоятельный путь без памяти; по умолчанию внешних вызовов нет.

- **Relay v1/v2:** выбор одного backend агентом, проверка project identity и
  capabilities, связь задач с repo/gates, проверка доставки. Синхронизация двух
  баз не входит в onboarding. Статус задачи в Relay не доказывает выполнение.
- **Hindsight:** opt-in provider поверх memory-контракта. Recall до согласования
  закрепляется снимком; retain доставляет подтверждённый итог отдельно от
  принятия Git; повтор операций безопасен. Реальные provider-тесты отделены от
  fake и идут на тестовых банках с заданным бюджетом.

## 6. Проверка удобства на практике

Воспроизводимые маршруты: свежая установка агентом, продолжение новой сессией,
техническая остановка с исправлением причины, содержательное отклонение reviewer
и исправление writer. Затем серия из 15–20 разнообразных реальных задач, включая
Turbo Starter. Учитывать подготовку, число и длительность вмешательств человека,
стоимость (с явными неизвестными), время до принятия, долю принятых результатов
и дефекты после приёмки. Сюда же — проверка, что новая задача из естественного
языка превращается в исполняемый граф без выдуманных gate/test ID.

## 7. Мелкое и техническое

- Тест `runner.test.ts` «Зависший git update-ref» зависит от времени и падал под
  параллельной нагрузкой (изолированно проходит). Сделать его независимым от
  нагрузки, не ослабляя проверку.
- Локальные служебные ветки прогонов `harness/run-*` и устаревшие worktree:
  решить, что из истории прогонов хранить. Исторические данные прогонов не
  переписываются; удаление — только по решению владельца.
