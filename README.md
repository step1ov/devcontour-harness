# devcontour-harness

Headless-движок исполнения инженерных поручений: согласованный граф работ,
изолированные попытки в Git worktree, обязательные gates, независимое ревью,
интеграция с принятой веткой через compare-and-swap и машинный результат с SHA
и доказательствами.

> Статус: `0.1.0-alpha.71` — предварительный выпуск (alpha). Договоры
> `v1alpha1` могут измениться между alpha-версиями; закрепляйте точную версию.
> Файл → ревью плана → кандидат → интеграция → принятие → результат JSON, с
> ограниченным восстановлением, повторным использованием кандидата, бюджетами,
> потребителями, свойствами и корпусом, совместной проверкой репозиториев и
> явным режимом одного вендора.

Пакет включает встроенные профили стеков (`profiles/`), skills
`skills/harness/SKILL.md` (работа с поручениями) и
`skills/harness-setup/SKILL.md` (установка, первая настройка и обновление
версии), шаблоны политики, графа и инструкции агентам (`templates/`).

## Требования

- Node.js ≥ 24.3.0, Git.
- CLI `codex` и `claude`, установленные и авторизованные (для живого запуска).
  `harness doctor` проверяет их без вызова модели.
- Проверки (gates) по умолчанию исполняются в песочнице ОС (sandbox-runtime:
  Seatbelt на macOS, bubblewrap на Linux; `isolation.mode: os`). На macOS в
  ней не запускаются setuid-программы: тест, вызывающий `ps`, `pgrep` или
  `top`, падает `spawn EPERM`, и harness называет это отказом среды
  `GATE_SANDBOX_PROCESS_LIST`, а не провалом кода. Открыть список процессов
  проверкам нельзя безопасно (`ps -E` показывает окружение всех процессов
  пользователя, в том числе токены), поэтому такой тест проверяет свои
  процессы по pid или выносится из gate. `harness doctor` и `harness smoke`
  называют эту возможность заранее ([договоры](docs/contracts.md)).

## Установка

Из npm — точная версия (воспроизводимо) или последняя alpha по тегу:

```sh
npm install --save-exact devcontour-harness@0.1.0-alpha.71   # точная версия
# или: npm install --save-exact devcontour-harness@alpha     # текущая alpha
npx harness --version
```

Выпуски публикуются под тегом `alpha`; ставьте точную версию или `@alpha`,
а не версию по умолчанию без тега.

Чтобы не менять зависимости и lockfile существующего проекта, пакет ставят в
отдельный каталог инструментов — снаружи репозитория или в `.harness-tools/`
внутри него ([standalone](docs/standalone.md#установка), skill
[harness-setup](skills/harness-setup/SKILL.md)).

Из локального архива `devcontour-harness-<version>.tgz` (поддерживаемый
способ без registry):

```sh
npm install --omit=dev --ignore-scripts ./devcontour-harness-<version>.tgz
```

В архиве уже собраны JavaScript, декларации и JSON-схемы: установка не
выполняет скриптов и не требует devDependencies (`--omit=dev
--ignore-scripts` допустимы и для установки из npm). Проверка архива
целиком — `npm run check:install -- <архив>` из checkout пакета: установка в
отдельный каталог без сети, CLI, библиотека, профили, полный цикл на fixture
runtime и отказы.

CLI ставится локально: `npx harness` находит его в `node_modules/.bin`
ближайшего каталога установки (в том числе из его подкаталогов). Вне этого
каталога `npx harness` предложит скачать другой пакет с именем `harness` —
откажитесь; глобальная команда `harness` в `PATH` не предполагается.

## Быстрый старт

Пример — вымышленный репозиторий с одной задачей: добавить `greet(name)`.
Команды выполняются из каталога, где установлен пакет; `harness` в таблице
ниже — тот же CLI (`npx harness …`).

```sh
cp -R node_modules/devcontour-harness/examples/single-task greeting && cd greeting
git init -q && git add -A && git commit -qm init
npx harness validate --graph graph.json --policy policy.json
npx harness run --graph graph.json --policy policy.json --state ../greeting-state \
  --author external --sink file:../greeting-results
npx harness result --state ../greeting-state --work add-greeting
git rev-parse refs/heads/harness/accepted   # совпадает с data.result.shas.result
```

`run` регистрирует граф, проводит ревью плана (reviewer по политике),
согласует его и ведёт очередь до простоя. Принятое поручение — коммит
интеграции в `refs/heads/harness/accepted`; ни основная ветка, ни рабочее
дерево не меняются. Результат и состояние доставки — `harness result`.

Конфигурации примера:

| Файл                      | Вендоры                                    |
| ------------------------- | ------------------------------------------ |
| `policy.json`             | writer claude, reviewer codex              |
| `policy-same-vendor.json` | reviewer того же вендора, разрешённый явно |

## Команды

| Команда                                         | Что делает                                         |
| ----------------------------------------------- | -------------------------------------------------- |
| `validate --graph F --policy F`                 | Проверка входов без моделей и записи               |
| `review-plan / review-contract … --author A`    | Раунд технического ревью с историей находок        |
| `approve --state D --subject ID --digest H`     | Согласование оператором (`approvalMode: operator`) |
| `reapprove … --by WHO --reason WHY`             | Согласование после правки политики, с записью      |
| `run --graph F --policy F --state D`            | Регистрация, согласование и работа до простоя      |
| `status / events / result --state D`            | Чтение без побочных эффектов                       |
| `wait --state D --policy F [--after N]`         | Ждать события: принято, отказ, вопрос, остановка   |
| `guide <topic>`                                 | Раздел инструкции ведущего по теме                 |
| `view --state D [--policy F] [--work ID]`       | Представление оператора для панели (только чтение) |
| `pause / resume / cancel / retry --state D`     | Управление очередью и поручением                   |
| `diagnose --state D --work ID --cause C`        | Разбор ведущего повторных отказов (`--hypothesis`) |
| `retry … --reset --by lead --diagnosis D1`      | Новый предел попыток от ведущего по разбору        |
| `diagnose … --addendum T`                       | Дополнение свежего разбора без нового разбора      |
| `lead begin / note / end --state D`             | Журнал ведущего: сессия и записи простыми словами  |
| `lead outline --state D --file F`               | План выпуска: этапы, размеры, исполнители          |
| `review-release --state D [--base REF]`         | Приёмка выпуска против договора и топологии        |
| `release done --state D --summary T`            | Итоговый отчёт ведущего: выпуск готов              |
| `proposal --state D --work ID --proposal P`     | Решение ведущего по предложению исполнителя        |
| `env-up` / `env-down` (шаги lifecycle)          | Сервисы попытки в docker compose                   |
| `env-sweep --state D [--yes]`                   | Уборка стеков env-up не идущих попыток             |
| `deliver --state D --work ID --sink file:D`     | Повтор доставки без моделей и интеграции           |
| `worktree-cleanup --state D [--dry-run]`        | Уборка деревьев завершённых попыток                |
| `cleanup --state D --run LS-…`                  | Повтор или сверка очистки записи smoke             |
| `profile --profile ID [--repository D]`         | Разрешение профиля стека без команд проекта        |
| `doctor`                                        | Версии, runtime, sandbox, совместимость состояния  |
| `report --state D [--format md\|html]`          | Отчёт об эффекте по данным проекта                 |
| `handoff --state D [--format md] [--intent T]…` | Пакет передачи контекста новой сессии агента       |
| `input-list / input-show / input-answer …`      | Вопрос исполнителя: ответ, снимок, применение      |
| `review-code --state D --base A --head B`       | Обзор написанной ветки: ревью, не приёмка          |
| `review-release --state D [--base A]`           | Ревью выпуска перед `release done`                 |
| `smoke --state D --sha HEAD [--human]`          | Окружение на коммите без gates и моделей           |
| `smoke … --writer-probe`                        | Команды исполнителя в его изоляции, без модели     |
| `update --state D --check/--apply/--rollback`   | Обновления harness и панели: проверка, откат       |
| `update --state D --schedule daily\|off`        | Ежедневная проверка (launchd; Linux — текст)       |
| `preview-start --state D [--work ID]`           | Превью принятого результата на loopback-адресе     |
| `preview-list / preview-stop --state D`         | Живые превью; остановка, срок и простой            |

stdout — один JSON (`devcontour-harness/v1alpha1`), диагностика — stderr. Exit
codes: 0 успех, 2 неверный вход, 3 отказ/блокировка, 4 инфраструктура.
Длительности (`lead begin --ttl`, `preview-start --ttl` и `--idle`) — всегда
с единицей: `90s`, `30m`, `2h`; голое число — неверный вход (кроме
`--idle 0`). Команда попадает в журнал ведущего, только если она ведущего:
`--by lead`/`--actor lead`, `diagnose` или, без явного актёра, при активной сессии
`lead begin`; команды оператора аренду ведущего не продлевают.
`HARNESS_CODEX_BIN` и `HARNESS_CLAUDE_BIN` подменяют исполняемые файлы runtime
— например, fixture executable в тестах (это не живая модель).

## Для оператора

Если вы ставите задачи и принимаете результат, но код не пишете, начните с
[руководства оператора](docs/operator-guide.md): что значат этапы, как
harness пишет «проверено», почему попытки повторяются, какие вопросы
приходят вам и что значит «принято» локально и в удалённом репозитории.
Следить за работой — в панели (skill `harness-ui`) или
`harness status --state D --human --watch`; поля документа панели —
[представление оператора](docs/operator-view.md).
Посмотреть принятый результат в браузере — [превью](docs/previews.md):
`harness preview-start --state D --ref accepted --work <id>` даёт адрес на
этой машине, harness сам останавливает превью по сроку и простою.
Режим по умолчанию — облегчённый ([облегчённый и строгий
режимы](docs/light-mode.md)): исполнитель и gates работают на хосте с
Docker, браузером и сетью, с одной границей — записью только в своё дерево
попытки, временный каталог и кеши; попытки разделены своим деревом, именем
проекта compose и портами. Строгий режим (`harnessMode: strict`) — выбор
владельца для чужого кода или секретов production. Перед `release done`
независимый reviewer принимает выпуск целиком против постановки, ответов
владельца и топологии развёртывания — [приёмка выпуска](docs/release-review.md);
UI-проверки — [браузер и мобильные](docs/ui-gates.md).
Настройка harness — только конфигурация с мягким бюджетом около 30 минут;
в строгом режиме код инфраструктуры (мосты, обёртки gates, приёмочные тесты)
пишется работами инфраструктуры обычным циклом, и панель показывает ход
настройки по шагам — [работы инфраструктуры](docs/infra-works.md).

Кто что решает — ведущий агент или вы — описано в принципе
[«Кто принимает решения»](docs/principles.md): технические решения о
восстановлении ведущий принимает сам в пределах бюджета, вам приходят
решения о продукте, противоречия, исчерпанный бюджет и явная эскалация.

## Что вы увидите: отчёт

`harness report --state D --format html --out report.html` строит по
каталогу состояния один HTML-файл (или Markdown, или JSON в конверте): что
дал harness на этом проекте. Сводка — не больше пяти чисел с основанием:
сколько поручений принято и сколько с первой попытки, сколько вернули
проверки, ревью или правило области до слияния, срок от согласования до
приёмки, известный расход на принятое поручение и доля отказов окружения.
Дальше — разделы о дефектах, автономности, скорости, расходе, окружении,
неделях, таблица поручений и «Ограничения и неизвестное».

Отчёт показывает только наблюдения: счёт и длительности из записанного
состояния, без «сэкономленных часов» и сравнения «до и после». Неизвестное
не превращается в ноль («≥ $5.73», «unknown»); процент — от 20 в
знаменателе, медиана — от 5 значений, меньше трёх принятых поручений —
«недостаточно данных». Тексты prompt, находок и ошибок, токены и домашний
каталог в отчёт не попадают; `--no-titles` убирает и заголовки. Тот же
каталог — те же байты: момент отчёта — последняя метка времени в данных.
Хост строит тот же отчёт из своего хранилища: `valueReport` из
`devcontour-harness/report`, файл отчёта — `writeReportFile` из корня пакета.
Подробно — [ValueReport](docs/contracts.md#valuereport).

## Библиотека

```js
import { Harness, validateInputs } from 'devcontour-harness';
```

Библиотека и CLI вызывают одни и те же операции `Harness`; операции «передать
PASS» нет. Адаптеры хоста реализуют порты `ExecutionStore`, `WorkSource`,
`ContextSource`, `ResultSink`; набор проверок договора хранилища —
`devcontour-harness/testing`.

Пакет поставляет декларации TypeScript (`lib/**/*.d.ts`) для `.`,
`/contracts` и `/testing`; JSON-схемы входов и выходов —
`devcontour-harness/schemas/<имя>.schema.json`. Декларации используют типы
Node.js: TypeScript-потребителю нужен `@types/node` (или `skipLibCheck`).

## Выпуск 0.1.0-alpha.71

Gates не исполняют то, что не изменилось: gate пакета workspace по
умолчанию пропускается, если diff не задел его пакет и зависимости, PASS
кандидата переносится на интеграцию при том же дереве, а приёмку выпуска
страхует полный прогон всех gates на цели (`review-release` исполняет его
сам). Повторы не тратят попытки на то же самое: тот же дефект второй раз —
разбор ведущего, отказ инструмента gate удерживает gate, разовые таймауты и
снятые исправлением удержания harness повторяет сам. Приёмка выпуска
сверяет принятую цель со всем брифом и ответами владельца, включая сбойные
пути сценариев. Ведущий ждёт событий через `harness wait`, а инструкцию
читает по разделам (`harness guide <topic>`); планирование — одна работа на
сценарий пользователя. Подробно —
[заметки выпуска](docs/release-notes/0.1.0-alpha.71.md).

## Выпуск 0.1.0-alpha.70

Ревью в два прохода: отказ проверяет второй, свежий вызов reviewer,
который опровергает ложные блокирующие находки (`review.passes`; приёмка
выпуска и работы с метками security/payments/auth — всегда). Исполнитель
может сдать сделанное с задачами-продолжениями и в начале попытки
предложить разделить работу — решает ведущий (`harness proposal`);
исследование задачи сохраняется для следующих попыток. Шаг документации
перед приёмкой выпуска, источники у критериев ведущего, справочник причин
отказов, уровни безопасности в `doctor`, сервисы попытки (`env-up`),
расход по работам и моделям в представлении (ревизия 10). Под границей
записи `.git` закрыт, как в alpha.69; gate, который меняет состояние git,
получает совет `GATE_GIT_WRITE`. Подробно —
[заметки выпуска](docs/release-notes/0.1.0-alpha.70.md).

## Выпуск 0.1.0-alpha.69

Облегчённый режим — режим по умолчанию (решение владельца): исполнитель и
gates работают на хосте с Docker, браузером и сетью, с одной границей —
записью только в своё дерево попытки, временный каталог и кеши (защита от
случайных ошибок, не граница безопасности); попытки разделены деревом,
именем проекта compose и портами, настройки CLI пользователя исполнителю
закрыты. Строгий режим — `harnessMode: strict`, заморожен. Перед
`release done` независимый reviewer принимает выпуск против постановки,
ответов владельца и топологии production (`review-release`); gates могут
идти через шлюз проекта, UI-проверки — блоком `ui` (Playwright; Maestro —
договор). Раунды ревью плана тратят только настоящие изменения плана, в
облегчённом режиме предела нет — есть бюджет и защита от круга. Контекст
задачи harness собирает сам из маршрутов обычной Relay 0.13. Подробно —
[заметки выпуска](docs/release-notes/0.1.0-alpha.69.md).

## Выпуск 0.1.0-alpha.68

Раунды ревью плана тратятся только на изменённый план: повторное ревью того
же плана с новым ответом или документом предел не тратит, у доработки
принятой работы — своя эпоха раундов, а остаток виден в `status` и панели.
Порядок источников контекста больше не порождает нового согласования,
записанные в источник ответы владельца не делают его устаревшим, тупик
переноса ответа закрыт, вторая причина того же отказа — `diagnose
--addendum`. Провал gate и шага окружения называет упавшие тесты и
маскированный хвост вывода; отказы песочницы (`kill`, браузер) — причина
окружения только по подтверждению пробой harness. План выпуска ведущего
(`lead outline`) делает прогноз прогнозом всего выпуска; представление
(ревизия 8) получает решения, путь разбора и итоги ревью попыток. Подробно —
[заметки выпуска](docs/release-notes/0.1.0-alpha.68.md).

## Выпуск 0.1.0-alpha.66

Технические решения о восстановлении принимает ведущий в пределах бюджета
политики ([принцип](docs/principles.md)): после повторных отказов — разбор

## Разработка

```sh
npm ci
npm run check         # lint, typecheck, схемы, сборка, тесты, проверка архива
npm run format:check
```

Три уровня проверки — от итерации над исправлением до выпуска:

| Уровень               | Команда                                   | Что запускает                                                                          |
| --------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------- |
| На каждое исправление | `npm run test:affected [-- --base <ref>]` | тест-файлы, в статическое замыкание которых входит изменённый файл                     |
| Быстрый               | `npm run test:fast`                       | весь suite без медленного яруса (тесты дольше ~60 с)                                   |
| Полный release check  | `npm run check`                           | lint, typecheck, схемы, сборка, весь suite с полным размером оракулов, проверка архива |

- `test:affected` сравнивает с merge-base с `master` (или с `--base`) и
  учитывает индекс, рабочее дерево и неотслеживаемые файлы. Замыкание идёт
  от `tests/*.test.ts` по относительным путям (`import`, `import()`,
  `new URL(…)`) через helpers и `src/`; barrel-модули уточняются по
  импортированным именам. Изменение вне `src/` и `tests/*.test.ts`
  (package.json, tsconfig, scripts, helpers и fixtures тестов, profiles,
  schemas, docs), удалённый или недостижимый файл `src/` — весь suite.
  Выбор и причина печатаются перед запуском. `npm run check:fast` —
  статические шаги и `test:affected`.
- Медленный ярус — список `slowTests` в `scripts/test.mjs` (начала имён
  тестов). `npm test` и `npm run check` выполняют его, как и раньше.
- Оракул H1 (`tests/explain-differential.test.ts`) сохраняет 100
  детерминированных случаев в обычном, выборочном и полном прогоне
  (`DIFF_N` переопределяет); быстрый ярус явно исключает этот тест.
- Статические шаги `npm run check` (lint, typecheck, schemas:check) идут
  параллельно; сборка, тесты и проверка архива — после них, по очереди.
- Все режимы запускают тесты одинаково: отдельный процесс на файл, tsx, не
  более четырёх файлов одновременно.
- Каждый тест-файл первым импортирует `tests/temp-scope.ts`: процесс пишет
  временные файлы (репозитории, состояния, хранилища, архивы) в свой каталог
  `harness-test-XXXXXX` в TMPDIR и удаляет его при выходе, в том числе при
  запуске отдельного файла через `node --test`. `HARNESS_KEEP_TEST_TMP=1`
  оставляет каталоги для отладки. `scripts/smoke-package.mjs` убирает свой
  каталог так же. В конце `npm run check` печатает предупреждение с размером
  оставшихся в TMPDIR каталогов `harness-test-*` этого прогона (файл убит
  сигналом, потомок писал после выхода); проверку это не валит и ничего не
  удаляет.

Тесты используют настоящие временные Git-репозитории, SQLite и fixture
executables CLI codex/claude; живые модели не вызываются. Результаты
fixture-тестов не являются проверкой качества моделей.
